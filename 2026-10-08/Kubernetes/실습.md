## 1. ConfigMap: Nginx 80 → 8000

### 목표

Nginx의 `default.conf`를 컨테이너 이미지와 분리해 ConfigMap으로 관리하고, 설정을 마운트한 Pod의 HTTP 응답을 확인한다.

### 1-1. 기존 Nginx 설정 추출

```bash
# 기존 nginx Pod 내부에 진입
k exec -it nginx -- /bin/bash
cd /etc/nginx/conf.d
cat default.conf
exit

# Pod → master1 로컬 파일 복사
k cp nginx:/etc/nginx/conf.d/default.conf ./default.conf
vi default.conf
```

`default.conf`의 두 리스너 포트를 변경한다.

```nginx
server {
    listen 8000;
    listen [::]:8000;
    server_name localhost;
    location / {
        root /usr/share/nginx/html;
        index index.html index.htm;
    }
}
```

> 위 코드는 바뀐 핵심 부분만 발췌한 예시다. 기존 파일의 다른 설정은 유지했다. `tar: Removing leading '/' from member names`는 `kubectl cp` 과정에서 출력될 수 있는 일반 메시지다.

### 1-2. ConfigMap 생성 및 점검

```bash
k create cm nginx-conf --from-file=default.conf
k get cm nginx-conf -o yaml
k get po nginx -o yaml > nginx.yaml
vi nginx.yaml
```

실습에서 추가한 핵심 YAML:

```yaml
spec:
  volumes:
    - name: nginx-conf
      configMap:
        name: nginx-conf
  containers:
    - name: nginx
      image: nginx
      volumeMounts:
        - name: nginx-conf
          mountPath: /etc/nginx/conf.d
          readOnly: true
```

- `volumes`: Pod 수준에서 ConfigMap을 볼륨으로 선언
- `volumeMounts`: 해당 볼륨을 컨테이너의 `/etc/nginx/conf.d`에 연결
- `readOnly: true`: 설정 파일을 컨테이너에서 직접 수정하는 방식 대신 ConfigMap을 사용
- 전체 디렉터리 마운트는 해당 경로의 기존 파일들을 가린다.

> 주의: 위 YAML은 **설명용 핵심 조각**이다. 실제 `nginx.yaml`에 기존 Pod의 필드와 합쳐야 하며, `kubectl get pod -o yaml`로 추출한 YAML에서는 서버가 자동 생성한 `status`, `resourceVersion`, `uid` 등을 정리하는 편이 안전하다. 실행 중인 Pod의 `volumes`/`volumeMounts`는 일반적인 `apply`로 추가 변경할 수 없으므로 재생성했다.

### 1-3. Pod 재생성 및 성공 확인 (실제 실행 로그)

```bash
k delete -f ./nginx.yaml
# pod "nginx" deleted from default namespace
k create -f ./nginx.yaml
# pod/nginx created
k exec nginx -- cat /etc/nginx/conf.d/default.conf
# listen 8000; 및 listen [::]:8000; 확인

k exec nginx -- nginx -t
# syntax is ok
# test is successful

k port-forward pod/nginx 8000:8000
# Forwarding from 127.0.0.1:8000 -> 8000
```

다른 터미널에서:

```bash
curl http://localhost:8000
# <h1>Welcome to nginx!</h1> 확인
```

**검증 결과:** ConfigMap 마운트 성공 → Nginx 설정 유효 → HTTP 응답 성공. 포트포워딩은 실행 중에만 유효하다.

## 2. Secret · MariaDB · PVC

### 2-1. ConfigMap과 Secret

| 구분 | ConfigMap | Secret |
|---|---|---|
| 용도 | 포트, 일반 설정 파일 | DB 비밀번호, API 키, 인증서 |
| 값 표현 | `data`에 문자열 | `data`는 base64 인코딩 |
| Pod 전달 | 환경변수 / 볼륨 | 환경변수 / 볼륨 |

> base64는 **암호화가 아니다**. Secret 접근 제어(RBAC), 저장 시 암호화 등 별도의 보안 설정이 필요하다. Kubernetes ServiceAccount 토큰 마운트는 최신 클러스터에서 `projected` 방식으로 제공되는 경우가 일반적이다.

```bash
k get secret -A
k describe secret <secret-name> -n <namespace>
# 실습용 생성 예시 (실제 생성 로그와는 구분)
k create secret generic db-secret --from-literal=username=admin --from-literal=password='example-only'
```

실제 수업 노트에는 Helm MariaDB 설치 후 Secret 확인 절차가 기록돼 있다.

```bash
helm version
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm install mydb bitnami/mariadb -n db --create-namespace
kubectl get pods,secrets,pvc -n db
```

- `mydb-mariadb`: MariaDB 자격증명 관련 Secret
- `sh.helm.release.v1.mydb.v1`: Helm release 정보를 저장하는 Secret (DB 비밀번호 전용 아님)

### 2-2. MariaDB Pending / PVC 확인

기존 노트에 `mydb-mariadb-0`과 PVC의 `Pending` 상태가 기록되어 있다. 수업 노트에서는 PV/StorageClass 바인딩 실패를 원인 흐름으로 다뤘다. 실제 원인 확정은 `Events` 확인이 필요하다.

```bash
kubectl get storageclass
kubectl get pv
kubectl get pvc -n db
kubectl describe pvc data-mydb-mariadb-0 -n db
kubectl describe pod mydb-mariadb-0 -n db
```

**핵심:** Secret 생성 성공과 DB Pod의 정상 실행은 별개이며, Stateful workload에는 스토리지 구성이 중요하다.

## 3. 고가용성 및 Service Mesh 이론

- **Application HA:** Deployment/ReplicaSet이 Replica 수를 유지하며 Pod 장애 후 재생성을 수행. 다른 노드에 여유 리소스가 있어야 장애 복구 가능.
- **Control Plane HA:** 여러 Control Plane과 API Server 진입점(Load Balancer) 사용.
- **Stacked etcd:** 각 Control Plane 노드에 etcd 함께 배치.
- **etcd quorum:** 3개 구성은 과반 2개가 필요하므로 최대 1개 장애를 허용.
- **Leader election:** Scheduler / Controller Manager 등이 리더를 선출해 조정 작업 수행.
- **Service Mesh:** 서비스 사이의 통신 기능을 애플리케이션과 분리하여 트래픽·보안·관측 기능 제공.
- **Istio:** Control Plane `istiod`, Sidecar 모드 Data Plane `Envoy`.
- **관측 도구:** Kiali(서비스 관계), Prometheus(메트릭), Grafana(대시보드), Jaeger(분산 추적).

## 5. Pod Self-Healing · NodePort · Gateway

### 5-1. Deployment 자가 복구 확인

```bash
k get po -n bookinfo
# Pod 이름은 매번 변경되므로 실제 이름을 확인
k delete po -l app=details -n bookinfo
# 모든 Bookinfo Pod 삭제: --all의 하이픈은 2개
k delete po --all -n bookinfo
watch -n 2 'kubectl get po -n bookinfo'
```

실습에서 처음 `k delete po -all -n bookinfo`를 입력하여 `unknown shorthand flag: 'a'` 오류가 발생했다. 올바른 옵션은 **`--all`**. Deployment가 유지되면 ReplicaSet이 Pod를 다시 생성한다.

### 5-2. Productpage NodePort로 직접 접속

```bash
k edit svc/productpage -n bookinfo
# spec.type: ClusterIP → NodePort 로 수정
k get svc productpage -n bookinfo
k get nodes -o wide
```

- `port: 9080`: Service 포트
- `targetPort: 9080`: 애플리케이션 Pod 포트
- 실습에서 확인한 NodePort **31182** 및 master1 IP **192.168.120.150** (해당 날짜 실습 환경)

```text
http://192.168.120.150:31182/productpage
```

실제 브라우저에 Bookinfo가 표시되어 접속 성공을 확인했다. 이는 **productpage Service 직접 접속**이지 Istio Ingress Gateway 경유 테스트는 아니다.

### 5-3. Istio Gateway · VirtualService 생성

```bash
kubectl apply -f samples/bookinfo/networking/bookinfo-gateway.yaml
# gateway.networking.istio.io/bookinfo-gateway created
# virtualservice.networking.istio.io/bookinfo created
k get -f samples/bookinfo/networking/bookinfo-gateway.yaml
k get -f samples/bookinfo/networking/bookinfo-gateway.yaml -o yaml
istioctl analyze
# ✔ No validation issues found when analyzing namespace: bookinfo.
```

실제 적용 YAML 핵심:

```yaml
# Gateway: Istio Ingress Gateway 프록시 내부 HTTP 리스너
spec:
  selector:
    istio: ingressgateway
  servers:
    - hosts: ["*"]
      port:
        name: http
        number: 8080
        protocol: HTTP
```

```yaml
# VirtualService: 지정된 경로를 productpage:9080으로 전달
spec:
  gateways: [bookinfo-gateway]
  hosts: ["*"]
  http:
    - match:
        - uri: {exact: /productpage}
        - uri: {prefix: /static}
        - uri: {exact: /login}
        - uri: {exact: /logout}
        - uri: {prefix: /api/v1/products}
      route:
        - destination:
            host: productpage
            port: {number: 9080}
```

이 YAML은 `spec`의 발췌이며 독립 적용용 완전한 리소스 파일은 아니다. Gateway의 포트 `8080`과 외부 노출 NodePort 번호는 다를 수 있다.

## 6. Port Forwarding과 연결 실패 기록

### 6-1. ClusterIP에서도 임시 접근

```bash
kubectl port-forward svc/productpage -n bookinfo --address 0.0.0.0 5000:9080
# Forwarding from 0.0.0.0:5000 -> 9080
```

```text
http://192.168.120.150:5000/productpage
```

- Service를 NodePort로 변경하지 않아도 `kubectl port-forward`를 사용할 수 있다.
- `5000`은 master1 로컬 포트, `9080`은 Service의 포트이며 실제로 선택된 Pod에 전달된다.
- 포트포워딩 프로세스가 실행 중이어야 한다. `Ctrl+C` 종료 후에는 접속 불가능.
- `--address 0.0.0.0`은 모든 인터페이스를 열므로 신뢰 네트워크에서만 사용하고 실습 후 종료한다.

### 6-2. 발생한 오류와 점검

```text
failed to connect to localhost:9080 inside namespace
IPv4: dial tcp4 127.0.0.1:9080: connect: connection refused
error: lost connection to pod
```

**관찰 사실:** 포워딩 리스너는 열렸으나 Pod 내부 포트 연결이 거부됐다. 당시 일부 Bookinfo Pod가 `Init:1/2`였고, 추후 `2/2 Running`으로 복구되는 모습이 보였다. 그러나 오류 원인이 Pod 초기화 지연이었다고 **확정할 근거는 없음**. 또한 이후 5000 포트 경유 접속이 최종 성공했다는 로그는 없다.

```bash
kubectl get pods -n bookinfo -o wide
kubectl describe pod -n bookinfo -l app=productpage
kubectl logs -n bookinfo -l app=productpage -c productpage --tail=50
kubectl exec -n bookinfo deploy/productpage-v1 -c productpage -- curl -I http://127.0.0.1:9080/productpage
```

## 7. Kiali 및 트래픽 라우팅

### 7-1. Istio Addons 설치 및 상태 확인

```bash
kubectl apply -f samples/addons
kubectl get pods -n istio-system
```

실습에서 Grafana, Jaeger, Kiali, Loki, Prometheus 리소스가 생성됐다. 초기에는 Kiali·Prometheus 등 일부가 Ready 전이었으나 이후 Kiali `1/1`, Prometheus `2/2`, Grafana `1/1`, Jaeger `1/1`, Istiod `1/1`을 확인했다. **Loki는 당시 `Pending` 상태**여서 해결 완료로 표시하지 않는다.

```bash
kubectl port-forward -n istio-system svc/kiali --address 0.0.0.0 20001:20001
# 접속: http://192.168.120.150:20001/kiali
```

Kiali에서 `Traffic Graph` → Namespace `bookinfo` → `Versioned app graph` 확인. 처음에는 최근 트래픽이 없어 그래프가 비어 있었으나 Bookinfo 브라우저 새로고침 후 연결선이 나타났다.

### 7-2. HTTP 요청 발생 및 코드 확인

```bash
# 1차 실습: HTTP 응답 확인용 1회 요청 (ratings 컨테이너 내부)
kubectl exec -n bookinfo   "$(kubectl get pod -n bookinfo -l app=ratings -o jsonpath='{.items[0].metadata.name}')"   -c ratings -- curl -sS http://productpage.bookinfo.svc.cluster.local:9080/productpage   | grep -o '<title>.*</title>'

# master1에서 NodePort로 100회 트래픽 전송
for i in $(seq 1 100); do
  curl -s -o /dev/null 'http://192.168.120.150:31182/productpage'
done

# 상태 코드도 표시
for i in $(seq 1 100); do
  curl -s -o /dev/null -w '%{http_code}\n' 'http://192.168.120.150:31182/productpage'
done
```

> 실제 출력에서 HTTP `200`이 연속 확인됐다. 로그에는 일부 결과만 공유됐으므로 **100건 전부 성공**이라고 단정하지 않는다. Kiali에서 약 4개 앱/6개 버전/4개 서비스와 트래픽 연결선이 표시되고, 스크린샷 시점의 성공률이 100%로 나타났다.

### 7-3. 환경변수로 접속 주소 저장

```bash
# 특수 따옴표(“ ”)가 아니라 쉘 따옴표(" ") 사용
export GATEWAY_URL="192.168.120.150:31182"
echo "$GATEWAY_URL"
for i in $(seq 1 100); do
  curl -s -o /dev/null "http://$GATEWAY_URL/productpage"
done
```

> 이름이 `GATEWAY_URL`이어도 이 값은 **productpage NodePort**다. 실제 Istio Ingress Gateway를 가리키지 않는다.

### 7-4. Kiali Request Routing (Reviews 버전 가중치)

UI에서 설정한 비율: **v1=7%, v2=70%, v3=23%**. Kiali 화면에는 DestinationRule / VirtualService 생성 미리보기 및 `Create` 단계가 나타났다. 실제 저장·적용 후 결과 YAML은 대화에 없으므로 **적용 완료라고 단정하지 않는다**.

이해를 돕기 위한 대표적인 YAML 예시:

```yaml
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata:
  name: reviews
  namespace: bookinfo
spec:
  host: reviews
  subsets:
    - name: v1
      labels: {version: v1}
    - name: v2
      labels: {version: v2}
    - name: v3
      labels: {version: v3}
---
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: reviews
  namespace: bookinfo
spec:
  hosts: [reviews]
  http:
    - route:
        - destination: {host: reviews, subset: v1}
          weight: 7
        - destination: {host: reviews, subset: v2}
          weight: 70
        - destination: {host: reviews, subset: v3}
          weight: 23
```

```bash
kubectl get destinationrules,virtualservices -n bookinfo
istioctl analyze -n bookinfo
```

DestinationRule은 버전을 subset으로 정의하고 VirtualService는 목적지와 가중치를 지정한다. 단기 샘플 요청에서 결과가 정확히 7:70:23이 될 필요는 없다.

### 8-2. Node Exporter Full Dashboard ID 1860

Grafana에서 Dashboard ID **1860**을 Import해 노드 사용량을 확인하는 실습. 해당 Dashboard는 node-exporter 지표가 Prometheus에서 수집되어야 값이 나온다.

실습 스크린샷 기준 표시 항목: CPU Busy, RAM Used, Root FS Used, Uptime, 네트워크 등. 값은 캡처 시점 데이터이므로 지속적인 현황으로 해석하지 않는다.

### 8-3. Helm으로 Node Exporter + kube-state-metrics 설치 (실제 실행)

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

helm install node-exporter prometheus-community/prometheus-node-exporter   -n monitoring --create-namespace

kubectl get pods -n monitoring -l app.kubernetes.io/name=prometheus-node-exporter
# 2개 Pod 1/1 Running 확인

helm install kube-state-metrics prometheus-community/kube-state-metrics   -n monitoring
# STATUS: deployed 확인 (Pod Ready 별도 확인 필요)
```

- **Node Exporter:** 서버 OS 수준의 CPU/메모리/디스크/네트워크 등 메트릭 제공. DaemonSet으로 각 노드에 배치되는 경우가 많다.
- **kube-state-metrics:** Kubernetes 오브젝트의 상태 지표(Deployment, Pod, Node 등)를 제공.
- **Prometheus:** Exporter `/metrics` 엔드포인트를 스크래핑하여 저장.
- **Grafana:** Prometheus에서 수치를 조회해 대시보드로 표현.

### 8-4. 오타 Namespace

```bash
k create ns monitering
# namespace/monitering created
```

`monitoring`과 `monitering`은 **서로 다른 Namespace**다. 실제 Helm 릴리스는 `monitoring`에 설치됐다. `monitering`은 실수로 만든 것으로 보이므로 다른 리소스가 없는지 확인 후 삭제 가능.

```bash
kubectl get ns | grep -E 'monitoring|monitering'
kubectl get all -n monitering
# 비어 있고 필요 없을 때만
kubectl delete ns monitering
```

## 1. Kubernetes Secret 확인

## 3. MariaDB Secret과 Helm Release Secret

### `mydb-mariadb`

MariaDB에서 사용하는 실제 애플리케이션 관련 Secret이다.

값 자체를 노출하지 않고 구조만 확인:


### `sh.helm.release.v1.mydb.v1`

Helm이 release 상태를 저장하기 위해 자동 생성한 Secret이다.

```text

 ├─ PVC
 ├─ Service

 └─ sh.helm.release.v1.mydb.v1
```

## 4. MariaDB Pod Pending 문제

설치 직후 Pod가 Pending 상태였다.

```text
mydb-mariadb-0   0/1   Pending
```

PVC도 Pending 상태였다.

```text
data-mydb-mariadb-0   Pending
data-mydb2-mariadb-0  Pending
```

### 원인 흐름

```text
MariaDB Pod
   ↓
PVC 요청
   ↓
사용 가능한 PV / StorageClass 필요
   ↓
바인딩 실패
   ↓
Pod Pending
```

### 확인 명령

```bash
kubectl get storageclass
kubectl get pv
kubectl describe pvc data-mydb-mariadb-0 -n db
kubectl describe pod mydb-mariadb-0 -n db
```

특히 `describe` 결과의 `Events:`를 확인한다.

예상 가능한 메시지:

```text
pod has unbound immediate PersistentVolumeClaims
```

또는

```text
no persistent volumes available for this claim
```

즉 Secret 생성 자체는 성공했지만, MariaDB Pod가 실제로 Running 되려면 Storage 구성이 추가로 필요하다.

# 5. Kubernetes 고가용성(HA) Cluster

## 5-1. Application 계층의 가용성

Deployment Controller 기반으로 여러 Replica를 구성하면 Pod 장애 시 새로운 Pod를 생성해 서비스를 유지할 수 있다.

```text
Deployment
 ├─ Pod 1
 ├─ Pod 2
 └─ Pod 3
```

핵심:

- Replica를 여러 개 유지
- Pod 장애 시 Controller가 재생성
- Worker Node 장애 시 다른 Node에 새 Pod 생성 가능
- 애플리케이션 자체의 가용성을 높임

---

## 5-2. Control Plane 고가용성

Control Plane 한 대만 사용하면 해당 노드 장애 시 Kubernetes 제어 기능이 영향을 받을 수 있다.

따라서 HA 환경에서는 Control Plane Node를 여러 대 구성한다.

```text
                Load Balancer
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
 Control Plane 1  Control Plane 2  Control Plane 3
```

각 Control Plane에는 다음 구성 요소가 포함된다.

```text
kube-apiserver
controller-manager
scheduler
etcd
```

---

## 5-3. Stacked etcd 구조

Stacked etcd는 **각 Control Plane Node 안에 etcd도 같이 배치**하는 방식이다.

```text
Control Plane 1
 ├─ API Server
 ├─ Controller Manager
 ├─ Scheduler
 └─ etcd

Control Plane 2
 ├─ API Server
 ├─ Controller Manager
 ├─ Scheduler
 └─ etcd

Control Plane 3
 ├─ API Server
 ├─ Controller Manager
 ├─ Scheduler
 └─ etcd
```

### etcd 역할

Kubernetes Cluster 상태를 저장하는 Key-Value Store.

대표적으로 저장되는 정보:

- Pod
- Deployment
- Service
- ConfigMap
- Secret
- Node 상태
- Cluster 설정

### 왜 3개를 많이 사용하는가?

etcd는 과반수(quorum)를 기준으로 동작한다.

```text
etcd 3대 구성
→ 2대 이상 정상 시 quorum 유지
→ 1대 장애까지 허용
```

---

## 5-4. Leader Election

Controller Manager와 Scheduler는 여러 Control Plane에서 실행될 수 있지만, 실제 작업은 Leader를 선출해서 수행한다.

```text
master1 → Leader
master2 → Standby
master3 → Standby
```

Leader 장애 시:

```text
master1 장애
   ↓
새 Leader 선출
   ↓
master2 → Leader
```

# 6. Service Mesh 개념

## 6-1. 왜 Service Mesh가 필요한가?

Microservice Architecture(MSA)를 사용하면 서비스가 분리되면서 서비스 간 통신이 크게 증가한다.

예:

```text
Service A → Service B
Service A → Service C
Service B → Service D
Service C → Service D
```

MSA는 Monolithic Architecture의 단점을 줄이고 Cloud 환경에서 유리하지만, 서비스 수가 증가하면서 **런타임 복잡성**이 커진다.

Service Mesh는 이런 서비스 간 통신 기능을 애플리케이션 코드 바깥의 인프라 계층으로 분리한다.

### 장점

- 애플리케이션 외부에서 공통 기능 구현
- 기능 재사용 가능
- MSA 런타임 복잡성 완화
- 개발 언어/미들웨어 종속성 감소

### 단점

- 런타임 인스턴스 수 증가
- 네트워크 레이어 추가
- 운영 복잡도 및 리소스 사용량 증가 가능

---

# 7. Service Mesh란?

Service Mesh는 **서비스 간 통신을 제어하는 전용 인프라 계층**이다.

요청은 각 서비스와 함께 실행되는 Proxy를 통해 전달된다.

```text
Service A
 ├─ App
 └─ Sidecar Proxy
        │
        ▼
Service B
 ├─ App
 └─ Sidecar Proxy
```

각 서비스에 붙는 Proxy를 **Sidecar**라고 부른다.

Sidecar Proxy들이 서로 통신하면서 Mesh Network를 형성한다.

---

# 8. Istio

Istio는 대표적인 Service Mesh 구현체이다.

핵심 구조:

```text
Data Plane    = Envoy
Control Plane = Istiod
```

---

## 8-1. Envoy

Envoy는 각 서비스의 Sidecar Proxy로 배포되어 실제 데이터 트래픽을 처리한다.

주요 기능:

- 동적 Service Discovery
- Load Balancing
- TLS 종료
- HTTP/2 / gRPC Proxy
- Circuit Breaker
- Health Check
- 가중치 기반 Traffic Split
- Fault Injection
- Metrics 생성
- Retry / Failover

즉 서비스 코드 자체를 수정하지 않고 네트워크 기능을 추가할 수 있다.

---

## 8-2. Istiod

Istiod는 Istio의 Control Plane 역할을 한다.

주요 역할:

- Service Discovery
- Envoy 설정 생성 및 전달
- 인증서 관리
- 서비스 간 인증
- mTLS를 위한 인증서 발급
- 라우팅 정책 배포

```text
              Istiod
                │
        설정 / 정책 / 인증서
                │
       ┌────────┴────────┐
       ▼                 ▼
 Envoy Proxy A      Envoy Proxy B
       │                 │
       └──── Traffic ────┘
```

---

# 17. 핵심 정리

```text
Service Mesh
= 서비스 간 통신을 관리하는 인프라 계층

Istio
= Service Mesh 구현체

Envoy
= 실제 트래픽을 처리하는 Sidecar Proxy

Istiod
= Envoy 설정과 정책을 관리하는 Control Plane

VirtualService
= 트래픽을 어디로 보낼지 결정

DestinationRule
= 대상 서비스의 Version / Subset / 정책 정의

Gateway
= 외부 트래픽의 Mesh 진입점

Kiali
= Service Mesh Traffic Flow 시각화
```

# 18. 기존 Kubernetes 실습과 연결

```text
Deployment / Replica
→ 애플리케이션 가용성

Service
→ Pod 접근점

Rolling Update
→ 버전 교체

Blue/Green / Canary
→ 배포 전략

Prometheus / Grafana
→ Metric 기반 모니터링

Istio VirtualService
→ 세밀한 Traffic Split

Istio DestinationRule
→ Version/subset 정책

Envoy
→ Retry / Timeout / Circuit Breaker / mTLS

Kiali
→ Service 간 Traffic Flow 시각화
```

Service Mesh는 기존 Kubernetes 기능을 대체한다기보다, **서비스 간 통신 제어·보안·관측 기능을 추가하는 계층**으로 이해하면 된다.

## 오늘 실습에서 기억할 포인트

1. Helm으로 MariaDB를 설치하면 애플리케이션 Secret과 Helm Release Secret이 함께 생성될 수 있다.
2. Pod가 `Pending`이라면 Secret뿐 아니라 PVC/PV/StorageClass 상태도 확인한다.
3. Kubernetes HA는 Application Replica와 Control Plane HA를 구분한다.
4. Stacked etcd는 Control Plane Node 내부에 etcd를 같이 배치하는 방식이다.
5. Service Mesh는 MSA의 서비스 간 통신 복잡성을 줄이기 위한 인프라 계층이다.
6. Istio의 핵심은 `Envoy + Istiod`이다.
7. `VirtualService + DestinationRule` 조합으로 Version별 Traffic Routing이 가능하다.
8. Grafana는 수치 중심, Kiali는 Service Traffic 관계 중심으로 본다.
