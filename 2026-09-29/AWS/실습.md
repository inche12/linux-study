<a id="1-오늘-실습-전체-흐름"></a>
# 1. 오늘 실습 전체 흐름

오늘 실습은 완성된 Auto Scaling 환경을 직접 구축한 것이 아니라, **Auto Scaling 실습 전에 사용할 웹 서버가 정상적으로 자동 구성되는지 확인하는 단계**까지 진행했다.

전체 흐름은 다음과 같다.

```text
기존 VPC / Public Subnet 환경
        ↓
기존 ALB + Target Group 구조 확인
        ↓
Amazon Linux 2023 EC2 생성
        ↓
Advanced details → User Data 입력
        ↓
Apache / PHP / Git / 실습 웹 앱 자동 설치
        ↓
Public IPv4로 웹 접속 시도
        ↓
ERR_CONNECTION_REFUSED 발생
        ↓
systemctl status httpd 확인
        ↓
httpd inactive 확인
        ↓
User Data의 특수 대시(–) 문제 발견
        ↓
systemctl enable --now httpd
        ↓
웹페이지 정상 출력
        ↓
cloud-init 로그 / 웹 파일 확인
        ↓
Auto Scaling 구조 사전 학습
        ↓
ASG가 실제로는 아직 생성되지 않았음을 콘솔에서 확인
        ↓
EC2 / ALB / 기타 과금 리소스 정리 방법 확인
        ↓
Billing & Cost Management에서 비용 확인
```

<a id="2-강의-아키텍처-이미지-이해"></a>
# 2. 강의 아키텍처 이미지 이해

강의 자료의 그림에서는 대략 다음과 같은 구조가 제시되었다.

```text
                    Internet
                       │
                       ▼
               Internet Gateway
                       │
                VPC 10.0.0.0/16
                       │
        ┌──────────────┴──────────────┐
        │                             │
Availability Zone A            Availability Zone C
        │                             │
Public Subnet A                Public Subnet C
10.0.10.0/24                   10.0.20.0/24
        │
        ▼
 EC2 Linux Web Server
```

## 화면 확인 포인트

강의 이미지에는 다음 요소가 표시되어 있었다.

- AWS Cloud 영역
- 하나의 VPC
- 서로 다른 두 Availability Zone
- 각 AZ에 위치한 Public Subnet
- Internet Gateway
- Public Subnet 안의 Linux EC2 Web Server

이 그림의 목적은 **한 VPC 안에서 여러 AZ를 사용하여 웹 서버를 배치할 수 있는 구조**를 보여주는 것이다.

> 강의 이미지의 CIDR과 실제 실습 계정의 CIDR은 다르다.
> 그림은 개념 구조이고, 실제 실습에서는 `10.126.0.0/16` VPC를 사용했다.

## 강의 이미지 ↔ 실제 실습 환경 대응

| 강의 그림 | 실제 실습 환경 |
|---|---|
| VPC `10.0.0.0/16` | `example-vpc` / `10.126.0.0/16` |
| Public Subnet A | `example-pub-sub1` |
| Public Subnet C | `example-pub-sub2` |
| AZ A | `ap-northeast-2a` |
| AZ C | `ap-northeast-2c` |
| Internet Gateway | Public Route Table의 기본 경로가 연결된 IGW |
| Linux Web Server | `webserver 1`, `ELB-vm1`, `ELB-vm2` 등 |

<a id="3-기존-vpc--subnet--route-table-구조"></a>
# 3. 기존 VPC / Subnet / Route Table 구조

## VPC

```text
Name: example-vpc
CIDR: 10.126.0.0/16
Region: ap-northeast-2 (Seoul)
```

VPC는 AWS 안에서 사용하는 논리적으로 격리된 네트워크이다.

```text
example-vpc
10.126.0.0/16
```

안에 여러 Subnet을 나누어 사용했다.

---

## Public Subnet 1

```text
Name: example-pub-sub1
CIDR: 10.126.0.0/24
AZ: ap-northeast-2a
```

## Public Subnet 2

```text
Name: example-pub-sub2
CIDR: 10.126.2.0/24
AZ: ap-northeast-2c
```

서로 다른 AZ에 Subnet을 나누면 한 AZ에 장애가 생기더라도 다른 AZ를 사용할 수 있는 구조를 만들 수 있다.

---

## Public Route Table

Public Subnet을 인터넷과 연결하려면 Route Table에 다음과 같은 기본 경로가 필요하다.

```text
Destination       Target
10.126.0.0/16  →  local
0.0.0.0/0      →  Internet Gateway
```

### 의미

```text
10.126.0.0/16 → local
```

VPC 내부 통신은 VPC 내부에서 처리한다.

```text
0.0.0.0/0 → IGW
```

VPC 내부가 아닌 목적지, 즉 일반적인 인터넷 트래픽을 Internet Gateway로 보낸다.

---

## 실습 중 Route Table에서 있었던 확인 사항

`example-pub-sub2`가 처음에는 Private Route Table 쪽에 연결되어 있던 상황을 확인했고, Public Subnet으로 사용할 수 있도록 **Public Route Table에 연결**했다.

최종적으로 `example-pub-RT`는 다음 형태였다.

```text
10.126.0.0/16 → local
0.0.0.0/0     → igw-0220da7497d04cca3
```

```text
example-pub-sub2
        ↓
example-pub-RT
        ↓
0.0.0.0/0 → IGW
```

> Subnet의 이름에 `public`이 들어가 있다고 자동으로 Public Subnet이 되는 것이 아니다.
> **실제로 연결된 Route Table이 IGW로 기본 경로를 가지는지 확인해야 한다.**

<a id="4-기존-alb-실습-구조-복습"></a>
# 4. 기존 ALB 실습 구조 복습

앞선 실습에서 Application Load Balancer를 구성했다.

## 주요 리소스

```text
ALB: web-ALB
Target Group: web-tg
Protocol: HTTP
Port: 80
```

Target EC2:

```text
ELB-vm1
ELB-vm2
```

구조는 다음과 같다.

```text
                         Internet
                            │
                            ▼
                        web-ALB
                            │
                         web-tg
                       /        \
                      ▼          ▼
                 ELB-vm1      ELB-vm2
                   EC2          EC2
```

---

## ALB Security Group

```text
Name: alb-sg
ID: sg-00b5d7cb52f6585b1
```

Inbound:

```text
HTTP
TCP 80
Source: 0.0.0.0/0
```

외부 사용자가 ALB의 HTTP 80 Listener로 접근할 수 있게 허용했다.

---

## Target Group 상태

두 EC2가 Target Group에 등록되었고 이후 모두 Healthy 상태가 되었다.

```text
ELB-vm1 → Healthy
ELB-vm2 → Healthy
```

Target Group이 Healthy라는 것은 Health Check 요청에 웹 서버가 정상 응답하고 있다는 의미이다.

---

## ALB DNS

사용했던 DNS:

```text
web-ALB-1279089505.ap-northeast-2.elb.amazonaws.com
```

웹 브라우저에서는 다음처럼 **`http://`를 명시**하여 접근했다.

```text
http://web-ALB-1279089505.ap-northeast-2.elb.amazonaws.com
```

### 왜 `http://`를 명시했는가?

현재 Listener가:

```text
HTTP : 80
```

만 설정되어 있었기 때문이다.

HTTPS 443 Listener와 인증서가 구성되어 있지 않은 상태에서 브라우저가 HTTPS로 접근하려 하면 정상 연결되지 않을 수 있다.

---

## ALB 실습에서 확인한 개별 EC2 웹 페이지

```text
43.201.85.228 → website for ELB - 1
13.124.51.204 → website for ELB - 2
```

각 EC2를 직접 접속했을 때 서로 다른 웹 페이지를 확인했고, ALB를 통해 접속하면 두 Target으로 요청이 분산되는 구조를 이해했다.

<a id="5-ec2-webserver-1-생성"></a>
# 5. EC2 `webserver 1` 생성

Auto Scaling 관련 실습에 앞서 별도의 웹 서버 EC2를 생성했다.

## 생성 정보

```text
Name: webserver 1
Instance ID: i-0506c86a4ce1772d1
AMI: Amazon Linux 2023
Kernel: 6.18 계열 선택
Instance Type: t3.micro
Key Pair: ktcloud-vm
VPC: example-vpc
Subnet: example-pub-sub2
AZ: ap-northeast-2c
Private IPv4: 10.126.2.51
Storage: 8 GiB gp3
```

생성 당시 Public IPv4 자동 할당을 활성화했다.

실습 당시 확인한 Public IPv4:

```text
54.180.86.71
```

> 일반 Public IPv4는 인스턴스를 Stop → Start 하면 바뀔 수 있다.
> 고정 Public IP가 필요하면 Elastic IP 등을 별도로 고려한다.

---

## 네트워크 구조

```text
Internet
   │
   ▼
Internet Gateway
   │
   ▼
example-vpc
10.126.0.0/16
   │
   ▼
example-pub-sub2
10.126.2.0/24
ap-northeast-2c
   │
   ▼
webserver 1
Private IP: 10.126.2.51
Public IP: 54.180.86.71
```

현재 구조에서는 EC2가 Public Subnet에 있고 Public IPv4도 할당되어 있기 때문에, Security Group에서 HTTP를 허용하면 인터넷에서 직접 웹 서버에 접속할 수 있다.

<a id="6-security-group과-외부-접속-조건"></a>
# 6. Security Group과 외부 접속 조건

`webserver 1`에서 사용한 Security Group:

```text
example-sg
sg-0157602e2b5352b42
```

화면에서 다음 Inbound 규칙을 확인했다.

```text
All ICMP - IPv4
Source: 0.0.0.0/0
```

```text
HTTP
TCP 80
Source: 0.0.0.0/0
```

---

## Public EC2에 웹 접속하기 위한 조건

Public Subnet의 EC2라고 해서 무조건 인터넷에서 접속 가능한 것은 아니다.

최소 다음 조건이 연결되어야 한다.

```text
1. Subnet Route Table
   0.0.0.0/0 → IGW

2. EC2에 Public IPv4 존재

3. Security Group
   TCP 80 허용

4. EC2 내부에서 웹 서버 실행
   httpd active (running)

5. 웹 서버가 실제로 80번 포트에서 Listen
```

즉:

```text
Public Subnet
+ Public IP
+ IGW Route
+ Security Group
+ Running Web Server
= Browser HTTP 접속 가능
```

<a id="7-고급-세부-정보---user-data"></a>
# 7. 고급 세부 정보 - User Data

EC2 생성 화면의 **Advanced details(고급 세부 정보)**에서 수행했던 핵심 작업은 **User Data 입력**이었다.

Auto Scaling Group을 생성한 것이 아니다.

경로:

```text
EC2
→ Instances
→ Launch instances
→ 기본 인스턴스 설정
→ Advanced details
→ User data
```

---

## User Data의 역할

User Data는 EC2가 처음 초기화될 때 실행할 명령을 지정하여 서버 초기 구성을 자동화하는 데 사용한다.

이번 실습에서는:

```text
EC2 생성
   ↓
User Data 실행
   ↓
MariaDB 관련 패키지 설치
   ↓
PHP 설치
   ↓
Apache(httpd) 설치
   ↓
Git 설치
   ↓
Apache 시작
   ↓
S3에서 Workshop 웹 앱 다운로드
   ↓
/var/www/html에 배치
   ↓
AWS SDK for PHP 다운로드
```

순으로 자동화하려고 했다.

<a id="8-user-data-명령어-상세-해석"></a>
# 8. User Data 명령어 상세 해석

아래는 실습 스크립트에서 Apache 시작 옵션을 올바른 ASCII 하이픈으로 표기한 정리본이다. 당시 잘못 입력된 특수 대시와 수동 수정 과정은 9절에 별도로 보존했다.

```bash
#!/bin/sh

# Install a LAMP stack
sudo dnf install -y mariadb105 php
sudo yum -y install httpd php-mbstring
sudo yum -y install git

# Start the web server
sudo systemctl enable --now httpd

# Install the web pages for our lab
if [ ! -f /var/www/html/aws-boarding-pass-webapp.tar.gz ]; then
    cd /var/www/html

    wget -O 'techcamp-webapp-2024.zip' \
    'https://ws-assets-prod-iad-r-icn-ced060f0d38bc0b0.s3.ap-northeast-2.amazonaws.com/600420b7-5c4c-498f-9b80-bc7798963ba3/techcamp-webapp-2024.zip'

    unzip techcamp-webapp-2024.zip

    sudo mv techcamp-webapp-2024/* .
    sudo rm -rf techcamp-webapp-2024
    sudo rm -rf techcamp-webapp-2024.zip
fi

# Install the AWS SDK for PHP
if [ ! -f /var/www/html/aws.zip ]; then
    cd /var/www/html

    sudo mkdir vendor
    cd vendor

    sudo wget https://docs.aws.amazon.com/aws-sdk-php/v3/download/aws.zip
    sudo unzip aws.zip
fi

# Update existing packages
sudo yum -y update
```

## 8-5. Apache 활성화 및 즉시 시작

```bash
sudo systemctl enable --now httpd
```

여기서 두 부분을 구분해야 한다.

```bash
systemctl enable httpd
```

→ 다음 부팅 이후에도 Apache가 자동 실행되도록 설정

```bash
systemctl start httpd
```

→ Apache를 지금 즉시 실행

`--now`를 붙이면 `enable`과 동시에 현재 서비스도 시작한다.

```bash
sudo systemctl enable --now httpd
```

즉 개념적으로 다음 두 명령을 한 번에 수행한다.

```bash
sudo systemctl enable httpd
sudo systemctl start httpd
```

<a id="9-웹-접속-실패-트러블슈팅"></a>
# 9. 웹 접속 실패 트러블슈팅

EC2 생성 이후 Public IPv4로 접속했다.

```text
http://54.180.86.71
```

하지만 브라우저에서:

```text
ERR_CONNECTION_REFUSED
```

가 발생했다.

---

## 9-1. 가장 먼저 확인한 것

Security Group에서 HTTP 80이 열려 있는지 확인했다.

```text
TCP 80
Source: 0.0.0.0/0
```

HTTP가 이미 허용되어 있었으므로 EC2 내부 서비스 상태를 확인했다.

---

## 9-2. Apache 상태 확인

```bash
sudo systemctl status httpd
```

### 명령어 역할

```text
systemctl
→ systemd 서비스 관리

status
→ 현재 서비스 상태 확인

httpd
→ Apache 서비스
```

결과:

```text
Loaded: loaded (...); disabled
Active: inactive (dead)
```

### 해석

```text
loaded
→ Apache 설치 자체는 되어 있음

disabled
→ 부팅 자동 시작 설정 안 됨

inactive (dead)
→ 현재 Apache 실행 안 됨
```

즉:

```text
Apache 설치 성공
하지만 실행되지 않음
```

이었다.

---

# 9-3. 원인: `--now`의 특수 대시 문제

원래 실행되어야 했던 명령:

```bash
sudo systemctl enable --now httpd
```

하지만 복사한 스크립트에는 다음처럼 보이는 문자가 포함되어 있었다.

```text
sudo systemctl enable –-now httpd
```

문제는 첫 번째 문자가:

```text
-
```

일반 ASCII 하이픈이 아니라:

```text
–
```

Unicode En Dash였다는 것이다.

겉보기에는 비슷하지만 Linux CLI에서는 다른 문자로 취급된다.

---

## 올바른 명령

```bash
sudo systemctl enable --now httpd
```

`now` 앞에 **일반 하이픈 2개**가 있어야 한다.

```text
--now
^^
ASCII '-' 2개
```

---

## 9-4. 수동으로 문제 해결

EC2에 접속하여 직접 실행했다.

```bash
sudo systemctl enable --now httpd
```

이후 다시:

```bash
sudo systemctl status httpd
```

확인 결과:

```text
Loaded: loaded (...); enabled
Active: active (running)
```

추가로:

```text
Server configured, listening on: port 80
```

상태를 확인했다.

즉 Apache가 정상적으로 80번 포트에서 동작하기 시작했다.

---

## 9-5. 웹 페이지 정상 확인

Apache를 실행한 이후 다시 브라우저에서:

```text
http://54.180.86.71
```

접속했다.

Workshop 웹 페이지가 정상적으로 표시되었다.

화면에는 다음과 같은 정보가 있었다.

```text

i-0506c86a4ce1772d1

Availability Zone
ap-northeast-2c

Current CPU Load
0%
```

그리고 메뉴에는:

```text
LOAD TEST
RDS
```

등이 표시되었다.

<a id="11-웹페이지가-실제로-표시되는-과정"></a>
# 11. 웹페이지가 실제로 표시되는 과정

Public IP를 입력했을 때 AWS가 자동으로 페이지를 만들어 주는 것은 아니다.

실제 흐름:

```text
사용자 Browser
     │
     │ HTTP Request : TCP 80
     ▼
54.180.86.71
Public IPv4
     │
     ▼
Internet Gateway
     │
     ▼
Public Subnet
     │
     ▼
Security Group
HTTP 80 허용
     │
     ▼
EC2 webserver 1
     │
     ▼
Apache httpd
     │
     ▼
/var/www/html/index.php
     │
     ▼
Workshop Web Application
```

웹 애플리케이션 자체가 EC2의 메타데이터를 조회하여:

```text
Instance ID
Availability Zone
CPU Load
```

등을 화면에 보여준다.

이 기능은 이후 여러 EC2를 만들었을 때 **현재 요청이 어느 인스턴스로 전달되었는지 확인하는 데 유용하다.**

---

<a id="12-alb와-ec2-2대의-관계"></a>
# 12. ALB와 EC2 2대의 관계

EC2 인스턴스 목록 화면에서 다음 상태를 확인했다.

| Name | 상태 | Type |
|---|---|---|
| `ktcloud-vm` | 중지됨 | `t3.micro` |
| `webserver 1` | 중지됨 | `t3.micro` |
| `ELB-vm1` | 실행 중 | `t3.micro` |
| `ELB-vm2` | 실행 중 | `t3.micro` |

화면에는 총 인스턴스 수가 5개로 표시되었지만, 캡처에서 명확하게 확인 가능한 것은 위 네 개였다.

> 보이지 않은 나머지 인스턴스의 이름/상태는 캡처만으로 확정하지 않는다.

---

## `ELB-vm1`, `ELB-vm2`는 무엇인가?

이 두 서버는 기존 ALB 실습에서 만든 Target EC2이다.

```text
web-ALB
    │
    ▼
web-tg
 ┌──┴──┐
 ▼     ▼
ELB-vm1 ELB-vm2
```

즉 Auto Scaling에서 자동 생성된 인스턴스가 아니라 **ALB Target으로 직접 만든 EC2**이다.

---

<a id="13-auto-scaling-사전-학습"></a>
# 13. Auto Scaling 사전 학습

Auto Scaling은 필요한 EC2 인스턴스 수를 자동으로 유지하거나 부하에 따라 증가/감소시키는 기능이다.

---

## 기본 구조

```text
Launch Template
      │
      ▼
Auto Scaling Group
      │
      ├────────────┐
      ▼            ▼
   EC2 #1        EC2 #2
   AZ-A          AZ-C
```

---

## Launch Template

Launch Template은 새로운 EC2를 **어떤 설정으로 생성할지** 정의한다.

예:

```text
AMI
Instance Type
Key Pair
Security Group
User Data
Storage
```

쉽게 표현하면:

```text
Launch Template
= EC2 생성 설계도
```

---

## Auto Scaling Group

ASG는 Launch Template을 사용해서 EC2를 만들고 인스턴스 개수를 관리한다.

예:

```text
Min     = 2
Desired = 2
Max     = 4
```

### Min

최소한 유지해야 할 인스턴스 수

### Desired

현재 정상적으로 유지하고 싶은 인스턴스 수

### Max

Scale Out할 수 있는 최대 인스턴스 수

---

## 예시

```text
Min = 2
Desired = 2
Max = 4
```

평상시:

```text
EC2 #1
EC2 #2
```

두 대를 유지한다.

부하 증가:

```text
EC2 #1
EC2 #2
EC2 #3
EC2 #4
```

필요에 따라 Scale Out할 수 있다.

부하 감소:

```text
EC2 #1
EC2 #2
```

불필요한 인스턴스를 Scale In할 수 있다.

---

<a id="14-asg-화면에서-실제-확인한-내용"></a>
# 14. ASG 화면에서 실제 확인한 내용

AWS 콘솔에서:

```text
EC2
→ Auto Scaling 그룹
```

으로 이동했다.

화면에는:

```text
Auto Scaling 그룹 생성
```

버튼이 표시되었고, 기존 Auto Scaling Group 목록은 나타나지 않았다.

## 화면 확인 결론

**오늘 실제로 Auto Scaling Group을 생성하지 않았다.**

즉:

```text
webserver 1
```

은 ASG가 자동 생성한 EC2가 아니라 **사용자가 EC2 생성 화면에서 직접 만든 인스턴스**이다.

---

## 오늘 어디까지 한 것인가?

```text
EC2 직접 생성
        ↓
User Data 자동 구성 확인
        ↓
웹 서버 동작 검증
        ↓
ASG 개념 확인
```

여기까지 진행한 것으로 정리할 수 있다.

다음 실습에서는 이 정상 동작 구성을 바탕으로:

```text
Launch Template
        ↓
Auto Scaling Group
        ↓
Multi-AZ EC2 생성
        ↓
ALB Target Group 연결
```

방향으로 확장할 수 있다.

---

<a id="15-ec2-중지--종료와-asg-관계"></a>
# 15. EC2 중지 / 종료와 ASG 관계

이 부분은 리소스 정리 시 중요하다.

## ASG가 존재하는 경우

예:

```text
Desired = 2
```

인 상태에서 ASG가 관리하는 EC2 한 대를 직접 종료하면:

```text
EC2 한 대 종료
    ↓
ASG가 현재 인스턴스 1대라고 감지
    ↓
Desired = 2를 만족하지 못함
    ↓
새 EC2 자동 생성
```

될 수 있다.

따라서 ASG 실습을 완전히 정리할 때는 **ASG를 먼저 확인**해야 한다.

---

## 오늘 환경

콘솔에서 실제 ASG가 없음을 확인했기 때문에:

```text
ELB-vm1
ELB-vm2
webserver 1
```

등을 중지하더라도 ASG가 새 EC2를 생성하지 않는다.

---

<a id="16-실습-종료-후-비용-절감-포인트"></a>
# 16. 실습 종료 후 비용 절감 포인트

실습을 끝낸 후에는 EC2만 보면 안 되고 여러 리소스를 함께 확인해야 한다.

---

## 16-1. EC2

현재 다시 쓸 예정이면:

```text
Stop
```

완전히 필요 없으면:

```text
Terminate
```

를 고려한다.

### Stop

```text
인스턴스 Compute 실행 중지
EBS는 유지
나중에 다시 Start 가능
```

### Terminate

```text
인스턴스 삭제
설정에 따라 Root EBS도 삭제
```

다음 수업에서 이어서 사용할 가능성이 있다면 Stop이 안전하다.

---

## 16-2. ALB

ALB는 EC2와 별도 리소스이다.

```text
EC2 Stop
≠
ALB Stop
```

ALB에는 일반 EC2처럼 `Stop` 개념이 없기 때문에:

```text
유지
또는
삭제
```

를 판단해야 한다.

기존 ALB:

```text
web-ALB
```

를 앞으로 사용하지 않는다면 삭제를 고려한다.

---

## 16-3. Target Group

```text
web-tg
```

Target Group 자체는 EC2와 별도 리소스이다.

ALB 실습을 완전히 정리한다면 ALB 삭제 후 더 이상 사용하지 않는 Target Group도 정리할 수 있다.

---

## 16-4. NAT Gateway

VPC 실습에서 NAT Gateway를 만들었다면 반드시 확인한다.

경로:

```text
VPC
→ NAT Gateways
```

NAT Gateway는 EC2를 중지했다고 함께 중지되는 리소스가 아니다.

필요 없다면 삭제 여부를 검토한다.

---

## 16-5. Elastic IP

경로:

```text
EC2
→ Elastic IP addresses
```

사용하지 않는 Elastic IP가 있다면 연결 상태를 확인한다.

NAT Gateway를 삭제하더라도 연결했던 Elastic IP가 계정에 남아 있을 수 있으므로 따로 확인한다.

---

## 16-6. EBS Volume

경로:

```text
EC2
→ Volumes
```

중지된 EC2의 EBS는 그대로 유지된다.

필요 없는 독립 EBS Volume이 남아 있는지 확인한다.

---

## 16-7. Snapshot / AMI

실습 과정에서 AMI 또는 Snapshot을 만들었다면 저장공간을 확인한다.

```text
EC2
→ AMIs

EC2
→ Snapshots
```

---

## 16-8. 비교적 그대로 두어도 되는 기본 네트워크 객체

다음은 그 자체로 EC2처럼 계속 실행되는 서버 리소스는 아니다.

```text
VPC
Subnet
Route Table
Internet Gateway
Security Group
NACL
```

다음 실습에서 계속 사용할 계획이면 굳이 매번 삭제하지 않아도 된다.

---

## 비용 정리 체크리스트

```text
[ ] 실행 중 EC2 확인
[ ] ASG 존재 여부 확인
[ ] ALB 존재 여부 확인
[ ] NAT Gateway 확인
[ ] Elastic IP 확인
[ ] EBS Volume 확인
[ ] Snapshot 확인
[ ] AMI 확인
```


가 표시된 부분도 있었다.

따라서 이 화면만 보고 바로:

```text
실제로 카드에서 2.65달러가 결제됐다
```

라고 단정하면 안 된다.

실제 청구 여부를 확인할 때는:

```text
Bills
→ 서비스별 상세
→ Credits
→ Taxes
→ 최종 결제 예정액
```

등을 함께 확인해야 한다.

# 19. 오늘 실습 핵심 개념 한 번에 정리

## VPC

## Subnet

```text
VPC의 IP 범위를 더 작은 네트워크로 분할
```

단, EC2 자체가 직접 인터넷 통신하려면 Public IP 등 추가 조건이 필요하다.

```text

```

```text

```

```text
AWS의 가상 서버
```

# 최종 아키텍처 관점에서 연결

오늘까지 배운 내용을 최종적으로 연결하면:

```text
                           Internet
                              │
                              ▼
                       Internet Gateway
                              │
                       ┌──────┴──────┐
                       │     VPC     │
                       │10.126.0.0/16│
                       └──────┬──────┘
                              │
                    ┌─────────┴─────────┐
                    │                   │
             Public Subnet 1      Public Subnet 2
              ap-northeast-2a      ap-northeast-2c
                    │                   │
                    └─────────┬─────────┘
                              │
                            ALB
                              │
                        Target Group
                         /          \
                        ▼            ▼
                     EC2 #1        EC2 #2
                        ▲            ▲
                        └──────┬─────┘
                               │
                        Auto Scaling Group
                               ▲
                               │
                        Launch Template
                               │
                         ┌─────┴─────┐
                         │ User Data │
                         └───────────┘
```

이번 실습은 이 구조 전체를 한 번에 완성한 것이 아니라:

```text
VPC / Subnet
→ ALB / Target Group
→ EC2 Web Server
→ User Data
→ 웹 서버 정상 동작 확인
→ Auto Scaling 개념 확인
```

순서로 기반을 만든 과정이다.
