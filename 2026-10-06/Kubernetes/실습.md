## 1. Helm 기본 개념

Helm은 Kubernetes의 **패키지 매니저**이다.

여러 개의 Kubernetes YAML 리소스를 `Chart`라는 단위로 묶어서 설치, 업데이트, 삭제, 롤백할 수 있다.

```text
Helm Chart
   ↓
values.yaml + templates/*.yaml
   ↓
Kubernetes YAML 렌더링
   ↓
Deployment / Service / StatefulSet / Pod / PVC 등 생성
```

### Helm 핵심 용어

- **Chart**
  - Kubernetes 애플리케이션 배포에 필요한 YAML 템플릿 묶음
- **Repository**
  - Chart를 저장하는 저장소
- **Release**
  - Chart를 실제 Kubernetes 클러스터에 설치한 하나의 배포 인스턴스

예:

```bash
helm install mydb bitnami/mariadb
```

```text
mydb             → Release 이름
bitnami/mariadb  → 사용할 Chart
```

### Helm v2 / v3 차이

Helm v2:

```text
Helm Client
   ↓
Tiller Server
   ↓
Kubernetes
```

Helm v3:

```text
Helm Client
   ↓
Kubernetes API
```

Helm v3부터는 Tiller가 제거되어 구조가 단순해졌다.

# 5. MariaDB Pod Pending 원인 확인

설치 직후 Pod 상태:

```text
mydb-mariadb-0   0/1   Pending
```

Pod 상세 상태 확인:

```bash
kubectl -n db describe pod mydb-mariadb-0
```

`describe`는 Pod의 상세 상태와 Events를 확인할 때 사용한다.

전체 YAML 자체를 보고 싶다면:

```bash
kubectl -n db get pod mydb-mariadb-0 -o yaml
```

## 확인된 원인

`describe`의 Events:

```text
FailedScheduling
0/2 nodes are available:
pod has unbound immediate PersistentVolumeClaims
```

또한:

```text
Node: <none>
PodScheduled: False
```

즉 MariaDB가 요청한 PVC가 PV와 연결되지 않아 Scheduler가 Pod를 Node에 배치할 수 없었다.

흐름:

```text
MariaDB StatefulSet
       ↓
PVC 요청
       ↓
PV 필요
       ↓
PV 없음 / Bound 실패
       ↓
Pod Scheduling 실패
       ↓
Pending
```

확인 명령:

```bash
kubectl get pvc -n db
kubectl get pv
kubectl get sc
```

PVC 상세 확인:

```bash
kubectl -n db describe pvc data-mydb-mariadb-0
```

### Chart.yaml

```yaml
apiVersion: v2
name: myapp
description: A Helm chart for Kubernetes
type: application
version: 0.1.0

```

의미:

```text
apiVersion → Helm Chart API 버전

type       → application / library

appVersion → 실제 애플리케이션 버전
```

### values.yaml

Chart의 설정값을 관리한다.

예:

```yaml
replicaCount: 3

image:
  repository: rosehs00/test
  pullPolicy: IfNotPresent
  tag: "nginx"

  type: NodePort
  port: 80
```

흐름:

```text
values.yaml
    ↓
templates/*.yaml
    ↓
Helm 렌더링
    ↓
최종 Kubernetes YAML
```

```bash

```

파일로 저장:

```bash

```

흐름:

```text
Chart.yaml
values.yaml
templates/*.yaml
       ↓
helm template
       ↓
myapp.yaml
```

## Helm Release 삭제

```bash
helm -n db uninstall myapp
```

또는:

```bash
helm delete -n db myapp
```

## 렌더링한 YAML을 kubectl로 배포

```bash
kubectl -n db create -f myapp.yaml
```

생성된 리소스:

```text
serviceaccount/myapp
service/myapp
deployment.apps/myapp
pod/myapp-test-connection
```

이 경우 Kubernetes 리소스는 존재하지만 **Helm Release는 존재하지 않는다.**

```text
kubectl create/apply로 생성
→ Kubernetes 리소스 존재
→ Helm Release 없음
→ helm upgrade 불가
```

확인:


# 9. Helm 관리와 kubectl 직접 관리 차이

## kubectl 방식

```bash
kubectl apply -f deployment.yaml
kubectl apply -f service.yaml
```

또는:



정리:

```text
kubectl/YAML
→ 리소스 단위 직접 관리

Helm
→ 애플리케이션 단위 패키지 관리
→ install / upgrade / rollback / uninstall
```

<a id="section-11"></a>

# 11. Helm Rollback

Revision 1로 Rollback:

```bash
helm -n db rollback myapp 1
```

결과:

```text
Rollback was a success!
```

Rollback 후 이전 `replicaCount: 3` 상태가 복구되어 Pod 3개가 다시 생성되었다.

```text
Revision 1 → Pod 3개
Revision 2 → Pod 1개
Rollback 1
     ↓
이전 설정 복원
     ↓
Pod 다시 3개
```

Rollback도 새로운 Revision으로 기록된다.

이력 확인:

```bash
helm history myapp -n db
```

중요:

`helm rollback`은 **클러스터의 Release 상태를 이전 Revision으로 복원**하는 것이며, 로컬의 `values.yaml` 파일 내용을 되돌리지는 않는다.

<a id="section-12"></a>

# 12. MariaDB Pending 해결 - Persistence 비활성화

Bitnami MariaDB Chart 전체 다운로드 및 압축 해제:

```bash
helm fetch --untar bitnami/mariadb
```

생성:

```text
mariadb/
├── charts
├── Chart.yaml
├── README.md
├── templates
└── values.yaml
```

MariaDB 기본 설정 수정:

```bash
vi mariadb/values.yaml
```

`primary.persistence.enabled` 변경:

```yaml
primary:
  persistence:
    enabled: false
```

원래:

```text
enabled: true
→ PVC 생성
→ PV 필요
→ PV 없음
→ Pod Pending
```

변경 후:

```text
enabled: false
→ PVC 사용하지 않음
→ 임시 저장공간 사용
→ Scheduling 가능
→ Pod Running
```

## Upgrade 시 발생한 비밀번호 오류

```bash
helm -n db upgrade mydb mariadb/
```

오류:

```text
PASSWORDS ERROR:
You must provide your current passwords when upgrading the release.
```

Bitnami Chart는 upgrade 시 기존 root password를 다시 전달하도록 요구하였다.

실습에서는 기존 Release를 삭제하고 다시 설치하였다.

```bash
helm -n db delete mydb
helm -n db install mydb mariadb/
```

Pod 확인:

```bash
kubectl get po -n db -w
```

정상:

```text
mydb-mariadb-0   1/1   Running
```

> 주의: `persistence.enabled=false`는 실습용으로 적합하지만 Pod가 재생성되면 DB 데이터가 유지되지 않을 수 있다. 운영 환경에서는 PV/PVC 기반 영구 저장소를 구성해야 한다.

# 14. MariaDB Client Pod로 DB 접속

임시 Client Pod 생성:

```bash
kubectl run mydb-mariadb-client \
  --rm --tty -i \
  --restart='Never' \
  --image registry-1.docker.io/bitnami/mariadb:latest \
  --env MARIADB_ROOT_PASSWORD=$MARIADB_ROOT_PASSWORD \
  --namespace db \
  --command -- bash
```

옵션:

```text
--rm             → 종료 시 Pod 자동 삭제
--tty -i         → Interactive Terminal
--restart=Never  → 일회성 Pod
--namespace db   → db Namespace
```

MariaDB 접속:

```bash
mysql -h mydb-mariadb.db.svc.cluster.local \
  -uroot \
  -p \
  my_database
```

접속 성공:

```text
MariaDB [my_database]>
```

테이블 확인:

```sql
show tables;
```

초기 상태:

```text
Empty set
```

즉 DB는 존재하지만 아직 Table이 없는 상태였다.

종료:

```sql
quit;
```

Client Pod Shell 종료:

```bash
exit
```

`--rm` 옵션 때문에 Client Pod가 자동 삭제되었다.

<a id="section-16"></a>

# 16. StatefulSet Scale 실습

MariaDB StatefulSet을 2개로 확장:

```bash
kubectl -n db scale statefulset mydb-mariadb --replicas 2
```

Pod:

```text
mydb-mariadb-0
mydb-mariadb-1
```

StatefulSet 특징:

```text
생성: 0 → 1 → 2
삭제: 2 → 1 → 0
```

Replica를 0으로 축소:

```bash
kubectl -n db scale statefulset mydb-mariadb --replicas 0
```

Pod가 모두 제거된다.

다시 2개로 확장:

```bash
kubectl -n db scale statefulset mydb-mariadb --replicas 2
```

실제 확인:

```text
mydb-mariadb-0 먼저 생성
        ↓
Ready
        ↓
mydb-mariadb-1 생성
```

즉 StatefulSet은 Pod를 순차적으로 생성한다.

<a id="section-17"></a>

# 17. Deployment와 StatefulSet 차이

## Deployment

주로 Stateless Application에서 사용한다.

```text
Deployment
    ↓
ReplicaSet
    ↓
Pods
```

특징:

- Pod 이름/신원이 중요하지 않음
- Pod는 서로 대체 가능
- Web/App Server 등에 많이 사용
- Replica Scale에 적합

## StatefulSet

주로 Stateful Application에서 사용한다.

```text
StatefulSet
├─ app-0
├─ app-1
└─ app-2
```

특징:

- Pod 이름이 고정됨
- 고유한 Network Identity
- 생성/삭제 순서 보장
- DB 등에 적합
- 일반적으로 Pod별 개별 PVC 사용

정리:

```text
Deployment
→ 교체 가능한 Stateless Pod

StatefulSet
→ 고유 Identity / Storage가 중요한 Stateful Pod
```

```text
Pod 삭제
  ↓
emptyDir 데이터 삭제
```

특징:

```text
Pod 삭제 → 데이터 삭제
```

MariaDB의 `persistence.enabled=false` 실습에서 영구 저장 대신 임시 저장을 사용하였다.

## ConfigMap / Secret

영구 데이터 저장용 볼륨이라기보다 설정값/비밀값을 Pod에 전달하기 위한 용도이다.

```text
ConfigMap / Secret
        ↓
Pod에 Volume으로 Mount
```

Pod가 삭제되더라도 ConfigMap/Secret Kubernetes 객체는 별도로 남아 있을 수 있다.

## PersistentVolumeClaim

```text
Pod
 ↓
PVC
 ↓
PV
 ↓
실제 Storage
```

Pod가 삭제되어도 PV/PVC가 유지되면 새 Pod가 다시 데이터를 사용할 수 있다.

<a id="section-19"></a>

# 19. hostPath Volume

`hostPath`는 **Node의 실제 디렉터리와 Pod 내부 디렉터리를 직접 매핑**하는 방식이다.

예:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hostpath-test
spec:
  containers:
    - name: nginx
      image: nginx
      volumeMounts:
        - name: host-volume
          mountPath: /mnt/data

  volumes:
    - name: host-volume
      hostPath:
        path: /data
        type: Directory
```

구조:

```text
Worker Node
/data
  │
  │ hostPath
  ▼
Pod
/mnt/data
```

Node:

```text
/data/hello.txt
```

Pod:

```text
/mnt/data/hello.txt
```

### 특징

- Pod가 삭제되어도 Node의 `/data` 데이터는 남는다.
- 특정 Node에 종속된다.
- Pod가 다른 Node에 재배치되면 기존 데이터를 바로 사용할 수 없다.
- Cluster 전체 영구 저장소 용도로는 적합하지 않다.
- DaemonSet 기반 로그 수집 등에서 많이 사용한다.

예:

```text
각 Worker Node
/var/log
    ↓ hostPath
로그 수집 Pod
    ↓
외부 로그 서버
```

# 20. 실습 중 주요 Troubleshooting

## 1) MariaDB Pod Pending

증상:

```text
Status: Pending
PodScheduled: False
```

Events:

```text
pod has unbound immediate PersistentVolumeClaims
```

원인:

```text
PVC는 생성되었지만 사용 가능한 PV가 없음
```

해결:

```yaml
primary:
  persistence:
    enabled: false
```

실습에서는 Persistence를 비활성화하여 Pod를 정상 실행하였다.

---

## 2) `helm upgrade` 실패

오류:

```text
"myapp" has no deployed releases
```

원인:

`myapp`을 Helm으로 설치한 Release가 아니라 `kubectl create -f myapp.yaml`로 직접 생성한 상태였기 때문이다.

정리:

```text
kubectl create/apply로 생성
→ kubectl로 관리

helm install로 생성
→ helm upgrade로 관리
```

해결:

```bash
kubectl delete -n db -f myapp.yaml
helm install -n db myapp .
```

---

## 3) Bitnami MariaDB Upgrade Password 오류

오류:

```text
PASSWORDS ERROR:
You must provide your current passwords when upgrading the release.
```

Bitnami MariaDB Chart는 기존 비밀번호를 유지하기 위해 현재 root password를 다시 요구하였다.

실습에서는 기존 Release를 제거하고 수정한 Chart로 다시 설치하였다.

---

## 4) `tree` 명령 없음

오류:

```text
Command 'tree' not found
```

해결:

```bash
sudo apt install tree
```

<a id="section-21"></a>

# 21. 오늘 실습 핵심 정리

```text
Helm
→ Kubernetes Package Manager

Chart
→ Kubernetes 리소스 템플릿 패키지

Release
→ Chart를 실제 설치한 배포 단위

values.yaml
→ 사용자가 변경하는 설정값

templates/
→ Deployment / Service 등의 YAML Template
```

배포 관리:

```text
helm install
→ 최초 설치

helm upgrade
→ values / Chart 변경 반영

helm rollback
→ 이전 Revision으로 복구

helm uninstall
→ Release 삭제
```

렌더링:

```text
helm template
→ 실제 설치하지 않고 최종 Kubernetes YAML 생성
```

설정 분리:

```text
helm show values
→ 기본 values 출력

-f custom-values.yaml
→ 사용자 설정 Override
```

StatefulSet:

```text
고유 Pod 이름
순차 생성/삭제
Stateful App에 적합
DB 등에 많이 사용
```

Volume:

```text
emptyDir
→ Pod 삭제 시 데이터 삭제

hostPath
→ Node 디렉터리를 Pod에 직접 매핑
→ Pod 삭제 후 Node 데이터는 남음
→ Node 종속

PVC/PV
→ Pod와 독립적인 영구 저장에 사용
```

# 22. 자주 사용한 명령어 모음

```bash
# Helm Repository
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm search repo bitnami
helm search repo bitnami | grep -i mariadb

# Helm Release
helm install -n db mydb bitnami/mariadb
helm list -n db
helm upgrade -n db myapp .
helm rollback -n db myapp 1
helm uninstall -n db myapp
helm history -n db myapp

# Chart 생성
helm create myapp
tree myapp

# Template 렌더링
helm template myapp .
helm template myapp . > myapp.yaml

# Chart 다운로드
helm fetch --untar bitnami/mariadb

# 기본 values 추출
helm show values bitnami/mariadb > mydb-values.yaml

# 사용자 values 적용
helm install -n db mydb2 \
  -f mydb-values.yaml \
  bitnami/mariadb

# Kubernetes 확인
kubectl get all -n db
kubectl get po -n db -w
kubectl get svc -n db
kubectl get pvc -n db
kubectl get pv
kubectl get sc

# 상세 상태
kubectl describe pod -n db <pod-name>

# StatefulSet Scale
kubectl scale statefulset -n db mydb-mariadb --replicas 2
kubectl scale statefulset -n db mydb-mariadb --replicas 0
```
