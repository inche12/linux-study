# 2026-10-07 Kubernetes NFS 공유 및 Worker 노드 실습

> KT Cloud 인프라 과정 실습 기록
> 환경: VMware Workstation, Ubuntu 기반 Kubernetes (`master1`, `w1`), NFS
> **기록 기준:** 대화와 터미널 화면에서 실제로 확인된 내용은 **확인**, 안내만 받고 실행 결과를 제시하지 않은 항목은 **예정/미확인**으로 구분한다.

## 1. 오늘의 실습 목표

- NFS(Network File System) 서버의 공유 디렉터리를 구성한다.
- Kubernetes Worker Node에서 NFS 서버의 export 목록을 확인한다.
- 기존 Worker VM을 복제하여 두 번째 Worker를 준비한다.
- 복제로 인한 IP/호스트명/Kubernetes 노드 식별 정보 중복을 해결한다.
- 기존 Blue/Green 배포 리소스를 정리하여 NFS Pod 실습 환경을 준비한다.

> **진행 범위:** NFS export 확인, 복제 VM의 동일 IP 확인, nginx Pod 생성 및 접속, 기존 리소스 조회가 화면으로 확인되었다. `w2` 클러스터 가입, NFS 클라이언트 마운트, PV/PVC를 통한 Pod 공유 테스트, green/blue 삭제 완료 여부는 아직 확인되지 않았다.

## 3. kubectx/kubens 설치 안내(실행 미확인)

강의자료에 적힌 명령의 URL과 인자 사이에 공백이 빠져 있었다. 아래와 같이 실행해야 한다.

```bash
sudo git clone https://github.com/ahmetb/kubectx /opt/kubectx
sudo ln -s /opt/kubectx/kubectx /usr/local/bin/kubectx
sudo ln -s /opt/kubectx/kubens /usr/local/bin/kubens
```

- `git clone`: 도구 저장소를 로컬 디렉터리로 복제한다.
- `ln -s`: 실행 스크립트에 심볼릭 링크를 만들어 명령어로 접근하게 한다.
- `kubectx`: Kubernetes context 간 전환에 사용한다.
- `kubens`: Kubernetes namespace 간 전환에 사용한다.
- **상태:** 명령어가 실습자료에 제시되었으며 실제 설치 성공 출력은 없음.

## 4. Ubuntu master1에 NFS 서버 설정

### 4.1 서버 패키지와 공유 디렉터리

강의자료의 흐름:

```bash
sudo apt-get update
sudo apt-get install -y nfs-kernel-server
sudo mkdir -m 1777 /share
sudo mkdir -m 1777 /share/nfs
sudo touch /share/hello.txt
```

- `nfs-kernel-server`: Ubuntu에서 NFS 서버 기능을 제공한다.
- `mkdir -m 1777`: 모든 사용자가 읽기/쓰기/접근 가능한 디렉터리를 만들고 sticky bit를 설정한다. 다른 사용자가 만든 파일의 삭제/이름 변경은 소유권 규칙에 따라 제한된다.
- `/share/nfs`: Pod 공유 실습에 사용할 하위 디렉터리.
- `touch`: 빈 테스트 파일을 만든다.
- **상태:** 강의자료에 나온 절차. 파일·디렉터리 생성 결과를 별도로 확인한 출력은 없음.

### 4.2 `/etc/exports` 설정

```bash
sudo vim /etc/exports
```

자료에 제시된 예:

```exports
/share/* *(rw,sync,no_root_squash,subtree_check)
```

이후 다른 자료에는 아래 설정이 제시됨:

```exports
/share/ *(rw,sync,no_root_squash)
```

실제 확인된 export 결과는 **`/share` 경로**였다. 따라서 문서의 `/share/*` 표현과 최종 서버 적용값은 동일하다고 단정하지 않는다. 실제 파일 내용 확인이 필요하다.

| 옵션 | 의미 |
|---|---|
| `*` | 모든 클라이언트에 공유 (실습용; 운영에서는 IP/CIDR 제한 권장) |
| `rw` | 읽기·쓰기 허용 |
| `sync` | 변경 내용을 안정적인 저장소에 반영하는 동기 처리 |
| `no_root_squash` | 클라이언트 root의 권한을 서버에서 익명 사용자로 매핑하지 않음 (보안 주의) |
| `subtree_check` | export가 파일시스템의 하위 디렉터리일 때 하위 경로 검사 |

**안전 참고:** 실습에서는 허용했지만 `*`와 `no_root_squash` 조합은 운영 환경에서 사용을 피한다. 또한 공유할 경로가 `/share` 전체인지 `/share/nfs` 하나인지 정확히 정해야 한다.

### 4.3 export 반영 및 확인 — 실제 확인

```bash
sudo exportfs -ra   # /etc/exports를 다시 읽고 export 재설정
sudo exportfs -v    # 현재 공유 경로와 적용 옵션 상세 조회
```

실제 출력:

```text
/share          <world>(sync,wdelay,hide,sec=sys,rw,secure,no_root_squash,no_all_squash)
```

- `/share`: 내보내진 서버 디렉터리.
- `<world>`: 클라이언트 접근 대상을 전체로 설정.
- `wdelay`: 쓰기 요청 묶음 처리 지연 옵션.
- `sec=sys`: 일반적인 AUTH_SYS 인증 방식.
- `secure`: 일반적으로 1024 미만 클라이언트 소스 포트 요구.
- `no_all_squash`: 일반 사용자들을 모두 익명 사용자로 매핑하지 않음.

추가 확인 명령:

```bash
cat /etc/exports
ls -ld /share /share/nfs
sudo systemctl status nfs-kernel-server
```

**상태:** `exportfs -v` 결과 확인. 서비스 상태 출력은 미제공.

## 5. NFS 클라이언트 구성 (Worker)

### Ubuntu Worker

```bash
sudo apt-get update
sudo apt-get install -y nfs-common
showmount -e master1
```

- `nfs-common`: Ubuntu에서 NFS 클라이언트 명령 및 마운트 기능을 제공.
- `showmount -e master1`: 서버에서 내보낸 NFS export 목록 조회 (직접 마운트 성공까지 증명하는 것은 아님).

### RHEL/Rocky 계열의 참고 명령

```bash
# NFS 서버
sudo yum install -y nfs-utils
sudo systemctl enable --now nfs-server
sudo systemctl status nfs-server

# NFS 클라이언트
sudo yum install -y nfs-utils
showmount -e master1
```

강의자료의 예상 출력:

```text
Export list for master1:
/share *
```

> 이 출력은 강의자료 예시이며, 실제 `w1`/`w2`에서 `showmount` 실행한 결과로 확인된 것은 아니다.

선택적인 실제 마운트 테스트 (실행 미확인):

```bash
sudo mkdir -p /mnt/nfs-test
sudo mount -t nfs master1:/share /mnt/nfs-test
mount | grep nfs
ls -la /mnt/nfs-test
sudo umount /mnt/nfs-test
```

마운트 오류 시 서버 주소 해석, 네트워크 연결, NFS 서버 포트(주로 TCP 2049), export 허용 주소, 서버·클라이언트 패키지를 확인한다.

## 6. VMware Worker 복제 및 네트워크 중복 문제

### 6.1 복제 배경

NFS를 서로 다른 Worker의 Pod에서 공유하는 상황을 재현하기 위해 `w1`을 복제하여 `w2`를 추가하려 했다.

VMware Workstation에서 일반적인 복제 절차:

1. 원본 `w1` 종료.
2. **Manage → Clone → Current state → Create a full clone**.
3. 복제 VM 이름을 `w2`로 설정.
4. 복제 VM 부팅 뒤 네트워크와 노드 식별 정보를 변경.

### 6.2 실제로 관찰된 IP 충돌

두 콘솔 모두 `student@w1`로 표시됐고, `ip -br addr`에 다음 주소가 나타남:

```text
ens160 UP 192.168.120.151/24
```

원인: VM Clone 시 기존 IP 설정과 hostname 등이 복사됨. 원본과 복제본을 동시에 켜면 주소 충돌 및 Xshell 접속 혼선이 생길 수 있음.

선택한 목표 주소:

| 노드 | IP |
|---|---|
| `w1` | `192.168.120.151/24` 유지 |
| `w2` | `192.168.120.161/24`로 변경 예정 |

`.152`, `.153`은 별도 프로젝트 VM에서 사용 중이라 제외했다. `.161`은 DHCP 풀 및 다른 장비와 중복되지 않는지 확인해야 한다.

### 6.3 w2의 hostname / IP 변경 가이드 (적용 미확인)

**반드시 복제본 `w2`의 VMware 콘솔에서만 실행한다. 원본 `w1`의 설정을 수정하면 안 된다.**

```bash
sudo hostnamectl set-hostname w2
ls /etc/netplan/
sudo cat /etc/netplan/*.yaml
```

현재 정적 IP 설정이 `192.168.120.151/24`라면 해당 YAML의 **기존 주소만** `192.168.120.161/24`로 수정한다. 게이트웨이/DNS 등 나머지는 기존 구성에 맞춰 유지한다. DHCP 사용 중이라면 정적 IP 변경 방식부터 다시 결정해야 한다.

```bash
sudo netplan try        # VMware 콘솔에서 변경 검증 및 승인
ip -br addr
hostname
```

Xshell 연결 대상은 `w1: 192.168.120.151`, `w2: 192.168.120.161`로 구분한다. SSH 호스트 키 경고가 발생할 수 있으므로 대상 VM을 확인한 뒤 해당 IP의 기존 known_hosts 항목을 검토한다.

### 6.4 Kubernetes 노드 복제 시 추가 작업

**중요:** IP와 hostname만 변경한 복제 Worker는 독립적인 Kubernetes 노드로 안전하게 사용할 수 없다. 복제된 kubelet 인증서/노드 등록 상태, machine-id, CNI 네트워크 상태를 점검하고 새 노드로 초기화·재가입해야 한다.

아래는 *전체 수행 기록이 아니라* 점검·재가입 흐름이다.

```bash
# w2에서 kubeadm 클러스터 상태 초기화(복제본에서만)
sudo kubeadm reset -f

# master1에서 새 가입 명령 출력
sudo kubeadm token create --print-join-command

# w2에서 출력된 실제 kubeadm join 명령 실행
# sudo kubeadm join <MASTER_IP>:6443 --token ... --discovery-token-ca-cert-hash sha256:...

# master1에서 확인
kubectl get nodes -o wide
```

`kubeadm reset`만으로 모든 복제 식별정보가 정리되지는 않는다. `w1`과 인증서/`/etc/machine-id` 및 CNI 설정 중복을 확인하고, 실제 구성에 맞는 정리 절차를 거친 뒤 가입한다. 기존 원본 노드의 kubelet 인증이나 네트워크 구성을 삭제하지 않도록 주의한다.

**상태:** `w2` Join 성공 화면 없음. 클러스터에 실제 등록됐다고 기록하지 않음.

## 7. Kubernetes Pod 실습 및 이전 리소스 정리

### 7.1 nginx Pod 직접 생성 — 실제 확인

```bash
kubectl run nginx --image=nginx
kubectl exec -it nginx -- /bin/bash
exit
```

- `kubectl run nginx --image=nginx`: 단일 nginx Pod 생성.
- `kubectl exec -it nginx -- /bin/bash`: nginx 컨테이너 내부 셸 접속.
- `exit`: 컨테이너 셸 종료 (Pod 삭제 아님).

터미널에 `pod/nginx created`, `root@nginx:/#`, 이후 `exit`가 표시됐고 Pod 조회 화면에도 `nginx 1/1 Running`으로 나타났다.

### 7.2 기존 Green Pod 확인 — 실제 확인

`kubectl get po,cm` 반복 조회 화면에 이전 `green` Pod 세 개가 나타남:

```text
pod/green-6f7cbb6c86-2gr6z   1/1 Running  AGE 16d
pod/green-6f7cbb6c86-m67w7   1/1 Running  AGE 16d
pod/green-6f7cbb6c86-nzjxm   1/1 Running  AGE 16d
pod/nginx                     1/1 Running
```

실행 전 관리 객체 확인:

```bash
kubectl get deployments
kubectl get replicasets
```

이전에 `green` Deployment가 관리하던 Pod라면 Pod만 삭제해도 재생성된다. **다른 실습에서 사용 중이지 않은 것을 확인한 뒤** 다음 명령으로 Deployment를 제거한다.

```bash
kubectl delete deployment green
kubectl get pods
```

**상태:** 삭제를 안내했지만 삭제 성공 출력은 제시되지 않음.

### 7.3 Service 조회 — 실제 확인

```bash
kubectl get svc
```

실제 출력:

```text
NAME         TYPE        CLUSTER-IP       EXTERNAL-IP   PORT(S)        AGE
blue         NodePort    10.110.133.202   <none>        80:31962/TCP   17d
kubernetes   ClusterIP   10.96.0.1        <none>        443/TCP        20d
```

| Service | 판단 |
|---|---|
| `blue` | 기존 Blue/Green 연습용 Service로, 사용하지 않는다면 삭제 가능 |
| `kubernetes` | Kubernetes API 접근용 기본 Service. **삭제하지 않음** |

```bash
kubectl delete svc blue
kubectl get svc
```

`kubectl delete deployment green`과 `kubectl delete svc blue`는 별개이며, Service 삭제만으로 Pod가 삭제되지는 않는다.

**상태:** Service 조회는 확인, `blue` 삭제 완료는 미확인.

## 8. 트러블슈팅 기록

| 현상 | 원인/해석 | 대응 | 확인 상태 |

| 복제한 두 VM의 IP가 모두 `.151` | Clone이 원본의 네트워크 설정 복사 | `w2`에 `.161` 할당, hostname 변경, DHCP/중복 검사 | 중복은 확인, 해결 완료 미확인 |

## 10. 핵심 개념 정리

- **NFS:** 서버의 파일시스템 경로를 네트워크로 다른 머신에 공유하는 프로토콜.
- **NFS Export:** 서버의 `/etc/exports`에 명시한 공유 디렉터리 및 접근 조건.
- **`showmount -e`:** NFS export 목록 조회. 실제 읽기/쓰기 성공을 뜻하지는 않음.
- **Kubernetes Pod:** 컨테이너를 실행하는 최소 배포 단위.
- **Deployment vs Pod:** Deployment는 Pod 개수 및 상태를 유지하므로 관리 Pod를 직접 삭제하면 다시 생성될 수 있음.
- **Service:** Pod의 변경되는 IP와 분리된 네트워크 진입점을 제공. Deployment 삭제 시 자동 삭제되지 않음.
- **PV/PVC:** Pod와 독립적인 스토리지 리소스 및 사용 요청을 표현. NFS 스토리지를 여러 Pod에서 사용하는 실습에 활용 가능.
