## 2. Kubernetes kube-proxy 확인

### 2.1 노드와 kube-proxy Pod 확인

```bash
kubectl get nodes -o wide
kubectl get pods -n kube-system | grep kube-proxy
```

- `master1`은 `192.168.120.150`, `w1`은 `192.168.120.151`로 확인했다.
- 당시 kube-proxy Pod 명칭은 `kube-proxy-gl4tv`, `kube-proxy-nlls4`였다. Pod가 재생성되면 뒤쪽 접미사는 달라진다.

```bash
# 현재 표시된 kube-proxy Pod 이름으로 바꿔 실행
kubectl logs -n kube-system kube-proxy-gl4tv | more
```

- 실제 로그에서 `Using iptables proxy`, `Using iptables Proxier`가 확인됐다.
- `nodePortAddresses is unset; NodePort connections will be accepted on all local IPs` 경고가 나타났다. NodePort가 모든 로컬 IP에서 수신될 수 있다는 구성 경고이며, 그 자체로 kube-proxy 기동 실패를 의미하지는 않는다.

### 2.2 kube-proxy ConfigMap 확인

```bash
kubectl get configmap kube-proxy -n kube-system \
  -o jsonpath='{.data.config\.conf}' | grep -E 'mode:|strictARP:'
```

당일 **변경 전** 출력:

```text
strictARP: false
mode: ""
```

- `mode: ""`은 기본 프록시 모드 선택 상태를 의미하며, 실제 적용 모드는 로그를 통해 `iptables`로 확인했다.
- 강의 예제에는 `mode: "ipvs"`, `ipvs.strictARP: true`로 변경하고 kube-proxy Pod를 재생성하는 내용이 등장했다.
- **주의:** 대화에서 실제 ConfigMap 수정 및 IPVS 전환 완료 로그는 확인하지 못했다. 당일 기록에는 **iptables 확인 완료 / IPVS 전환은 완료 여부 미확인**으로 남긴다. MetalLB L2 모드는 IPVS 전환이 반드시 필요한 것은 아니다.
- kube-proxy 설정을 변경한 경우에는 DaemonSet이 관리하는 kube-proxy Pod를 재생성하여 새 설정을 적용할 수 있으나, 기존 서비스의 순간적인 영향과 동작 모드 호환성을 확인해야 한다.

## 3. MetalLB 설치·설정 및 LoadBalancer 확인

### 3.1 MetalLB 구성요소 상태

강의에서 참조한 공식 문서 및 매니페스트:

- 설치 문서: https://metallb.universe.tf/installation/
- 실습 매니페스트: https://raw.githubusercontent.com/metallb/metallb/v0.15.2/config/manifests/metallb-native.yaml

```bash
# 강의에서 사용한 설치 방식 (실행 전에 버전·클러스터 호환성 확인)
kubectl apply -f \
  https://raw.githubusercontent.com/metallb/metallb/v0.15.2/config/manifests/metallb-native.yaml

# 실제 설치 여부 확인
kubectl get pods -n metallb-system -o wide
```

당일 확인된 Pod 예시:

```text
controller-6dd55858b4-5t7tl   1/1 Running   w1
speaker-7w7p8                 1/1 Running   w1
speaker-fws46                 1/1 Running   master1
```

- `controller`: LoadBalancer Service에 IP 주소를 배정하는 제어 역할.
- `speaker`: L2 모드에서 서비스 외부 IP의 도달 경로를 ARP 등으로 광고.
- 설치 직후 `ContainerCreating`이었으나 약 89초 후 3개 Pod 모두 `Running`으로 전환됐다.

### 3.2 네트워크 인터페이스 확인

```bash
ip -br addr
```

- `master1`: `ens160 UP 192.168.120.150/24`
- `w1`: `ens160 UP 192.168.120.151/24`
- `docker0`, `cali*`, `vxlan.calico` 등도 보였지만 MetalLB L2 광고용 물리/VM NIC로는 `ens160`을 설정했다.

### 3.3 metallb-config.yaml 작성

```bash
vi metallb-config.yaml
# vi에서 i → 내용 입력 → Esc → :wq
```

실제로 적용한 설정:

```yaml
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: first-pool
  namespace: metallb-system
spec:
  addresses:
    - 192.168.120.200-192.168.120.210
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: example
  namespace: metallb-system
spec:
  ipAddressPools:
    - first-pool
  interfaces:
    - ens160
```

- `IPAddressPool`: LoadBalancer Service에 배정할 IP 범위를 정의한다.
- `L2Advertisement`: 특정 풀의 IP를 L2 방식으로 네트워크에 광고한다.
- `interfaces: ens160`: 해당 NIC에서 광고하도록 설정한다. 두 노드에서 NIC 이름이 일치하는 것도 확인했다.
- **운영 주의:** `.200-.210`은 당일 실제로 사용한 값이지만 DHCP와 충돌하지 않는다는 검증 증거는 없다.

### 3.4 적용 및 조회

```bash
kubectl apply -f metallb-config.yaml
kubectl get -f metallb-config.yaml
```

실제 출력 핵심:

```text
ipaddresspool.metallb.io/first-pool created
l2advertisement.metallb.io/example created

ipaddresspool.metallb.io/first-pool ... ["192.168.120.200-192.168.120.210"]
l2advertisement.metallb.io/example ... ["first-pool"] ... ["ens160"]
```

두 리소스의 생성과 설정 확인 완료.

## 4. Istio Bookinfo 외부 접속

### 4.1 IngressGateway LoadBalancer 확인

```bash
kubectl get ns istio-system
kubectl get svc -n istio-system
```

당일 확인 결과:

```text
istio-system   Active
istio-ingressgateway  LoadBalancer  10.104.71.176  192.168.120.200
```

- `ClusterIP=10.104.71.176`: 클러스터 내부 서비스 주소.
- `EXTERNAL-IP=192.168.120.200`: MetalLB가 할당한 외부 접속용 IP.
- MetalLB가 IP를 할당하는 대상은 **Bookinfo의 productpage Service가 아니라 Istio IngressGateway Service**다.

### 4.2 Windows 브라우저에서 접속

```text
http://192.168.120.200/productpage
```

**실제 결과:** Istio Bookinfo 샘플의 *The Comedy of Errors* 화면, Book Details 및 Book Reviews 영역이 브라우저에 표시됨. 주소 할당뿐 아니라 실질적인 HTTP 웹 접근까지 성공했다.

### 4.3 Bookinfo Pod/Service 확인

```bash
kubectl get pods,svc -A | grep -E 'productpage|details|reviews|ratings'
kubectl get gateway,virtualservice -A
```

당일 확인:

| 항목 | 확인 내용 |
|---|---|
| Namespace | `bookinfo` |
| Pods | `details-v1`, `productpage-v1`, `ratings-v1`, `reviews-v1/v2/v3` 모두 `2/2 Running` |
| details | `ClusterIP:9080` |
| productpage | `NodePort 9080:31182` |
| ratings | `ClusterIP:9080` |
| reviews | `ClusterIP:9080` |
| Gateway | `bookinfo-gateway` |
| VirtualServices | `bookinfo`, `reviews` |

- Bookinfo Pod의 `2/2`는 애플리케이션 컨테이너와 Istio Envoy 사이드카의 조합으로 해석할 수 있으며 실제 컨테이너 이름은 `kubectl describe pod`로 검증할 수 있다.
- `reviews` VirtualService는 별도로 존재했다. 하지만 실제 버전별 라우팅 비율은 YAML을 조회하지 않았으므로 확인되지 않았다.

**요청 흐름(개념):**

```text
Windows Chrome
    │ GET /productpage (192.168.120.200)
    ▼
MetalLB L2 광고 (접속 가능한 외부 IP)
    │
    ▼
Istio IngressGateway (LoadBalancer)
    │
    ▼
Istio Gateway + VirtualService
    │
    ▼
productpage → details / reviews → ratings (라우팅 설정에 따라)
```

## 5. Worker Node kubectl 연결 이슈

`w1`에서 실행:

```bash
kubectl get nodes -o wide
```

오류:

```text
Get "http://localhost:8080/api?timeout=32s":
connect: connection refused
The connection to the server localhost:8080 was refused
```

- **진단:** `w1`의 현재 사용자에 유효한 kubeconfig/API Server 연결 정보가 없는 것으로 추정. 이 오류만으로 `w1`의 kubelet 또는 클러스터 전체 장애라고 단정할 수 없다.
- `master1`에서 클러스터 관리 명령어가 정상 동작했고 `w1`의 MetalLB Speaker도 Running이었다.
- 현재 결정: **클러스터 관리 작업은 master1에서 계속 수행하고, w1에서 kubectl을 직접 써야 할 때 별도로 설정한다.**

나중에 `w1`에서 먼저 확인할 명령어:

```bash
echo "$KUBECONFIG"
ls -la ~/.kube/
kubectl config view --minify
```

이는 **상태 확인 명령어**이며 kubeconfig를 자동 구성하지 않는다. 설정이 필요하면 최소 권한 사용자용 kubeconfig를 별도로 준비하고 관리자 자격 증명(`admin.conf`)을 무분별하게 복사하지 않도록 한다.

## 6. Prometheus와 Grafana 접근 및 기초 모니터링

### 6.1 Prometheus ClusterIP → NodePort 변경

```bash
kubectl get svc prometheus -n istio-system
kubectl patch svc prometheus -n istio-system \
  -p '{"spec":{"type":"NodePort"}}'
kubectl get svc prometheus -n istio-system
```

실제 결과:

```text
prometheus NodePort 10.107.76.114 <none> 9090:30835/TCP
```

접속:

```text
http://192.168.120.150:30835/query
```

- 기존 서비스 포트 `9090`은 유지하면서 노드 외부 포트 `30835`가 배정됐다.
- Windows에서 Prometheus 웹 UI 접근 성공.

### 6.2 PromQL up 조회

```promql
up
```

- 실제 Prometheus 웹 UI에서 실행했고 `master1` cAdvisor, `istiod`, `reviews-v2`, `istio-ingressgateway`, `jaeger`, `CoreDNS` 등 대상 시계열이 표시됐다.
- `up=1`은 마지막 메트릭 수집 성공, `up=0`은 마지막 수집 실패를 의미한다. 스크린샷에는 대상 목록이 확인되지만 **모든 대상이 1인지 전체 값은 검증하지 않았다.**

자주 쓰는 확인 쿼리:

```promql
# job별 타깃 수
count by (job) (up)

# Istio 요청량(해당 메트릭이 수집될 경우)
sum(rate(istio_requests_total[5m]))

# 코드별 Istio 요청량
sum by (response_code) (rate(istio_requests_total[5m]))
```

> **복습 시 주의:** 위 예시에서 서비스 요청량은 환경의 Istio 메트릭 수집 여부에 따라 결과가 다르다. HTTP 클라이언트·서버 측 중복 집계를 피하려면 `reporter` 라벨을 고려한다.

### 6.3 Grafana ClusterIP → NodePort 변경

```bash
kubectl get svc grafana -n istio-system
kubectl patch svc grafana -n istio-system \
  -p '{"spec":{"type":"NodePort"}}'
kubectl get svc grafana -n istio-system
```

실제 결과:

```text
grafana NodePort 10.100.107.121 <none> 3000:32212/TCP
```

접속:

```text
http://192.168.120.150:32212
```

- Windows Chrome에서 Grafana Welcome 대시보드 확인.
- Grafana와 Prometheus 연결 여부는 별도의 Data source 설정에서 검증 필요.
- 필요 시 내부 접근용 URL 예: `http://prometheus.istio-system.svc.cluster.local:9090`.

### 6.4 NodePort 노출 주의

Prometheus, Grafana UI는 운영 환경에서 인증·접근제어를 고려해야 한다. 실습 후 NodePort 공개가 불필요하다면 다음과 같이 되돌릴 수 있다 (**당일 되돌린 기록은 없음**).

```bash
kubectl patch svc prometheus -n istio-system -p '{"spec":{"type":"ClusterIP"}}'
kubectl patch svc grafana -n istio-system -p '{"spec":{"type":"ClusterIP"}}'
```

## 7. Grafana 대시보드·알림 및 Kubernetes 모니터링 이론

### 7.1 Grafana Labs 대시보드 Import

강의 실습 경로:

```text
Grafana → Dashboards → New → Import
→ Grafana Labs Dashboard ID 입력 → Load
→ Data source 선택 → Import
```

- 공유 대시보드 예: **Kubernetes Horizontal Pod Autoscaler (HPA)**
- Dashboard ID: **22128**
- 링크: https://grafana.com/grafana/dashboards/22128-horizontal-pod-autoscaler-hpa/
- 당일 화면에서 Grafana Import 입력 페이지까지 확인했다. **대시보드를 실제로 Import 완료했거나 그래프가 표시됐다는 증거는 없다.**
- HPA 관련 그래프가 비어 있으면 HPA 리소스 존재 여부, Prometheus 데이터 소스 및 필요한 메트릭 수집 상태를 확인한다.

```bash
kubectl get hpa -A
```

### 7.2 Grafana Slack Alerting 개념

당일 화면: `Alerting → Contact points`에 기본 `grafana-default-email` 연락처가 표시됨.

학습한 예정 절차:

1. Slack에서 Incoming Webhook 생성(비밀 URL은 외부 공유 금지).
2. Grafana `Alerting → Contact points → Create contact point`에서 Slack 선택.
3. Webhook 연동 및 테스트 알림 전송.
4. `Alert rules`를 생성하고 Contact point 또는 Notification policy에 연결.

**상태:** **Slack Contact point 생성/실제 발송은 확인되지 않음(개념 학습 및 설정 화면 확인 단계).**

- **Prometheus Alertmanager 방식:** Prometheus가 알림 규칙 평가 → Alertmanager가 그룹화/전달.
- **Grafana Alerting 방식:** Grafana가 데이터 소스를 조회해 규칙 평가 → Grafana Contact point로 Slack/Email 등 전송.

### 7.3 Kubernetes 모니터링 대상

강의 자료에 등장한 감시 대상:

- Node Down, `NotReady`
- Kubernetes 주요 구성요소 비정상
- 리소스 요청량 과다로 Pod 스케줄링 실패
- CPU/메모리 사용률 과다
- `OOMKilled`, 컨테이너 반복 재시작
- PV/마운트 파일시스템 용량 부족

### 7.4 Node Exporter 주요 메트릭

| 메트릭 | 의미 |
|---|---|
| `node_cpu_seconds_total` | CPU 모드별 누적 시간 |
| `node_memory_MemAvailable_bytes` | 사용 가능한 메모리 |
| `node_memory_MemTotal_bytes` | 총 메모리 |
| `node_filesystem_size_bytes` | 파일시스템 총 크기 |
| `node_filesystem_free_bytes` | 파일시스템 남은 용량 |
| `node_network_receive_bytes_total` | 누적 수신 바이트 |
| `node_network_transmit_bytes_total` | 누적 송신 바이트 |
| `node_load1`, `node_load5`, `node_load15` | 시스템 평균 부하 |
| `node_disk_io_time_seconds_total` | 누적 디스크 I/O 시간 |
| `node_temperature_celsius` | CPU 온도(지원 시) |
| `node_time_seconds` | 현재 시스템 시각 |
| `node_boot_time_seconds` | 부팅 시각 |

실습에 응용할 수 있는 쿼리(데이터 존재 시):

```promql
# CPU 사용률 (%)
100 * (1 - avg by(instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])))

# 메모리 사용률 (%)
100 * (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)

# 루트 파일시스템 사용률 (%)
100 * (1 - node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"})

# ens160 초당 수신량 (bytes/sec)
rate(node_network_receive_bytes_total{device="ens160"}[5m])
```

강의 자료의 Node Exporter 수집 실패 감지 예제:

```promql
up{job="kubernetes-service-endpoints",app_kubernetes_io_name="prometheus-node-exporter"} == 0
or
absent(up{job="kubernetes-service-endpoints",app_kubernetes_io_name="prometheus-node-exporter"})
```

- `up == 0`: 발견된 타깃에 대한 스크레이프 실패.
- `absent(...)`: 선택 조건에 맞는 시계열 자체가 없음.
- 강의 환경의 label을 사용한 예제이므로 **내 클러스터에 맞게 job·label을 확인해야 한다.** 전체 노드 중 일부 타깃만 사라진 경우를 전부 감지하는 식은 아니다.

공식/참고:

- https://promlabs.com/promql-cheat-sheet/
- https://prometheus.io/docs/introduction/media/
- Prometheus UI의 `Status → Target health`에서 수집 대상·상태 확인.

## 8. IaC / Terraform 개념 정리

### 8.1 IaC란?

Infrastructure as Code: 서버, VPC, Subnet, Security Group 등의 인프라를 코드로 선언하고 생성·변경·삭제하는 방식.

| 비교 | 절차 지향 | 선언형 |
|---|---|---|
| 중심 질문 | 어떤 순서로 작업할까? | 최종 상태는 무엇이어야 하나? |
| 강의 자료의 대표 도구 | Chef, Ansible | Terraform, CloudFormation 등 |
| 특성 | 작업 절차 중심 | 목표 상태와 차이를 반영 |

**보충:** Ansible에도 선언형/멱등성 모듈이 있으며 Terraform은 `count`, `for_each`, 조건식을 지원한다. 위 표는 강의의 대표적 비교를 단순화한 것이다.

### 8.2 Terraform vs CloudFormation

| 항목 | Terraform | AWS CloudFormation |
|---|---|---|
| 플랫폼 | AWS, Azure, GCP, OpenStack 등 | AWS 중심 |
| 형식 | HCL `.tf` | YAML / JSON |
| 실행 | `init`, `plan`, `apply` | Stack / Change Set |
| 상태 | `terraform.tfstate` | CloudFormation에서 Stack 상태 관리 |
| 재사용 | Module | Nested Stack 등 |

### 8.3 OpenTofu 배경

- 2023년 HashiCorp가 Terraform의 새 버전 라이선스를 MPL에서 BSL로 전환.
- 이에 대응하여 Terraform의 기존 오픈소스 코드에서 파생된 **OpenTofu**가 등장.
- IBM의 HashiCorp 인수 완료(2025)는 OpenTofu 출범 이후의 일.
- Terraform 명령 `terraform`, OpenTofu 명령 `tofu`. HCL 사용법은 유사하나 버전별 호환성 확인 필요.

### 8.4 Registry: Provider vs Module

- Registry: https://registry.terraform.io/
- **Provider:** 외부 플랫폼 API 및 리소스 유형 구현 (`hashicorp/local`, `hashicorp/aws` 등).
- **Module:** 여러 Terraform 리소스를 재사용 가능한 구성 단위로 묶은 코드.
- 강의에서 AWS S3 Bucket, VPC, EKS, Security Group 모듈을 확인함.
- Module 사용 시에도 입력 변수, 네트워크, 비용, 버전 호환성을 검토해야 한다.

## 9. Windows Terraform 개발 환경 구성

### 9.1 Terraform 설치

1. 공식 설치 페이지: https://developer.hashicorp.com/terraform/install
2. Windows → **AMD64** ZIP 다운로드 (`v1.16.5`).
3. 압축 해제 후 `terraform.exe`를 `C:\Users\user\bin`에 배치.
4. Windows 환경 변수의 `Path`에 `C:\Users\user\bin` 등록.
5. PowerShell을 새로 열어 확인:

```powershell
terraform version
where.exe terraform
```

실제 성공 결과:

```text
Terraform v1.16.5
on windows_amd64
```

**중간 오류:** `terraform: CommandNotFoundException`. 처음에는 압축을 푼 하위 폴더에 실행 파일이 있어 PATH 검색 범위와 일치하지 않았다. 실행 파일을 `bin`에 옮겨 해결.

### 9.2 Git Bash 설치·alias 설정

- Git for Windows x64 Setup 설치: https://git-scm.com/install/windows
- 기본 설치 경로: `C:\Program Files\Git`
- Git Bash에서 사용자 프로필 편집:

```bash
vi ~/.bash_profile
```

적용한 내용:

```bash
export PATH="$HOME/bin:$PATH"
alias tf='terraform'
```

저장(`Esc → :wq`) 후 **현재 셸에서 다시 읽어야 함**:

```bash
source ~/.bash_profile
# 또는 . ~/.bash_profile

tf version
```

실제 성공 결과:

```text
Terraform v1.16.5
on windows_amd64
```

**트러블슈팅:**

- 잘못된 경로 `~./bash_profile`로 저장 시 Vim `E212: Can't open file for writing` 발생 → `~/.bash_profile`로 수정.
- alias를 작성하고도 `tf: command not found` 발생 → `source ~/.bash_profile`로 현재 셸에 반영.
- PowerShell의 `terraform`과 Git Bash의 `tf`는 구분: `tf`는 Bash alias로 정의한 것.

### 9.3 VS Code 설치·개발환경

- VS Code에서 `C:\terraform` 폴더 열기.
- `Ctrl + J`: 아래 패널 보이기/숨기기.
- 터미널 오른쪽 `+` 옆 메뉴에서 **Git Bash** 선택.
- `.tf` 파일 편집용 **HashiCorp HCL** 확장 검색·설치 진행.
- **YAML (Red Hat)**, **Kubernetes Support (ipedrazas)** 설치 완료 화면 확인.
- 참고: Terraform `.tf`는 HCL, Kubernetes 매니페스트는 YAML.

**중간 오류:** PowerShell에서 `code .` → `CommandNotFoundException`. VS Code를 직접 열어 `C:\terraform` 폴더를 선택해 작업 진행. 필요 시 VS Code `bin`을 PATH에 추가하여 `code .` 사용 가능.

### 9.4 교안 GitHub 저장소 Clone

VS Code의 Git Bash에서 `/c/terraform` 위치에서 실행:

```bash
git clone https://github.com/terraform101/terraform-basic
git clone https://github.com/terraform101/terraform-module-repo.git
```

두 저장소 모두 Clone 완료가 화면에 확인됨.

```text
C:\terraform\
├── 1D\                    # 실제 local_file 실습 디렉터리
├── terraform-basic\       # 교안 기본 실습 파일
└── terraform-module-repo\ # 교안 모듈 실습 파일
```

**주의:** `terraform-basic`에는 `3-1.tf`, `3-2.tf` 등 수많은 예제 파일이 있으므로 **예제 전체를 같은 루트에서 곧바로 apply하지 말고**, 독립 작업 폴더에서 필요한 예제만 실습한다.

## 10. Terraform Local Provider 실습

### 10.1 실습 목표 및 코드

실습 위치: `C:\terraform\1D` (Git Bash: `/c/terraform/1D`)

`main.tf`:

```hcl
resource "local_file" "abc" {
  content  = "abc!"
  filename = "${path.module}/abc.txt"
}
```

- `resource "local_file" "abc"`: local Provider의 파일 리소스를 `abc`라는 Terraform 논리 이름으로 선언.
- `content`: 기록할 문자열.
- `filename`: 생성 경로. `${path.module}`은 현재 모듈 디렉터리.

### 10.2 Init

```bash
cd /c/terraform/1D
tf init
```

실제 출력:

```text
Finding latest version of hashicorp/local...
Installing hashicorp/local v2.9.1...
Installed hashicorp/local v2.9.1 (signed by HashiCorp)
Terraform has created a lock file .terraform.lock.hcl
Terraform has been successfully initialized!
```

- `tf init`: 작업 디렉터리·Provider·Backend 초기화.
- `.terraform/`: Provider 실행 파일 등이 설치되는 폴더.
- `.terraform.lock.hcl`: 선택된 Provider 의존성 버전과 해시를 기록한 잠금 파일.

**트러블슈팅:** 처음 `tf init`에서는 Provider 설치 로그가 없었음. VS Code `main.tf` 탭의 미저장 표시(흰 점)를 확인하고 `Ctrl + S`로 저장한 뒤 `tf init`을 다시 실행하여 v2.9.1 설치 성공.

### 10.3 Plan

```bash
tf plan
```

실제 계획:

```text
+ resource "local_file" "abc" {
    + content  = "abc!"
    + filename = "./abc.txt"
  }
Plan: 1 to add, 0 to change, 0 to destroy.
```

- `+ create`: 새로 만들 리소스.
- `(known after apply)`: 실제 생성 후에 값이 확정되는 속성(파일 해시 등).
- `plan`은 **변경 계획만 보여주고 파일을 생성하지 않는다.**
- `-out` 없이 실행한 계획은 후속 `apply`가 반드시 같은 계획으로 실행된다는 보장은 없다.

### 10.4 Apply & 검증

```bash
tf apply
# 승인 질문에 yes 입력
cat abc.txt
```

실제 출력:

```text
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.
abc!
```

- Local Provider가 `abc.txt`를 생성함.
- `cat`으로 파일에 실제로 `abc!`가 기록됐음을 확인.

### 10.5 Destroy

```bash
tf destroy
# 승인 질문에 yes 입력
```

실제 결과:

```text
Plan: 0 to add, 0 to change, 1 to destroy.
Destroy complete! Resources: 1 destroyed.
```

- **`destroy`는 `.tf` 코드 파일을 삭제하는 명령이 아님.** 해당 상태 파일(State)이 관리하는 실제 리소스를 제거한다.
- 이번에는 `local_file.abc`가 삭제되어 `abc.txt`가 제거됨.
- `main.tf`, `.terraform/`, `.terraform.lock.hcl` 등은 남아 재실습이 가능함.
- AWS 리소스 등으로 확장할 때는 `destroy`가 인프라와 데이터를 삭제할 수 있으므로 계획과 영향 범위를 반드시 확인.

### 10.6 State 개념

- Terraform은 `terraform.tfstate`를 통해 관리 리소스의 식별자·속성과 현재 관리 상태를 추적한다.
- `plan`은 구성 코드와 State 및 실제 상태를 비교해 작업을 도출한다.
- State 파일에 민감 정보가 포함될 수 있으므로 GitHub에 공개하지 않는다.
