아래는 기존 ~/.kube 전체 삭제를 제외한 재사용 정리본이다.

```bash
#!/bin/bash
set -e
mkdir -p "$HOME/.kube"
sudo cp -i /etc/kubernetes/admin.conf "$HOME/.kube/config"
sudo chown "$(id -u):$(id -g)" "$HOME/.kube/config"
chmod 600 "$HOME/.kube/config"
```

student에서 ksetup 후 kubectl get nodes 성공. 스크립트 전체를 sudo로 실행하지 않는다.

파일 작성 시 $HOME, $(...) 앞의 역슬래시는 제거한다. heredoc 생성 단계의 이스케이프와 최종 스크립트 문법을 혼동하지 않는다.

root에서 student로: sudo -i로 들어왔다면 exit, 새 로그인 셸로 전환하려면 su - student.
/ etc 경로를 명령처럼 입력하면 Is a directory가 나온다. 디렉터리는 cd로 이동하거나 ls로 조회한다.

## 2. Xshell 연결 끊김 점검

유휴 상태에서 SSH만 끊기는 증상. 연결 유지 메시지 30~60초 설정을 안내했으나 최종 해결 확인은 없다.
자동 재접속 간격과 Keep Alive 전송 간격은 서로 다르다.

```bash
echo "$TMOUT"
sshd -T | grep -Ei 'clientaliveinterval|clientalivecountmax|channeltimeout|unusedconnectiontimeout'
```

TMOUT 빈 값. clientaliveinterval 0, clientalivecountmax 3, unusedconnectiontimeout none, channeltimeout none.
조회한 기본 설정에서는 직접적인 유휴 제한이 보이지 않았다. Match 조건, 네트워크 장비, 절전 등은 추가 확인 대상이다.

```bash

source <(kubeadm completion bash)
#source <(helm completion bash)
```

## 4. Pod 생성과 세 가지 접속 경로

```bash
k run web --image=nginx
k get po -o wide
curl http://172.20.190.66
k expose po web --port=80 --target-port=80 --type=NodePort
k get po,svc
curl http://10.100.230.191
```

web Pod: 172.20.190.66, web Service: 10.100.230.191, NodePort: 30380.
브라우저 192.168.120.150:30380에서 Nginx 기본 페이지 확인.

```text
노드에서 Pod IP:80 → Pod 직접 접근
노드에서 ClusterIP:80 → Service 규칙 → Pod:80
PC에서 노드 IP:30380 → Service 규칙 → Pod:80
```

Service는 별도 웹 서버 컨테이너가 아니라 접속 주소·포트·선택 대상을 정의하는 리소스다.
NodePort로 접속한 노드와 실제 Pod 실행 노드는 같을 필요가 없다.
--port는 Service 포트, --target-port는 컨테이너 목적지 포트, nodePort는 외부 접속 포트다.
Calico는 Pod의 네트워크 연결과 노드 간 통신 경로를 구성한다.

## 6. 조회·이벤트·로그·리소스 범위

```bash
k run nginx-pod --image=nginx
k get po -o wide
k describe po nginx-pod
k get events --sort-by=.metadata.creationTimestamp
k logs nginx-pod
k logs -f nginx-pod
k api-resources | more
k api-resources --namespaced=false
k api-resources --namespaced=true
k get po nginx-pod -o yaml
k get po nginx-pod -v=9
```

Pod created는 생성 요청 성공이다. READY 1/1, STATUS Running으로 실행 상태를 확인한다.
RESTARTS 0은 컨테이너 수가 아니라 재시작 횟수다.
describe는 배치·이미지·상태·이벤트, logs는 앱의 표준 출력/오류를 확인한다.
ImagePullBackOff는 재시도 간격을 늘려 대기하는 상태; 기다리는 것만으로 인증/이미지 부재가 해결되지는 않는다.
logs --previous는 재시작 전 컨테이너 로그; 이전 실행이 없으면 조회할 로그가 없을 수 있다.
-f/-w 조회를 Ctrl+C로 종료해도 앱은 유지된다.

-v=9는 클라이언트 디버깅 로그, -o yaml은 리소스 표현이다.
api-resources의 SHORTNAMES는 po/svc/deploy/cm/ns/no 등을 보여준다.
NAMESPACED false: Node, Namespace, PV. true: Pod, Service, Deployment, PVC.
apiVersion은 리소스 API 버전으로 노드의 Kubernetes v1.36.4와 다르다.
API 변경 시 api-resources와 explain으로 확인하되 apiVersion 문자열만 바꿔 모든 호환 문제가 해결되지는 않는다.

```bash
k get cm kube-root-ca.crt
k get cm kube-root-ca.crt -o yaml
```

DATA 1은 데이터 항목 1개. ca.crt는 서버 인증서 검증용 CA 인증서이며 개인키/로그인 토큰이 아니다.

## 8. YAML과 다중 컨테이너

초기 simple.yaml 오류는 kind: POD와 images: nginx였다. Pod와 image로 수정 후 생성 성공.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: mypod
spec:
  containers:
    - name: nginx
      image: nginx
    - name: c2
      image: busybox
      command: ['sh', '-c', 'echo hello k8s!!! && sleep 3600']
```

2/2 Running, w1, 172.20.190.71 확인. c2는 3600초 후 종료하며 기본 restartPolicy Always에 따라 재시작할 수 있다.

```bash
k exec mypod -- hostname
k exec mypod -c c2 -- hostname
k exec mypod -c c2 -- ip a
k exec mypod -c c2 -it -- /bin/sh
```

두 컨테이너 hostname은 mypod, Pod IP는 공유된다.
-c는 대상 컨테이너 지정. 생략 시 이번에는 nginx가 선택됐다.
같은 Pod는 네트워크·포트 공간을 공유하지만 루트 파일시스템은 각각 별개다.
공유 Volume은 따로 설정해야 한다. c2의 localhost에서 nginx 접근은 제안했으나 사용자 실행 출력은 미제시.

```bash
k exec web -- ls /
k exec web -- env
k exec -it web -- /bin/bash
df -h
cat /etc/hosts
id
exit
```

컨테이너 root와 master1 student는 별개 실행 환경이다.

k exec의 추가 셸 종료는 주 Nginx 프로세스를 종료하지 않는다.

## 10. Deployment 템플릿과 dry-run

```bash
k create deploy example --image=nginx --dry-run=client -o yaml > deploy_template.yaml
k create -f deploy_template.yaml
k get deploy,rs,po
```

example-7bd779fd5d-khhfj, w1, 172.20.190.74에서 Nginx 응답 확인.

```bash
k create deploy test --image=nginx --dry-run=server -o yaml > deploy_full_template.yaml
diff -u deploy_template.yaml deploy_full_template.yaml
```

| 항목 | client | server |
|---|---|---|
| 실제 저장 | 없음 | 없음 |
| 생성 요청의 서버 검증 | 없음 | 권한·정책·중복 이름 등 검증 |
| 서버 기본값 | 미반영 | 반영 |
| 실제 Pod 배치·이미지 실행 시험 | 없음 | 없음 |

기존 example 이름으로 server create dry-run은 already exists 오류가 났다.
test로 바꿔 검증 성공. server 출력의 UID/생성 시각은 실제 저장을 의미하지 않는다.
shell의 >는 명령 실패 시에도 파일을 생성하거나 비울 수 있다.
비교 파일의 example/test 이름 차이는 사용자가 다르게 지정한 결과다.
diff의 <는 첫 파일, >는 두 번째, a는 추가, c는 변경이다.

## 11. 컨트롤러·스케일·삭제 복구

example은 replicas 3으로 확장된 상태를 확인했다. 정확한 확장 입력 명령은 제공되지 않았다.
이후 YAML의 spec.replicas 3, ready/available/updatedReplicas 각각 3을 확인했다.
generation 2, revision 1은 복제본 수 변경과 일치한다. Pod template 변경 없는 scale은 새 rollout을 만들지 않는다.

```bash
k delete po --all
```

당시 default의 모든 Pod를 삭제했다. Deployment/ReplicaSet/Service는 삭제되지 않는다.
단독 Pod들은 사라졌고 example은 ReplicaSet이 새 Pod bmd6d(.75)를 생성했다.
이후 example 3개: master1의 .73, w1의 .75와 .76이 확인됐다.
Pod가 분산됐지만 이것만으로 모든 장애에 대한 무중단 고가용성을 보장하지는 않는다.

| 종류 | 역할 |
|---|---|
| Deployment | 교체 가능한 앱 Pod 개수·배포 상태 관리. 프론트엔드와 백엔드 API 모두 가능 |
| StatefulSet | 안정적인 Pod 식별자 및 설정된 Pod별 PVC 연결. DB 복제/읽기 전용은 DB 자체 설정 |
| DaemonSet | 대상 노드마다 Pod 유지. replicas 필드로 개수를 정하지 않음 |
| Job | 성공 완료가 목표인 작업. completions/parallelism/backoffLimit |
| CronJob | 일정에 따라 Job 생성 |

StatefulSet 기본 OrderedReady의 생성/확장은 순서대로, 축소는 역순이다. 병렬 정책과 리소스 삭제 시 예외를 구분한다.
PV/PVC는 저장소 유지·연결이고 백업 자체가 아니다. emptyDir는 Pod 삭제 시 사라진다.
DaemonSet은 노드별 수집 에이전트에 적합하며 분석은 중앙 시스템에서 할 수 있다.

## 12. 두 화면 차이: 이름·라벨·ReplicaSet

추가 실행:

```bash
k create deploy nginx --image=nginx
kubectl get all -o wide --show-labels
```

마지막 화면 기준 example 3개, nginx 1개 Pod가 있다.
nginx Pod는 nginx-7f8fbb96d-hs6fg, w1, 172.20.190.77로 확인됐다.

```text
Deployment example → ReplicaSet example-7bd779fd5d → Pod 3개 (app=example)
Deployment nginx   → ReplicaSet nginx-7f8fbb96d    → Pod 1개 (app=nginx)
```

강사 화면과 사용자 화면의 차이:
1. 사용자 터미널 폭이 좁아 오른쪽 LABELS가 다음 줄로 내려왔다. 이름 아래 app=... 줄은 별도 Pod가 아니다.
2. 줄바꿈으로 화면 높이를 더 써서 Deployment/ReplicaSet 표가 아래에 가려졌다.
3. Deployment가 2개이므로 해당 표와 ReplicaSet 표에 각각 두 행이 정상이다.
4. Pod 이름의 마지막 임의 문자열, IP, AGE, Service 자동 할당 포트는 환경별로 다르다.
5. 강사 hhs와 사용자 lsm은 직접 정한 이름 차이다.

별도 조회:

```bash
k get deploy,rs -o wide --show-labels
k get po -l app=example -o wide
k get po -l app=nginx -o wide
```

Deployment selector app=example은 관리 대상을 식별한다.
ReplicaSet은 app=example과 pod-template-hash를 함께 사용해 해당 템플릿의 Pod를 구분한다.
Service web/lsm은 run=web/run=lsm을 선택하므로 example/nginx에는 연결되지 않는다.
get all은 모든 리소스 종류를 뜻하지 않으며 현재 네임스페이스 기준이다. -A는 전체 네임스페이스.
