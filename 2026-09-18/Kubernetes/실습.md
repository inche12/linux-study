### 9월 21일 보완: Service 유형·selector·kube-proxy

Pod가 재생성되면 IP가 바뀔 수 있다. 일반적인 Service는 수명 동안 유지되는 ClusterIP와 DNS 이름으로 접근 지점을 제공한다.
Service selector와 일치하는 Pod가 연결 대상이 되고, EndpointSlice에 대상 주소와 준비 상태가 반영된다.
일반적인 트래픽 전달은 Ready인 backend를 대상으로 한다. Service를 삭제 후 재생성하면 같은 ClusterIP가 보장되지 않는다.

| 유형 | 접근 방식 | 구분할 점 |
|---|---|---|
| ClusterIP | 클러스터 내부의 가상 IP·DNS | 기본 유형 |
| NodePort | NodeIP:NodePort | 일반적으로 ClusterIP도 제공하며 방화벽·네트워크 경로 확인 필요 |
| LoadBalancer | 외부 Load Balancer 연동 | 제공자/컨트롤러가 필요하며 로컬 VM에서 자동으로 외부 IP가 생기지는 않음 |
| ExternalName | 외부 DNS 이름으로 CNAME 응답 | Pod selector 기반 프록시나 ClusterIP 할당 방식이 아님 |

`clusterIP: None`인 headless Service도 있으므로 모든 Service가 가상 IP를 갖는 것은 아니다.

실습에 기록된 템플릿 생성 명령:

```bash
kubectl expose svc svc-example \
  --port=80 --name=blue --type=NodePort --target-port=80 \
  --dry-run=client -o yaml > svc_template.yaml
kubectl get svc
kubectl get ep
kubectl get svc,ep,deploy,rs,po -o wide --show-labels
```

`expose svc`는 문법 오류가 아니다. 기존 `svc-example` Service의 selector를 이용해 새 Service를 생성하는 방식이며,
원본 Service가 먼저 있어야 한다. client dry-run도 원본 리소스 조회에는 API 서버 연결이 필요하다.
9월 18일 말의 기록에는 `svc-example` 생성이 없으므로, 없는 환경에서는 아래처럼 기존 Deployment를 기준으로 만든다.
이는 **재현을 위한 보충 대안**이며 실제 발생한 오류로 기록하지 않는다.

```bash
kubectl get deployment example -o wide
kubectl expose deployment example \
  --name=blue --type=NodePort --port=80 --target-port=80 \
  --dry-run=client -o yaml > svc_template.yaml
cat svc_template.yaml
kubectl apply -f svc_template.yaml
kubectl get svc blue -o yaml
kubectl get pods -l app=example -o wide --show-labels
kubectl get endpointslices -l kubernetes.io/service-name=blue -o wide
```

확인 기준은 `blue.spec.selector`가 `app: example`이고 EndpointSlice 주소가 대상 Pod IP에 대응하는지다.
`kubectl get ep`는 당시 명령으로 보존하되, Endpoints API는 Kubernetes v1.33부터 deprecated이므로 새 확인 절차는 EndpointSlice를 사용한다.

```text
Client → Service 접근 주소 → 노드의 전달 규칙 → backend Pod
                 selector → 대상 Pod 식별 → EndpointSlice 반영
```

kube-proxy는 Service/EndpointSlice 변화를 반영해 노드의 전달 규칙을 구성한다.
iptables 모드에서는 각 요청이 kube-proxy 사용자 공간 프로세스를 통과하는 구조가 아니다.
실습 정리본에는 iptables 모드 사용으로 기록되어 있다. 다음 보충 명령으로 설정 내용과 실행 로그를 확인한다.

```bash
kubectl get -n kube-system cm kube-proxy -o yaml
kubectl logs -n kube-system -l k8s-app=kube-proxy --tail=100
```

`kubectl get cm kube-proxy` 목록 출력만으로 모드를 판정하지 않는다. `mode`가 비어 있으면 기본값과 로그를 함께 확인한다.
iptables/IPVS 등은 Service Type이 아니라 프록시 구현 방식이다. CNI 설정에 따라 kube-proxy를 대체하는 구현도 있다.


### 9월 21일 보완: Node label과 nodeSelector

Pod label은 Service/ReplicaSet이 **대상 Pod를 선택**할 때, Node label은 스케줄러가 **실행 노드를 선택**할 때 사용한다.
`disktype=hdd`는 관리자가 붙이는 문자열이며 실제 디스크 종류를 검사하거나 변경하지 않는다.

```bash
kubectl label node master1 disktype=ssd
kubectl get node master1 --show-labels
kubectl label node master1 disktype=hdd --overwrite
kubectl get nodes -l disktype=hdd
```

기존 다중 컨테이너 예제를 다시 복사하지 않고, `simple.yaml`의 `spec.containers`와 같은 들여쓰기 수준에 아래 필드를 추가한다.
다음은 전체 Pod 명세가 아닌 **추가할 spec 일부**다.

```yaml
spec:
  nodeSelector:
    disktype: hdd
```

```bash
# mypod가 이미 있으면 먼저 상태와 파일을 확인한다.
kubectl get pod mypod -o wide
# 기존 standalone Pod의 nodeSelector 변경은 일반적으로 재생성이 필요하다.
# 보존할 데이터가 없는 실습 Pod일 때만 삭제 후 수정한 파일로 생성한다.
kubectl delete pod mypod
kubectl create -f simple.yaml
kubectl get pod mypod -o wide
kubectl describe pod mypod
```

조건에 맞는 노드가 없으면 Pending이 될 수 있다. 맞는 label이 있어도 taint, 자원 부족 등 다른 배치 조건을 함께 만족해야 한다.
9월 18일에는 master1의 control-plane taint를 제거한 상태였다. 그 설정이 없는 다른 환경에서 같은 결과를 단정하지 않는다.
원문에는 배치 원리가 기록되어 있으나 9월 21일의 최종 NODE 출력은 없어 특정 배치 결과를 추가하지 않았다.

```bash
# nodeSelector 실습 종료 후 label 삭제
kubectl label node master1 disktype-
```

이미 실행 중인 Pod를 Node label 삭제만으로 자동 이동시키지는 않는다. 이후 새 Pod의 배치에는 영향을 준다.

```bash
k exec web -- ls /
k exec web -- env
k exec -it web -- /bin/bash
df -h
cat /etc/hosts
id
exit
```

컨테이너 root와 master1 student는 별개 실행 환경이다.
overlay 약 48G는 노드 기반 파일시스템 용량이며 컨테이너에 전용 48G가 할당된 뜻이 아니다.
k exec의 추가 셸 종료는 주 Nginx 프로세스를 종료하지 않는다.

```bash
cp mypod.yaml pod_template.yaml
```

위 명령들은 서로 다른 실습 시점에 수행한 기록이며 그대로 연속 실행하는 스크립트가 아니다.
재생성 후 mypod는 2/2 Running, IP .71 → .72로 변경됐다.
파일 저장은 설정 보관이며 컨테이너 내부 파일·실행 메모리 백업이 아니다.
템플릿에서는 status, UID, 생성 시각, resourceVersion, 이전 IP annotation 등 불필요한 자동 정보를 정리한다.
nodeName을 제거하면 기존 노드 지정에 묶이지 않는다.
mypod-1 템플릿은 이름을 변경하고 c2를 제외한 Nginx 단일 Pod로 단순화했다. .73에서 실행 확인.

## 10. Deployment 템플릿과 dry-run

```bash
k create deploy example --image=nginx --dry-run=client -o yaml > deploy_template.yaml
k create -f deploy_template.yaml
k get deploy,rs,po
```

example-7bd779fd5d-khhfj, w1, 172.20.190.74에서 Nginx 응답 확인.

```bash
k create deploy test --image=nginx --dry-run=server -o yaml > deploy_full_template.yaml
diff -u deploy_template.yaml deploy_full_template.yaml
```

| 항목 | client | server |
|---|---|---|
| 실제 저장 | 없음 | 없음 |
| 생성 요청의 서버 검증 | 없음 | 권한·정책·중복 이름 등 검증 |
| 서버 기본값 | 미반영 | 반영 |
| 실제 Pod 배치·이미지 실행 시험 | 없음 | 없음 |

기존 example 이름으로 server create dry-run은 already exists 오류가 났다.
test로 바꿔 검증 성공. server 출력의 UID/생성 시각은 실제 저장을 의미하지 않는다.
shell의 >는 명령 실패 시에도 파일을 생성하거나 비울 수 있다.
비교 파일의 example/test 이름 차이는 사용자가 다르게 지정한 결과다.
diff의 <는 첫 파일, >는 두 번째, a는 추가, c는 변경이다.

## 11. 컨트롤러·스케일·삭제 복구

example은 replicas 3으로 확장된 상태를 확인했다. 정확한 확장 입력 명령은 제공되지 않았다.
이후 YAML의 spec.replicas 3, ready/available/updatedReplicas 각각 3을 확인했다.
generation 2, revision 1은 복제본 수 변경과 일치한다. Pod template 변경 없는 scale은 새 rollout을 만들지 않는다.

9월 21일 정리본에는 확장 명령도 명시됐다. 아래 조회는 desired와 Ready 개수를 비교하는 보충 절차다.

```bash
kubectl scale deployment example --replicas=3
kubectl get deployment example
kubectl get pods -l app=example -o wide
```

`spec.replicas=3`은 원하는 개수이며, 준비 완료 3개를 즉시 보장하지 않는다. Pending·이미지 다운로드·readiness 상태를 확인한다.

```bash
k delete po --all
```

당시 default의 모든 Pod를 삭제했다. Deployment/ReplicaSet/Service는 삭제되지 않는다.
단독 Pod들은 사라졌고 example은 ReplicaSet이 새 Pod bmd6d(.75)를 생성했다.
이후 example 3개: master1의 .73, w1의 .75와 .76이 확인됐다.
Pod가 분산됐지만 이것만으로 모든 장애에 대한 무중단 고가용성을 보장하지는 않는다.

9월 21일 재시작·삭제 명령:

```bash
kubectl rollout restart deployment green
kubectl rollout status deployment green
# 삭제 실습은 대상 label로 범위를 좁힌다.
kubectl get pods -l app=green
kubectl delete pod -l app=green
```

`rollout restart`는 Pod template의 재시작 annotation을 바꿔 Deployment 전략에 따라 Pod를 교체한다.
`delete pod --all`은 현재 네임스페이스의 모든 Pod가 대상이며 전체 클러스터라는 뜻은 아니다.
Deployment/ReplicaSet 관리 Pod는 다시 생성되지만 standalone Pod는 자동 복구되지 않는다.
동시 삭제는 일시적인 서비스 중단을 만들 수 있으므로 배포 교체와 같은 동작으로 생각하지 않는다.

| 종류 | 역할 |
|---|---|
| Deployment | 교체 가능한 앱 Pod 개수·배포 상태 관리. 프론트엔드와 백엔드 API 모두 가능 |
| StatefulSet | 안정적인 Pod 식별자 및 설정된 Pod별 PVC 연결. DB 복제/읽기 전용은 DB 자체 설정 |
| DaemonSet | 대상 노드마다 Pod 유지. replicas 필드로 개수를 정하지 않음 |
| Job | 성공 완료가 목표인 작업. completions/parallelism/backoffLimit |
| CronJob | 일정에 따라 Job 생성 |

StatefulSet 기본 OrderedReady의 생성/확장은 순서대로, 축소는 역순이다. 병렬 정책과 리소스 삭제 시 예외를 구분한다.
PV/PVC는 저장소 유지·연결이고 백업 자체가 아니다. emptyDir는 Pod 삭제 시 사라진다.
DaemonSet은 노드별 수집 에이전트에 적합하며 분석은 중앙 시스템에서 할 수 있다.

## 12. 두 화면 차이: 이름·라벨·ReplicaSet

추가 실행:

```bash
k create deploy nginx --image=nginx
kubectl get all -o wide --show-labels
```

마지막 화면 기준 example 3개, nginx 1개 Pod가 있다.
nginx Pod는 nginx-7f8fbb96d-hs6fg, w1, 172.20.190.77로 확인됐다.

```text
Deployment example → ReplicaSet example-7bd779fd5d → Pod 3개 (app=example)
Deployment nginx   → ReplicaSet nginx-7f8fbb96d    → Pod 1개 (app=nginx)
```

강사 화면과 사용자 화면의 차이:
1. 사용자 터미널 폭이 좁아 오른쪽 LABELS가 다음 줄로 내려왔다. 이름 아래 app=... 줄은 별도 Pod가 아니다.
2. 줄바꿈으로 화면 높이를 더 써서 Deployment/ReplicaSet 표가 아래에 가려졌다.
3. Deployment가 2개이므로 해당 표와 ReplicaSet 표에 각각 두 행이 정상이다.
4. Pod 이름의 마지막 임의 문자열, IP, AGE, Service 자동 할당 포트는 환경별로 다르다.
5. 강사 hhs와 사용자 lsm은 직접 정한 이름 차이다.

별도 조회:

```bash
k get deploy,rs -o wide --show-labels
k get po -l app=example -o wide
k get po -l app=nginx -o wide
```

Deployment selector app=example은 관리 대상을 식별한다.
ReplicaSet은 app=example과 pod-template-hash를 함께 사용해 해당 템플릿의 Pod를 구분한다.
Service web/lsm은 run=web/run=lsm을 선택하므로 example/nginx에는 연결되지 않는다.
get all은 모든 리소스 종류를 뜻하지 않으며 현재 네임스페이스 기준이다. -A는 전체 네임스페이스.

### 9월 21일 보완: Pod label 변경과 대체 생성

Dashboard에서 `app: green`을 `app: green-failed`로 변경하자 ReplicaSet이 원하는 복제본 수를 맞추기 위해 새 Pod를 생성했다고 기록했다.
관리 대상에서 빠진 기존 Pod도 실행 중일 수 있어 **전체 Pod 수**와 **selector로 세는 관리 Pod 수**가 다를 수 있다.
Service도 `app=green`을 선택하고 있었다면 바뀐 Pod는 트래픽 대상에서 제외된다.

같은 원리를 CLI로 확인하는 보충 예시다. `<대상-Pod>`는 실제 이름으로 바꾼다.

```bash
kubectl get rs,pods -l app=green -o wide --show-labels
kubectl label pod <대상-Pod> app=green-failed --overwrite
kubectl get pods -o wide --show-labels
kubectl get pods -l app=green
kubectl get pods -l app=green-failed
kubectl get endpointslices -l kubernetes.io/service-name=blue -o wide
```

Pod 하나의 label을 바꾸는 것과 Deployment의 `spec.template.metadata.labels`를 수정하는 것은 다르다.
새 Pod는 template의 label을 받는다. 고립된 실습 Pod는 이름과 데이터를 확인한 뒤 개별 삭제하여 정리할 수 있다.

## 13. Rolling Update·Blue/Green·Canary — 9월 21일

### 개념과 사전 확인

| 방식 | 교체/전환 방식 | 복구 시 핵심 |
|---|---|---|
| Rolling Update | 기존 ReplicaSet을 줄이며 새 ReplicaSet을 늘림 | 보존된 revision과 정상 이미지 확인 |
| Blue/Green | 두 Deployment를 준비하고 Service selector 전환 | 이전 환경을 유지하고 selector 복구 |
| Canary | 신버전을 일부 투입하고 관찰 후 확대 | 신버전 트래픽 축소/중단 |

`example → v1`, `green → v2`, `blue`는 Service 이름으로 사용한다. `nginx`는 이미지 이름이 아니라 변경할 **컨테이너 이름**이다.
`rosehs00/app:v1`, `v2`는 강의 정리본의 이미지이며 현재 접근 가능성·응답 내용은 재검증하지 않았다.

```bash
kubectl get deployment example -o yaml
kubectl get svc blue -o yaml
kubectl get pods -o wide --show-labels
```

### Rolling Update 명령과 확인

```bash
kubectl set image deployment/example nginx=rosehs00/app:v1
kubectl rollout status deployment/example
kubectl set image deployment/example nginx=rosehs00/app:v2
kubectl rollout status deployment/example
kubectl rollout history deployment/example
kubectl get rs,pods -l app=example -o wide
```

Pod template이 바뀌면 그 템플릿에 맞는 ReplicaSet으로 rollout한다. 보통 새 ReplicaSet이 생성되지만 이전 템플릿으로 돌아갈 때는 기존 것이 재사용될 수 있다.
`maxSurge`는 목표 개수보다 추가로 만드는 Pod 수, `maxUnavailable`은 교체 중 허용할 사용 불가 Pod 수를 조절한다.
기본 RollingUpdate 값은 각각 25%이며 반올림 방향이 다르다. replicas 3이면 각각 1개/0개가 된다.
애플리케이션 readinessProbe가 없으면 Kubernetes의 Ready만으로 실제 서비스 준비를 충분히 판별하지 못할 수 있다.

```bash
kubectl rollout history deployment/example
# revision 3이 실제로 존재하고 원하는 이미지인지 먼저 확인
kubectl rollout history deployment/example --revision=3
kubectl rollout undo deployment/example --to-revision=3
kubectl rollout status deployment/example
```

revision 번호는 각 환경의 배포 이력에 따라 다르다. scale 자체는 새 revision을 만들지 않으며,
rollback은 Pod template 복구이지 외부 DB·데이터·별도 ConfigMap 전체 복구가 아니다.

### Blue/Green: 준비 → 검증 → 전환 → 복구

Rolling 실습에서 example을 v2로 바꿨다면 먼저 v1으로 복구해 두 환경을 구분한다.
아래는 원문의 전환 명령에 사전 확인을 추가한 재현 절차다.

```bash
kubectl set image deployment/example nginx=rosehs00/app:v1
kubectl rollout status deployment/example
# green이 없는 경우 생성. 이미 있다면 먼저 image와 replicas를 조회한다.
kubectl create deployment green --image=rosehs00/app:v2
kubectl scale deployment green --replicas=3
kubectl rollout status deployment/green
kubectl get pods -l app=green -o wide
```

전환 전 신버전 응답 확인을 위한 보충 절차(별도 터미널에서 접속):

```bash
kubectl port-forward deployment/green 8080:80
```

```bash
curl http://127.0.0.1:8080/
```

```bash
kubectl set selector svc blue app=green
kubectl get svc blue -o yaml
kubectl get endpointslices -l kubernetes.io/service-name=blue -o wide
# 문제가 있으면 이전 환경으로 복구
kubectl set selector svc blue app=example
kubectl get endpointslices -l kubernetes.io/service-name=blue -o wide
```

전환 후에는 `kubectl get svc blue`로 실제 NodePort를 확인하고 해당 주소의 앱 응답까지 검증한다.
selector를 바꾸면 신규 연결의 대상 집합이 바뀌지만 규칙 전파 시간과 기존 연결 때문에 모든 요청이 즉시 동시에 전환되는 것은 아니다.
빠른 복구를 위해 example을 유지한다. 두 환경이 공유하는 데이터나 스키마의 호환성은 별도로 확보해야 한다.

### Canary 개념 보완

v1 여러 개와 v2 일부가 **같은 Service selector를 만족**해야 두 버전에 트래픽을 보낼 수 있다.
현재 `app=example`과 `app=green`은 서로 다르므로 한쪽 selector만 쓰면 Canary가 되지 않는다.
구현할 때는 두 Deployment의 고유 selector를 유지하면서 Pod template에 공통 서비스용 label을 추가하고 그 label로 Service를 구성할 수 있다.
Pod 개수 비율은 실제 요청 비율의 정확한 보장이 아니다. 연결 재사용·세션 고정·트래픽 정책 등의 영향을 받는다.
정밀한 가중치 제어에는 이를 지원하는 게이트웨이나 서비스 메시 등의 구성이 필요하다.
이번 자료에는 Canary 개념만 있으며 실제 Canary 배포·트래픽 측정 성공 기록은 없다.

## 14. Metrics Server와 Troubleshooting — 9월 21일

### 목적·설치 기록·확인

Metrics Server는 kubelet에서 CPU/메모리 지표를 수집해 Metrics API로 제공한다.
`kubectl top`과 리소스 지표 기반 HPA에서 사용하며 장기 이력 저장/분석 시스템은 아니다.

```bash
# 당시 사용한 설치 URL. latest는 시간이 지나면 다른 버전을 가리킨다.
kubectl apply -f \
  https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl top nodes
kubectl top pods -A
kubectl top pods -A --containers
```

재현 시에는 클러스터 버전과 공식 호환성 표를 확인하고 릴리스 버전을 고정한다.
원문에는 실제 설치 이미지 태그가 없어 특정 Metrics Server 버전을 사용했다고 단정하지 않는다.

```bash
# 설치 버전과 상태를 남기는 보충 조회
kubectl get deployment metrics-server -n kube-system \
  -o jsonpath='{.spec.template.spec.containers[*].image}'
kubectl get pods -n kube-system -l k8s-app=metrics-server
kubectl get apiservice v1beta1.metrics.k8s.io
```

### 실제 오류: 두 옵션을 하나의 args 문자열로 입력

**증상:** 정리본에는 Metrics Server Pod가 CrashLoopBackOff가 되었다고 기록되어 있다.

```bash
kubectl logs -n kube-system <metrics-server-pod>
# 재시작 직전 실패 로그가 필요할 때
kubectl logs -n kube-system <metrics-server-pod> --previous
```

**기록된 오류 메시지:**

```text
invalid argument "10250 --kubelet-insecure-tls" for "--secure-port" flag
```

**잘못 입력한 설정:** CLI 명령 자체의 오타가 아니라 Deployment YAML의 args 항목을 잘못 합친 것이었다.

```yaml
args:
  - --secure-port=10250 --kubelet-insecure-tls
```

컨테이너 args의 각 목록 항목은 별도 인자 하나다. 셸이 공백을 자동 분리해 주지 않아 port 값에 뒤 옵션까지 포함된다.

**수정 명령과 올바른 설정:**

```bash
kubectl edit deployment -n kube-system metrics-server
```

```yaml
args:
  - --cert-dir=/tmp
  - --secure-port=10250
  - --kubelet-insecure-tls
  - --kubelet-preferred-address-types=InternalIP,ExternalIP,Hostname
  - --kubelet-use-node-status-port
  - --metric-resolution=15s
```

위 내용은 해당 컨테이너의 args 부분이며 Deployment 전체를 대체하는 YAML이 아니다.
`--kubelet-insecure-tls`는 Metrics Server → kubelet 인증서 검증을 생략하는 **실습용 예외**다.
이번 직접 원인은 인자 형식 오류이며, 자료에 없는 인증서 오류가 발생했다고 추가하지 않는다.
운영에서는 검증 가능한 kubelet serving 인증서·CA·주소를 구성하고 해당 우회 옵션을 제거한다.

```bash
kubectl rollout status deployment/metrics-server -n kube-system
kubectl get pods -n kube-system -l k8s-app=metrics-server
kubectl top nodes
kubectl top pods -A --containers
```

**기록된 결과:** 수정 후 Pod `1/1 Running`, `kubectl top nodes` 성공.
`top pods` 상세 값은 제공되지 않았다. 방금 생성한 Pod는 지표 수집까지 잠시 기다려야 할 수 있다.
계속 실패하면 Pod 이벤트/로그, APIService의 Available 상태, kubelet 연결·인증서 등을 순서대로 확인한다.
`Running`만으로 Metrics API가 정상임을 단정하지 않는다.

아래는 강의에서 사용한 구버전 절차를 보존한 것이며 새 운영 환경의 설치 지침이 아니다.

```bash
kubectl apply -f \
  https://raw.githubusercontent.com/kubernetes/dashboard/v2.6.1/aio/deploy/recommended.yaml
kubectl get svc -n kubernetes-dashboard
kubectl edit svc kubernetes-dashboard -n kubernetes-dashboard
```

Service의 `spec.type`을 변경한 부분:

```yaml
spec:
  type: NodePort
```

실습 접근 주소는 `https://192.168.120.150:30319/`로 기록됐다. 30319는 이 환경의 할당값이며 고정 기본값이 아니다.
GUI에서 Pod 목록, CPU/메모리, 로그, YAML Edit Resource, label 변경, Resource Delete/Create를 다뤘다.
CPU/메모리 표시에는 지표 공급 경로의 정상 동작이 필요하다. Pod label 변경 결과는 12절에 병합했다.

### ServiceAccount: 인증 주체와 토큰

ServiceAccount는 네임스페이스에 속하는 Kubernetes API 인증 주체다. Pod/애플리케이션이 사용할 수 있으며 권한은 RBAC 등으로 별도 부여한다.

```bash
kubectl get sa -n kubernetes-dashboard
kubectl create token kubernetes-dashboard -n kubernetes-dashboard
```

토큰 발급 성공과 관리자 권한은 별개다. 발급 토큰은 만료되는 자격 증명이며 토큰 값은 저장소·스크린샷에 남기지 않는다.
권한 오류를 토큰 재발급만으로 해결하려 하지 말고 바인딩을 확인한다.

### RBAC 객체와 네임스페이스 범위

| 객체 | 의미 |
|---|---|
| Role | 특정 네임스페이스 리소스에 대한 권한 정의 |
| ClusterRole | 클러스터 수준 객체로 권한 정의; namespaced/cluster-scoped 리소스 규칙을 담을 수 있음 |
| RoleBinding | 해당 네임스페이스 범위에서 Role 또는 ClusterRole을 subject에 연결 |
| ClusterRoleBinding | ClusterRole을 클러스터 전체 범위로 subject에 연결 |

ClusterRole을 RoleBinding으로 연결해도 Node 같은 cluster-scoped 리소스 권한이 생기지는 않는다.
RoleBinding의 네임스페이스는 **권한이 적용되는 범위**이고 subject의 네임스페이스는 **ServiceAccount의 소속**이다.

원문의 `test-ns`가 미리 만들어졌는지 확인하고, 없는 경우에만 생성한다.

```bash
kubectl get namespace test-ns
# 없을 때만 실행
kubectl create namespace test-ns
kubectl create role service-rd \
  --verb=get,list --resource=services -n test-ns
kubectl create rolebinding test-rolebinding \
  --role=service-rd -n test-ns --serviceaccount=test-ns:default
kubectl get clusterrole cluster-admin -o yaml
```

원문의 반복 `--verb=get --verb=list`은 `--verb=get,list`로 표기를 정리했다. 실제 오류가 있었다는 뜻은 아니다.
default ServiceAccount가 `test-ns`의 Service get/list 권한을 받는 예다. 운영 앱에는 용도별 ServiceAccount를 사용한다.

**보충 검증**(impersonation 권한이 있는 관리자 컨텍스트에서):

```bash
kubectl auth can-i list services -n test-ns --as=system:serviceaccount:test-ns:default
kubectl auth can-i delete services -n test-ns --as=system:serviceaccount:test-ns:default
kubectl auth can-i list pods -n test-ns --as=system:serviceaccount:test-ns:default
```

이 Role만 부여된 전제의 기대 결과는 순서대로 yes/no/no다. 다른 바인딩이 이미 있으면 결과가 달라질 수 있다.
위 결과를 이번에 실행해 확인한 것은 아니다.

### 실습용 관리자 권한·Skip Login과 복구

정리본의 관리자 권한 부여 명령:

```bash
kubectl create clusterrolebinding kdb-admin \
  --serviceaccount=kubernetes-dashboard:kubernetes-dashboard \
  --clusterrole=cluster-admin
kubectl edit deployment kubernetes-dashboard -n kubernetes-dashboard
```

Dashboard 컨테이너의 실습용 args:

```yaml
args:
  - --enable-skip-login
  - --disable-settings-authorizer
  - --auto-generate-certificates
  - --namespace=kubernetes-dashboard
```

Pod template 변경으로 새 rollout이 일어난다. 두 우회 옵션이 RBAC 권한을 직접 만드는 것은 아니지만,
로그인 생략과 Dashboard ServiceAccount의 cluster-admin 권한이 결합하면 접근자가 강한 권한을 사용할 수 있다.
이 설정은 격리된 실습망에서 다룬 기록이며 운영 권장사항과 분리한다.

| 실습에서 사용한 설정 | 운영 관점 |
|---|---|
| Dashboard ServiceAccount에 cluster-admin | 인증된 사용자별 최소 권한 적용 |
| skip-login·settings authorizer 비활성화 | 로그인·권한 검사 유지 |
| NodePort 직접 노출 | 인증·TLS·접근 제어를 갖춘 관리 경로 설계 |
| 구버전 Dashboard | 유지보수되는 관리 도구 검토 |

아래는 **실습 종료 후 복구 제안**이며 원문에 완료 기록은 없다. 편집 중 우회 옵션 두 개를 제거하고 필요한 기존 args를 유지한다.

```bash
kubectl delete clusterrolebinding kdb-admin
kubectl edit deployment kubernetes-dashboard -n kubernetes-dashboard
kubectl rollout status deployment/kubernetes-dashboard -n kubernetes-dashboard
# 외부 NodePort가 더 이상 필요하지 않을 때 spec.type 변경 및 nodePort 필드 제거
kubectl edit svc kubernetes-dashboard -n kubernetes-dashboard
kubectl get svc -n kubernetes-dashboard
```

다른 바인딩까지 없어진다고 가정하지 말고 실제 권한을 확인한다. 로그인 토큰을 만들었다는 이유로 토큰 내용을 Git에 저장하지 않는다.

## 16. API Server 보안 흐름 — 9월 21일

```text
Client → Authentication(누구인가) → Authorization/RBAC(허용된 작업인가)
       → Admission·API 유효성 검사 → 허용된 리소스 변경 저장(etcd)
```

위 그림은 리소스 **변경 요청**의 개념도다. 모든 요청이 admission과 etcd 쓰기를 거치는 것은 아니다.
조회 요청은 저장을 일으키지 않고, aggregated API 등은 별도 서버에서 처리될 수 있다.
Admission에는 변경/검증 단계가 있으며 단순 도식만으로 모든 내부 검증 순서를 표현하지 않는다.
일반 사용자는 etcd를 직접 편집하지 않고 API Server를 통해 리소스를 관리한다.
Linux 파일 권한, Kubernetes 인증, RBAC 인가를 구별하면 `Permission denied`, 인증 실패, `Forbidden`을 나눠 점검할 수 있다.

## 17. 9월 21일 복습·확인 범위

- Service selector는 트래픽 대상을, ReplicaSet selector는 관리 Pod를, nodeSelector는 실행 Node를 고른다.
- scale과 Pod template 변경의 차이, Rolling/Blue-Green/Canary의 전환·복구 방법을 설명할 수 있어야 한다.
- Metrics Server 오류는 증상 → 로그 → 잘못된 args → 분리 수정 → top 성공 순서로 복습한다.
- SA는 인증 주체, Role/ClusterRole은 권한 규칙, Binding은 주체와 권한의 연결이다.
- 기록된 결과: Metrics Server `1/1 Running` 및 `top nodes` 성공, Pod label 변경 후 대체 Pod 생성.
- 추가 증거가 없는 항목: rollout별 응답 화면/성공 출력, Canary 트래픽 비율, RBAC can-i 결과, 보안 설정 복구 완료.
