# AWS — 9월 21일 기초 학습

사용자가 제공한 GPT 공동 정리본의 AWS 학습 내용을 정리했다.
이번 범위는 서비스 모델·글로벌 인프라·IAM **개념 학습**이다. AWS 계정에서 리소스를 생성하거나 정책을 적용했다는 실행 기록은 없다.
Kubernetes 내용은 [기존 Kubernetes 노트](../../2026-09-18/Kubernetes/실습.md)에 병합했다.

## 1. 학습 목표와 이전 실습 연결

Docker에서 애플리케이션 실행 환경을, Kubernetes에서 배치·복구·서비스 접근·권한을 다뤘다.
AWS에서는 이 자원을 어디에 배치하고, 어떤 계층을 공급자가 관리하며, 누가 접근할 수 있는지 구분한다.

| 질문 | 연결되는 개념 |
|---|---|
| 운영체제와 런타임을 누가 관리하는가? | IaaS/PaaS/SaaS와 책임 범위 |
| 어떤 지역에 서비스를 둘 것인가? | Region |
| 한 장애 영역에 모든 서버가 몰려 있지 않은가? | Availability Zone(AZ) |
| 네트워크를 어떻게 나눌 것인가? | VPC·Subnet |
| 누가 어떤 자원에 어떤 작업을 할 수 있는가? | IAM |

## 2. Cloud Service Model

### 개념

| 모델 | 공급자가 주로 관리하는 범위 | 사용자가 주로 관리하는 범위 |
|---|---|---|
| On-Premises | 자체 구축이면 외부 클라우드 공급자 관리 없음 | 네트워크·스토리지·서버·가상화·OS·미들웨어·런타임·데이터·앱 |
| IaaS | 물리 네트워크·스토리지·서버·가상화 | 게스트 OS·미들웨어·런타임·데이터·앱 |
| PaaS | 인프라와 OS·미들웨어·런타임 등 | 주로 앱·데이터·서비스 설정 |
| SaaS | 애플리케이션 제공과 서비스 운영 | 사용자·접근 권한·설정·자신의 데이터 사용 및 관리 책임 |

관리 범위는 추상화 수준을 이해하기 위한 일반적인 구분이다. 세부 책임은 서비스에 따라 달라진다.
SaaS를 사용한다고 계정 관리나 데이터에 대한 사용자 책임이 모두 사라지는 것은 아니다.
IaaS에서도 VPC·보안 그룹처럼 사용자가 구성하는 논리 네트워크 설정은 사용자 책임이다.

### 기존 실습과 비교

VM에 Linux, Docker, Kubernetes를 직접 설치했다면 OS 패치와 구성, 컨테이너 이미지, 접근 권한을 직접 관리했다.
EC2 같은 가상 서버를 사용해도 게스트 OS와 애플리케이션 운영 업무가 자동으로 없어지지는 않는다.
관리형 서비스를 선택할수록 직접 관리하는 계층은 줄어들지만 앱 설정·데이터·권한 설계는 계속 필요하다.

## 3. Region과 Availability Zone

### Region 선택

Region은 AWS 인프라가 위치하는 지리적 영역이다. 다음 조건을 함께 고려한다.

1. 규정 준수와 데이터 저장 위치 요구
2. 사용자와의 거리 및 지연 시간
3. 필요한 서비스·기능의 제공 여부
4. 서비스 요금과 데이터 전송 비용

특정 Region의 서비스 지원이나 가격은 변할 수 있으므로 실제 설계 시 확인한다.
이번 자료에는 Region 선택이나 리소스 생성 결과가 없다.

### AZ와 고가용성

AZ는 Region 안의 서로 격리된 인프라 위치이며 하나 이상의 데이터센터로 구성될 수 있다.
단일 서버 여러 개를 같은 AZ에 두는 것과 여러 AZ로 분산하는 것은 장애 대응 범위가 다르다.

```text
Region
├── AZ-A: EC2 인스턴스
└── AZ-B: EC2 인스턴스
```

여러 AZ에 배치하고 트래픽 전환, 충분한 잔여 용량, 데이터 복제 등을 함께 설계해야 한 AZ 장애 시 서비스를 이어갈 수 있다.
인스턴스 두 개를 만들었다는 사실만으로 자동 장애 조치나 데이터 일관성을 보장하지 않는다.
Multi-AZ는 Region 전체 장애를 대비하는 Multi-Region 설계와도 구분한다.

## 4. 다음 VPC 학습과 연결

```text
Region
└── VPC (Region 범위)
    ├── AZ-A
    │   ├── Public Subnet A
    │   └── Private Subnet A
    └── AZ-B
        ├── Public Subnet B
        └── Private Subnet B
```

VPC는 Region 범위이고 Subnet 하나는 AZ 하나에 속한다. 여러 AZ를 사용하려면 각 AZ에 별도 Subnet을 만든다.
위 계층 그림은 배치 관계를 표현한 것으로 AZ를 VPC 안에 새로 생성한다는 뜻은 아니다.

Public Subnet은 Internet Gateway로 직접 나가는 경로가 있는 서브넷이다.
이름에 public을 붙이는 것만으로 외부 연결이 생기지 않는다. 인스턴스의 공인 주소와 라우팅, 보안 그룹/NACL 등도 확인해야 한다.
Private Subnet의 외부 통신은 NAT 등 별도 경로 설계와 연결된다. 이 부분은 다음 실습에서 실제 경로를 확인한다.

## 5. IAM: 주체·정책·역할

IAM(Identity and Access Management)은 AWS 리소스 접근 주체와 권한을 관리한다.

| 요소 | 의미 | 혼동하기 쉬운 점 |
|---|---|---|
| User | AWS 계정 내 IAM 신원 | 장기 자격 증명을 만들 수 있지만 모든 사람에게 장기 키가 필요한 것은 아님 |
| Group | IAM User 묶음에 권한 관리 | Role을 묶는 그룹이나 로그인 주체가 아님 |
| Policy | 어떤 작업을 어떤 자원에 허용/거부할지 정의 | 정책 문서만 작성했다고 자동으로 주체에 적용되지 않음 |
| Role | 허용된 주체가 맡아 임시 자격 증명으로 사용하는 역할 | 신뢰 정책과 권한 정책을 구분해야 함 |

### Policy 읽기

원문의 Statement 조각을 완전한 정책 문서 형태로 보완한 예시다. 실제 계정에 적용한 정책이 아니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ec2:DescribeInstances",
      "Resource": "*"
    }
  ]
}
```

- `Version`은 정책 언어 버전이며 작성일을 넣는 칸이 아니다.
- `Effect`는 허용/거부, `Action`은 API 작업, `Resource`는 적용 자원이다.
- 이 예시는 인스턴스 **조회** 권한이며 생성·종료 권한을 주지 않는다.
- `DescribeInstances`는 개별 리소스 ARN 지정 방식의 권한 제한을 지원하지 않아 `Resource: "*"`를 사용한다.
- 다른 작업까지 무조건 `*`로 허용하는 패턴으로 일반화하지 않는다.

기본적으로 명시적 허용이 없으면 거부되고, 적용되는 명시적 Deny는 Allow보다 우선한다.
실제 유효 권한은 identity/resource 정책과 조직 정책·permissions boundary 등 여러 제한의 영향을 받을 수 있다.

### Role: EC2에서 S3에 접근하는 예

```text
EC2 인스턴스
  → Instance Profile로 IAM Role 연결
  → 임시 자격 증명 사용
  → Role 권한 정책과 대상 자원 정책 등으로 허용 여부 평가
  → 허용된 S3 작업 수행
```

신뢰 정책은 **누가 Role을 맡을 수 있는지**, 권한 정책은 **그 Role로 무엇을 할 수 있는지**를 정한다.
EC2에 Role을 연결했다고 S3 전체 권한이 자동으로 생기지 않으며 필요한 bucket/object 작업을 정책에 정의해야 한다.
EC2 내부 파일이나 소스 코드에 장기 Access Key를 저장하는 대신 Role과 임시 자격 증명을 사용한다.
사람의 접근도 조직의 연동 로그인 및 임시 자격 증명을 우선 검토한다.

### Kubernetes RBAC와 비교

| 구분 | Kubernetes | AWS |
|---|---|---|
| 워크로드 신원 예 | ServiceAccount | 서비스가 사용하는 IAM Role |
| 권한 정의 예 | Role/ClusterRole의 rules | IAM Policy의 Statement |
| 권한 연결 예 | RoleBinding/ClusterRoleBinding | Policy 연결 및 Role 사용 관계 |

개념 비교이며 같은 객체라는 뜻은 아니다. Kubernetes Role은 권한 규칙 객체이고 IAM Role은 맡아 사용할 수 있는 신원이므로 이름만 보고 대응시키지 않는다.
AWS IAM 권한과 Kubernetes 내부 RBAC도 별도 체계다.

## 6. 복습 질문과 다음 실습 확인 항목

- IaaS를 사용하면서도 게스트 OS 패치가 필요한 이유는 무엇인가?
- Region 1개와 AZ 2개를 선택하면 어느 장애 범위까지 대비할 수 있는가?
- Subnet 하나가 AZ 두 개에 걸쳐 존재할 수 있는가? → 하나의 AZ에 속한다.
- IAM Role의 신뢰 정책과 권한 정책은 각각 어떤 질문에 답하는가?
- EC2에 장기 키를 저장하지 않고 AWS API를 호출하려면 무엇을 연결하는가? → Instance Profile을 통한 Role.

다음 실습에서는 선택한 Region/AZ, VPC CIDR, Subnet별 AZ/CIDR/라우팅,
Role 신뢰 관계와 허용/거부 API 결과를 기록한다. 자격 증명 값은 기록하지 않는다.
이번에는 실제 AWS 오류 로그가 없어 Troubleshooting 사례나 성공 결과를 만들어 추가하지 않았다.
