# 2026-09-08 LVM Snapshot·tar·RAID1·Swap·GitHub SSH

출처: 「9.8 tar 백업 경로 설명」 대화의 Ubuntu·Rocky Linux 실습 명령과 출력. 실제 확인된 결과와 대화에서 안내받은 개념·수정 방법을 구분했다. Swap와 `/etc/stab` 관련 후속 질문도 함께 정리하되, 별도 실행 출력이 없는 내용을 9/8 실습 성공으로 기록하지 않는다.

## 1. LVM Snapshot과 tar 백업의 차이

| 구분 | LVM Snapshot | tar 백업 |
|---|---|---|
| 역할 | LV의 특정 시점 상태를 보존 | 지정한 파일·디렉터리를 아카이브 파일로 저장 |
| 원본과 관계 | 일반적인 CoW 스냅샷은 원본 LV에 의존 | 생성 완료한 아카이브 내용은 원본 변경에 따라 자동 갱신되지 않음 |
| 변경 처리 | 원본 블록 변경 전 데이터를 보존해 스냅샷 시점 유지 | 다시 백업하지 않으면 이후 변경은 반영되지 않음 |
| 활용 | 백업할 시점의 파일을 읽거나 일부 파일 복구 | 별도 저장·이동·파일 추출 |

Snapshot은 원본과 독립된 전체 복사본이 아니다. tar 파일도 같은 디스크에만 두면 디스크 장애에 대비한 별도 보관이 되지는 않는다. `tar cf`는 파일을 묶으며 압축 옵션은 사용하지 않은 형태다.

### 실제 확인한 스냅샷과 파일 복구

Ubuntu에서 실행:

```bash
mount -o ro,nouuid /dev/vg01/snap /snap
ls /snap
```

```text
pam.conf  passwd  passwd-  profile  protocols
```

- `ro`: 읽기 전용 마운트.
- `nouuid`: XFS에서 원본과 같은 파일시스템 UUID를 가진 스냅샷을 마운트할 때 UUID 중복 검사를 생략하는 옵션.
- `/dev/vg01/snap`: 스냅샷 LV. `/snap`: 그 내용을 읽는 마운트 경로.

원본 `/xfs`에는 `f1 f2 f3 f4 passwd passwd- profile protocols`가 있었고, 스냅샷의 `pam.conf`를 복사했다.

```bash
cd /snap
cp pam.conf /xfs
ls /xfs
```

이후 `/xfs` 목록에 `pam.conf`가 추가됐다. 이는 스냅샷에서 파일 하나를 복구한 결과이며, LV 전체 되돌리기나 tar 복구 결과는 아니다. 스냅샷 생성 명령의 전체 옵션·크기는 대화에 없어 추가하지 않았다.

## 2. tar의 현재 디렉터리 `.`과 백업 경로 오류

### 실제 실행과 결과

root 홈 디렉터리(`~`, 이 실습에서는 `/root`)에서 실행했다.

```bash
tar cf /var/tmp/xfs.tar .
ls -l /var/tmp/xfs.tar
tar tf /var/tmp/xfs.tar
```

아카이브 크기는 20,480바이트였고, 목록에는 `./.bashrc`, `./d1/`, `./f1`, `./.profile`, `./.ssh/` 등 `/root`의 내용이 나왔다. `/snap`의 다섯 파일은 들어 있지 않았다.

| 표기 | 의미 |
|---|---|
| `c` | 아카이브 생성 |
| `t` | 아카이브 내부 목록 조회 |
| `x` | 아카이브 추출 |
| `f` | 사용할 아카이브 파일 지정 |
| `/var/tmp/xfs.tar` | 저장할 아카이브 경로 |
| `.` | 명령 실행 당시 현재 디렉터리. 그 아래 내용도 포함 |

`mount ... /snap`이나 `ls /snap`은 셸의 현재 디렉터리를 바꾸지 않는다. 백업 파일 이름이 `xfs.tar`여도 `/xfs`나 `/snap`이 자동으로 선택되지 않는다.

실제 추출:

```bash
mkdir /tar
cd /tar
tar xf /var/tmp/xfs.tar
ls
```

```text
d1  f1
```

아카이브가 `/root`를 담았으므로 `/snap`의 파일이 나오지 않은 것이 원인이다. 일반 `ls`는 숨김 파일을 표시하지 않는다. `ls -la /tar`는 숨김 파일까지 확인하는 안내 명령이며, 그 실행 출력은 기록에 없다.

### 함께 발생한 오타와 오류

| 입력 | 결과·원인 | 수정 방법 |
|---|---|---|
| `cd/ snap` | `-bash: cd/: No such file or directory` | `cd /snap`: 명령과 경로 사이에 공백 필요 |
| `tar cf /var/tmp/xfs.tar` | `Cowardly refusing to create an empty archive` | 백업할 파일·디렉터리 인자가 빠짐 |

### 대화에서 안내받은 수정 방법

현재 위치와 관계없이 `/snap`을 대상으로 지정하는 방법:

```bash
tar cf /var/tmp/snap.tar -C /snap .
tar tf /var/tmp/snap.tar
```

`-C /snap`은 tar가 이후의 `.`을 `/snap` 기준으로 해석하게 한다. `cd /snap` 후 `tar cf /var/tmp/snap.tar .`을 실행하는 방법도 같다. 목록을 확인한 뒤 `/tar`에서 추출하는 방법을 안내받았다.

```bash
cd /tar
tar xf /var/tmp/snap.tar
```

이 수정 백업·추출의 실제 완료 출력은 대화에 없다. 기존 `/var/tmp/xfs.tar`가 정상적인 스냅샷 백업으로 교체됐다고 단정하지 않는다.

## 3. 백업 후 스냅샷을 제거하는 이유와 watch 종료

“계속 트랜잭션되니 삭제한다”는 설명은 백업용 임시 스냅샷을 유지할 때 발생하는 변경 전 블록 보존 작업으로 이해했다. 일반적인 CoW 스냅샷은 원본의 변경 영역이 늘면 보존 공간을 더 사용하고 추가 I/O가 발생한다. 모든 쓰기 이력을 끝없이 기록하는 트랜잭션 로그와는 다르다. 공간이 가득 차면 스냅샷을 사용할 수 없게 될 수 있다.

안내받은 흐름은 **스냅샷 내용 백업 → 백업 확인 → 마운트 해제 → 임시 스냅샷 제거**다.

```bash
# 백업 확인 후 필요 없어진 스냅샷에 대한 안내 명령
umount /snap
lvremove /dev/vg01/snap
```

제거 대상은 임시 스냅샷 LV이며 보관할 tar 백업 파일이 아니다. 이 대화에는 스냅샷 제거 완료 출력이 없다. 특히 앞 절의 잘못된 `/root` 백업만으로 스냅샷 백업 완료를 판단하면 안 된다.

`watch` 종료 방법을 질문했고 **Ctrl+C**로 종료해 프롬프트로 돌아가는 방법을 확인했다. `watch`는 지정한 명령 결과를 반복 표시한다. 대화에 나온 `watch lvs`는 사용 예시이며 실제 실행 인자는 확인되지 않았다.

## 4. mdadm으로 RAID1 생성과 상태 확인

Rocky에서 사용한 명령:

```bash
mdadm -C -v /dev/md1 -l1 -n 2 /dev/nvme0n3 /dev/nvme0n4
```

| 항목 | 의미 |
|---|---|
| `mdadm` | Linux 소프트웨어 RAID 관리 도구 |
| `-C` | RAID 생성 |
| `-v` | 상세 출력 |
| `/dev/md1` | 생성할 RAID 장치 |
| `-l1` | RAID 레벨 1, 미러링 |
| `-n 2` | 구성 장치 2개 |
| `/dev/nvme0n3`, `/dev/nvme0n4` | 이번 실습에서 사용한 멤버 디스크 |

write-intent bitmap 활성화 질문에 `y`를 입력했다. bitmap은 동기화가 필요할 수 있는 영역을 추적하여 중단 후 재동기화 범위를 줄이는 데 도움을 준다. 별도 백업 기능은 아니다.

생성 도중 `/boot`로 사용할 경우 부트로더의 RAID 메타데이터 지원을 확인하라는 안내가 나왔고, `size set to 1046528K`가 표시됐다. RAID1은 동일 내용을 두 장치에 저장하므로 두 디스크 용량을 합쳐 사용하는 방식이 아니다.

실제 상태 조회:

```bash
cat /proc/mdstat
```

```text
Personalities : [raid1]
md1 : active raid1 nvme0n4[1] nvme0n3[0]
      1046528 blocks super 1.2 [2/2] [UU]
      bitmap: 1/1 pages [4KB], 65536KB chunk

unused devices: <none>
```

- `active raid1`: RAID1 활성 상태.
- `super 1.2`: RAID 메타데이터 버전.
- `[2/2]`: 구성 장치 2개 중 2개 활성.
- `[UU]`: 두 멤버 모두 정상 참여. `[U_]`, `[_U]`는 한쪽 멤버가 빠진 상태를 나타내는 비교 표기다.
- `bitmap`: write-intent bitmap이 활성화된 상태.

다른 시점의 `lsblk -f`에는 두 멤버 아래 동일한 `/dev/md1`과 XFS가 표시됐다. 두 개의 별도 XFS가 아니라 같은 RAID 장치를 트리에서 각각 보여준 것이다. `mdadm --detail /dev/md1`도 상세 조회 방법으로 안내받았으나 실행 출력은 없다.

## 5. RAID 오류·정리와 pvremove의 차이

### 실제 오류와 원인 확인

| 상황·오류 | 기록으로 확인한 의미 |
|---|---|
| RAID 생성 중 `Device or resource busy` | `lsblk -f`와 `/proc/mdstat`에서 두 디스크가 이미 활성 `/dev/md1`에 참여 중임을 확인 |
| `--zero-superblock` 실행 시 `Couldn't open ... for write - not zeroing` | 쓰기 접근을 확보하지 못해 메타데이터 제거가 수행되지 않음. “이미 삭제됨”을 뜻하지 않음 |
| `mdadm --stop /dev/md1`에서 `Cannot get exclusive access` | 사용 중인 장치의 독점 접근 실패. 실제 점유 주체는 로그만으로 확정하지 못함 |
| `mdadm --stop /dev/nvme0n3`에서 `does not appear to be an md device` | 멤버 물리 디스크를 RAID 장치 중지 대상으로 잘못 지정 |
| `pvremove /dev/nvme0n3`에서 `No PV found on device /dev/nvme0n3.` | 해당 디스크에서 제거할 LVM PV 정보를 찾지 못함 |

사용 여부와 마운트를 먼저 확인·해제한 뒤 RAID를 중지하는 순서를 안내받았다. 정확한 마운트 해제 명령의 성공 출력은 남아 있지 않다. 이후 사용자는 아래 세 명령을 모두 실행했다고 확인했다.

```bash
mdadm --stop /dev/md1
mdadm --zero-superblock /dev/nvme0n3
mdadm --zero-superblock /dev/nvme0n4
```

| 명령 | 대상·역할 |
|---|---|
| `mdadm --stop` | `/dev/md1` 같은 RAID 배열 중지 |
| `mdadm --zero-superblock` | 멤버 디스크의 RAID 메타데이터 제거 |
| `pvremove` | LVM Physical Volume 메타데이터 제거 |

RAID 정리에 `pvremove`를 대신 사용하는 것은 맞지 않는다. 메타데이터 제거가 디스크 전체 데이터의 안전한 완전 삭제를 의미하지도 않는다.

### 정리 후 실제 확인

```bash
pvs
lsblk -f
```

`pvs`에는 시스템용 `/dev/nvme0n1p3`와 VG `rl_rocky10`만 남았다. `lsblk -f`에서 `/dev/nvme0n3`, `/dev/nvme0n4` 아래에는 RAID·파일시스템 정보가 표시되지 않았다. 이 출력과 사용자의 실행 확인을 근거로 실습 RAID 정리 결과를 기록한다. 시스템 디스크의 LVM을 제거한 것은 아니다.

## 6. Swap 개념과 /etc/fstab 오타

Swap은 RAM의 일부 메모리 페이지를 옮겨 둘 수 있는 디스크 공간이다. RAM 확보를 보조하지만 RAM보다 느리며, 일반 파일시스템처럼 디렉터리에 마운트해 사용하는 공간은 아니다.

실제 Rocky의 `lsblk -f`에서 `rl_rocky10-swap`과 파일시스템 유형 `swap`을 확인했다. 이것만으로 현재 활성 여부나 사용량까지 확인되지는 않는다.

후속 대화에서 정리한 명령의 역할:

| 명령 | 의미 |
|---|---|
| `mkswap` | 지정 장치·파일에 Swap 영역 초기화 |
| `swapon` | Swap 활성화 |
| `swapoff` | Swap 비활성화 |
| `swapon --show` | 활성 Swap 조회 |
| `free -h` | 메모리·Swap 용량과 사용량 조회 |
| `swapoff -a` | 활성 Swap 전체 비활성화 시도 |
| `swapon -a` | `/etc/fstab`의 자동 활성화 대상 Swap 활성화 |

새 Swap 생성·활성화 성공 출력이나 새 장치명은 대화에 없다. [9/7 실습](../2026-09-07/실습.md#swap와-부팅-대상)에 있는 `swapoff -a`와 fstab 주석 처리 기록은 그 날짜에 유지한다.

`/etc/fstab`은 부팅 시 파일시스템·Swap을 설정하는 파일이다. Swap 행을 주석 처리하는 것은 다음 부팅의 자동 활성화 설정 변경이며, 지금 사용 중인 Swap을 즉시 끄는 `swapoff`와 역할이 다르다.

### /etc/stab을 열었더니 빈 화면

실제로 질문한 입력:

```bash
vi /etc/stab
```

올바른 파일명은 `/etc/fstab`이다. 존재하지 않는 경로를 vi로 열면 새 파일 편집 화면이 나오므로, 빈 화면만으로 기존 fstab이 지워졌다고 판단할 수 없다.

안내받은 해결 순서:

```vim
:q!
```

```bash
vi /etc/fstab
```

잘못 연 화면을 저장하지 않고 종료한 뒤 정확한 파일을 연다. 이 후속 대화에는 저장·복구 완료 출력이 없으며, `/etc/stab` 파일이 실제 생성됐는지도 확인되지 않았다.

## 7. Ubuntu에서 GitHub SSH 22번 거부와 443번 연결

### 실제 오류 변화

```bash
ssh -T git@github.com
```

```text
ssh: connect to host github.com port 22: Connection refused
```

이 단계는 키 인증 이전의 연결 거부다. VMware NAT 문제인지 질문했으나 정확한 거부 원인은 확인되지 않았다.

443번으로 접속:

```bash
ssh -T -p 443 git@ssh.github.com
```

호스트 키 확인 화면과 `known_hosts` 등록 메시지가 나온 뒤 다음 오류가 발생했다.

```text
git@ssh.github.com: Permission denied (publickey).
```

443번에서는 서버에 도달했지만 공개키 인증을 통과하지 못한 상태다. 22번 연결 거부와 구분한다.

### ED25519 키 생성·등록

`ls -la ~/.ssh`의 첫 출력에는 `authorized_keys`와 `known_hosts`만 있었다. 키 생성 방법을 안내받았다.

```bash
ssh-keygen -t ed25519 -C "github"
```

이후 실제 목록에서 `id_ed25519`와 `id_ed25519.pub` 생성이 확인됐다. 재접속은 여전히 `Permission denied (publickey)`여서 공개키 등록을 안내받았다.

```bash
cat ~/.ssh/id_ed25519.pub
```

GitHub의 **Settings → SSH and GPG keys → New SSH key**에 공개키를 등록하고 443번 인증을 다시 테스트하는 흐름이다. 이후 사용자가 “연결됐는데”라고 확인했으므로 연결 성공을 사용자 확인으로 기록한다. 등록 화면과 최종 인증 성공 출력 자체는 대화에 없다.

- `id_ed25519`: 개인키. 기술노트에 실제 내용을 저장하지 않는다.
- `id_ed25519.pub`: GitHub 계정에 등록하는 공개키.
- `authorized_keys`: 이 Ubuntu 계정으로 들어오는 SSH 로그인에 허용할 공개키 목록.
- `known_hosts`: 접속한 SSH 서버의 호스트 키 기록.

이번 명령은 Ubuntu `root`에서 실행했으므로 `/root/.ssh`를 사용했다. 다른 컴퓨터·사용자의 SSH 키 등록과는 별개다.

### 이후 안내받은 443번 기본 설정

`~/.ssh/config` 설정 예시:

```sshconfig
Host github.com
    HostName ssh.github.com
    User git
    Port 443
```

```bash
chmod 600 ~/.ssh/config
ssh -T git@github.com
```

이 설정은 일반 `git@github.com` 주소를 443번 SSH 연결로 연결한다. 설정 파일 저장·적용 출력과 당시 Git push 완료 출력은 없어 성공 사실로 추가하지 않았다.

## 핵심 정리

- `tar cf 백업파일 .`의 백업 대상은 실행 당시 현재 디렉터리다. 백업 후 목록을 확인해야 한다.
- 스냅샷의 파일 복사 성공과 스냅샷의 tar 백업 성공은 별도로 확인한다.
- 백업용 스냅샷은 검증된 백업을 확보한 뒤 필요에 따라 제거한다.
- `watch` 종료는 Ctrl+C다.
- `[UU]`는 RAID1 두 멤버의 정상 참여 표시다. RAID 정리와 LVM PV 제거는 다른 작업이다.
- Swap의 현재 활성 상태와 `/etc/fstab`의 부팅 설정을 구분한다. 파일명은 `/etc/fstab`이다.
- SSH 연결 거부는 연결 단계, `Permission denied (publickey)`는 인증 단계의 오류다.
