# 2. Amazon DynamoDB

## 2.1 DynamoDB란?

Amazon DynamoDB는 AWS에서 제공하는 **완전관리형 NoSQL 데이터베이스 서비스**다.

완전관리형이라는 것은 사용자가 직접 DB 서버를 설치하거나 OS 패치, 장애 복구, 확장 등을 관리할 필요가 거의 없다는 의미다.

```text
일반 DB 서버
사용자 → 서버/OS/DB 직접 관리

DynamoDB
사용자 → Table과 데이터 중심으로 사용
AWS    → 서버, 스토리지, 확장, 가용성 관리
```

### 주요 특징

- NoSQL 기반 Key-Value / Document 데이터베이스
- 완전관리형 서비스
- 자동 확장 지원
- SSD 기반 저장
- 여러 AZ에 데이터를 복제하여 고가용성 제공
- 서버를 직접 생성하지 않고 Table 중심으로 사용

---

## 2.2 DynamoDB 주요 용어

### Item

RDBMS의 `행(Row)`과 비슷한 개념이다.

예:

```json
{
  "id": 100,
  "name": "jongil",
  "age": 30,
  "hobby": "golf"
}
```

이 전체 데이터 한 묶음이 하나의 Item이다.

### Attribute

Item을 구성하는 각각의 데이터 필드이다.

```text
id
name
age
hobby
```

RDBMS의 Column과 비슷하게 이해할 수 있다.

### Partition Key

DynamoDB에서 Item을 구분하고 저장 위치를 결정하는 핵심 키이다.

예:

```text
id = 100
```

Partition Key는 특정 Item을 빠르게 찾을 수 있도록 하는 기본 Key이다.

### Sort Key

같은 Partition Key를 가진 여러 Item을 정렬하거나 세부적으로 구분할 때 사용한다.

예:

```text
Partition Key : user_id
Sort Key      : created_at
```

---

## 2.3 Partition Key + Sort Key 예

실습 Table:

```text
Table Name    : lsm-demo
Partition Key : id   (Number)
Sort Key      : name (String)
```

Item:

```text
id    = 100
name  = jongil
age   = 30
hobby = golf
```

---

## 2.4 Query vs Scan

### Query

Partition Key를 기준으로 데이터를 조회한다.

```text
Partition Key
     ↓
특정 범위의 Item 조회
```

Sort Key까지 함께 사용하면 더욱 세부적인 조건 조회가 가능하다.

### Scan

Table 전체를 읽으면서 조건에 맞는 데이터를 찾는다.

```text
전체 Table 읽기
     ↓
Filter 적용
```

따라서 일반적으로 대량 데이터에서는 Query가 Scan보다 효율적이다.

### Filter

DynamoDB에서 조회된 결과에 추가 조건을 적용할 수 있다.

```text
Query / Scan
      ↓
결과 반환
      ↓
Filter 적용
```

---

## 2.5 읽기 일관성

### Eventually Consistent Read

데이터 변경 직후 모든 복제본에 변경 사항이 바로 반영되지 않을 수 있다.

```text
Write
 ↓
복제 진행
 ↓
잠시 이전 값이 조회될 가능성
```

일정 시간이 지나면 최신 데이터로 수렴한다.

### Strongly Consistent Read

읽기 요청 시점 이전의 변경 내용을 반영한 최신 데이터를 반환하도록 한다.

정합성이 중요할 때 사용할 수 있지만 비용과 처리량 측면을 함께 고려해야 한다.

---

## 2.6 Capacity Mode

### On-Demand

실제 요청량에 따라 자동 처리되며 사용량 기준으로 비용이 발생한다.

```text
트래픽 적음 → 적게 사용
트래픽 증가 → 자동 대응
```

### Provisioned

미리 읽기/쓰기 처리량을 지정한다.

```text
RCU / WCU 사전 설정
```

트래픽이 일정하거나 예측 가능할 때 활용할 수 있다.

<a id="section-3"></a>
# 3. Serverless Architecture

## 3.1 기본 서버리스 구조

대표적인 서버리스 구조:

```text
Client
  ↓
API Gateway
  ↓
Lambda
  ↓
DynamoDB
```

### API Gateway

외부 요청을 받아 Backend 서비스로 전달하는 API 입구이다.

```text
GET /users
POST /users
PUT /todo/1
DELETE /users/1
```

API Gateway가 요청을 받고 Lambda 등 Backend 서비스에 전달한다.

### Lambda

서버를 직접 생성하거나 운영하지 않고 코드를 실행할 수 있는 AWS Serverless Compute 서비스이다.

```text
Event 발생
   ↓
Lambda 실행
   ↓
Code 실행
   ↓
작업 완료 후 종료
```

예:

```text
API Gateway 요청
→ Lambda
→ DynamoDB 조회/수정
```

---

## 3.2 Event-driven Architecture

### 동기식

```text
Client
  ↓
API Gateway
  ↓
Lambda
  ↓
DynamoDB
  ↓
응답
  ↓
Client
```

작업이 완료된 뒤 결과를 반환한다.

### 비동기식

```text
Client
  ↓
API Gateway
  ↓
EventBridge
  ↓
빠른 응답

EventBridge
  ↓
Lambda
  ↓
Backend 처리
```

사용자 요청과 실제 작업 처리를 분리할 수 있다.

---

## 3.3 Fan-out

하나의 이벤트를 여러 처리 경로로 분배하는 패턴이다.

```text
Event
  ↓
EventBridge
  ├─ Status=Created   → SQS → Lambda
  ├─ Status=Processed → SQS → Lambda
  └─ Status=Refunded  → SQS → Lambda
```

### EventBridge

이벤트의 내용에 따라 적절한 Target으로 라우팅한다.

### SQS

메시지를 Queue에 저장하여 생산자와 소비자를 분리한다.

```text
Producer
  ↓
SQS
  ↓
Consumer
```

갑자기 요청량이 증가해도 메시지를 Queue에 쌓아두고 Backend가 처리 가능한 속도로 소비할 수 있다.

### DLQ

Dead Letter Queue.

정상 처리되지 못한 메시지를 별도로 저장하여 추후 확인할 수 있다.

# 4. AWS SAM

AWS SAM(Serverless Application Model)은 서버리스 애플리케이션을 코드로 정의하고 배포하기 위한 도구이다.

## 4.1 CloudFormation과 차이

SAM은 CloudFormation 기반이며 다음 Transform 구문을 추가한다.

```yaml
AWSTemplateFormatVersion: '2010-09-09'
Transform: AWS::Serverless-2016-10-31
```

CloudFormation:

```yaml
Type: AWS::Lambda::Function
```

SAM:

```yaml
Type: AWS::Serverless::Function
```

서버리스 리소스를 더 간단하게 작성할 수 있다.

### 기억할 것

```text
SAM
= CloudFormation 기반
+ Transform
+ AWS::Serverless::* 간편 문법
```

---

## 4.2 SAM CLI

대표 명령:

```bash
sam build
```

애플리케이션 빌드

```bash
sam local start-api
```

로컬 API 실행

```bash
sam deploy
```

AWS에 배포

<a id="section-5"></a>
# 5. AWS Cloud Adoption Framework (CAF)

AWS CAF는 조직이 AWS Cloud를 도입하거나 마이그레이션할 때 참고하는 프레임워크이다.

6개의 관점으로 구성된다.

| 관점 | 핵심 내용 |
|---|---|
| Business | Cloud 투자가 Business 목표와 연결되는지 확인 |
| People | 조직, 인력, 교육, 변화관리 |
| Governance | 정책, 비용, 위험, IT 전략 관리 |
| Platform | Cloud Architecture 및 Migration 설계 |
| Security | IAM, 보안 통제, 감사, 보안 목표 |
| Operations | 운영, 모니터링, 장애 대응, 복구 |

### 한 줄 요약

```text
AWS CAF
= Cloud 도입/마이그레이션을
Business / People / Governance /
Platform / Security / Operations
관점에서 점검하는 Framework
```

<a id="section-6"></a>
# 6. AWS Migration Strategy

## 6.1 6R 전략

### Rehost

Lift-and-Shift.

기존 시스템 구조를 거의 변경하지 않고 Cloud로 이전한다.

```text
On-Premise VM
     ↓
Amazon EC2
```

### Replatform

큰 구조는 유지하면서 일부를 Cloud Managed Service로 전환한다.

```text
직접 운영 MySQL
      ↓
Amazon RDS
```

또는:

```text
기존 Application
      ↓
Container Service
```

### Refactor

Application 구조 자체를 Cloud Native 방식으로 재설계한다.

```text
기존 Monolithic App
        ↓
API Gateway + Lambda + DynamoDB
```

### Repurchase

기존 시스템을 SaaS 서비스 등으로 교체한다.

### Retain

당장 Cloud로 이동하지 않고 기존 환경에 유지한다.

### Retire

더 이상 필요 없는 Application을 폐기한다.

### 정리

```text
Rehost     = 그대로 옮김
Replatform = 조금 수정해서 옮김
Refactor   = 구조까지 재설계
Repurchase = 다른 제품/SaaS 구매
Retain     = 기존 환경 유지
Retire     = 폐기
```

# 7. AWS 데이터 마이그레이션 서비스

## 7.1 AWS Storage Gateway

On-Premise와 AWS Storage를 연결하는 Hybrid Storage 서비스이다.

대표 형태:

- File Gateway
- Volume Gateway
- Tape Gateway

File Gateway는 On-Premise Application이 NFS/SMB처럼 파일을 사용하면서 실제 데이터를 S3에 저장할 수 있도록 한다.

```text
Application
  ↓ NFS/SMB
File Gateway
  ↓
S3
```

---

## 7.2 AWS DataSync

On-Premise 또는 다른 Storage에서 AWS Storage로 데이터를 자동 전송하는 서비스이다.

```text
NFS/SMB
  ↓
DataSync Agent
  ↓
AWS DataSync
  ↓
S3 / EFS / FSx
```

### rsync와 차이

| rsync | AWS DataSync |
|---|---|
| Linux 명령어 | AWS 관리형 서비스 |
| 직접 Script 관리 | AWS에서 Task 관리 |
| 서버/SSH 관리 필요 | 관리형 전송 |
| 파일 동기화 | 대규모 Migration에 적합 |
| cron 등 직접 구성 | 예약/모니터링 기능 제공 |

---

## 7.3 Transfer Family

SFTP, FTPS, FTP 기반 전송 Workflow를 AWS Storage와 연결할 수 있는 서비스이다.

예:

```text
SFTP Client
    ↓
AWS Transfer Family
    ↓
S3 / EFS
```

# 8. Amazon CloudFront

CloudFront는 AWS의 CDN(Content Delivery Network) 서비스이다.

## 8.1 기본 동작

```text
User
  ↓
Nearest Edge Location
  ↓
Cache Hit?
 ├─ Yes → 바로 반환
 └─ No  → Origin에서 가져옴
              ↓
            Cache
              ↓
            User
```

### Origin

원본 콘텐츠가 있는 위치.

예:

- S3
- ALB
- EC2
- External HTTP Server

### Edge Location

사용자 가까이에 위치한 CloudFront 캐시 거점이다.

### Distribution

CloudFront의 하나의 배포 구성 단위이다.

### TTL

CloudFront Cache 유지 시간을 결정한다.

# 9. CloudFront 보안

## 9.1 OAI / OAC 개념

S3를 Public으로 직접 노출하지 않고 CloudFront를 통해서만 접근하도록 제한할 수 있다.

```text
User → S3 직접            X
User → CloudFront → S3    O
```

기존에는 OAI(Origin Access Identity)를 많이 사용했으며 현재는 OAC(Origin Access Control)를 사용하는 방식이 일반적이다.

```text

?Expires=...
&Signature=...
```

<a id="section-15"></a>
# 15. 504 Gateway Time-out Troubleshooting

처음 ALB 주소로 접속했을 때:

```text
504 Gateway Time-out
```

발생.

Target Group 상태:

```text
Unhealthy
```

원인은 EC2 Security Group에 ALB가 Backend 3000 Port로 접근할 수 있는 규칙이 없었기 때문이다.

해결:

```text
EC2 SG
Custom TCP : 3000
Source     : 3tier-alb-sg
```

추가.

잠시 후 Target 상태:

```text
Healthy
```

로 변경.

<a id="section-17"></a>
# 17. Frontend를 S3로 Migration

기존에는 Frontend를 Docker Nginx Container에서 실행했다.

```text
EC2
├─ frontend : 80
├─ backend  : 3000
└─ mysql    : 3306
```

Frontend를 S3 Static Website로 이동했다.

```text
S3 Bucket : web-lsm123
```

`index.html`의 API 주소를 ALB DNS로 수정:

```javascript
fetch('http://<ALB-DNS>/api')
```

# 29. 이번 실습에서 이해한 핵심

## ALB

Application Load Balancer.

```text
HTTP/HTTPS 요청
   ↓
ALB
   ↓
Healthy Target
```

이번 실습:

```text
ALB :80
 ↓
Target Group
 ↓
EC2 Backend :3000
```

## Target Group

ALB가 요청을 전달할 실제 Backend 대상의 묶음이다.

```text
Target Group
├─ EC2-1 :3000
├─ EC2-2 :3000
└─ EC2-3 :3000
```

Health Check를 통해 정상 서버에만 요청을 전달할 수 있다.

## CloudFront

사용자와 Origin 사이에 위치하여 콘텐츠를 Edge Location에서 제공하는 CDN 서비스이다.

```text
User
 ↓
CloudFront
 ↓
Origin
```

## S3

이번 실습에서는 Frontend 정적 파일 저장 및 Hosting 역할.

## Backend

Node.js Application이 API 요청을 처리한다.

## MySQL

실제 Data를 저장한다.

<a id="section-30"></a>
# 30. 주요 Troubleshooting 정리

## 30.1 Backend `Cannot GET /`

증상:

```bash
curl http://localhost:3000
```

```text
Cannot GET /
```

원인:

Backend Application에 `/` GET Route가 없음.

해결:

```bash
curl http://localhost:3000/api
```

실제 API Route 사용.

---

## 30.2 ALB 504 Gateway Time-out

증상:

```text
504 Gateway Time-out
```

Target Group:

```text
Unhealthy
```

원인:

ALB Security Group에서 Backend EC2의 3000 Port로 접근할 수 없었음.

해결:

Backend EC2 SG:

```text
Custom TCP
Port : 3000
Source : 3tier-alb-sg
```

추가.

결과:

```text
Unhealthy
   ↓
Healthy
```

---

## 30.3 HTTP ALB API를 HTTPS CloudFront에서 호출

CloudFront Frontend는 HTTPS이므로 HTML에서 HTTP ALB API를 직접 호출하면 Browser Mixed Content 문제가 발생할 수 있다.

해결:

```text
Frontend CloudFront
      ↓
Backend CloudFront
      ↓
ALB
```

Backend CloudFront HTTPS 주소를 `fetch()`에서 사용.

---

## 30.4 CloudFront에 수정된 HTML이 반영되지 않음

원인:

Edge Cache에 이전 HTML이 남아 있음.

해결:

```text
CloudFront
→ Invalidations
→ /index-cloudfront.html
```

또는:

```text
/*
```

<a id="section-31"></a>
# 31. Resource Cleanup

실습 후 불필요한 요금을 방지하기 위해 리소스를 정리한다.

## DynamoDB

실습 Table 삭제.

## EC2

계속 사용할 필요가 없다면:

```text
EC2 → ktcloud-vm → Stop
```

주의:

EC2를 Stop하더라도 EBS Storage 비용은 계속 발생할 수 있다.

## ALB

ALB는 Stop 기능이 없으므로 사용하지 않으면 삭제한다.

```text
EC2
→ Load Balancers
→ 3tier-alb
→ Actions
→ Delete load balancer
```

## Target Group

ALB 삭제 후 필요 없다면:

```text
EC2
→ Target Groups
→ 3tier
→ Delete
```

## CloudFront

실습용 Distribution이 더 이상 필요 없다면 Disable 후 삭제를 검토한다.

이번 실습에서 생성한 Distribution:

```text
Frontend CloudFront
Backend API CloudFront
```

## S3

학습 자료로 유지할 경우 남겨도 되지만 완전히 정리하려면:

```text
Object 삭제
→ Bucket 삭제
```

## Elastic IP / Public IPv4

사용하지 않는 Elastic IP가 남아 있는지 확인한다.

## NAT Gateway / RDS / EFS

이전 실습 리소스가 남아 있으면 별도 요금이 발생할 수 있으므로 확인한다.
