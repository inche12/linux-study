# 2026년 9월 14일 — Linux 네트워크와 Wireshark 실습

사용자가 제공한 터미널 출력·강의 이미지·패킷 캡처를 정리했다. **실제 관찰 결과와 설명용 예시를 구분**한다. AWS 로그인 관련 대화는 제외했다. 아래 명령은 기록이며 모든 예시를 실행한 것은 아니다.

## 2. SSH와 관련 파일

SSH 흐름: TCP 연결 → 알고리즘 협의·키 교환·서버 신원 검증 → 암호화 시작 → 사용자 인증 → 명령 실행·파일 전송. **비밀번호 인증 전에 암호화가 시작된다.** 서버 호스트 키와 사용자 인증 키는 역할이 다르다.

| 경로 | 역할 |
|---|---|
| `/etc/services` | 서비스 이름과 표준 포트 번호 목록. 수정해도 실제 리슨 포트는 바뀌지 않음 |
| `/etc/ssh/sshd_config` | SSH 서버 설정 |
| `/etc/ssh/ssh_config` | SSH 클라이언트의 공통 설정 |
| `/etc/ssh/sshd_config.d/` | 서버 추가 설정 |
| `/etc/ssh/ssh_host_*` | 서버 호스트 키. `.pub`은 공개키 |
| `~/.ssh/known_hosts` | 클라이언트가 기억하는 서버 키 |
| `~/.ssh/authorized_keys` | 해당 계정에 접속을 허용할 사용자 공개키 |
| `~/.ssh/id_rsa`, `id_ed25519` | 사용자 개인키. 서버로 전송하지 않음 |

`~`는 현재 사용자의 홈이며 root는 보통 `/root`, student는 보통 `/home/student`이다. `~student`는 student의 홈을 뜻한다. 점으로 시작하는 `.ssh`는 숨김 디렉터리다.

### SSH 220번을 22번으로 되돌리는 절차 — 안내 예시

기존 SSH 창을 유지하고, 방화벽·접근 규칙에서 TCP 22를 허용한 뒤 진행한다.

```bash
vi /etc/ssh/sshd_config
# 기존 Port 220을 Port 22로 수정
sshd -t
systemctl restart sshd   # Rocky
# systemctl restart ssh # Ubuntu/Debian
ss -lntp 'sport = :22'
```

새 터미널에서 `ssh -p 22 사용자명@서버IP`로 확인한다. 추가 설정이나 Ubuntu의 ssh.socket 사용 여부에 따라 적용 절차가 달라질 수 있다. 이후 실제 Nmap 결과에서는 Ubuntu의 TCP 22가 열려 있었다.

`ss -lntp`: 리슨 중(`-l`)인 TCP(`-t`) 소켓을 숫자(`-n`)와 프로세스(`-p`)로 표시한다. LISTEN은 방화벽 허용을 보장하지 않는다.

## 3. VPN·LAMP 기본 개념

| 개념 | 의미 |
|---|---|
| Client-to-Site VPN | 개인 PC와 네트워크 연결. 온프레미스·클라우드 모두 가능 |
| Site-to-Site VPN | 네트워크끼리 연결. 본사–지사 또는 온프레미스–클라우드 |
| 하이브리드 환경 | 온프레미스와 클라우드를 함께 사용하는 환경 |
| SSH 포트 포워딩 | 특정 TCP 서비스의 통신을 SSH 연결로 전달 |

VPN 두 형태는 SSH 터널링의 하위 분류가 아니다. Site-to-Site는 하이브리드 연결에 쓰이지만 그 자체가 하이브리드와 동의어는 아니다.

LAMP: Linux(운영체제), Apache(웹 요청·응답), MySQL(데이터 저장), PHP(서버 측 프로그램). 동적 요청은 Apache → PHP 실행 환경 → DB 조회·HTML 생성 → Apache 응답 순으로 처리할 수 있다. 클라이언트에는 PHP 소스가 아닌 실행 결과가 전달된다.

## 4. 호스트 이름 조회

실제 `/etc/hosts` 등록:

```text
192.168.120.129 ubuntu u1
```

Ubuntu에서 확인한 `/etc/nsswitch.conf`:

```text
hosts: files dns
```

| 명령 | 조회 방법 |
|---|---|
| `nslookup`, `dig` | DNS 서버에 직접 질의 |
| `getent hosts u1` | NSS 설정 순서에 따라 파일·DNS 등 사용 |

`files dns`는 `/etc/hosts`를 먼저 보고 해당 항목이 없으면 DNS를 사용한다. 항상 두 곳을 동시에 조회한다는 뜻은 아니다. 머신별 hosts 파일은 자동 공유되지 않는다.

Rocky에서 `ping rocky10`은 `fe80::e6c5:2e1d:f7a9:6c08%ens160`으로 응답했다. `/etc/hosts`에 자기 이름이 없어도 `myhostname` 같은 NSS 기능으로 해석될 수 있으나, 실제 사용된 방법은 출력만으로 확정하지 않았다.

```bash
hostname
grep '^hosts:' /etc/nsswitch.conf
ip -6 addr show dev ens160
```

`systemd-hostnamed`는 호스트 이름 관리 서비스다. `list-unit-files`의 static은 고정 IP나 실행 중이라는 뜻이 아니다. alias는 다른 유닛을 가리키는 별칭이다.

## 5. FTP로 루트 힌트 파일 받기 — 실제 실행

Ubuntu의 `/etc/ssh`에서 다음 순서로 실행했다.

```text
ftp ftp.internic.org
Name: anonymous
ftp> cd domain
ftp> dir
ftp> get named.cache
226 Transfer complete.
3315 bytes received
ftp> bye
```

`notepad named.cache`는 Ubuntu에 해당 명령이 없어 실패했다. `cat named.cache`로 정상 확인했다. 파일은 로컬 작업 디렉터리인 `/etc/ssh/named.cache`에 저장됐다. FTP의 `cd domain`은 원격 디렉터리만 바꾼다.

파일에는 A~M 루트 서버의 NS·A·AAAA가 있었다. 이는 DNS 재귀 조회를 시작하는 데 사용하는 **루트 힌트**이며, 내려받는 것만으로 DNS 서버 설정에 적용되지 않는다. 파일에 표시된 마지막 갱신일은 2026-09-10, 관련 루트 존 버전은 2026091001이었다.

```dns
.                   3600000 IN NS A.ROOT-SERVERS.NET.
A.ROOT-SERVERS.NET.  3600000 IN A  198.41.0.4
A.ROOT-SERVERS.NET.  3600000 IN AAAA 2001:503:ba3e::2:30
```

## 6. 정방향·역방향 존 파일 — 강의 예시

정방향은 이름 → 주소, 역방향은 주소 → 이름이다. A·AAAA·PTR은 별도 레코드이므로 자동으로 함께 생기지 않는다.

### 정방향 example.com 존

아래는 강의의 SOA 주 서버 이름을 NS와 일치하도록 정리한 예시다.

```dns
$TTL 86400
@ IN SOA server1.example.com. root.example.com. (
    2012012001 ; Serial
    28800      ; Refresh
    14400      ; Retry
    3600000    ; Expire
    600        ; Negative cache TTL
)
@         IN NS server1.example.com.
localhost IN A 127.0.0.1
server1   IN A 10.100.0.254
```

- `@`: 현재 존의 기준 이름. 이 예에서는 `example.com.`이다.
- `IN`: 인터넷 클래스, `SOA`: 존 관리 정보, `NS`: 담당 DNS 서버.
- `root.example.com.`: 관리자 이메일 `root@example.com`의 DNS 표기.
- TTL 86400은 기본 캐시 시간 1일. Serial은 데이터 수정 시 증가시킨다.
- Refresh 8시간, Retry 4시간, Expire 약 41.7일은 보조 DNS의 갱신 관련 값이다.
- 음성 캐시 TTL은 SOA TTL과 마지막 값 중 작은 값으로 정한다.
- 끝에 점이 없는 이름에는 현재 존 이름이 붙는다. `localhost`는 여기서 `localhost.example.com.`이다.

### 역방향 0.100.10.in-addr.arpa 존

```dns
254 IN PTR server1.example.com.
$GENERATE 1-45 $ PTR station$.example.com.
```

`10.100.0.254`의 역방향 이름은 `254.0.100.10.in-addr.arpa.`이다. `$GENERATE`는 1~45에 대응하는 station1~station45 레코드를 생성한다. 실제 사용하려면 BIND 설정에서 존 이름과 파일을 연결해야 한다.

```bash
dig @DNS서버IP -x 10.100.0.254
```

## 7. Unbound 캐시·포워딩 서버 — 강의 예시

```yaml
server:
    interface: 192.168.108.152
    access-control: 192.168.108.0/24 allow
    # 필요한 영역만 DNSSEC 검증 예외로 지정
    # domain-insecure: "domain.com"
forward-zone:
    name: "."
    forward-addr: 192.168.108.2
```

캐시에 유효한 답이 있으면 직접 응답하고, 없으면 상위 DNS에 전달한다. interface는 자신의 수신 주소, access-control은 허용 클라이언트 범위, forward-addr는 상위 DNS다. `domain-insecure`는 DNSSEC 검증 예외이며 필수 설정이 아니다. `forward-zone`의 forward는 다른 서버로 전달한다는 뜻으로 정방향 조회와 다르다.

```bash
dnf install -y unbound
unbound-checkconf
systemctl enable --now unbound
# 설정 변경 후 검사에 통과하면
systemctl restart unbound
```

실제 네트워크에 맞게 주소를 바꾸고, 외부 클라이언트가 이용하려면 방화벽의 UDP·TCP 53도 확인한다.

## 8. nslookup·dig — 실제 결과

기본 DNS는 `192.168.120.2#53`이었다.

```text
nslookup
> naver.com
> google.com
> set type=ns
> naver.com
> set type=mx
> naver.com
> exit
```

- naver.com A: `223.130.200.219`, `223.130.192.248`, `223.130.192.247`, `223.130.200.236`.
- google.com은 IPv4와 IPv6 주소가 모두 반환됐다.
- 네이버 NS: ns1, ns2, ns3.naver.com. 각 주소는 `61.247.220.6`, `61.247.221.6`, `211.188.44.6`.
- MX: 우선순위 10의 mx1.mail.naver.com, 20의 mx5·mx4·mx6.mail.naver.com. 숫자가 낮을수록 우선한다.
- Non-authoritative는 해당 존의 권한 서버가 직접 권한 응답한 것이 아니라는 뜻이지, 잘못된 답이라는 뜻은 아니다. 위 주소는 실습 시점 관찰값이다.

```bash
dig @8.8.8.8
dig @8.8.8.8 naver.com
dig +trace google.com
```

첫 명령은 루트 `.`의 NS를 조회해 13개 이름을 받았다. TTL 87203, UDP, 52ms였다. 두 번째는 기본 A 조회로 4개 주소를 받았고 TTL 254, 55ms였다. TTL은 캐시에 남은 시간일 수 있다.

`+trace`는 루트 → .com → google.com 권한 서버 순으로 위임을 따라갔다. 루트 요청 시간 초과와 IPv6 network unreachable이 있었으나 이후 IPv4 응답으로 진행해 ns2.google.com에서 최종 A 레코드를 받았다. 일부 시도 실패가 전체 조회 실패를 뜻하지 않았다.

## 9. traceroute·TTL·방화벽

Windows `tracert`는 ICMP Echo, Linux의 일반적인 `traceroute` 기본값은 UDP 탐색이다. TTL을 1, 2, 3…으로 증가시키고 중간 라우터의 ICMP Time Exceeded 응답을 이용한다. 각 행의 세 시간은 세 탐색에 대한 왕복 시간이다.

Windows는 첫 홉 `192.168.0.1` 이후 여러 라우터가 표시됐다. Rocky는 첫 홉 `192.168.120.2` 이후 `*`가 이어졌다. 두 환경은 가상 NAT 경로와 프로토콜이 달라 **하이퍼바이저 차단으로 확정할 수 없다.** `*`는 제한 시간 내 응답 부재이며, 필터링·응답 제한·손실·NAT 처리 등이 원인일 수 있다.

비교용 안내 명령(실행 결과는 제공되지 않음):

```bash
traceroute -n -I -m 12 -w 1 172.217.209.139
traceroute -n -T -p 443 -m 12 -w 1 172.217.209.139
```

DNS TTL은 캐시 시간이고 IP TTL은 홉 제한이다. 스위치는 IP TTL을 줄이지 않는다. 방화벽이 ICMP를 제한하면서 HTTPS TCP 443은 허용할 수 있으므로 경로 추적 실패와 웹 접속 실패는 다르다.

## 10. SELinux — 강의 예시

```bash
getenforce
getsebool -a | grep http
chcon -t admin_home_t myfile
semanage fcontext -a -t admin_home_t '/root/myfile'
restorecon -v /root/myfile
semanage port -l | grep http_port_t
# 미등록 포트일 때 추가하는 예시
semanage port -a -t http_port_t -p tcp 808
```

- Enforcing은 정책 위반 차단, Permissive는 기록 위주, Disabled는 비활성화.
- chcon은 현재 라벨 변경, semanage fcontext는 경로별 지속 규칙 등록, restorecon은 규칙 적용.
- 강의의 상대 경로 myfile은 실제 사용 시 절대 경로로 지정한다.
- `restorecon -RFvv`: 재귀, 전체 컨텍스트 재설정, 상세 출력.
- HTTP 808 포트 등록은 Apache의 Listen 설정이나 방화벽 개방을 대신하지 않는다. 기존 포트 타입을 확인한 후 변경한다.
- SSH 비표준 포트도 ssh_port_t 매핑을 확인한다. SELinux·서비스 리슨 설정·방화벽은 별도다.

## 11. Nmap·RPC·nc

`nmap: 명령을 찾을 수 없습니다` 이후 설치 안내는 `dnf install -y nmap`이었다. 이어 제공된 결과에서는 Nmap 7.92가 실행됐다.

```bash
nmap -O u1
nmap --iflist
rpcinfo -t u1 100003
nmap -sSUVR -O -p U:53,111,T:21-25,80 u1
```

첫 스캔: TCP 22(ssh), 80(http), 111(rpcbind), 2049(nfs) 열림. 기본 검사한 나머지 996개 TCP 포트는 닫힘. 서비스 이름만으로 실제 프로그램을 확정하지 않는다.

버전 스캔: OpenSSH 9.6p1 Ubuntu 3ubuntu13.19, Apache 2.4.58 Ubuntu, UDP 111 rpcbind 2–4. TCP 21·23·24·25와 UDP 53은 closed. TCP 53과 389는 이 검사 범위에 없었다. Linux 4.15–5.6은 OS 추정값이며 실제 커널 버전은 `uname -r`로 확인한다.

`-sS` TCP SYN, `-sU` UDP, `-sV` 버전, `-O` OS 추정. `-sR`은 현재 -sV 별칭이라는 경고가 표시됐다. 중복 제거 예시:

```bash
nmap -sS -sU -sV -O -p U:53,111,T:21-25,80 u1
```

`rpcinfo -t u1 100003`에서 NFS 프로그램의 버전 3·4가 ready and waiting으로 응답했다. 100003은 포트가 아니라 RPC 프로그램 번호다. 마운트나 파일 접근 성공까지 확인한 것은 아니다.

### 주소 오타

실제 입력은 `nmap -sP 102.168.120.0/24`였다. 실습망은 **192.168.120.0/24**이며 102로 시작하는 것은 다른 공인 범위다. 출력만으로 발견된 호스트의 실체를 확정하지 않는다. 자신의 실습망 호스트 발견용으로는 다음을 사용한다.

```bash
nmap -sn 192.168.120.0/24
```

### 임시 리스너 확인

```bash
# Ubuntu
nc -l 389
# Rocky
nc -z -v u1 389
```

Connected to 192.168.120.129:389, 0 bytes sent/received로 TCP 연결이 성공했다. 389는 일반적으로 LDAP 포트지만 이번 서비스는 nc이며 LDAP 서버가 아니다.

## 12. lsof·작업 제어·fuser

```bash
lsof -c /nfs/ -a -U
lsof -N
lsof +d /var/
lsof +D /var
lsof -e /run/user/1000/gvfs -e /run/user/1000/doc +D /var/log
lsof -iUDP@localhost
```

| 옵션 | 의미 |
|---|---|
| `-c /nfs/ -a -U` | 이름에 nfs가 있는 프로세스 AND UNIX 소켓. /nfs/는 정규식 |
| `-N` | NFS 파일시스템에서 프로세스가 연 파일 |
| `+d` | 지정 디렉터리와 바로 아래 항목 |
| `+D` | 하위 디렉터리 재귀 검색 |
| `-e 경로` | 해당 파일시스템에 대한 일부 블로킹 조회를 제외 |
| `-iUDP@localhost` | localhost 관련 UDP 소켓 |

`can't stat() fuse.gvfsd-fuse`와 `fuse.portal`은 사용자 FUSE 마운트 조회 경고다. root도 마운트 접근 제한을 받을 수 있다. 명령 전체가 실패했다는 뜻은 아니다.

`+d /var`는 결과 없이 반환했고 `+D /var`는 Ctrl+Z로 정지했다. 제외 옵션과 /var/log 범위로 바꾼 명령은 auditd·firewalld·httpd·rsyslogd·VMware 도구·PCP 등의 열린 로그를 출력했다. 두 조건을 동시에 바꿨으므로 성공 원인을 FUSE 하나로 단정하지 않는다.

이후 `fg %6`으로 재개한 /var 전체 검색도 결과를 출력했다. 다만 `/var/lib/selinux/targeted/active/modules/100/unprivuser/cil`에 대해 can't lstat / Connection timed out이 있었다. 경로에 selinux가 있다는 이유로 정책 차단이라고 확정할 수 없다.

`httpd ... 7w ... access_log`: 파일 디스크립터 7을 쓰기 모드로 열고 있음. `u`는 읽기·쓰기, `cwd`는 현재 작업 디렉터리다.

UDP 결과: chronyd가 IPv4·IPv6 localhost:323, rpc.statd가 IPv4 localhost:721을 사용했다. 이는 각 프로그램이 그 소켓을 열고 있다는 뜻이며 외부 접근 허용을 뜻하지 않는다.

```bash
jobs
fg %6
# 해당 작업이 앞으로 오면 Ctrl+C로 중단
```

Ctrl+Z는 중단(suspend), Ctrl+C는 현재 포그라운드 작업에 인터럽트를 보낸다. 프롬프트에서 Ctrl+C를 눌러도 정지된 작업은 종료되지 않는다. 작업 번호는 jobs로 확인한다.

`fuser -m ~student`도 실행했다. -m은 해당 경로가 속한 파일시스템을 사용하는 프로세스를 조회하므로 홈 폴더 하위만 검색하는 것과 다르다. c는 현재 디렉터리, m은 메모리 매핑 관련 사용 표시다.

## 13. ARP·이웃 테이블

```bash
arp -a
arp -an
ip neigh list
```

Ubuntu는 `192.168.120.129 → 00:0c:29:25:c6:5a`, 게이트웨이는 `192.168.120.2 → 00:50:56:e9:56:13`으로 확인됐다. STALE은 재확인이 필요한 캐시 상태이지 즉시 연결 실패를 뜻하지 않고, REACHABLE은 최근 도달 가능성이 확인된 상태다.

## 14. SIP·DIP·SNAT·DNAT — 강의 그림

그림 예시의 내부 PC는 10.1.0.1, NAT 외부 주소는 67.2.10.12, 웹 서버는 74.125.224.143이다. 실제 VM 주소와 구분한다.

| 시점 | SIP(출발지) | DIP(목적지) |
|---|---|---|
| 외부 요청 전 | 10.1.0.1 | 74.125.224.143 |
| SNAT 후 | 67.2.10.12 | 74.125.224.143 |
| 서버 응답 | 74.125.224.143 | 67.2.10.12 |
| 기존 NAT의 역변환 후 | 74.125.224.143 | 10.1.0.1 |

응답 방향 역변환을 위해 별도 포트 포워딩을 만드는 것은 아니다. 별도의 DNAT 예시는 외부에서 67.2.10.12:80으로 들어온 연결의 목적지를 내부 10.1.0.1:80으로 바꾸는 설정이다. 그림만으로 DNAT 규칙의 존재는 확인되지 않았다.

일반 라우팅에서는 IP 목적지가 유지되고 MAC은 이더넷 구간별로 바뀐다. NAT 지점에서는 IP·필요시 포트도 바뀐다.

## 15. VM 저장 공간

VM 프로그램 설치 데이터는 가상 디스크에 저장된다. 그 파일이 C:에 있으면 C:를 사용하며 동적 디스크는 쓰기에 따라 커질 수 있다. 고정 할당은 이미 공간을 확보했을 수 있다. 게스트에서 삭제해도 호스트의 가상 디스크 크기가 자동으로 줄지 않을 수 있다.

C:가 가득 차도 D:로 자동 이동하지 않는다. 추가 공간이 필요하면 설치 실패나 VM 정지가 발생할 수 있다. 이동할 경우 VM을 완전히 종료하고 가상머신 파일을 적절한 방식으로 옮겨 등록한다.
