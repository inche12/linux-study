## 1. 캡처 범위와 확인 방법

사용자가 제공한 원본은 `9.14 네이버, 핑연습.pcapng`이며 53,640바이트다. VMnet8에서 캡처한 파일을 tshark로 다시 읽어 **338개 프레임, 프레임 길이 합계 41,688바이트**를 확인했다. 파일 크기에는 pcapng 메타데이터 등이 포함되므로 패킷 바이트 합계와 다르다.

| 프로토콜 | 패킷 수 | 전체 338개 대비 |
|---|---:|---:|
| IPv4 | 299 | 88.5% |
| IPv6 | 31 | 9.2% |
| TCP | 264 | 78.1% |
| SSH | 250 | 74.0% |
| HTTP | 2 | 0.6% |
| ICMP | 10 | 3.0% |
| ARP | 8 | 2.4% |

Ethernet → IPv4 → TCP → SSH처럼 같은 패킷을 계층별로 세므로 행 전체를 더하면 안 된다. SSH가 많다는 것은 SSH 패킷 비중이 크다는 뜻이지 명령 내용을 복호화했다는 뜻은 아니다. tshark의 계층별 bytes 집계와 GUI의 프로토콜 자체 바이트 비율도 같은 의미로 혼용하지 않는다.

## 2. ping 요청·응답

Rocky에서 `ping u1`을 두 번 실행했다. 첫 실행은 요청 2개·응답 2개, 두 번째는 요청 3개·응답 3개로 모두 손실 0%였다. 합계 10개 ICMP 패킷과 캡처가 일치한다.

| 패킷 | 방향 | 내용 |
|---|---|---|
| 329 / 330 | .128 → .129 / .129 → .128 | 첫 요청·응답 |
| 333 / 334 | .128 → .129 / .129 → .128 | 두 번째 요청·응답 |
| 337 / 338 | .128 → .129 / .129 → .128 | 세 번째 요청·응답 |

두 VM은 같은 /24의 가상 스위치 구간에 있으므로 일반적으로 게이트웨이를 거치지 않는다. 캡처의 TTL은 64였다. 이는 64초 또는 이미 64홉을 지났다는 뜻이 아니다. 요청과 응답의 TTL은 각각 독립적으로 설정된다.

```text
Ethernet 14 + IPv4 20 + ICMP 8 + ping 데이터 56 = 98바이트
```

터미널 `56(84)`는 데이터 56, IP 패킷 84를 뜻한다. VM 내부 ping의 RTT와 Windows 캡처 지점의 패킷 시간차는 측정 위치가 달라 일치하지 않을 수 있다.

ARP 335·336에서는 Ubuntu가 게이트웨이 192.168.120.2의 MAC을 질문하고 `00:50:56:e9:56:13`이라는 응답을 받았다. 이것만으로 VM 간 ping이 게이트웨이를 거쳤다고 해석하지 않는다.

## 3. IPv4·Ethernet 헤더 대응: NTP 패킷 1

| 항목 | 실제 값 | 의미 |
|---|---|---|
| Ethernet Source | 00:0c:29:8d:12:b2 | Rocky MAC |
| Ethernet Destination | 00:50:56:e9:56:13 | 다음 홉인 가상 게이트웨이 MAC |
| EtherType | 0x0800 | IPv4 |
| Version | 4 | IPv4 |
| IHL | 5 → 20바이트 | 단위 4바이트 |
| DSCP/ECN | 0x00 | 기본 DSCP, ECN 미사용 |
| Total Length | 76 | IP 헤더 포함 |
| Identification | 0x0d34 = 3380 | 단편 식별 관련 값 |
| Flags | 010, DF=1 | 단편화 금지 |
| Fragment Offset | 0 | 조각 오프셋 |
| TTL | 64 | 캡처 지점에서의 값 |
| Protocol | 17 | UDP. 포트 번호가 아님 |
| Header Checksum | 0x8ae5 | 화면에서는 검증 비활성화, 오류 확정 아님 |
| Source IP | 192.168.120.128 | Rocky |
| Destination IP | 158.247.202.103 | NTP 서버 |
| Options/Padding | 없음 | 기본 IP 헤더 20바이트 |

```text
Ethernet 14 + IPv4 20 + UDP 8 + NTP 48 = 90바이트
```

IP 목적지는 외부 서버지만 MAC 목적지는 현재 링크의 게이트웨이다. 외부로 출발할 때 TTL 64를 관측했으므로 서버에 도착했을 때의 TTL은 이 화면으로 알 수 없다.

## 4. IPv6·ICMPv6 Neighbor Solicitation 대응

| IPv6 필드 | 화면의 값 |
|---|---|
| Version | 6 |
| Traffic Class | 0x00 |
| Flow Label | 0x00000 |
| Payload Length | 32 (IPv6 기본 헤더 제외) |
| Next Header | 58 = ICMPv6 |
| Hop Limit | 255 |
| Source | fe80::b45c:e50b:be28:cea2 |
| Destination | ff02::1:ffb7:492e |

| ICMPv6 필드 | 화면의 값 |
|---|---|
| Type / Code | 135 Neighbor Solicitation / 0 |
| Checksum | 0x2fcf, correct |
| Reserved | 0 |
| Target Address | fe80::b6b6:86ff:feb7:492e |
| Option Type | 1, Source link-layer address |
| Option Length | 1 → 전체 옵션 8바이트 |
| Source MAC option | 00:50:56:c0:00:08 |

이는 대상 IPv6 주소의 링크 계층 주소를 묻는 이웃 탐색이다. MAC 옵션은 찾는 상대의 MAC이 아니라 **보낸 쪽의 MAC**이다. 대상의 마지막 24비트 b7:492e에 대응하는 solicited-node 멀티캐스트 주소로 질문했다.

Hop Limit 255는 이웃 탐색에서 요구하는 값이다. 수신자가 255인지 검사하면 라우터를 지나 감소한 요청을 거를 수 있다. ff02는 링크 범위 멀티캐스트이며 멀리 보내기 위해 255를 쓰는 것이 아니다. 응답은 Neighbor Advertisement(136)이지만, 요청 화면만으로 응답 성공을 확정하지 않는다.

```text
Ethernet 14 + IPv6 기본 헤더 40 + NS 고정 부분 24 + 옵션 8 = 86바이트
```

IPv6 기본 헤더는 40바이트 고정이고 헤더 체크섬은 없다. 여기의 체크섬은 ICMPv6 체크섬이다.

## 5. curl과 HTTP 스트림

```bash
curl naver.com
```

터미널에서는 301 Moved Permanently HTML이 출력됐다. TCP 스트림 1에서 확인한 요청:

```http
GET / HTTP/1.1
Host: naver.com
User-Agent: curl/8.5.0
Accept: */*
```

응답 주요 헤더:

```http
HTTP/1.1 301 Moved Permanently
Date: Mon, 14 Sep 2026 06:45:29 GMT
content-type: text/html
transfer-encoding: chunked
location: https://www.naver.com/
vary: Accept-Encoding,User-Agent
referrer-policy: unsafe-url
server: nfront
```

- 301은 다른 주소로 이동하라는 정상 HTTP 응답이며, 새 주소는 Location에 있다.
- curl 기본 동작은 자동 추적이 아니다. 예시 `curl -L http://naver.com`으로 따라갈 수 있다.
- `curl -I http://naver.com`은 HEAD 요청으로 헤더만 확인한다.
- chunked 본문 앞 A2는 16진수 162바이트, 마지막 0은 청크 종료다.
- Vary는 캐시가 응답 선택 시 고려할 요청 헤더, Server는 서버가 알린 식별 문자열이다.
- HTTP라 평문을 볼 수 있다. 이후 HTTPS 본문은 일반적인 TCP 스트림 보기만으로 읽을 수 없다.

## 6. TCP 플로: 연결·전송·종료

클라이언트는 Ubuntu `192.168.120.129:52298`, 서버는 `223.130.200.219:80`이다. 다음 Seq/Ack는 Wireshark의 상대 번호다.

| 순서 | 방향 | 내용 |
|---|---|---|
| 1 | 클라이언트 → 서버 | SYN Seq=0, MSS=1460 |
| 2 | 서버 → 클라이언트 | SYN ACK Seq=0 Ack=1 |
| 3 | 클라이언트 → 서버 | ACK Seq=1 Ack=1 — 연결 수립 |
| 4 | 클라이언트 → 서버 | HTTP GET, TCP 데이터 72바이트 |
| 5 | 서버 → 클라이언트 | ACK Ack=73 |
| 6 | 서버 → 클라이언트 | HTTP 301, TCP 데이터 410바이트 |
| 7 | 클라이언트 → 서버 | ACK Seq=73 Ack=411 |
| 8 | 클라이언트 → 서버 | FIN ACK Seq=73 Ack=411 |
| 9 | 서버 → 클라이언트 | ACK Seq=411 Ack=74 |
| 10 | 서버 → 클라이언트 | FIN PSH ACK Seq=411 Ack=74 |
| 11 | 클라이언트 → 서버 | ACK Seq=74 Ack=412 |

처음 세 줄이 3-way handshake, 마지막 네 줄이 이 캡처의 연결 종료다. ACK=N은 N-1까지 받고 다음 N을 기다린다는 뜻이다. SYN·FIN은 데이터 길이 0이어도 순서 번호를 하나 사용한다. TCP ACK는 수신 확인이며 HTTP 301은 애플리케이션 응답이다.

패킷 199는 해당 TCP 스트림의 4번째 패킷이다. Seq=1(raw 1863506381), Ack=1(raw 789475717), Len=72, 다음 Seq=73이었다.

```text
Ethernet 14 + IPv4 20 + TCP 20 + HTTP 요청 데이터 72 = 126바이트
```

### MTU·MSS

```text
MTU 1500 - IPv4 기본 헤더 20 - TCP 기본 헤더 20 = MSS 1460
```

MTU는 해당 링크의 IP 패킷 크기 한도, MSS는 TCP 데이터 한도다. HTTP 헤더도 TCP 입장에서는 데이터다. SYN의 MSS는 상대에게 알리는 수신 한도이며 항상 그 크기로 보낸다는 뜻은 아니다. IP/TCP 옵션과 경로 MTU에 따라 실제 데이터는 더 작아질 수 있다. Ethernet 헤더는 위 MTU 1500에 포함되지 않는다.

## 7. Wireshark 조작과 문제 구분

표시 필터 예시:

```text
icmp && ip.addr == 192.168.120.128 && ip.addr == 192.168.120.129
http.response.code == 301
tcp.stream eq 1
ip.ttl == 64
```

- TCP 스트림 따라가기는 같은 연결의 데이터 재조립, 플로 그래프는 패킷 방향과 시간 순서 확인에 사용한다.
- IPv4 Time to Live를 열로 추가해 값 비교가 가능하다. TTL 열 정렬 시 시간순이 아니므로 No. 열로 복귀한다.
- 화면을 고정해 캡처하려면 캡처 중지 → 패킷 선택 → 모두 접기 → TCP만 펼치기.
- 다른 창으로 전환할 때 항목이 다시 펼쳐진다는 현상은 원인을 확정하지 못했다. 자동 스크롤과 포커스 문제를 구분하고, 마우스 전환/Alt+Tab 비교 및 별도 패킷 창을 대안으로 안내했다. 확정된 해결책으로 기록하지 않는다.
