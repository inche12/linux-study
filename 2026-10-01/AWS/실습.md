## 기록 범위

CloudFormation IaC와 Drift, Stack 삭제, SQL/NoSQL 개념, RDS MySQL 생성과 Workbench 연결, 인증 및 네트워크 문제 점검, Security Group 설계, 샘플 앱 후보 검토, 트래픽 급증 대응형 하이브리드 프로젝트 구상을 정리한다.

원 대화에서 확인 가능한 내용은 앱 후보와 프로젝트 방향이다. 앞부분의 상세 실습 화면·리소스 설정값·정확한 오류 메시지·최종 성공 여부는 가져온 대화에 포함되지 않았다. 따라서 아래 실습 절차는 요청한 학습 범위에 따른 복습용 재구성이며, 명령어는 재현 예시다. 프로젝트 아키텍처와 모니터링 항목은 향후 구현 계획이다.

실제 Endpoint, 계정 비밀번호, 액세스 키는 기록하지 않는다. 예시의 `lab-stack`, `lab-mysql`, 리전, 경로, 사용자 이름은 자신의 환경에 맞게 변경한다. AWS 명령어는 AWS CLI 인증과 해당 리소스 권한이 준비된 환경에서 실행한다.

## 1. 실습 순서

<a id="section-1-1"></a>

### 1.1 CloudFormation으로 인프라 관리 흐름 익히기

1. YAML/JSON 템플릿의 `Parameters`, `Resources`, `Outputs` 역할을 확인한다.
2. 템플릿을 검증하고 Stack을 생성한다.
3. Events에서 생성 진행 및 실패 원인을 확인한다.
4. 콘솔에서 리소스를 직접 변경한 경우 Drift를 탐지한다.
5. 템플릿과 실제 설정을 비교하고 변경을 반영하거나 원래 설정으로 복원한다.
6. 실습 종료 시 보존 정책과 종속 리소스를 확인하고 Stack을 삭제한다.

아래는 **PowerShell** 예시다. 실제 생성에 사용할 `infra.yaml`은 별도로 준비해야 한다.

```powershell
# 템플릿 형식과 기본 구성을 검증한다. 실제 배포 성공까지 보장하지는 않는다.
aws cloudformation validate-template --template-body file://infra.yaml --region ap-northeast-2

# 템플릿으로 Stack을 생성한다. IAM 리소스가 있으면 필요한 capabilities를 별도로 지정한다.
aws cloudformation create-stack --stack-name lab-stack --template-body file://infra.yaml --region ap-northeast-2

# Stack 생성 완료를 기다린다. 실패하면 아래 Events로 원인을 확인한다.
aws cloudformation wait stack-create-complete --stack-name lab-stack --region ap-northeast-2

# 최근 이벤트를 확인하여 실패한 리소스와 StatusReason을 찾는다.
aws cloudformation describe-stack-events --stack-name lab-stack --region ap-northeast-2
```

#### Drift 점검

```powershell
# 실제 리소스와 템플릿 사이의 차이 탐지를 시작하고 탐지 ID를 보관한다.
$driftId = aws cloudformation detect-stack-drift --stack-name lab-stack --region ap-northeast-2 --query StackDriftDetectionId --output text

# 탐지 진행 상태를 확인한다. DETECTION_COMPLETE가 될 때까지 확인한다.
aws cloudformation describe-stack-drift-detection-status --stack-drift-detection-id $driftId --region ap-northeast-2

# 탐지 완료 후 리소스별 속성 차이를 확인한다.
aws cloudformation describe-stack-resource-drifts --stack-name lab-stack --region ap-northeast-2
```

`IN_SYNC`는 탐지 대상 설정이 일치한다는 의미이고, `DRIFTED`는 차이가 발견됐다는 의미다. 지원하지 않는 리소스나 명시하지 않은 속성까지 모두 검사되는 것은 아니다. Drift 탐지는 차이를 보고하며 자동 복구하지 않는다. 단순히 같은 템플릿을 다시 배포한다고 모든 수동 변경이 복구되는 것도 아니다. 변경 내용을 확인한 후 템플릿 갱신 또는 실제 설정 복원을 선택한다. [AWS Drift 문서](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-cfn-stack-drift.html)

#### Stack 삭제

삭제 전에 데이터 백업, `DeletionPolicy`, 삭제 방지, 외부 리소스와의 연결을 확인한다. 다음 명령어는 실제 리소스 삭제를 요청한다.

```powershell
# 실습 Stack 삭제를 요청한다. 보존 대상으로 설정된 리소스는 남을 수 있다.
aws cloudformation delete-stack --stack-name lab-stack --region ap-northeast-2

# 삭제 완료를 기다린다. 실패하면 Events에서 DELETE_FAILED 원인을 확인한다.
aws cloudformation wait stack-delete-complete --stack-name lab-stack --region ap-northeast-2
```

- `Delete`: 리소스를 삭제한다. 일부 리소스에는 기본값 예외가 있다.
- `Retain`: Stack 삭제 후에도 리소스를 남긴다. 남은 리소스는 별도로 관리한다.
- `Snapshot`: 지원하는 리소스의 스냅샷을 만든 뒤 삭제한다.
- 독립 RDS DBInstance 등에는 기본 Snapshot 정책 예외가 있으므로 템플릿을 확인한다.
- `DeletionPolicy`는 Stack 삭제·리소스 제거에, `UpdateReplacePolicy`는 업데이트 중 리소스 교체에 관련된다.
- 삭제된 Stack 밖의 스냅샷·보존 리소스에는 비용이 계속 발생할 수 있다.

근거: [AWS DeletionPolicy](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-attribute-deletionpolicy.html), [CloudFormation 문제 해결](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/troubleshooting.html).

### 1.2 SQL과 NoSQL 개념 비교

| 항목 | SQL/관계형 DB | NoSQL |
|---|---|---|
| 모델 | 테이블, 행, 열, 관계 | 키-값, 문서, 그래프, 와이드 컬럼 등 |
| 설계 | 스키마와 관계를 중심으로 설계 | 제품별 모델과 접근 패턴을 중심으로 설계 |
| 질의 | SQL, JOIN, 집계 | 제품별 API/질의 언어, 데이터 모델에 따른 질의 |
| 적합한 예 | 원서·예약·주문 등 관계와 정합성이 중요한 데이터 | 캐시, 유연한 문서, 특정 키 중심의 대규모 접근 |
| 예시 | MySQL, PostgreSQL | DynamoDB, MongoDB, Redis |

SQL은 질의 언어이고 NoSQL은 여러 DB 유형을 묶는 용어다. NoSQL이 항상 빠르거나 트랜잭션을 지원하지 않는다는 뜻은 아니다. 확장성·일관성·트랜잭션 지원은 제품과 설계에 따라 다르다. 이번 실습은 관계형 DB인 RDS MySQL을 중심으로 한다.

<a id="section-1-3"></a>

### 1.3 RDS MySQL 생성

1. RDS 콘솔에서 표준 생성과 MySQL 엔진을 선택한다.
2. DB 식별자, 엔진 버전, 인스턴스 크기, 스토리지를 설정한다.
3. 마스터 사용자와 비밀번호 관리 방식을 확인한다.
4. VPC, DB Subnet Group, Security Group을 선택한다.
5. 로컬 PC 직접 연결 실습이라면 퍼블릭 액세스와 인터넷 경로를 함께 확인한다.
6. 초기 DB 이름, 백업 보존 기간, 삭제 방지, 모니터링 설정을 확인한다.
7. 상태가 `Available`이 되면 Endpoint와 Port를 확인한다.

DB 식별자는 AWS 리소스 이름이며, MySQL 내부 데이터베이스 이름과는 별개다. 초기 DB 이름을 지정하지 않았다면 접속 후 DB를 생성할 수 있다.

<a id="section-1-4"></a>

### 1.4 퍼블릭 액세스와 Endpoint 이해

퍼블릭 액세스를 켜는 것만으로 외부 연결이 허용되지는 않는다. 로컬 PC에서 인터넷을 통해 직접 접속하려면 RDS의 공개 접근 설정, DB 서브넷의 인터넷 게이트웨이 경로, VPC DNS 설정, Security Group, NACL, 클라이언트 측 방화벽이 함께 맞아야 한다. VPN 등 사설 경로를 쓰는 경우에는 별도 설계가 가능하다. [AWS RDS 연결 문서](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_ConnectToInstance.html)

Endpoint는 DB 연결용 DNS 이름이다. Workbench Hostname에는 `https://`나 경로 없이 Endpoint만 입력하고 포트는 별도 입력한다. IP가 바뀔 수 있으므로 고정 IP를 저장하는 대신 Endpoint를 사용한다.

```powershell
# DB 상태, Endpoint, 포트, 공개 접근 설정을 조회한다.
aws rds describe-db-instances --db-instance-identifier lab-mysql --region ap-northeast-2 --query 'DBInstances[0].{Status:DBInstanceStatus,Endpoint:Endpoint.Address,Port:Endpoint.Port,Public:PubliclyAccessible}'

# 실제 Endpoint로 바꿔 DNS 조회가 되는지 확인한다.
Resolve-DnsName db-endpoint.example

# TCP 3306 도달 여부를 확인한다. 성공해도 DB 인증 성공을 의미하지는 않는다.
Test-NetConnection db-endpoint.example -Port 3306
```

### 1.5 MySQL Workbench 연결

| 설정 | 입력 내용 |
|---|---|
| Connection Method | Standard TCP/IP |
| Hostname | RDS Endpoint |
| Port | RDS에 설정된 포트, 기본 3306 |
| Username | 생성 시 지정한 DB 사용자 |
| Password | 해당 사용자의 DB 비밀번호 |
| Default Schema | 생성된 DB가 있으면 지정, 없으면 비워 두기 |
| SSL | 서버 요구사항에 맞춰 설정하고 RDS CA로 검증 |

`Test Connection`으로 확인한다. AWS 콘솔 로그인 계정과 MySQL 계정은 별개다. 아래는 MySQL 클라이언트가 설치된 환경의 접속 예시이며, CA 파일은 AWS에서 제공하는 인증서 번들을 준비한다.

```powershell
# 비밀번호를 명령어에 넣지 않고 입력 프롬프트를 사용한다. 서버 인증서도 검증한다.
mysql --host=db-endpoint.example --port=3306 --user=lab_admin --password --ssl-mode=VERIFY_IDENTITY --ssl-ca=C:/certs/global-bundle.pem
```

접속 후 다음 SQL로 서버 응답과 현재 인증 계정을 확인한다. 이는 복습 예시이며 원 대화의 실제 실행 결과는 아니다.

```sql
-- 서버 버전과 인증된 계정을 확인한다.
SELECT VERSION(), CURRENT_USER();

-- 접근 가능한 DB 목록을 확인한다.
SHOW DATABASES;

-- 학습용 DB를 만들고 선택한다. 생성 권한이 필요하다.
CREATE DATABASE IF NOT EXISTS lab_db CHARACTER SET utf8mb4;
USE lab_db;

-- 테이블 생성과 데이터 저장·조회 흐름을 확인한다.
CREATE TABLE IF NOT EXISTS lab_notes (
    id INT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(100) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
INSERT INTO lab_notes (title) VALUES ('RDS connection practice');
SELECT * FROM lab_notes;
```

`INSERT`를 반복하면 행이 추가된다. 운영 앱은 마스터 계정 대신 필요한 DB 권한만 가진 별도 계정을 사용한다.

### 1.6 RDS Security Group 구성

| 목적 | RDS 인바운드 | 허용 소스 |
|---|---|---|
| 로컬 Workbench 실습 | TCP 3306 | 현재 PC의 공인 IPv4 `/32` |
| AWS App → RDS | TCP 3306 | App EC2에 연결된 Security Group |
| 온프레미스 → AWS RDS | TCP 3306 | VPN 경유 온프레미스 앱의 실제 출발지 CIDR |

공인 IP와 사설 IP를 구분한다. PC가 공유기 뒤에 있다면 보통 공유기/NAT의 공인 출발지 주소를 허용해야 한다. IP가 바뀌면 실습 규칙도 수정한다. 앱에서 접속할 때는 실제 RDS에 연결된 SG와 앱 SG를 확인한다. VPN 트래픽은 NAT 여부에 따라 실제 출발지 주소가 달라질 수 있다.

웹 구조의 SG 연결 예시는 다음과 같다.

```text
사용자 → ALB SG: HTTPS 443
ALB SG → App SG: 앱 포트(예: HTTP 80)
App SG → RDS SG: MySQL 3306
```

위 흐름에는 각 대상의 인바운드와 출발지의 아웃바운드 허용이 필요하다. SG는 상태 기반이므로 허용된 연결의 응답 트래픽은 자동 허용한다. NACL은 상태를 추적하지 않으므로 응답용 임시 포트까지 고려한다. 운영 DB는 사설 서브넷에 두고 앱 또는 관리용 사설 경로에서 접근하도록 설계한다.

## 2. 핵심 개념

| 개념 | 핵심 정리 |
|---|---|
| IaC | 인프라 구성을 코드로 기록하여 검토·재현·변경 추적에 활용 |
| Template / Stack | Template은 설계, Stack은 그 설계로 관리되는 리소스 집합 |
| Drift | 템플릿의 기대 설정과 실제 리소스 사이의 차이 |
| RDS | DB 운영 작업을 관리형 서비스로 제공하지만 앱의 SQL·계정·접근 설계는 별도 필요 |
| Endpoint | DB 접속용 DNS 이름 |
| Security Group | 리소스의 네트워크 접근을 제어하는 상태 기반 규칙 |
| ALB | HTTP/HTTPS 요청을 정상 Target으로 분산 |
| Auto Scaling | 정책에 따라 앱 서버 수를 조절하며 DB 병목까지 자동 해결하지는 않음 |
| Health Check | 프로세스 생존, 요청 처리 가능 여부, 의존성 상태 등을 목적에 맞게 검사 |

Health Check에 DB까지 포함하면 서비스 이상을 찾기 쉽지만, 공유 DB 장애로 모든 앱이 동시에 비정상 판정을 받을 수 있다. ALB의 트래픽 제외 기준, ASG의 인스턴스 교체 기준, 외부 서비스 모니터링은 각각 목적에 맞게 설계한다.

## 3. 트러블슈팅

<a id="section-3-1"></a>

### 3.1 RDS 연결 문제를 계층별로 확인

```text
DB Available 확인
  → Endpoint/Port 확인
  → DNS 확인
  → TCP 연결 확인
  → TLS 및 MySQL 인증 확인
  → DB 선택과 권한 확인
```

| 증상 | 점검 대상 | 대응 |
|---|---|---|
| DNS 조회 실패 | Endpoint 오타, DNS 환경 | 콘솔 Endpoint와 비교하고 DNS 점검 |
| 연결 시간 초과 | SG, 공인 IP 변경, 경로, NACL, 방화벽 | TCP 검사 후 차단 계층 확인 |
| TCP 성공 + Access denied | 사용자, 비밀번호, 접속 host에 따른 계정·권한 | DB 계정 정보와 Workbench 저장 비밀번호 확인 |
| Unknown database | Default Schema 오타 또는 미생성 DB | Schema를 비우고 접속 후 DB 확인 |
| 인증 플러그인 관련 오류 | 서버/클라이언트 버전과 인증 방식 | 호환되는 클라이언트와 TLS 설정 점검 |
| SSL/인증서 오류 | CA, 인증서 검증, 서버 이름, 클라이언트 시간 | 올바른 CA와 Endpoint로 검증 |

인증 실패를 SG 변경으로 해결하려 하지 않는다. 반대로 타임아웃 상태에서 비밀번호만 바꿔도 네트워크 문제는 해결되지 않는다. 비밀번호 변경이 필요하면 RDS 수정 상태를 확인하고 저장된 자격 증명도 갱신한다. 인증 플러그인을 임의로 낮추기 전에 엔진과 클라이언트 호환성을 확인한다.

<a id="section-3-2"></a>

### 3.2 CloudFormation 삭제 실패

1. Events에서 `DELETE_FAILED` 리소스와 이유를 확인한다.
2. S3 버킷 내부 객체·버전, 사용 중인 SG/ENI, 다른 리소스의 참조, DB 삭제 방지 등을 점검한다.
3. 필요한 데이터를 보존하고 해당 종속성 또는 설정을 해결한다.
4. 삭제를 다시 시도한 뒤 보존 리소스와 스냅샷까지 확인한다.

성공 여부는 콘솔/CLI 결과로 확인한다. 이 기록에는 실제 오류 문자열과 삭제 완료 증거가 없어 특정 원인을 확정하지 않았다.

<a id="section-4"></a>

## 4. 프로젝트 메모

<a id="section-4-1"></a>

### 4.1 프로젝트 주제

**마감 직전 트래픽이 급증하는 접수·예약 서비스를 위한 하이브리드 인프라와 모니터링 구축**

유웨이어플라이 접속 장애를 문제 사례로 참고한다. 사용자가 제시한 [뉴스1 기사](https://www.news1.kr/society/education/6290254)는 보안 강화 중 버그와 전년 대비 30% 이상 트래픽 증가를 보도한다. [중앙일보 기사](https://www.joongang.co.kr/article/25465961)는 데이터센터 이전과 관리·감독 문제를 다룬다. 장애 원인을 단순 서버 용량 부족 하나로 단정하지 않고, 배포 안정성·병목 관찰·용량 계획을 함께 고려한다. 사례의 연월과 세부 경위는 발표 자료 작성 시 기사 원문 날짜를 다시 대조한다.

이 프로젝트는 실제 원서접수 시스템 복제가 아니라, 접수·예약 형태의 샘플 앱으로 부하 분산과 확장, 장애 탐지, 복구를 검증하는 계획이다.

<a id="section-4-2"></a>

### 4.2 샘플 앱 후보 검토

| 앱 | 용도 / 기술 구성 | DB 및 Health Check | 프로젝트 메모 |
|---|---|---|---|
| pretix | 티켓 판매·참가자 관리 / Python | 현재 문서상 PostgreSQL, `/healthcheck/` | 예약 시나리오에 적합, Redis·worker 등 추가 운영 요소 고려 |
| alf.io | 티켓 예약 / Java | PostgreSQL, 전용 헬스 경로는 배포 버전에서 추가 확인 | JVM 자원과 기동 시간, 운영 설정 검토 |
| Hi.Events | 행사·티켓 관리 / Laravel·React | PostgreSQL 기반, 앱 헬스 경로와 Redis 구성은 버전별 확인 | 화면 시연에 적합, 프런트·백엔드 배포 구성 검토 |
| BookStack | 위키·문서 관리 / PHP | MySQL/MariaDB, `/status` | 기존 RDS MySQL 실습 연계가 쉬움, 접수 업무와는 기능 차이 |

pretix `/healthcheck/`는 DB·설정된 캐시·사용하는 Redis 연결을 확인하며 정상 시 200, 문제 시 5xx를 반환한다. BookStack은 공식 설치 문서에 `/status`를 안내한다. alf.io와 Hi.Events의 전용 endpoint를 이 기록에서 확정하지 않았으며, 미확인을 곧바로 기능 부재로 해석하지 않는다.

이전 대화의 pretix MySQL 지원 설명은 수정한다. 현재 공식 설정 문서의 DB backend는 SQLite/PostgreSQL이며, 프로젝트 배포는 PostgreSQL을 기준으로 검토한다. [pretix 설정](https://docs.pretix.eu/self-hosting/config/), [pretix 모니터링](https://docs.pretix.eu/self-hosting/maintenance/), [BookStack 설치](https://www.bookstackapp.com/docs/admin/installation/), [alf.io 저장소](https://github.com/alfio-event/alf.io), [Hi.Events 저장소](https://github.com/HiEventsDev/Hi.Events).

선정 방향은 다음과 같다.

- RDS MySQL과 인프라 구축 시연 우선: BookStack 검토.
- 예약·접수에 가까운 기능 우선: pretix, alf.io, Hi.Events 검토.
- 최종 선정 전에 버전/라이선스, DB, 세션·업로드 공유, 백그라운드 작업, 인증 없는 헬스 경로, 설치 재현성을 확인한다.

<a id="section-4-3"></a>

### 4.3 하이브리드 아키텍처 초안

```text
사용자
  │
  ▼
AWS Public ALB
  ├── AWS Private App Subnets: EC2 Auto Scaling Group
  └── 온프레미스 App: 사설 IP Target (연결 조건 검증 필요)
              ▲
      Site-to-Site VPN 등 사설 연결

AWS 앱 / 온프레미스 앱
  └── 공통 데이터 계층: RDS (MySQL 또는 PostgreSQL, 앱 선정 후 결정)

온프레미스 + AWS 지표/로그
  └── Prometheus·Grafana / CloudWatch → 알림 및 대응
```

ALB에 온프레미스 서버를 붙이는 방식은 IP Target 지원 조건, 주소 범위, VPN 라우팅, 보안 규칙, 헬스체크 도달성을 검증해야 한다. 이 초안은 구축 완료 상태가 아니다.

클라우드 확장 서버도 동일한 DB·세션·파일 저장소에 접근할 수 있어야 한다. 로컬 디스크에만 세션이나 업로드를 저장하면 분산 시 문제가 생길 수 있다. 공통 RDS를 AWS에 두면 온프레미스 앱의 VPN 지연·장애가 DB 접근에 영향을 준다. DB를 양쪽에서 독립적으로 쓰는 경우에는 복제와 충돌·정합성 설계가 추가로 필요하다.

ALB만으로 온프레미스 포화 시 AWS가 자동으로 증설되는 것은 아니다. 요청량·응답 시간·포화 지표에 따른 ASG 정책과 온프레미스 Target 비중 조절을 별도로 설계한다. 예측 가능한 마감 시간에는 사전 증설과 인스턴스 warm-up도 검토한다.

<a id="section-4-4"></a>

### 4.4 온프레미스 점검 명령어

아래는 **Linux 서버에서 실행하는 향후 프로젝트 점검 예시**다. `nginx`, `app` 등 서비스 이름은 실제 구성에 맞춰 바꾼다.

```bash
# CPU 부하, 메모리, 디스크 사용량을 확인한다.
uptime
free -h
df -h

# 프로세스와 수신 포트를 확인한다.
top
ss -lntp

# 웹 서버 상태와 최근 로그를 확인한다.
systemctl status nginx --no-pager
journalctl -u nginx --since "10 minutes ago" --no-pager

# 라우팅과 서버 DNS 설정을 확인한다.
ip route
cat /etc/resolv.conf

# 컨테이너를 사용하는 경우 상태·자원 사용·최근 로그를 확인한다.
docker compose ps
docker stats --no-stream
docker compose logs --tail=100 app

# BookStack 예시: HTTP 상태와 응답 시간을 확인한다. 실제 도메인으로 교체한다.
curl --max-time 10 -sS -o /dev/null -w 'status=%{http_code} total=%{time_total}s\n' https://app.example/status
```

pretix를 선택하면 마지막 URL 경로를 `/healthcheck/`로 바꾼다. 헬스 응답은 사용자 요청의 전체 성공을 보장하지 않으므로 로그인·예약 등 대표 흐름도 별도로 검증한다.

<a id="section-4-5"></a>

### 4.5 모니터링 및 부하 테스트 계획

| 계층 | 수집 항목 | 검증 목적 |
|---|---|---|
| 사용자/앱 | 요청량, p95/p99 지연, 오류율, 로그인·예약 성공률 | 실제 서비스 품질 |
| ALB | TargetResponseTime, Target/ELB 5xx, HealthyHostCount, RequestCountPerTarget | 부하 분산과 Target 이상 |
| 서버 | CPU, 메모리, 디스크, 연결 수, 프로세스 상태 | 자원 포화와 장애 |
| RDS | CPU, 연결 수, FreeableMemory, I/O 지연, 느린 쿼리·잠금 | DB 병목 |
| 사설 연결 | VPN 상태, 지연, 패킷 손실, 전송량 | 하이브리드 경로 영향 |
| ASG | 인스턴스 수, 확장 이벤트, 기동·준비 시간 | 확장 효과와 소요 시간 |

EC2 메모리 등은 기본 지표만으로 충분하지 않아 에이전트/exporter가 필요할 수 있다. 온프레미스에는 Node Exporter, 서비스 상태 확인에는 Blackbox Exporter 등을 검토한다. 임계값은 정상 부하에서 측정한 기준선으로 정한다.

테스트는 관리하는 실습 환경에서 수행한다.

1. 정상 부하에서 요청량·지연·오류율과 DB 부하를 기록한다.
2. 전년 대비 30% 증가라는 사례를 참고한 비교 부하와, 별도의 순간 급증 부하를 구성한다.
3. 확장 전후 지표, 추가 서버가 준비되는 시간, 성공 처리량을 비교한다.
4. 앱 인스턴스 중단 시 헬스체크와 트래픽 제외·복구를 확인한다.
5. VPN 단절 또는 DB 병목 시 영향 범위와 알림을 확인한다.
6. 부하 감소 후 축소, 세션 유지, 중복 예약 방지와 데이터 정합성을 검증한다.

서버 증설로 해결되지 않는 애플리케이션 버그·DB 잠금·쿼리 병목도 분리해 관찰한다. 부하 시험에서는 가상 사용자 수뿐 아니라 RPS, 요청 종류, 지속 시간, 측정 조건을 함께 기록한다.

## 5. 학습 정리

CloudFormation은 인프라 재현과 변경 추적의 기반이고, Drift는 수동 변경을 확인하는 수단이다. RDS 접속에서는 네트워크 도달 여부와 DB 인증을 나눠 점검해야 한다. 프로젝트 앱은 화면 기능뿐 아니라 DB 호환성, 헬스체크, 세션·파일 공유, 확장 시 동작을 기준으로 고른다. 하이브리드 프로젝트의 목표는 부하 증가에 따른 확장 효과와 장애 영향을 실제 지표로 검증하는 것이다.
