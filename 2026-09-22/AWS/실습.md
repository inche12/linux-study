## 2. IAM: 로그인 계정과 권한 이해하기

### 2.1 Root Account와 IAM User

| 구분 | Root User | IAM User |
|---|---|---|
| 정체성 | AWS 계정 생성 시 만들어지는 루트 사용자 | 계정 안에 생성하는 사용자 |
| 로그인 | 계정 이메일과 인증 수단 | 계정 ID 또는 Alias, 사용자 이름, 인증 수단 |
| 권한 | 루트 전용 작업을 포함하는 강력한 권한 | 연결된 정책과 적용되는 제한에 따라 결정 |
| 이번 실습의 의미 | 계정 소유자와 일반 작업용 신원 구분 | 사용자별 로그인 및 권한 실습 |

IAM User에 `AdministratorAccess`를 붙여도 Root User로 바뀌지 않는다. 루트 전용 작업은 별도로 남는다. 일상 작업에서는 루트 사용을 피하고 MFA를 적용한다. 실제 조직에서는 사람의 접근에 IAM Identity Center 등의 연동 및 임시 자격 증명을 사용하는 방식도 알아둘 필요가 있다.

### 2.2 사용자 생성, 그룹, 로그인 흐름

1. IAM에서 실습용 User를 생성한다.
2. 콘솔 로그인이 필요한 사용자에는 콘솔 접근과 초기 암호를 설정한다.
3. IAM Group을 만들고 필요한 정책을 그룹에 연결한다.
4. 사용자를 그룹에 추가해 그룹의 권한을 받도록 한다.
5. 해당 계정의 IAM 로그인 페이지에서 사용자 이름으로 로그인한다.
6. MFA를 등록해 암호 외의 추가 인증 수단을 적용한다.

> 💡 코멘트: Group은 여러 IAM User의 권한을 함께 관리하는 수단이다. Group 자체가 로그인하거나 Role을 Assume하는 주체는 아니다. 실습에서 사용한 실제 사용자명과 그룹명은 제공되지 않았다.

### 2.3 정책 종류와 역할

| 종류 | 연결 대상과 의미 | 실습에서 구분할 점 |
|---|---|---|
| AWS Managed Policy | AWS가 관리하는 재사용 정책 | `AdministratorAccess` 등이 해당한다. |
| Customer Managed Policy | 고객 계정에서 만들어 관리하는 재사용 정책 | 여러 User/Group/Role에 연결할 수 있다. |
| Inline Policy | 특정 User/Group/Role에 종속되는 정책 | 독립된 재사용 정책과 구분한다. |
| Resource-based Policy | 리소스에 부착하는 정책 | S3 Bucket Policy, Role Trust Policy 등이 있다. |
| Permissions Boundary | User/Role의 identity-based 권한 상한 | 자체적으로 권한을 부여하지 않는다. |
| SCP | Organizations에서 멤버 계정의 주체에 적용하는 권한 상한 | 자체 Allow만으로 작업 권한이 생기지 않는다. |
| ACL | 일부 서비스에서 사용하는 접근 제어 목록 | S3 ACL은 IAM JSON 정책과 다르며, 최신 S3 기본 설정에서는 ACL이 비활성화된다. |
| Session Policy | 임시 세션에 추가하는 권한 제한 | Role 권한을 넘어 새 권한을 추가할 수 없다. |

`AdministratorAccess`는 폭넓은 관리 권한을 제공하지만, 적용되는 명시적 Deny나 SCP 등의 제한까지 무시하지 않는다. 일반적인 identity-based 권한은 정책의 Allow와 적용되는 상한을 함께 만족해야 한다. Resource-based Policy는 어떤 Principal에 허용했는지에 따라 세부 평가가 달라지므로 모든 경우를 단순한 교집합으로 외우지는 않는다. [AWS 정책 종류](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies.html), [Permissions Boundary 평가](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_boundaries.html)

> 💡 코멘트: 이 표는 실습에서 확인한 개념을 정리한 것이다. 모든 정책 종류를 실제로 생성하거나 적용했다는 의미는 아니다. S3 ACL과 서브넷 트래픽을 제어하는 Network ACL도 서로 다른 기능이다.

## 3. Access Key와 AWS CLI 인증

콘솔 암호와 CLI 자격 증명은 용도가 다르다. Access Key ID와 Secret Access Key는 프로그램이 AWS API 요청을 서명할 때 사용한다. 임시 자격 증명에는 Session Token도 필요하다. MFA를 켰다고 기존 장기 Access Key 요청마다 자동으로 MFA가 강제되는 것은 아니다.

다음은 **복습용 CLI 설정 예시**다. 실제 키는 문서, 캡처, Git 저장소에 넣지 않는다.

```bash
aws configure --profile lab-user
```
> 💡 코멘트: 로컬 PC의 `lab-user` 프로파일에 실습용 자격 증명과 기본 설정을 저장하는 대화형 명령이다. 기본 리전은 `ap-northeast-2`, 출력 형식은 `json`으로 설정할 수 있다. EC2에 Role이 연결되어 있다면 이 방식으로 장기 키를 별도 저장할 필요가 없다.

```bash
aws sts get-caller-identity --profile lab-user
```
> 💡 코멘트: 현재 호출자의 Account와 ARN을 확인한다. IAM User로 호출하는지, AssumeRole 세션으로 호출하는지 구분할 때 사용한다. S3 조회 성공 여부만으로 호출자의 정확한 신원을 단정하지 않기 위한 보완 명령이다. 실제 출력은 첨부되지 않았다.

[AWS CLI GetCallerIdentity 설명](https://docs.aws.amazon.com/cli/latest/reference/sts/get-caller-identity.html)

## 4. IAM Role: 권한과 신뢰 관계 분리하기

Role은 필요한 주체가 맡아서 사용하는 권한 집합이다. IAM User의 장기 키를 공유하는 대신 STS가 발급하는 만료 시간 있는 자격 증명으로 작업한다.

| 정책 | 답하는 질문 | 예 |
|---|---|---|
| Permission Policy | 이 Role이 무엇을 할 수 있는가? | S3 버킷 목록 조회 |
| Trust Policy | 누가 이 Role을 Assume할 수 있는가? | EC2 서비스, 특정 계정의 사용자 |

Permission Policy가 S3를 허용해도 Trust Policy가 호출자를 신뢰하지 않으면 Role을 맡을 수 없다. Trust Policy가 허용해도 Role에 필요한 S3 권한이 없으면 S3 작업은 실패한다. [AWS IAM Role 설명](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles.html)

### 4.1 실습에 등장한 Role과 정책

| 이름 | 기록에서 확인되는 내용 |
|---|---|
| `lsmS3-VPC` | 실습에서 생성 또는 사용한 Role. 실제 정책 원문 미제공 |
| `lsmEC2` | 실습에서 생성 또는 사용한 Role. 실제 정책 원문 미제공 |
| `lsmEC2-S3` | `ktcloud-vm`에 연결한 EC2 IAM Role |
| `lsmSTS` | STS 관련 실습 정책 이름. 실제 JSON 원문 미제공 |
| `sts:AssumeRole` | 대상 Role의 임시 세션을 요청하는 Action |

이름에 `S3` 또는 `VPC`가 포함되어 있다는 이유만으로 실제 권한 범위를 확정하지 않는다. 콘솔의 Permissions와 Trust relationships를 각각 확인해야 한다.

기록의 `arn:aws:iam:::role/lsm`은 계정 ID가 빠진 불완전한 ARN이다. 이를 그대로 정책에 복사하지 않는다. 실제 Role의 ARN을 콘솔에서 복사하고, Role 경로가 있다면 경로까지 포함한다.

<!-- 캡처: lsmS3-VPC, lsmEC2, lsmEC2-S3의 Permissions와 Trust relationships -->

### 4.2 EC2 서비스용 Trust Policy 예시

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "ec2.amazonaws.com" },
      "Action": "sts:AssumeRole"
    }
  ]
}
```
> 💡 코멘트: EC2 서비스가 Role을 사용할 수 있도록 신뢰하는 교육용 예시다. S3 작업 권한을 부여하는 코드는 아니다. EC2에는 Instance Profile을 통해 Role이 연결되며, 실제 `lsmEC2-S3`의 원문을 복원한 것은 아니다.

### 4.3 최소한의 S3 목록 조회 Permission Policy 예시

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:ListAllMyBuckets",
      "Resource": "*"
    }
  ]
}
```
> 💡 코멘트: 인자 없는 `aws s3 ls`의 버킷 목록 조회를 설명하기 위한 예시다. 이 Action은 특정 버킷 ARN으로 제한하는 방식이 아니므로 `Resource`에 `*`를 사용한다. 버킷 안의 객체 목록은 `s3:ListBucket`, 객체 읽기는 `s3:GetObject` 등 별도 권한이 필요하다. 실습 Role의 전체 권한은 이 예시만으로 알 수 없다.

## 5. Cross Account AssumeRole

### 5.1 계정과 접근 흐름

```text
내 계정 111111111111의 IAM User
  │ Identity Policy: 대상 Role에 sts:AssumeRole 허용
  ▼
AWS STS: 대상 Role의 Trust Policy 등 확인
  │ 대상 계정 222222222222 (Alias: jyl)
  │ 대상 Role: ljyS3-VPC
  ▼
임시 자격 증명 발급
  AccessKeyId + SecretAccessKey + SessionToken + Expiration
  ▼
ljyS3-VPC Role 세션으로 상대 계정 리소스 접근
  └─ Role의 Permission Policy와 적용되는 제한 범위 안에서 수행
```
> 💡 코멘트: 내 사용자 권한과 대상 Role 권한을 합치는 과정이 아니다. AssumeRole 이후 요청은 대상 Role 세션의 자격 증명으로 수행한다. Alias `jyl`은 로그인 편의를 위한 이름이며 ARN에는 계정 ID를 사용한다.

Cross Account Role Assume에는 **호출자의 Identity Policy 허용**과 **대상 Role의 Trust Policy 신뢰**가 모두 필요하다. 조건이나 상위 정책의 Deny가 있으면 이 둘의 Allow만으로 성공이 보장되지는 않는다. Role을 맡은 이후 리소스 작업 권한도 별도로 필요하다. [AWS Cross Account 설명](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies-cross-account-resource-access.html)

### 5.2 호출자 측 정책 예시: lsmSTS의 목적 이해

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::222222222222:role/ljyS3-VPC"
    }
  ]
}
```
> 💡 코멘트: 내 계정의 호출자에게 상대 Role을 Assume하도록 허용하는 예시다. `lsmSTS` 정책의 목적을 설명하며 실제 원문은 아니다. Role에 별도 경로가 없다는 가정이다. 이 정책 자체는 상대 S3 버킷을 읽을 권한을 주지 않는다.

### 5.3 대상 Role의 Trust Policy 예시

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111111111111:root" },
      "Action": "sts:AssumeRole"
    }
  ]
}
```
> 💡 코멘트: 상대 계정의 `ljyS3-VPC`가 내 계정에 신뢰를 위임하는 교육용 예시다. 여기의 `:root`는 루트 사용자만 뜻하는 것이 아니라 해당 계정 Principal을 의미한다. 내 계정의 모든 사용자가 자동으로 접근하는 것은 아니며 호출자 측 Allow도 필요하다. 실제 운영에서는 신뢰할 사용자/Role과 조건을 더 좁혀 설정한다.

<!-- 캡처: lsmSTS의 대상 Role ARN 및 ljyS3-VPC의 Trust Policy -->

### 5.4 CLI로 AssumeRole 요청하기 — 복습용 예시

```bash
aws sts assume-role --role-arn arn:aws:iam::222222222222:role/ljyS3-VPC --role-session-name lab-20260922 --profile lab-user
```
> 💡 코멘트: STS에 대상 Role 세션을 요청한다. 성공 응답의 `Credentials`에는 임시 키, Session Token, 만료 시간이 포함된다. 응답에는 비밀값이 있으므로 Git이나 캡처에 노출하지 않는다. 이 명령을 실행하는 것만으로 이후 CLI의 기본 자격 증명이 자동 전환되지는 않는다.

다음은 로컬 `~/.aws/config`에 추가할 수 있는 **복습용 Role 프로파일**이다.

```ini
[profile cross-jyl]
role_arn = arn:aws:iam::222222222222:role/ljyS3-VPC
source_profile = lab-user
role_session_name = lab-20260922
region = ap-northeast-2
```
> 💡 코멘트: AWS CLI가 `lab-user`로 AssumeRole을 수행하고 임시 자격 증명을 사용하도록 구성한다. `lab-user`가 먼저 설정되어 있어야 한다. 임시 키를 직접 환경 변수로 복사하는 대신 Role 프로파일로 전환 과정을 명확히 할 수 있다.

```bash
aws sts get-caller-identity --profile cross-jyl
```
> 💡 코멘트: 성공하면 대상 계정 `222222222222`와 해당 Role의 assumed-role 세션 ARN을 확인할 수 있다. 이는 예상 확인 기준이며 당시 출력값을 재현한 것은 아니다.

```bash
aws s3 ls --profile cross-jyl
```
> 💡 코멘트: 상대 Role 세션으로 S3 버킷 목록 조회를 시도한다. AssumeRole 성공과 S3 조회 성공은 별도 단계다. Role에 목록 조회 권한이 없으면 Role 전환은 성공했어도 이 명령은 거부될 수 있다.

## 6. S3로 현재 권한 확인하기

실습 기록에 등장한 버킷 이름은 다음과 같다. 이름 속 계정 ID나 사용자 문자열은 명명 규칙이며, 그 자체가 소유권 증명은 아니다.

- `hello-lsm-111111111111-ap-northeast-2-an`
- `hello-lsm-222222222222-ap-northeast-2-an`
- `hello-ljy-222222222222-ap-northeast-2-an`

```bash
aws s3 ls
```
> 💡 코멘트: 현재 선택된 자격 증명으로 계정 소유 버킷 목록을 조회한다. 외부 계정에서 공유받아 접근 가능한 모든 버킷의 통합 목록을 보여주는 명령은 아니다. 성공하면 목록 조회 권한이 있음을 확인할 수 있지만 객체 읽기·쓰기 권한까지 입증되지는 않는다. [AWS S3 CLI 설명](https://docs.aws.amazon.com/cli/latest/userguide/cli-services-s3-commands.html)

복습할 때는 `get-caller-identity`로 신원을 확인하고, 같은 프로파일로 S3 명령을 실행해 결과를 연결해서 읽는다. `AccessDenied`이면 작업 권한과 제한을 점검하고, 만료된 토큰 오류이면 자격 증명부터 갱신한다. 당시 어떤 세션에서 어떤 버킷이 출력됐는지에 대한 원본 출력은 제공되지 않았다.

## 7. Amazon Linux 2023 EC2 생성 및 접속

### 7.1 생성 설정과 접속 순서

1. 서울 리전에서 Amazon Linux 2023 AMI를 선택한다.
2. 이름을 `ktcloud-vm`, 인스턴스 유형을 `t3.micro`로 설정한다.
3. SSH에 사용할 키 페어를 선택하고 PEM Private Key를 로컬에서 보관한다.
4. `ap-northeast-2c`의 실습 서브넷, Public IP 할당, 라우팅을 확인한다.
5. Security Group에 접속 출발지의 TCP 22를 허용한다.
6. IAM Role `lsmEC2-S3`를 연결한다.
7. Running 및 상태 검사를 확인한 뒤 현재 Public IP로 접속한다.

위 순서는 기록된 설정을 따라 정리한 재현 절차다. 키 페어 이름, 서브넷 ID, 보안 그룹 ID는 제공되지 않았다.

Xshell에서는 프로토콜 SSH, 현재 Public IP, 포트 `22`, 사용자 이름 `ec2-user`, 해당 키 페어의 PEM 파일을 설정한다. Amazon Linux 2023의 기본 사용자 이름은 `ec2-user`다.

> 💡 코멘트: SSH 사용자 이름은 Linux 로그인 계정이다. AWS IAM User 이름이나 계정 Alias를 입력하는 곳이 아니다. IAM Role은 AWS API 권한, PEM은 SSH 인증에 사용되므로 서로 대체할 수 없다.

<!-- 캡처: Xshell 호스트/포트/사용자 설정 및 인증 성공 화면 -->

### 7.2 EC2에서 실행한 명령

```bash
aws s3 ls
```
> 💡 코멘트: EC2 내부에서 S3 목록 조회를 시도해 연결된 Role 권한을 확인했다. CLI는 다른 자격 증명이 우선하지 않는 경우 인스턴스 메타데이터를 통해 Role의 임시 자격 증명을 얻는다. 환경 변수나 저장된 키가 있다면 다른 신원으로 호출될 수 있어 Role 연결만으로 호출자를 단정하지 않는다.

```bash
id
```
> 💡 코멘트: 현재 Linux 사용자의 UID, GID, 소속 그룹을 확인한다. AWS 계정 ID나 IAM Role을 보여주는 명령은 아니다.

```bash
pwd
```
> 💡 코멘트: 현재 작업 디렉터리의 절대 경로를 확인한다. 파일을 찾거나 상대 경로 명령을 실행하기 전에 현재 위치를 파악하는 데 사용한다.

```bash
cd ~/.ssh
```
> 💡 코멘트: 현재 Linux 사용자의 홈 아래 `.ssh` 디렉터리로 이동한다. `~`는 현재 사용자의 홈이므로 `ec2-user`로 실행할 때와 다른 사용자로 실행할 때 경로가 다를 수 있다.

```bash
ls
```
> 💡 코멘트: 현재 디렉터리의 파일 이름을 확인한다. `.ssh`로 이동한 뒤 `authorized_keys` 파일이 있는지 확인하는 단계다.

```bash
cat authorized_keys
```
> 💡 코멘트: 해당 Linux 계정으로 로그인할 수 있는 공개키 목록을 읽는다. 실습 기록에서는 `ssh-rsa`로 시작하는 공개키를 확인했다. 공개키의 존재만으로 로컬 PEM과의 일치가 증명되지는 않으며, 최종적으로 핫스팟에서 해당 PEM으로 SSH 인증이 성공했다.

<!-- 캡처: EC2에서 id, pwd, .ssh 목록과 authorized_keys 확인 -->

### 7.3 PEM과 authorized_keys의 관계

```text
PC의 PEM Private Key ── 소유 증명/서명 ──┐
                                      ▼
                                  SSH 인증 성공
                                      ▲
EC2의 ~/.ssh/authorized_keys ── 공개키로 검증 ─┘
```
> 💡 코멘트: 개인키를 서버에 전송해 대조하는 방식이 아니다. SSH 클라이언트가 개인키 소유를 증명하고 서버가 등록된 공개키로 검증한다. 개인키는 PC에 보관하며 `authorized_keys`에 넣지 않는다. SSH 인증 전에 TCP 연결부터 성립해야 한다.

## 8. VPC와 네트워크 연결 구조

```text
Internet / 접속 PC
    │ EC2의 Public IP:22
    ▼
Internet Gateway (VPC에 연결)
    ▼
VPC
  └─ Public Subnet
       ├─ 연결된 Route Table: 0.0.0.0/0 → Internet Gateway
       └─ EC2의 네트워크 인터페이스
            ├─ Security Group으로 트래픽 제어
            └─ EC2: Private IP 172.31.39.200, sshd TCP 22
```
> 💡 코멘트: 논리 구조도다. Security Group은 EC2 뒤에 놓인 별도 네트워크 장비가 아니라 네트워크 인터페이스의 트래픽을 제어한다. IGW 경로, Public IP, 보안 그룹 허용 등이 함께 갖춰져야 인터넷에서 직접 SSH 접속할 수 있다.

| 개념 | 이번 실습에서의 의미 |
|---|---|
| VPC | EC2를 배치하는 논리적으로 격리된 네트워크 |
| Subnet | 특정 가용 영역에 속하는 VPC 주소 범위 |
| Route Table | 목적지 주소에 따라 트래픽을 보낼 경로 결정 |
| Internet Gateway | VPC와 인터넷 연결에 사용하는 게이트웨이 |
| Security Group | 허용 규칙 기반의 상태 저장 방화벽 |
| Public IP | 인터넷에서 접속 대상으로 사용하는 주소 |
| Private IP | VPC 내부 주소. 집 PC에서 인터넷을 통해 바로 접근하는 주소가 아님 |

```text
Destination: 0.0.0.0/0
Target: Internet Gateway
```
> 💡 코멘트: 더 구체적인 경로에 일치하지 않는 IPv4 목적지를 IGW로 보내는 기본 경로다. 이 라우트가 연결된 서브넷은 퍼블릭 서브넷으로 구성할 수 있지만, 라우트 한 줄이 Public IP를 부여하거나 모든 접속을 허용하는 것은 아니다.

```text
Inbound: SSH / TCP / 22
실습 당시 Source: 0.0.0.0/0
운영 시 권장 Source: 접속자의 공인 IPv4/32 또는 승인된 대역
```
> 💡 코멘트: 기본 SSH 서버가 TCP 22에서 연결을 받으므로 해당 포트를 허용한다. 실습에서는 전체 IPv4를 허용했지만 운영에서는 출발지를 제한한다. 집 PC의 `192.168.0.10`은 사설 IP이므로 인터넷 경유 접속의 보안 그룹 Source에는 일반적으로 집 네트워크의 공인 IP를 사용한다.

<!-- 캡처: VPC/Subnet 연결, 기본 경로가 있는 Route Table, SSH Security Group -->

SSH가 실패하면 Running 여부만 보지 않고 현재 Public IP, 실제 연결된 Security Group, 서브넷의 Route Table, IGW, 필요 시 Network ACL과 서버 상태를 함께 확인한다. [AWS Linux EC2 연결 문제 해결](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/TroubleshootingInstancesConnecting.html)

## 9. 이번 실습에서 기억할 구분

- **IAM User / Role 세션**: 누가 AWS API를 호출하는가.
- **Permission Policy / Trust Policy**: 무엇을 할 수 있는가 / 누가 Role을 맡을 수 있는가.
- **S3 목록 조회 / 객체 접근**: 각각 필요한 권한이 다르다.
- **IAM Role / PEM 키**: AWS API 권한 / Linux SSH 인증이다.
- **TCP 연결 / SSH 인증**: 네트워크 연결이 먼저이며 키 검증은 그다음이다.

마지막 SSH 장애에서는 집 Wi-Fi와 핫스팟의 TCP 22 결과가 달랐다. 원인 범위를 좁힌 과정과 남은 불확실성은 [SSH 트러블슈팅 요약](#ssh-troubleshooting)에서 이어진다.

## 10. SSH 연결 장애 요약 — 집 Wi-Fi와 핫스팟

앞서 제공된 9월 22일 트러블슈팅 기록의 핵심을 함께 보관한다. 이 문서 업로드 과정에서 접속 시험이나 AWS 설정 변경을 실행하지 않았다.

| 점검 | 당시 기록 | 해석 |
|---|---|---|
| EC2 | Running, 상태 검사 3/3 통과 | 상태 검사만으로 외부 SSH 도달성까지 보장하지 않음 |
| 보안 그룹 | SSH TCP 22, 소스 0.0.0.0/0 | 당시 IPv4 인바운드 허용 |
| 서브넷 라우팅 | 0.0.0.0/0 → IGW, 활성 | 확인한 인터넷 기본 경로 정상 |
| 집 Wi-Fi → EC2:22 | TCP 검사 실패 | 인증 이전의 연결 단계 실패 |
| 같은 PC의 핫스팟 → 동일 EC2:22 | TCP 검사 및 Xshell 로그인 성공 | 해당 시점의 SSH 서버·사용자·키 인증 동작 확인 |
| 집 Wi-Fi → github.com:22 | 실패 | 다른 SSH 목적지도 실패한 보조 단서 |
| 집 Wi-Fi → ssh.github.com:443 | TCP 검사 성공 | 해당 목적지의 443 연결 가능; Git 인증·push 성공과는 별개 |

당시 주소를 이용한 Windows PowerShell 확인 명령이다. 현재 실습에서는 EC2 콘솔의 Public IP를 먼저 확인한다.

```powershell
Test-NetConnection 3.39.25.212 -Port 22
```

Xshell 기록:

```text
집 Wi-Fi: Could not connect to '3.39.25.212' (port 22): Connection failed.
핫스팟: Amazon Linux 2023 로그인 화면과 ec2-user 셸 확인
```

집 네트워크 경로 또는 네트워크별 PC 보안 정책을 우선 의심할 수 있으나, **공유기 고장이나 특정 통신사의 차단으로 확정하지 않았다.** Windows 방화벽의 명시적 TCP 22 차단 규칙은 찾지 못했지만 Any·포트 범위·기본 정책·다른 보안 프로그램까지 배제한 검사는 아니었다. NACL과 서버의 출발지별 제한도 별도 확인 대상이다.

ipTIME N600의 WAN은 사설 주소였으며 상위 네트워크가 있는 구조를 시사했다. 이중 NAT 자체나 tracert의 무응답 홉이 SSH 차단의 증거는 아니다. 다른 공유기로 바꿔도 같은 상위 회선을 거칠 수 있다. 유선 연결 시험은 제안했으나 성공·실패 결과는 아직 기록되지 않았다.

- `X11 forwarding rejected`: 경고 뒤 셸 로그인이 성공했으므로 해당 접속 실패와 구분한다.
- `Socket error 10053`: 로그인 후 연결 중단 기록이며, 번호만으로 공유기 원인을 특정하지 않는다.
- EC2의 80/443 실패: 그 포트에 서비스와 허용 규칙이 있는지 확인하지 않았다면 회선 차단의 증거로 사용할 수 없다.
- 임시 해결: 실제 성공을 확인한 핫스팟으로 실습을 진행한다.
- 남은 비교: 다른 PC의 동일 회선 접속, Wi-Fi를 끈 유선 접속, 상위 장비 연결 비교. AWS 설정은 유지하며 한 조건씩 바꿔 확인한다.

참고: [AWS SSH 연결 문제 해결](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/TroubleshootingInstancesConnecting.html), [GitHub SSH 443 연결](https://docs.github.com/en/authentication/troubleshooting-ssh/using-ssh-over-the-https-port)
