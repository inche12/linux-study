# 2026년 9월 15일 — Docker 이미지 제작과 웹 배포

제공된 터미널 출력과 웹 접속 결과를 바탕으로 정리했다. 이미지는 추후 Notion 정리 시 추가하며, 단순 오타와 반복 입력은 제외했다. 명령은 실습 기록이며 실제 확인되지 않은 결과는 따로 표시한다. 로그인 인증 코드와 비밀번호는 기록하지 않는다.

공개 기록에서는 실제 IP를 `ROCKY_IP`, `UBUNTU_HOST_IP`, `UBUNTU_CONTAINER_IP`, `NGINX_CONTAINER_IP`로, Docker Hub 계정과 개인 이름을 예시 표기로 대체했다. 명령 재실행 시 해당 값을 본인 환경에 맞게 바꾼다. `0.0.0.0`, `[::]`, localhost는 수신 범위·루프백을 뜻하는 공통 표기이므로 유지했다.

## 2. VM과 컨테이너

VM Migration은 VM을 다른 물리 서버나 가상화 환경으로 이전하는 작업이다. Cold Migration은 VM을 중지하고 옮기며, Live Migration은 실행 상태를 전달해 서비스 중단을 최소화한다. 디스크 이동 여부는 공유 스토리지 구성 등에 따라 다르다.

| 비교 | VM | 컨테이너 |
|---|---|---|
| 실행 기반 | 하이퍼바이저가 제공하는 가상 하드웨어 | 호스트 커널 |
| OS·커널 | VM마다 게스트 OS와 커널 실행 | 호스트 커널 공유 |
| 격리 | 가상 하드웨어와 OS 단위 | 프로세스·파일시스템·네트워크 등 실행 환경 |
| 자원 사용 | 상대적으로 큼 | 상대적으로 작음 |
| 서버 한 대의 실행 밀도 | 상대적으로 낮음 | 상대적으로 높음 |

namespace는 보이는 프로세스·네트워크 등을 분리하고, cgroups는 자원 사용을 관리한다. VM의 격리가 강하다고 모든 위험이 사라지는 것은 아니며, 컨테이너도 여러 프로세스를 실행할 수 있다.

Docker는 개발·배포 환경의 라이브러리와 설정 차이로 발생하는 문제를 줄이기 위해 애플리케이션과 의존성을 이미지로 묶는다. 이식성이 높지만 커널·CPU 아키텍처 등 호환 조건은 필요하다.

## 3. 이미지·컨테이너·저장소 구조

이미지는 사진이 아니라 **프로그램·라이브러리·파일·실행 설정을 담은 읽기 전용 패키지**다. 컨테이너는 이미지로 생성한 실행 환경이다. 바이너리 파일이라고 해서 본질적으로 수정 불가능한 것은 아니다.

```text
Dockerfile + 파일 ──build──> 이미지 ──run──> 컨테이너
                              ↑                 │
                              └──commit─────────┘
                                  새 이미지 생성

로컬 이미지 ──push──> 레지스트리(Docker Hub)
            <─pull──
```

- 이미지 위에 컨테이너별 쓰기 레이어가 추가된다.
- 이미지 파일을 수정하면 변경 내용이 쓰기 레이어에 기록된다. 원본 이미지는 유지된다.
- CoW(Copy on Write)는 변경할 때 복사한 뒤 수정하는 방식이다. OverlayFS의 파일 수정에서는 하위 파일을 상위 쓰기 레이어로 복사하는 copy-up이 일어난다.
- 중지·재시작하면 쓰기 레이어가 유지되지만, 컨테이너 삭제 시 함께 삭제된다.
- 계속 보관할 데이터는 볼륨이나 바인드 마운트에 저장한다.
- 레지스트리는 이미지 배포 서비스이고, 리포지토리는 그 안에서 이미지와 태그를 관리하는 저장소다.
- `commit`은 파일 변경을 새 이미지로 저장한다. 프로세스 메모리와 볼륨 데이터는 포함하지 않는다. 이번 기록에는 commit 실행 결과는 없다.

## 4. Docker 설치와 사용자 권한

Ubuntu에서 설치 스크립트를 받아 실행한 뒤 `docker ps`가 정상 동작했다. 다운로드와 실행 권한 부여만으로 설치되는 것은 아니며 스크립트를 실행해야 한다.

```bash
curl -fsSL https://get.docker.com -o docker_install.sh
sh docker_install.sh
docker --version
docker ps
```

`-L`은 리다이렉트를 따라가고, `-o`는 파일로 저장한다. `sh 파일`로 실행할 때는 실행 권한 부여가 필수는 아니다.

root에서는 성공했지만 student는 Docker 소켓 접근 권한이 없어 실패했다. 다음으로 해결했다.

```bash
sudo usermod -aG docker student
id -a
id -a student
newgrp docker
docker ps
```

- `-aG`: 기존 그룹을 유지하면서 보조 그룹 추가
- `id`는 현재 프로세스의 그룹, `id student`는 시스템에 등록된 사용자의 그룹을 확인
- 그룹 변경은 기존 세션에 즉시 반영되지 않는다. 재로그인 또는 `newgrp docker`로 적용
- docker 그룹은 호스트를 강하게 제어할 수 있는 권한이므로 신뢰하는 사용자에게 부여

## 5. Docker Client/Server와 원격 제어

```text
Ubuntu의 Docker CLI → Docker API → Rocky의 dockerd → 컨테이너 실행
```

명령 입력 위치와 실행 위치는 다를 수 있다. 데몬이 이미지·컨테이너·네트워크·볼륨을 관리한다.

### Rocky에서 API 수신 설정 — 실습에서 수행한 방식

```bash
systemctl cat docker
vi /usr/lib/systemd/system/docker.service
```

서비스의 ExecStart에 TCP 수신 설정을 추가했다.

```ini
ExecStart=/usr/bin/dockerd -H tcp://0.0.0.0:2375 -H fd:// --containerd=/run/containerd/containerd.sock
```

```bash
systemctl daemon-reload
systemctl restart docker
ss -tlpn | grep docker
firewall-cmd --add-port=2375/tcp --permanent
firewall-cmd --reload
```

`daemon-reload`는 systemd가 서비스 설정을 다시 읽게 하고, 재시작은 변경 내용을 서비스에 적용한다. 패키지의 서비스 파일 직접 수정은 업데이트로 덮어써질 수 있으므로 유지 관리에는 systemd override를 사용하는 편이 적절하다.

처음에는 원격 연결에 `no route to host`가 발생했으며 방화벽에서 2375를 허용한 뒤 성공했다. 이 오류 자체가 항상 방화벽을 뜻하지는 않는다. LISTEN 상태도 방화벽 통과를 보장하지 않는다.

**2375는 일반적으로 TLS 없는 Docker API 포트다. 인증 없이 공개하면 원격 사용자가 호스트를 제어할 수 있으므로 실습망으로 제한하고, 운영에서는 SSH 또는 인증된 TLS 연결을 사용한다.**

### Ubuntu에서 원격 실행

```bash
docker -H s1:2375 ps -a
docker -H s1:2375 run -d nginx
alias rdocker='docker -H s1:2375'
echo "alias rdocker='docker -H s1:2375'" >> ~/.bashrc
rdocker image ls
```

반환된 컨테이너 ID를 Rocky에서도 확인했다. 원격 명령의 `sudo`는 원격 로그인 인증을 대신하지 않는다.

## 6. 이미지 조회와 컨테이너 생명주기

```bash
docker search ubuntu
docker pull ubuntu
docker images
docker image inspect ubuntu:latest
```

- `search`: Docker Hub 검색. 다운로드하지 않음
- `pull`: 로컬 이미지 다운로드
- 태그 생략 시 `latest` 사용. latest는 태그 이름이며 자동 업데이트를 의미하지 않음
- `inspect`의 `Created`는 이미지 생성 시각, `Config.Cmd`는 기본 실행 명령
- Ubuntu 이미지의 기본 명령은 `/bin/bash`로 확인

```bash
docker run nginx
docker ps
docker ps -a
docker stop 컨테이너
docker start 컨테이너
docker rm 컨테이너
docker image rm nginx:latest
```

`run`은 새 컨테이너 생성·시작, `start`는 기존 컨테이너 시작이다. `ps`는 실행 중인 것만, `ps -a`는 중지된 것도 표시한다. `Exited (0)`은 종료 코드 0으로 종료된 상태다. 이미지 삭제는 해당 이미지를 참조하는 컨테이너가 있어 거부됐으며, 컨테이너 중지·삭제와 이미지 삭제는 별개임을 확인했다.

`/var/lib/docker/containers/`에서 전체 컨테이너 ID로 된 디렉토리를 확인했다. 목록의 ID는 축약형이며 다른 컨테이너와 구분되는 앞부분을 명령에 사용할 수 있다. 이 디렉토리가 컨테이너의 모든 파일을 담는 것은 아니다. 이미지의 실제 저장 구조는 저장 방식에 따라 달라지므로 `image/`의 파일 목록만으로 이미지 유무를 판단하지 않고 Docker 명령으로 확인한다.

## 7. foreground/background, attach/exec

```bash
docker run -it --name hello-world ubuntu
```

`-i`는 표준 입력 유지, `-t`는 가상 터미널 할당이다. 옵션 없이 실행한 Ubuntu의 Bash는 바로 종료됐지만 `-it`로 대화형 명령을 입력할 수 있었다.

| 명령 | 동작 |
|---|---|
| `docker run -d nginx` | 터미널 연결을 분리해 실행 |
| `docker attach hello-world` | 기존 메인 프로세스 입출력에 연결 |
| `docker exec -it hello-world /bin/bash` | 추가 Bash 프로세스 실행 |
| `docker exec hello-world ps -ef` | 내부에서 명령 하나 실행 |
| `docker logs -f 컨테이너` | 로그 실시간 확인 |

컨테이너는 PID 1인 메인 프로세스가 종료되면 중지된다. attach로 연결한 메인 Bash에서 exit하면 컨테이너가 중지됐고, exec는 중지된 컨테이너에서 실행할 수 없었다. 다시 start한 뒤 exec가 성공했다.

exec로 연 Bash에서는 PID 1의 기존 Bash와 별도의 Bash가 보였다. 추가 Bash에서 exit한 뒤에도 컨테이너가 유지됐다. `-it`로 만든 컨테이너의 attach 연결은 Ctrl+P 다음 Ctrl+Q로 분리할 수 있다.

Nginx에 attach한 상태에서 Ctrl+C를 누르자 SIGINT가 전달되어 Nginx와 컨테이너가 종료됐다. 로그만 확인하려면 `docker logs -f`를 사용하며 여기서 Ctrl+C는 로그 보기만 끝낸다.

## 8. 컨테이너 내부와 Nginx 프로세스

```bash
hostname
cat /etc/hosts
id
df -h
ps -ef
env
```

- 기본 호스트 이름은 컨테이너 ID 앞부분이었다.
- `/etc/hosts`에 내부 IP와 호스트 이름 연결이 기록됐다.
- `id`의 root는 현재 실행한 컨테이너 셸 사용자다. 모든 서비스 프로세스가 root라는 뜻은 아니다.
- `df`의 overlay는 이미지와 쓰기 레이어를 합친 파일시스템이다. 표시된 64GB는 컨테이너 전용 할당량이 아니다.
- 이미지마다 포함된 도구가 다르다. Nginx 이미지에서 `ps`, `ip`가 없었지만 서비스와 네트워크는 동작했다.
- `env`로 PATH, HOSTNAME, NGINX_VERSION 등의 환경 변수를 확인했다.

Ubuntu 컨테이너에 Nginx를 설치한 뒤 다음을 비교했다. 설치 명령의 전체 출력은 생략됐지만 Nginx 실행 결과는 확인됐다.

```bash
nginx
ps -ef
pkill nginx
nginx -g "daemon off;"
```

`nginx`는 기본적으로 백그라운드로 분리되고, `daemon off;`는 포그라운드 실행을 유지한다. 이 실습에서는 Bash가 PID 1, Nginx master가 그 자식, www-data 사용자로 worker가 실행됐다. 포그라운드 실행만으로 Nginx가 PID 1로 바뀌지는 않는다.

## 9. 웹 페이지 수정과 내부 접속

Ubuntu 컨테이너의 `/etc/nginx/nginx.conf`에서 www-data 사용자와 worker 설정을 확인하고 웹 문서를 수정했다.

```bash
cd /var/www/html
mv index.nginx-debian.html index.nginx-debian.ori
cat > index.html
This is my home page.
# Ctrl+D로 입력 종료
ls
```

최종 파일은 `index.html`, `index.nginx-debian.ori` 두 개다. 기본 페이지를 백업하고 새 페이지를 제공했다.

```bash
apt update
apt install -y curl
curl http://localhost
curl http://UBUNTU_CONTAINER_IP
```

두 요청 모두 `This is my home page.`를 반환했다. 이때 Ubuntu 컨테이너 IP는 `UBUNTU_CONTAINER_IP`였다. 별도 Nginx 컨테이너는 `NGINX_CONTAINER_IP`이었으며 Rocky에서 curl로 기본 페이지 응답을 확인했다. 컨테이너 IP는 재생성 시 달라질 수 있다.

```bash
docker container inspect a67
docker exec a67 cat /etc/hosts
```

컨테이너 내부의 localhost는 해당 컨테이너 자신이다. 호스트에서 내부 IP로 직접 접속하는 것과 외부 PC에서 호스트 공개 포트로 접속하는 것은 구분한다.

## 10. Dockerfile로 웹 서버 이미지 만들기

수동 설치·파일 배치 작업을 Dockerfile에 기록해 반복 가능한 제작 과정으로 바꿨다. vi는 편집기이며 Dockerfile은 지시서다. 기존 컨테이너의 변경 내용을 자동 수집하는 과정은 아니다.

```bash
mkdir docker_class
cd docker_class
mkdir nginx
vi nginx/Dockerfile
```

빌드 컨텍스트 구성:

```text
/root/docker_class/nginx/
├── Dockerfile
└── index.html
```

실습에서 사용한 Dockerfile:

```dockerfile
FROM ubuntu
RUN apt update
RUN apt install -y nginx
CMD nginx -g "daemon off;"
COPY index.html /var/www/html/
```

| 지시어 | 의미 |
|---|---|
| FROM | 기반 이미지 |
| RUN | 빌드 중 실행 |
| COPY | 빌드 컨텍스트의 파일을 이미지에 복사 |
| CMD | 컨테이너 시작 시 기본 명령 지정 |

CMD는 빌드 중 실행되지 않는다. 실습의 CMD는 shell 형식으로 `docker ps`에 `/bin/sh -c ...`가 표시됐다. 개선 시 `CMD ["nginx", "-g", "daemon off;"]`와 같은 exec 형식으로 셸을 거치지 않도록 할 수 있다. 이 개선안은 실제 빌드 기록과 구분한다.

```bash
docker build -t test:nginx nginx/
docker images
```

`test`는 이미지 이름, `nginx`는 태그, `nginx/`는 빌드 컨텍스트다. 빌드 완료 후 이미지 ID `d19c0eb9b9fc`를 확인했다.

## 11. 포트 매핑으로 웹 배포

```bash
docker run -d -p 81:80 --name web test:nginx
docker ps
```

```text
브라우저 → ROCKY_IP:81 → web 컨테이너:80 → index.html
```

`-p 호스트포트:컨테이너포트`는 호스트로 들어오는 요청을 컨테이너 포트로 전달하도록 구성한다. 출력의 `0.0.0.0:81->80/tcp`, `[::]:81->80/tcp`는 호스트 IPv4·IPv6 인터페이스의 공개 포트다. 단순 `80/tcp` 표시만으로 호스트 포트가 공개된 것은 아니다.

브라우저에서 `http://ROCKY_IP:81`로 접속해 `This is my home page.`를 확인했다. 웹 배포는 이미지 제작뿐 아니라 컨테이너 실행과 외부 접근 경로 설정까지 포함한다.

## 12. Docker Hub 태그·로그인·push

```bash
docker tag test:nginx docker.io/MY_DOCKERHUB_ID/test:nginx
docker images
docker login
docker push MY_DOCKERHUB_ID/test:nginx
```

`test:nginx`와 `MY_DOCKERHUB_ID/test:nginx`의 ID가 같았다. 태그는 이미지 복제가 아니라 같은 이미지에 이름을 추가한 것이다.

```text
docker.io / MY_DOCKERHUB_ID / test : nginx
레지스트리 / 네임스페이스 / 저장소 : 태그
```

웹 인증 과정은 요청 제한으로 실패했고, push는 `insufficient_scope: authorization failed`로 거부됐다. **본인 이미지 push 성공은 제공된 기록에서 확인되지 않았다.** 일부 `Layer already exists` 출력은 전체 업로드 성공을 뜻하지 않는다.

후속 안내는 `docker login -u MY_DOCKERHUB_ID`로 인증한 뒤 재시도하는 것이었다. 개인 액세스 토큰을 쓴다면 업로드 가능한 쓰기 권한이 필요하다. 실제 완료 여부와 구분해 기록한다.

## 13. 공유 이미지 실행과 82번 포트 충돌 해결

```bash
docker run -d -p 82:80 SHARED_DOCKERHUB_ID/test:nginx
```

이미지는 다운로드됐지만 호스트 82번 포트가 사용 중이어서 컨테이너 시작은 실패했다.

```bash
ss -ltnp 'sport = :82'
```

결과에서 `httpd`가 `*:82`를 LISTEN 중이었다. 여러 Apache 프로세스가 같은 수신 소켓을 공유하고 있었다. 따라서 `ROCKY_IP:82`의 `This is www test page..`는 기존 호스트 Apache의 응답이며, 실패한 컨테이너의 응답이 아니다.

83번으로 바꿔 실행했다.

```bash
docker run -d -p 83:80 --name shared-web SHARED_DOCKERHUB_ID/test:nginx
```

컨테이너 ID `bcc897239772...`가 반환됐고 브라우저에서 `http://ROCKY_IP:83`에 접속해 `This is a classmate's home page...`를 확인했다. 공유 이미지로 다른 환경에서 웹 서비스를 재현한 결과다.

### 최종 웹 접속 확인

| 주소 | 응답 | 확인된 서비스 |
|---|---|---|
| `ROCKY_IP:81` | This is my home page. | `web`, 직접 제작한 test:nginx |
| `ROCKY_IP:82` | This is www test page.. | Rocky 호스트 Apache(httpd) |
| `ROCKY_IP:83` | This is a classmate's home page... | `shared-web`, 공유 이미지 |
| `UBUNTU_HOST_IP:81` | This is another classmate's home page.... | 브라우저 응답 확인. 이 기록만으로 컨테이너 구성은 확정하지 않음 |

## 14. 명령어 빠른 정리

| 목적 | 명령 |
|---|---|
| 이미지 검색·다운로드 | `docker search ubuntu`, `docker pull ubuntu` |
| 이미지 조회 | `docker images`, `docker image inspect 이미지` |
| 컨테이너 조회 | `docker ps`, `docker ps -a` |
| 기존 컨테이너 시작·중지 | `docker start 이름`, `docker stop 이름` |
| 기존 프로세스 연결 | `docker attach 이름` |
| 추가 셸 실행 | `docker exec -it 이름 bash` |
| 로그 조회 | `docker logs -f 이름` |
| 컨테이너·이미지 삭제 | `docker rm 이름`, `docker image rm 이미지` |
| 이미지 제작 | `docker build -t 이름:태그 경로` |
| 웹 포트 공개 | `docker run -d -p 호스트포트:80 이미지` |
| 원격 데몬 선택 | `docker -H s1:2375 ps` |
| 이미지 배포 | `docker tag 원본 계정/저장소:태그`, `docker push 계정/저장소:태그` |
| 포트 점유 확인 | `ss -ltnp 'sport = :82'` |

**핵심 흐름: 실행 환경을 이미지로 패키징 → 컨테이너 생성 → 프로세스·파일·네트워크 관리 → 포트 매핑으로 웹 공개 → 레지스트리를 통한 공유.**
