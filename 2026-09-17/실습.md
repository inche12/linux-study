# 9월 17일 Docker와 Kubernetes 실습 정리

Docker 사설 레지스트리와 네트워크를 확인하고, Compose로 WordPress와 MySQL을 실행했다. 이어 Kubernetes 구성 요소를 학습하고 Ubuntu 마스터 VM을 준비한 뒤 초기화 검증과 reset을 완료했다. 워커 VM은 별도로 준비하여 `192.168.120.151`에 SSH 접속했다. 이어 저녁 실습에서 Calico 구동과 w1 가입을 확인하고, master1과 w1 모두 Ready 상태까지 완료했다.

오늘의 대화·실행 로그와 제공된 `ktcloud-infra-k8s-강의노트.md`를 바탕으로 정리했다. 실제 확인된 결과와 강의의 다음 단계를 구분한다. RAM 성능, PC 이전, Codex 공유 관련 대화는 제외했다. 비밀번호·사용자 이메일·비밀번호 해시는 싣지 않았다.

## 1 실습 환경과 실행 위치

| 환경 | 주소 또는 경로 | 역할 |
|---|---|---|
| 기존 Rocky Docker 호스트 | `192.168.120.128` | 레지스트리, 이미지 빌드, Docker 네트워크와 Compose |
| 기존 Ubuntu Docker 호스트 | 수업에서 설정한 주소 | 레지스트리 API 조회와 이미지 작업 |
| Kubernetes master1 | 최초 DHCP `.129` → 고정 `192.168.120.150` | Ubuntu 24.04 컨트롤 플레인 준비 |
| Kubernetes w1 | `192.168.120.151` | 복제한 Ubuntu 워커 VM 준비 |
| Rocky 작업 폴더 | `/root/docker_class` | `cmd/`, `registry/`, `wp/` 실습 폴더 |

위 IP는 실습 환경의 기록이다. 다른 환경에 그대로 적용하기 전에 네트워크 대역을 확인한다.

| 프롬프트 예 | 현재 위치 | 입력하는 명령 |
|---|---|---|
| `root@rocky10:...#` | Rocky 호스트 | `docker`, `docker compose` |
| `/ #`, `bash-4.2#` | 컨테이너 안의 셸 | `ip`, `ping`, `wget`, `mysql` |
| `mysql>` | MySQL 클라이언트 | `SELECT`, `SHOW TABLES;` 등 SQL |
| Xshell 로컬 셸 | SSH 접속 전 Windows 측 | SSH 연결 명령; Linux의 `ip a` 실행 위치가 아님 |

## 2 사설 레지스트리 설정과 이미지 확인

### daemon.json 설정

Ubuntu의 `/etc/docker/daemon.json`에 HTTP 실습 레지스트리를 등록했다.

```json
{
  "insecure-registries": [
    "192.168.120.128:5000",
    "s1:5000",
    "rocky10:5000"
  ]
}
```

`5000i`처럼 포트 뒤에 잘못 붙은 문자를 지우고 Docker를 재시작했다.

```bash
sudo systemctl restart docker
sudo systemctl status docker --no-pager
```

실제 결과는 `Active: active (running)`이었다. 파일만 수정하면 적용되지 않으며, 재시작 성공까지 확인해야 한다. 이미 레지스트리에 정상 업로드한 이미지는 설정 변경 때문에 다시 push할 필요가 없다.

```bash
docker tag ubuntu:latest 192.168.120.128:5000/test:ubuntu
docker push 192.168.120.128:5000/test:ubuntu
curl http://s1:5000/v2/_catalog
curl http://s1:5000/v2/test/tags/list
```

실제 조회 결과:

```json
{"repositories":["test"]}
{"name":"test","tags":["alpine","cmd","ubuntu"]}
```

별도 요청 방식이나 데이터 옵션이 없는 `curl`은 GET을 사용하므로 `-X GET`을 생략했다. IP와 포트 사이에는 점이 아니라 콜론을 쓴다.

### 멀티 플랫폼 이미지

Rocky의 `/root/docker_class`에서 실행했다.

```bash
docker buildx build --platform linux/amd64,linux/arm64 \
  -t 192.168.120.128:5000/multi:cmd cmd/ --push
```

- `--platform`: AMD64와 ARM64용 이미지 빌드.
- `-t`: 레지스트리 주소, 저장소 `multi`, 태그 `cmd` 지정.
- `cmd/`: 현재 디렉터리를 기준으로 찾는 빌드 컨텍스트. `cmd/Dockerfile` 사용.
- `--push`: 빌드 결과를 바로 업로드하므로 별도의 push가 필요하지 않다.

Ubuntu 홈에서 실행한 첫 시도는 `cmd/`가 없어 실패했다. Rocky 전용 명령이 아니라, 파일이 있는 위치에서 실행해야 하는 명령이다. Rocky에서는 두 플랫폼의 빌드 및 `pushing manifest`까지 성공했다.

```bash
curl http://192.168.120.128:5000/v2/multi/manifests/cmd
```

응답은 OCI image index였고 `linux/amd64`, `linux/arm64` 이미지가 각각 포함되어 있었다. 추가된 `unknown/unknown` 두 항목은 `attestation-manifest`로 표시된 빌드 부가 정보이며 플랫폼 빌드 실패를 뜻하지 않는다.

## 3 Docker 네트워크

| 방식 | 의미 |
|---|---|
| Bridge | 같은 호스트의 컨테이너를 가상 네트워크로 연결 |
| None | 외부 네트워크 인터페이스 없이 실행. `null` 드라이버이며 VM Host-Only와 다름 |
| Container 공유 | 다른 컨테이너의 네트워크 네임스페이스 공유 |
| Host | 호스트의 네트워크 네임스페이스 공유 |
| Macvlan | 컨테이너가 물리망에서 별도 네트워크 장비처럼 통신 |
| Overlay | 여러 Docker 호스트의 컨테이너를 연결하는 네트워크. Swarm 실습에서 사용 |

`docker network create -d bridge`의 `-d`는 드라이버 선택이고, `docker run -d`의 `-d`는 백그라운드 실행이다.

### 사용자 정의 Bridge 생성

```bash
alias d='docker'
d network create net3 --subnet=172.21.0.0/16
d network ls
d run -d --net=net3 --name web nginx
d exec web cat /etc/hosts
```

`net3`는 `bridge`, `local`로 생성되었고 `web`의 IP는 `172.21.0.2`였다. 게이트웨이와 할당 범위를 별도로 지정하는 문법은 다음과 같다. 아래는 보충 예시이며 별도 실행 결과는 없다.

```bash
docker network create -d bridge \
  --subnet=172.31.0.0/16 --ip-range=172.31.0.0/24 \
  --gateway=172.31.0.1 my-net
```

### Alpine 셸과 통신

```bash
d run --net=net3 -it alpine /bin/sh
```

Alpine 기본 이미지에는 Bash가 없어 `/bin/bash`를 직접 지정하면 실패했다. 컨테이너 안에서 필요할 때 설치한다.

```sh
apk add --no-cache bash
exec /bin/bash
wget -qO- http://web
```

Nginx의 `Welcome to nginx!` HTML을 받았다. Bash 설치는 해당 컨테이너에만 반영되므로 새 Alpine에는 자동 적용되지 않는다. 컨테이너 안에서 호스트의 별칭 `d`를 실행하면 `command not found`가 발생한다.

별도 Alpine에서는 다음을 확인했다.

```sh
ip a
ping -c 2 web
```

Alpine `172.21.0.3`에서 `web`의 `172.21.0.2`로 ping 2회, 손실률 0%였다. `ping -c2 registry 'registry-server'`는 대상 두 개를 지정한 문법 오류다. 한 번에 호스트 하나만 지정한다.

```bash
d run --net=net3 --rm --link web:nginx alpine ping -c2 nginx
```

실습에서는 `web`을 `nginx`라는 별칭으로 찾아 ping에 성공했다. `--rm`은 실행이 끝난 임시 컨테이너를 삭제한다. `--link`는 오래된 연결 방식이며, 사용자 정의 Bridge에서는 기본적으로 컨테이너 이름으로 조회할 수 있다.

### web 네트워크 공유

```bash
docker run --net=container:web -it alpine
```

새 Alpine에서도 `web`과 같은 인터페이스와 IP `172.21.0.2`가 보였다. 별도 IP를 받은 것이 아니라 네트워크 공간을 공유한 것이다. 파일 시스템까지 공유하는 것은 아니다. 이 구성에서는 Alpine의 `127.0.0.1:80`으로 web의 Nginx에 접근할 수 있다.

## 4 Compose로 레지스트리와 WordPress 실행

Compose는 여러 서비스의 이미지, 포트, 환경변수, 네트워크, 저장 공간을 YAML에 정의하고 함께 관리한다. 서비스들이 같은 Compose 기본 네트워크에 연결되면 서비스 이름으로 접근할 수 있다.

### 레지스트리를 Compose로 전환

`/root/docker_class/registry/compose.yaml`:

```yaml
services:
  registry-server:
    image: registry
    restart: always
    container_name: registry-server
    ports:
      - "5000:5000"
    volumes:
      - "/registry:/var/lib/registry"
```

`docker compose up -d` 실행 시 기존 `registry-server` 이름과 충돌했다. 먼저 저장 위치를 확인했다.

```bash
docker inspect registry-server --format '{{json .Mounts}}'
```

실제 결과는 `Type: bind`, `Source: /registry`, `Destination: /var/lib/registry`였다. Compose 설정과 일치하므로 다음 교체 절차를 안내했다. 교체 후 실행 결과는 별도로 제시되지 않았다.

```bash
docker stop registry-server
docker rm registry-server
docker compose up -d
docker compose ps
curl http://localhost:5000/v2/_catalog
```

컨테이너 삭제와 호스트의 `/registry` 폴더 삭제는 다르다. 같은 폴더를 다시 마운트하면 기존 데이터를 사용할 수 있다. 모든 컨테이너를 강제 삭제하는 `drmall`은 이 이름 충돌 하나를 해결하기 위해 필요하지 않다.

### WordPress와 MySQL

`/root/docker_class/wp/compose.yaml` 구조를 아래처럼 맞췄다. 공개 정리본에는 비밀번호 대신 환경변수 참조를 사용했다. 실제 사용 시 `WORDPRESS_DB_PASSWORD`를 먼저 설정해야 하며, 기존 DB의 비밀번호와 일치해야 한다.

```yaml
services:
  wordpress:
    image: wordpress
    restart: always
    ports:
      - "8080:80"
    environment:
      WORDPRESS_DB_HOST: db
      WORDPRESS_DB_USER: exampleuser
      WORDPRESS_DB_PASSWORD: ${WORDPRESS_DB_PASSWORD:?DB 비밀번호를 설정하세요}
      WORDPRESS_DB_NAME: exampledb

  db:
    image: mysql:5.7
    restart: always
    environment:
      MYSQL_DATABASE: exampledb
      MYSQL_USER: exampleuser
      MYSQL_PASSWORD: ${WORDPRESS_DB_PASSWORD:?DB 비밀번호를 설정하세요}
      MYSQL_RANDOM_ROOT_PASSWORD: '1'
```

`wordpress`와 `db`는 같은 들여쓰기 수준이다. 포트 목록은 `- "8080:80"`처럼 하이픈 뒤에 공백을 넣는다. MySQL 5.7은 이날 강의에서 사용한 버전 기록이다.

```bash
docker compose config
docker compose up -d
docker compose ps
```

실제 생성 및 실행 결과:

- `wp_default` 네트워크 생성.
- `wp-db-1`과 `wp-wordpress-1` 모두 `Up`.
- WordPress 포트는 `0.0.0.0:8080->80/tcp`.
- `http://192.168.120.128:8080/wp-admin/`에서 관리자 로그인 성공.

```text
브라우저 → Rocky의 8080 → WordPress의 80 → db:3306 → MySQL
```

이 구성에는 명시적인 DB 영구 볼륨 선언이 없다. 컨테이너 stop/start와 삭제 후 재생성은 다르므로, 재생성 후 데이터 유지까지 검증한 것으로 보지 않는다.

### DB 컨테이너와 SQL

Rocky 호스트에서:

```bash
docker exec -it wp-db-1 /bin/bash
# wp 폴더에서는 아래 명령으로 같은 서비스에 접속 가능
docker compose exec db /bin/bash
```

컨테이너 셸에서:

```bash
mysql -u exampleuser -p exampledb
```

`-p` 뒤에 비밀번호를 직접 쓰지 않고 프롬프트에서 입력한다. `mysql>`이 나타나면 SQL을 입력한다.

```sql
SHOW TABLES;
SELECT ID, user_login, display_name FROM wp_users;
DESC wp_users;
SELECT DATABASE();
SHOW GRANTS;
```

확인된 WordPress 테이블은 12개였다.

```text
wp_commentmeta  wp_comments  wp_links  wp_options
wp_postmeta     wp_posts     wp_term_relationships
wp_term_taxonomy  wp_termmeta  wp_terms  wp_usermeta  wp_users
```

사용자 테이블에서는 설치 시 만든 계정 1개가 확인되었다. `user_pass`는 비밀번호 원문이 아닌 해시다.

첫 `show tables`에 세미콜론이 빠져 다음 줄의 `show tables;`와 합쳐지며 문법 오류가 발생했다. `->`는 추가 입력을 기다리는 상태다. `;`로 마치거나 `\c`로 입력을 취소한다.

| SQL | 역할 |
|---|---|
| SELECT | 조회 |
| INSERT / UPDATE / DELETE | 행 추가 / 수정 / 삭제 |
| CREATE / ALTER / DROP | DB·테이블 생성 / 구조 변경 / 삭제 |
| GRANT / REVOKE | 권한 부여 / 회수 |
| COMMIT / ROLLBACK | 트랜잭션 확정 / 미확정 변경 취소 |

`UPDATE`, `DELETE`는 WHERE 없이 실행하면 전체 행에 영향을 줄 수 있다. 권한 관리 명령은 접속 계정에 필요한 권한이 있어야 한다.

웹에서 글을 입력하면 WordPress의 서버 프로그램(PHP)이 MySQL에 저장한다. 페이지를 열 때 DB 내용을 조회하여 HTML을 만들고, 브라우저가 CSS와 함께 표시한다. HTML·CSS만으로 DB를 직접 관리하는 구조가 아니다.

### Compose 관리 명령

```bash
alias dp='docker compose'
dp top wordpress
dp logs db
dp logs --tail=30 db
dp logs -f db
dp exec -it db /bin/bash
dp stop wordpress
dp start wordpress
dp ps
```

- `top`: Apache 프로세스 여러 개를 확인했다. 컨테이너 여러 개라는 뜻은 아니다.
- `logs`: MySQL 시작·초기화 기록을 확인했다. TIMESTAMP Warning만으로 시작 실패를 뜻하지 않는다.
- `logs -f`의 Ctrl+C는 로그 보기만 종료한다.
- `exec`로 연 셸에서 `exit`하면 셸만 종료되고 DB는 계속 실행된다.
- WordPress stop/start 후 DB는 `Up 21 minutes`, WordPress는 `Up 4 seconds`였다. 해당 서비스만 중지·시작된 것이다.

## 5 Alpine을 두 Compose 네트워크에 연결

```bash
docker run --net=wp_default -it alpine
```

컨테이너 안에서:

```sh
ping -c 2 db
cat /etc/resolv.conf
nslookup wordpress
```

`db`는 `172.19.0.3`, `wordpress`는 `172.19.0.2`로 확인되었다. DNS 서버는 Docker의 내장 DNS `127.0.0.11`이었다. `/etc/hosts`에 서비스 이름이 없어도 DNS로 찾을 수 있다.

Rocky 호스트에서 실행 중인 Alpine에 두 번째 네트워크를 추가했다.

```bash
docker network connect registry_default 9de664c5a3b0
```

컨테이너 ID는 당시 기록이며 재사용하려면 `docker ps`로 확인한다.

| 인터페이스 | IP | 네트워크 |
|---|---|---|
| eth0 | `172.19.0.4/16` | wp_default |
| eth1 | `172.18.0.3/16` | registry_default |

```sh
ip a
ping -c 3 registry-server
```

`registry-server`가 `172.18.0.2`로 해석되고 ping 3회 손실률 0%였다. Alpine이 양쪽 망에 연결된 것이며, 두 네트워크 전체가 합쳐지거나 모든 컨테이너가 서로 통신하도록 바뀐 것은 아니다.

## 6 Kubernetes 개념

### 전체 구조

```text
클러스터
├─ 컨트롤 플레인 노드: API와 클러스터 관리
└─ 워커 노드: 애플리케이션 실행
   └─ Pod: 하나 이상의 컨테이너를 묶는 기본 실행 단위
      └─ 컨테이너
```

| 구성 요소 | 역할 |
|---|---|
| kube-apiserver | 관리 요청을 받고 인증·권한·요청 검증 수행 |
| etcd | 클러스터 설정과 상태 저장 |
| kube-controller-manager | 원하는 상태와 현재 상태를 비교해 조정 |
| kube-scheduler | 아직 배치되지 않은 Pod가 실행될 노드 선택 |
| cloud-controller-manager | 클라우드 인프라와 연동 |
| kubelet | 각 노드의 에이전트. 런타임에 Pod 컨테이너 실행 요청, 상태 보고 |
| containerd | 실제 컨테이너 실행을 관리하는 런타임 |
| kube-proxy | Service 트래픽이 Pod로 전달·분산되도록 네트워크 규칙 관리 |
| CNI 플러그인 | Pod 네트워크 구성 |

일반적인 Kubernetes 구성 요소는 API 서버를 통해 클러스터 상태에 접근한다. etcd를 각자 직접 수정하지 않고 검증된 API를 거치므로 상태 무결성을 관리하기 쉽다. 애플리케이션의 웹 요청까지 API 서버를 경유한다는 뜻은 아니다.

예를 들어 Pod 3개를 유지해야 하는데 하나가 사라지면, 컨트롤러가 대체 Pod를 만들고 스케줄러가 노드를 선택하며 해당 노드의 kubelet이 런타임에 실행을 요청한다. kube-proxy가 CPU 사용률을 보고 가장 한가한 Pod를 고르는 것은 아니다.

### 고가용성

| 구성 요소 | 일반적인 HA 동작 |
|---|---|
| API 서버 | 여러 인스턴스가 동시에 요청 처리하는 Active–Active |
| 스케줄러 | 리더 선출 후 리더가 배치 담당, 장애 시 승계 |
| 컨트롤러 매니저 | 리더 선출 후 주된 제어 작업 담당, 장애 시 승계 |
| etcd | 리더가 쓰기를 조율하고 멤버 과반수 합의로 반영 |

컨트롤 플레인 노드 전체를 하나의 Active–Standby 묶음으로 이해하지 않는다. 컴포넌트마다 리더가 다를 수 있다. etcd 3멤버 구성은 2멤버가 정상일 때 과반수를 유지한다. API 앞의 로드밸런서도 자체 장애에 대비해야 한다.

### 대시보드 용어

| 용어 | 의미 |
|---|---|
| Namespace | 자원을 논리적으로 구분하는 공간 |
| Node | 클러스터에 참여한 서버 |
| Deployment | Pod 복제 수와 업데이트 관리 |
| DaemonSet | 대상 노드마다 Pod 실행 |
| CronJob | 정해진 시간에 작업 실행 |
| Service / ClusterIP | Pod 접근 창구 / 클러스터 내부의 Service IP |
| PersistentVolume | 영구 저장 공간 자원 |
| StorageClass | 저장 공간 제공 방식 정의 |
| Role | 자원에 수행 가능한 작업의 권한 규칙 |
| Secret | 비밀번호·토큰 등 민감한 설정을 위한 자원 |
| Ingress | HTTP 경로·호스트에 따른 Service 연결 규칙; 컨트롤러가 실제 처리 |

### 도구와 환경 구분

- `kubeadm`: 클러스터 초기 구성과 노드 가입을 돕는 도구.
- `kubectl`: 클러스터 API를 조회·조작하는 클라이언트.
- Swarm: Docker의 클러스터 관리 기능. Kubernetes와 같은 오케스트레이션 범주.
- Compose: 함께 사용할 서비스를 파일에 정의하고 실행하는 도구.
- 온프레미스: 자체 시설의 서버 운영 방식. 인트라넷은 내부 구성원용 네트워크라는 별도 기준.
- kOps: 클라우드 자원과 연동한 클러스터 구축·운영 도구. 클라우드의 유일한 방식은 아님.
- Kubespray: Ansible 기반 Kubernetes 구축 자동화. 온프레미스와 클라우드 모두 활용 가능.
- WSL2: Windows의 Linux 실행 환경. Git Bash는 명령 입력용 셸 환경이며 Docker 엔진이 아님.

## 7 Kubernetes 노드 준비와 오류 해결

상세 설정과 다음 순서는 [Kubernetes 구축 로드맵](Kubernetes-구축-로드맵.md)에 정리했다.

### 호스트 이름과 고정 IP

Xshell에서 처음 `.129`로 Ubuntu에 접속한 뒤 실행했다.

```bash
sudo -i
hostnamectl set-hostname master1
exec bash
vi /etc/hosts
```

```text
127.0.0.1 localhost
127.0.1.1 master1
192.168.120.150 master1
192.168.120.151 w1
```

`/etc/hosts`는 이름과 주소의 대응표다. 실제 IP는 Netplan에서 변경했다.

`/etc/netplan/50-cloud-init.yaml`:

```yaml
network:
  version: 2
  ethernets:
    ens160:
      dhcp4: false
      addresses: [192.168.120.150/24]
      nameservers:
        addresses: [192.168.120.2, 8.8.8.8]
      routes:
        - to: default
          via: 192.168.120.2
```

```bash
netplan generate
netplan apply
```

`generate`가 오류 없이 끝난 뒤 적용했다. 적용 시 SSH 연결이 끊겼고 새 IP `.150`으로 재접속했다. `cat <<END`와 `END`는 셸의 파일 생성 문법이므로 vi에서 YAML 내용으로 입력하지 않는다.

### containerd 설정

```bash
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/g' /etc/containerd/config.toml
grep SystemdCgroup /etc/containerd/config.toml
sudo systemctl restart containerd
```

처음에는 닫는 따옴표와 `/etc/containerd/config.toml` 사이 공백이 없어 sed 오류가 발생했다. 고정 줄 번호 대신 실제 설정 항목을 확인한다.

### init 검증과 reset

```bash
sudo kubeadm init --pod-network-cidr=172.20.0.0/16
```

다시 실행했을 때 6443·10250·2379 등 포트 사용 중, manifest 파일 존재, etcd 디렉터리 비어 있지 않음 오류가 발생했다. 기존 초기화가 남아 있는 상태였다.

```bash
sudo kubectl --kubeconfig=/etc/kubernetes/admin.conf get nodes -o wide
sudo kubectl --kubeconfig=/etc/kubernetes/admin.conf get pods -A
sudo kubectl --kubeconfig=/etc/kubernetes/admin.conf describe node master1
```

실제 결과:

- `master1`: `NotReady`, `control-plane`, `192.168.120.150`.
- Kubernetes `v1.36.4`, containerd `2.3.5`.
- etcd·API 서버·컨트롤러·스케줄러·kube-proxy: Running.
- CoreDNS: Pending.
- 원인: `cni plugin not initialized`.
- 노드 PodCIDR: `172.20.0.0/24`. 전체 Pod 대역 `/16` 안에서 노드에 배정된 범위.

강의의 이 단계는 클러스터 완성이 아니라 **노드용 VM의 초기화 검증 → reset → 종료 → 복제**였다. 따라서 여기서는 CNI 설치 없이 reset으로 진행했다.

```bash
sudo kubeadm reset
# 확인 질문에 y
sudo shutdown -h now
```

처음 `sudo` 없이 실행하여 `IsPrivilegedUser` 오류가 났다. 관리자 권한으로 다시 실행한 결과 etcd 데이터와 Kubernetes 파일 삭제, kubelet 중지가 확인되었다. 마지막 CNI·필터 규칙·kubeconfig 미정리 안내는 reset 실패가 아니다.

워커는 복제 후 호스트 이름 `w1`, 고정 IP `.151`로 준비하고 Xshell 연결까지 확인했다. 이후 이어서 진행한 클러스터 구성 결과는 아래에 기록했다.


### 이어서 진행한 실습: master1과 w1 모두 Ready

#### 호스트 이름과 Swap 확인

호스트 이름 변경 인증은 정상 완료되었지만 기존 셸 프롬프트에 이전 이름이 남아 있었다. 실제 이름은 `hostname`으로 확인하고, `exec bash` 또는 SSH 재접속으로 프롬프트를 새로 표시한다.

마스터에서 확인한 Swap 설정:

```bash
swapon -s
sudo swapoff -a
sudo sed -i '/swap/s/^/#/' /etc/fstab
grep swap /etc/fstab
swapon -s
```

`/etc/fstab`의 해당 항목은 다음처럼 주석 처리되었고 마지막 `swapon -s` 출력은 비어 있었다.

```text
#/swap.img      none    swap    sw      0       0
```

현재 활성 Swap이 없고 해당 파일의 부팅 시 자동 활성화가 해제된 상태다. 재부팅 후 검증 결과는 이번 로그에 없다. 위 sed는 실행 기록이며 반복 실행용 스크립트가 아니다.

#### Calico와 시스템 Pod 확인

마스터에서 `custom-resources.yaml`을 편집하고 적용한 결과 Installation, APIServer, Goldmane, Whisker 자원의 생성 메시지를 확인했다. Tigera Operator 설치 명령에는 Calico `v3.32.2`가 사용되었다. 실제 편집한 YAML 전체는 이번 대화에 제공되지 않았다.

```bash
kubectl get pods -A -o wide
watch -n 2 'kubectl get pods -A -o wide'
```

워커 가입 전에는 master1의 Calico 구성 요소, CoreDNS, 컨트롤 플레인 Pod가 모두 Running이고 READY 수가 충족된 화면을 확인했다. `watch` 종료는 Ctrl+C이며 클러스터를 중지하는 동작이 아니다.

#### 마스터에서 join을 실행한 오류

처음에는 `root@master1`에서 워커 가입 명령을 실행하여 아래 오류가 발생했다.

```text
[ERROR FileAvailable--etc-kubernetes-kubelet.conf]: /etc/kubernetes/kubelet.conf already exists
[ERROR Port-10250]: Port 10250 is in use
[ERROR FileAvailable--etc-kubernetes-pki-ca.crt]: /etc/kubernetes/pki/ca.crt already exists
```

이미 구성된 마스터의 파일과 kubelet 포트가 존재하기 때문이다. 이 상황에서는 마스터를 reset하거나 preflight 오류를 무시하는 대신, 실제 워커 서버로 이동해야 한다.

Xshell 탭 이름만으로 접속 대상을 판단하지 않고 워커에서 확인했다.

```bash
hostname
hostname -I
```

실제 출력:

```text
w1
192.168.120.151 172.17.0.1
```

또한 `root@master1:~#`까지 복사하여 붙여넣으면 `command not found`가 발생한다. 프롬프트는 제외하고 명령어만 입력한다.

#### w1에서 관리자 권한으로 가입

워커에서 `sudo -i`로 root 셸에 진입한 뒤 가입 명령을 실행했다. 아래 토큰과 해시는 공개용 자리표시자이며, 실제 발급된 값으로 바꿔야 한다.

```bash
# w1에서 실행
sudo -i
kubeadm join 192.168.120.150:6443 \
  --token <JOIN_TOKEN> \
  --discovery-token-ca-cert-hash sha256:<CA_CERT_HASH>
```

kubelet 설정 파일 생성, kubelet health check, TLS Bootstrap을 거쳐 다음 성공 메시지가 출력되었다.

```text
This node has joined the cluster:
```

과정 중 kube-proxy `bindAddress` 권고 경고가 있었지만 이번 가입은 성공했다. 가입 직후 약 19초 시점에는 w1의 kube-proxy가 Running, calico-node가 Init:1/3, csi-node-driver가 ContainerCreating이었다. 이를 즉시 실패로 판단하지 않고 준비가 끝나는지 확인했다.

#### 최종 확인 결과

마스터에서 실행했다.

```bash
kubectl get nodes
```

실제 결과:

```text
NAME      STATUS   ROLES           AGE     VERSION
master1   Ready    control-plane   46m     v1.36.4
w1        Ready    <none>          2m21s   v1.36.4
```

두 노드 모두 Ready로 확인되었다. w1의 ROLES가 `<none>`인 것은 역할 라벨이 없다는 뜻이며 워커 가입 실패가 아니다. 최종 시점의 전체 Pod 목록은 별도로 제공되지 않았으므로 모든 워커 Pod의 최종 상태까지 확인한 것으로 기록하지 않는다.

가입 명령을 새로 발급해야 할 때는 **마스터에서** 다음 명령을 사용한다.

```bash
kubeadm token create --print-join-command
```

출력된 join 명령은 **새 워커에서** 실행한다. 이미 가입한 w1에는 다시 실행할 필요가 없다.

### Xshell 실습 화면 사용 팁

- 탭을 터미널 아래쪽 가장자리로 끌어 파란 표시가 나타날 때 놓으면 위아래로 분할할 수 있다. 위에서는 Pod 상태를 관찰하고 아래에서는 명령을 입력했다.
- 유휴 연결 종료를 줄이는 설정: 세션 등록 정보 → 연결 → 연결 유지에서 메시지 전송을 활성화하고 간격을 설정한다(예: 30초).
- 연결 종료 후 탭 보존: 도구 → 옵션 → 고급 → 연결 종료 시 로컬 셸로 복귀.
- PC 절전으로 네트워크가 중단되면 연결 유지 메시지만으로 SSH를 보장할 수 없다. 전원 연결 중 절전 설정과 화면 꺼짐 설정을 구분한다.
- 화면 분할은 확인했으며, 연결 유지 옵션 적용 결과는 별도로 확인하지 않았다.

## 8 오늘 만난 오류 빠른 복습

| 오류 | 원인과 해결 |
|---|---|
| Vim E212 | 저장 권한 또는 경로 확인. 관리자 권한으로 열고 부모 폴더 확인 |
| `/etc/docker/daemon/json` 없음 | 정확한 경로는 `/etc/docker/daemon.json` |
| `--no-pagersudo` | 명령 두 개를 붙여넣음. 한 줄씩 실행 |
| Docker 재시작 실패 | `5000i` 오타 수정 후 status와 로그 확인 |
| `cmd/ not found` | 빌드 컨텍스트 폴더가 있는 위치에서 실행 |
| Alpine `/bin/bash` 없음 | `/bin/sh` 사용 또는 Bash 설치 |
| 컨테이너에서 `d` 없음 | 호스트의 별칭은 컨테이너 안에 없음 |
| `registry-server` 이름 충돌 | 기존 마운트 확인 후 대상 컨테이너만 교체 |
| SQL 1064 | 세미콜론 누락으로 명령이 합쳐짐 |
| `/etc/netlan` 없음 | `/etc/netplan`이 맞음 |
| Netplan inconsistent indentation | `to`와 `via` 줄 분리, `version` 철자, 스페이스 확인 |
| `netplan appky` | `netplan apply` 오타 |
| sed unknown option | 치환 표현식과 파일 경로 사이 공백 필요 |
| kubeadm init 포트·파일 중복 | 기존 클러스터 초기화 여부 확인 |

| kubeadm reset 권한 오류 | `sudo kubeadm reset` 사용 |
| 마스터에서 join 실행 후 파일·10250 포트 충돌 | 실제 워커의 hostname과 IP를 확인하고 워커에서 실행 |
| `root@master1:~#: command not found` | 프롬프트까지 복사함. 명령어만 입력 |
| `kube get nodes` | 올바른 명령은 `kubectl get nodes` |
