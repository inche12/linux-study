## 3. Seoul VPC·Subnet·IGW·Route Table

### 구축 과정

1. 서울 리전에서 `example-vpc`, CIDR `10.126.0.0/16`을 사용했다.
2. 처음에 `VPC 등`으로 만들었다는 대화가 있었다. 이 방식은 옵션에 따라 서브넷·RT·IGW도 생성하므로 수동 작업 전에 이미 있는 리소스를 확인했다. 이후 전부 삭제하고 `VPC만`으로 재생성했다고 확정할 근거는 없다.
3. `ap-northeast-2a`에 Public `10.126.0.0/24`, Private `10.126.1.0/24`를 구성했다. 같은 VPC 안에서 CIDR이 겹치면 안 된다.
4. `example-igw`가 VPC에 Attached 상태인 것을 확인했다. 이미 연결된 IGW를 중복 생성할 필요가 없었다.
5. Public RT에 IGW 경로를 추가하고 **서브넷 연결**에서 Public Subnet을 명시적으로 연결했다.
6. Private Subnet도 Private RT에 연결했다. 처음에는 `local` 경로만 사용하고 나중에 NAT·Peering 경로를 추가했다.
7. EFS DNS 확인 과정에서 VPC의 DNS resolution·DNS hostnames 활성화 여부를 점검했다.

### 라우팅 표

| 적용 RT | 목적지 | 대상 | 의미 |
|---|---|---|---|
| Public | `10.126.0.0/16` | `local` | 같은 VPC 내부 |
| Public | `0.0.0.0/0` | `example-igw` | 인터넷 방향 기본 경로 |
| Private | `10.126.0.0/16` | `local` | 같은 VPC 내부 |
| Private, NAT 추가 후 | `0.0.0.0/0` | `nat-0693640cc240ffe3d` | Private EC2 외부 접속 |
| Private, Peering 추가 후 | `172.31.0.0/16` | `pcx-029b23ef955056191` | 오리건 사설망 |
| Private, 짝꿍 실습 | 상대 서브넷 CIDR, 대화 안내값 `10.125.1.0/24` | `pcx-0ae4436b018543733` | 짝꿍 EC2 방향 |

> 코멘트: RT 이름에 `pub`이 있어도 `local`만 있으면 인터넷 경로는 없다. **경로 추가와 서브넷 연결은 별도 작업**이다. 명시적 연결이 없는 서브넷은 Main RT를 사용한다. Public Subnet이 명시적으로 Public RT에 연결되어 있다면 Private RT가 Main이어도 Public RT를 사용한다.

`0.0.0.0/0`은 모든 IPv4에 해당하지만 더 구체적인 경로가 우선한다. 예를 들어 `172.31.33.213`은 `/16` Peering 경로로 가고, 같은 VPC의 EFS는 `local`로 간다. 둘 다 NAT 기본 경로를 사용하지 않는다.

## 4. Bastion과 Private EC2 접속

### EC2 생성과 SG

초기 `example-vm-pub`는 Public Subnet에 있었지만 **퍼블릭 IP 자동 할당이 비활성화**되어 있었다. 해당 인스턴스를 종료하고 Public IP 할당을 활성화하여 `example-bastion`을 생성했다. `example-sg already exists` 오류는 **기존 보안 그룹 선택**으로 해결했다. EC2 종료는 SG·Subnet·RT 삭제와 별개다.

Private EC2는 `example-pri-sub1`에 배치했다. 당시 `example-sg`에는 SSH 22와 ICMP를 `0.0.0.0/0`으로 허용한 화면이 있었지만, 다음 최소 범위 구성이 더 적절하다. 아래는 개선안이며 실제로 모두 적용했다고 단정하지 않는다.

| 대상 | 필요한 인바운드 | 소스 |
|---|---|---|
| Bastion | SSH TCP 22 | 관리자 공인 IP `/32` |
| Private EC2 | SSH TCP 22 | Bastion SG |
| Peering ping 대상 | ICMP Echo Request | 테스트 출발 EC2 또는 필요한 CIDR |
| EFS Mount Target | NFS TCP 2049 | 마운트하는 EC2 SG 또는 허용한 사설 IP |

### 초기 2단계 SSH 방식

대화에서는 Bastion의 `/home/ec2-user/ktcloud-vm.pem`을 이용한 접속도 수행했다. 키 본문은 기록하지 않는다. 최종 Windows ProxyCommand 구성에서는 인증키를 Windows에 두고 접속할 수 있다.

```bash
chmod 400 /home/ec2-user/ktcloud-vm.pem
# 목적: Linux 개인키 파일을 소유자만 읽도록 제한한다.
# 400 = 소유자 읽기(4), 그룹·기타 권한 없음(0, 0). 파일 소유자도 확인한다.

sudo vi /etc/hosts
# 목적: Bastion의 로컬 호스트 이름 매핑을 수정한다.
# sudo는 관리자 권한, vi는 편집기. 아래의 올바른 매핑으로 기존 잘못된 줄을 수정한다.
```

`/etc/hosts`의 해당 항목:

```text
10.126.1.154 example-pri-vm pri-vm
```

```bash
getent hosts pri-vm
# 목적: pri-vm이 실제 어느 IP로 해석되는지 확인한다.
# hosts는 호스트 이름 데이터베이스. 정상 결과는 10.126.1.154여야 한다.

ssh -i /home/ec2-user/ktcloud-vm.pem ec2-user@pri-vm
# 목적: Bastion에서 Private EC2로 로그인한다.
# -i는 인증키 파일 경로, ec2-user는 원격 로그인 계정, pri-vm은 목적지 이름이다.
# root 쉘에서도 원격 사용자를 생략하지 않는다. 생략하면 root로 접속을 시도할 수 있다.

hostname -I
# 목적: 로그인한 서버의 IP를 확인해 Bastion과 Private EC2를 구분한다.
# 대문자 -I는 호스트에 설정된 IP 주소들을 출력한다. 목표값은 10.126.1.154다.
```

Amazon Linux 배너가 보인다는 사실만으로 **원하는 서버** 접속까지 증명되지는 않는다. 처음에는 `pri-vm`이 Bastion 자신을 가리켰다. 최종 이름 해석과 IP를 함께 확인해야 한다.

## 5. NAT Gateway와 패키지 설치

Private RT에 `local`만 있으면 외부 패키지 저장소까지 갈 수 없다. 실습에서는 Public Subnet에 `example-nat`을 생성하고 EIP `3.35.28.218`을 연결했다. NAT가 Available이 된 뒤 Private RT에 `0.0.0.0/0 → NAT`를 추가했다.

```text
Private EC2 → Private RT → Public NAT Gateway → Public RT → IGW → 패키지 저장소
```

이는 **영역별 Public NAT Gateway를 사용한 이번 실습 구성**이다. NAT Gateway를 생성하는 것만으로 RT가 자동으로 바뀌지는 않는다. 인터넷에서 NAT EIP로 신규 SSH 연결을 시작해 Private EC2에 들어가는 용도도 아니다.

Private EC2에서 실행할 복습 명령:

```bash
curl https://checkip.amazonaws.com
# 목적: 외부 서비스가 보는 출발지 공인 IP를 확인한다.
# curl은 HTTPS 응답 본문을 출력한다. 이번 구성의 기대값은 NAT EIP 3.35.28.218이다.
# 대화에서 제안된 확인 명령이며 실제 curl 결과는 남아 있지 않다.

sudo dnf install -y amazon-efs-utils nfs-utils
# 목적: Amazon Linux 2023에 EFS mount helper와 일반 NFS 클라이언트를 설치한다.
# install은 패키지 설치, -y는 확인 질문에 자동 동의한다.
# amazon-efs-utils는 mount -t efs, nfs-utils는 NFS 마운트에 필요한 도구를 제공한다.

rpm -q amazon-efs-utils nfs-utils
# 목적: 두 패키지가 설치되었는지 버전을 조회한다.
# -q는 query이며 설치·변경을 하지 않는다. 복습용 확인 명령이다.
```

처음 `Complete!`가 나온 설치 로그는 **Bastion `10.126.0.174`**에서 실행한 것이었다. 이것만으로 Private NAT 경로를 검증했다고 하면 안 된다. 이후 Private EC2 `10.126.1.154`에서 저장소 다운로드, `nfs-utils` 기설치 메시지와 EFS helper를 통한 실제 마운트가 확인되었다. 네트워크 출구 자체를 확정하려면 RT와 NAT 지표·출구 IP 등도 함께 본다.

> 코멘트: 수업 예시의 `dnf install nfs-common`은 배포판 구분이 필요하다. Amazon Linux는 `nfs-utils`를 사용한다. `nfs-common`은 Debian/Ubuntu 계열에서 사용하는 이름이다. 강사 예시의 `10.100.1.140`을 본인 EC2 주소로 기록하지 않는다.

## 6. Windows OpenSSH config와 ProxyCommand

### 설정 파일 준비

PowerShell에서 실행한다. 아래 경로는 당시 실제 경로이며 PEM 본문은 포함하지 않는다.

```powershell
Set-Location $HOME
# 목적: 현재 Windows 사용자의 홈 폴더로 이동한다.
# $HOME은 읽어서 사용하는 기본 변수다. 프로필 실행 정책을 바꾸지 않아도 된다.

New-Item -ItemType Directory -Path "$HOME\.ssh" -Force
# 목적: OpenSSH 설정 폴더를 준비한다.
# -ItemType Directory는 폴더, -Path는 위치, -Force는 기존 폴더가 있어도 사용할 수 있게 한다.

notepad "$HOME\.ssh\config"
# 목적: 확장자 없는 SSH 사용자 설정 파일을 편집한다.
# 메모장 저장 시 파일 이름이 config.txt로 바뀌지 않았는지 확인한다.
```

`C:\Users\user\.ssh\config`의 최종 내용:

```sshconfig
Host bastion-ktcloud
    # 아래 설정을 적용할 SSH 별칭이다.
    HostName 54.180.128.244
    # 당시 Bastion 공인 IP. 다시 만든 환경에서는 현재 주소로 바꾼다.
    User ec2-user
    # Bastion의 Linux 로그인 계정이다.
    IdentityFile C:/Users/user/Desktop/KT-C/ktcloud-vm.pem
    # Windows에 있는 개인키 파일 경로다. 키의 내용은 설정 파일에 넣지 않는다.

Host ktcloud
    # 최종 Private EC2에 접속할 때 사용할 별칭이다.
    HostName 10.126.1.154
    # 최종 목적지는 Private EC2 사설 IP다.
    User ec2-user
    # 최종 목적지에서 인증할 Linux 사용자다.
    IdentityFile C:/Users/user/Desktop/KT-C/ktcloud-vm.pem
    # Private EC2 인증에도 Windows의 이 키를 사용한다.
    ProxyCommand ssh bastion-ktcloud -W %h:%p
    # 먼저 Bastion에 SSH 접속하고 표준 입출력을 최종 목적지 TCP로 연결한다.
    # -W는 stdio forwarding, %h는 최종 HostName, %p는 최종 포트(기본 22)다.
```

대화의 Windows 역슬래시 경로와 같은 파일을 가리키도록 설정 예시는 슬래시로 표기했다. `PS C:\...>` 프롬프트나 메모장을 여는 명령은 설정 파일 내용이 아니다.

### 적용 확인과 접속

```powershell
Get-Content "$HOME\.ssh\config"
# 목적: 파일 본문을 확인한다. Host 설정과 주석만 있어야 한다.

ssh -G ktcloud | Select-String 'hostname|user|identityfile|proxycommand'
# 목적: 접속 전에 OpenSSH가 해석한 최종 설정을 확인한다.
# -G는 설정 출력 후 종료, |는 출력을 전달, Select-String은 패턴과 일치하는 줄을 찾는다.
# hostname이 ktcloud 그대로가 아니라 10.126.1.154로 나오는지 확인한다.

ssh bastion-ktcloud
# 목적: 중간 서버 접속부터 단독 검증한다. Host 별칭에 대응하는 설정을 읽는다.
```

Bastion 원격 쉘에서:

```bash
exit
# 목적: Bastion 원격 쉘을 종료하고 Windows PowerShell로 돌아온다.
```

다시 Windows에서:

```powershell
ssh ktcloud
# 목적: ProxyCommand를 통해 Private EC2에 한 번에 로그인한다.
# Windows → Bastion:22 → Private EC2:22 순서이며 두 서버 인증을 각각 처리한다.
```

**실제 성공 근거:** Bastion 로그인 후 `exit`, 이어서 `ssh ktcloud` 실행 시 Amazon Linux 2023 배너가 나왔다. Private EC2 로그인 기록에는 출발지 `10.126.0.174`가 표시되었다. 첫 접속에서는 각 서버의 호스트 키 신뢰 확인이 별도로 발생했다.

> 코멘트: ProxyCommand는 SSH의 TCP 전달 기능이다. Bastion을 일반 IP 라우터로 만드는 작업이 아니므로 이 접속만을 위해 Linux IP forwarding이나 EC2 Source/Destination Check를 바꿀 필요는 없다. Windows의 `config`는 이름·접속 옵션이고, `known_hosts`는 서버 신원 기록이며, PEM은 사용자 인증키다.

## 7. Seoul ↔ Oregon VPC Peering

### 사전 비교와 연결

오리건 신규 VPC 구축은 처음에 생략했지만 이후 **기존 Default VPC**에 `peer-pub-vm`을 생성해 실습을 진행했다. 키 페어는 리전별 리소스라 오리건에서 `ktcloud-vm2`를 사용했다. 같은 공개키를 다른 리전에 가져오는 방법도 있지만 Peering 자체에는 SSH 키가 필요하지 않다.

Bastion에서 수행한 사전 테스트:

```bash
ping 35.89.197.91
# 목적: 오리건 EC2 공인 IP에 ICMP Echo Request를 보낸다.
# 옵션 없이 반복 실행되므로 Ctrl+C로 종료한다. Peering 검증용 주소는 아니다.

ping 172.31.33.213
# 목적: 같은 오리건 EC2의 사설 IP로 통신을 비교한다.
# 별도 VPC까지의 사설 경로가 필요하다. Ctrl+C 종료 후 손실률을 확인한다.
```

실제 결과는 Public IP **2회 송신·2회 수신·손실 0%, 평균 약 127.642ms**, Private IP **9회 송신·수신 0·손실 100%**였다.

1. 오리건에서 피어링 연결 생성: 요청자 `vpc-07bf2a8cc54091332`.
2. 수락자 리전 서울, VPC ID `vpc-037eed2a1ccfff04c` 지정.
3. 서울에서 `pcx-029b23ef955056191` 요청 수락 후 Active 확인.
4. 서울 Private RT에 `172.31.0.0/16 → pcx-029b23ef955056191` 추가.
5. 오리건 EC2가 속한 서브넷의 RT에 서울 응답 경로 추가.
6. 대상 EC2의 ICMP 규칙과 필요한 NACL 양방향 규칙 확인.

### 출발지에 따른 왕복 경로

| 테스트 출발지 | 서울에서 확인할 RT | 오리건 반환 경로에 포함되어야 하는 CIDR |
|---|---|---|
| Bastion `10.126.0.174` | Public Subnet의 `example-pub-RT` | `10.126.0.0/24` 또는 더 넓은 적절한 범위 |
| Private EC2 `10.126.1.154` | `example-pri-RT` | `10.126.1.0/24` 또는 더 넓은 적절한 범위 |

대화 중 `/16`, Public `/24`, Private `/24`가 번갈아 안내되었지만 서로 같은 의미는 아니다. **Private Subnet만 연결하려는 목표에서는 `10.126.1.0/24`가 맞다.** Bastion에서 ping하면서 그 반환 경로를 기대한 것이 문제였다.

Private EC2 로그인 뒤 재검증하도록 정리한 명령:

```bash
hostname -I
# 목적: 테스트 출발지가 10.126.1.154인지 확인한다. -I는 IP 주소 목록 출력이다.

ping -c 3 172.31.33.213
# 목적: Private EC2에서 오리건 사설 주소까지 왕복 ICMP를 검사한다.
# -c 3은 3회만 전송하는 복습용 옵션이다. 실제 최종 성공 출력은 대화에 남지 않았다.
```

Peering은 사설 IP 트래픽을 AWS 네트워크로 전달하는 연결이다. Active 상태만으로 RT·SG 구성이 완료되지는 않는다. [AWS VPC Peering 설명](https://docs.aws.amazon.com/vpc/latest/peering/what-is-vpc-peering.html)

<a id="08"></a>
## 8. 짝꿍 VPC Peering과 ping

짝꿍은 EC2 `10.125.1.186`, VPC `vpc-0b2153d4b96a6832f`를 공유했다. Peering 생성 시 입력하는 것은 **상대 EC2 IP가 아니라 VPC ID**다. 다른 계정이면 상대 계정·리전 정보도 필요하지만 이 문서에는 계정 번호를 싣지 않는다.

실제로는 상대가 보낸 `pcx-0ae4436b018543733` 요청을 수락했다. 내 Private RT에 상대 CIDR을, 상대 EC2의 RT에는 내 CIDR을 추가하도록 진행했다. IP 하나만 보고 서브넷 마스크를 확정하지 않는다.

```bash
ping 10.125.1.186
# 목적: 내 Private EC2에서 짝꿍 EC2 사설 IP까지 ICMP 왕복을 검증한다.
# Ctrl+C로 종료한다. ICMP 성공은 NFS TCP 2049 허용까지 증명하지 않는다.
```

실제 출력 요약:

```text
출발: 10.126.1.154
목적지: 10.125.1.186
3 packets transmitted, 3 received, 0% packet loss
rtt min/avg/max/mdev = 0.365/0.370/0.375/0.004 ms
```

### 상대가 보낸 ping은 어디에 보이나?

ping은 상대 터미널에 메시지를 출력하는 기능이 아니다. OS 네트워크 스택이 응답한다. 수신 관찰용으로 다음 명령을 안내받았지만 캡처 실행 결과는 남아 있지 않다.

```bash
sudo tcpdump -ni any icmp
# 목적: 이 서버로 오가는 ICMP 패킷을 실시간 관찰한다.
# -n은 주소 이름 변환 생략, -i any는 모든 인터페이스, icmp는 캡처 필터다.
# echo request는 요청, echo reply는 응답이다. 종료는 Ctrl+C다.
```

미리 캡처나 별도 로그 수집을 하지 않았다면 과거 ping 수신을 쉘 히스토리로 확인할 수 없다. 또한 내 ping의 왕복 성공과 **상대가 새로 시작하는 요청의 허용 여부**는 구분한다.

## 9. EFS 생성·마운트·파일 작성

### 생성과 네트워크 수정

EFS는 관리형 NFS 파일시스템이다. EC2 여러 대가 같은 파일시스템을 마운트해 파일을 공유한다. EC2에 붙이는 EBS 블록 장치나 S3 객체 저장소와 사용 방식이 다르다.

처음 `fs-008116ed56f3920fe`의 Mount Target은 **서울의 다른 Default VPC** `vpc-0ac55777427692308`에 있었다. 대화에 나온 Mount Target IP는 `172.31.6.106`, `172.31.23.226`, `172.31.43.100`, `172.31.51.71`이었다. 본인 EC2는 `10.126.1.154`이므로 의도한 같은 VPC 구성이 아니었다.

`example-vpc`를 선택하여 `fs-08c05eacc10723470`으로 다시 생성했다. Private Subnet에 만들자는 안내도 있었지만 **실제 최종 Mount Target은 Public Subnet `10.126.0.0/24`의 `10.126.0.110`**이었다. 같은 VPC 내 Private EC2에서 접근 가능하며, Public Subnet에 있다고 EFS가 공인 IP를 갖는 것은 아니다.

Mount Target의 실제 SG `sg-015e66f7e626959ea`에 NFS 인바운드 TCP 2049, 소스 `10.126.0.0/16`을 추가한 뒤 마운트가 성공했다. 실무에서는 EFS 전용 SG에 필요한 클라이언트 SG·IP만 허용한다. 클라이언트 아웃바운드와 NACL도 통신을 허용해야 한다. [EFS 네트워크 접근 요구사항](https://docs.aws.amazon.com/efs/latest/ug/network-access.html)

### DNS 확인

Private EC2에서:

```bash
cat /etc/resolv.conf
# 목적: 사용하는 DNS 서버를 확인한다. cat은 파일 내용을 출력한다.
# 실제 nameserver는 10.126.0.2였다. 자동 관리 파일이므로 무작정 직접 수정하지 않는다.

getent hosts fs-08c05eacc10723470.efs.ap-northeast-2.amazonaws.com
# 목적: OS 이름 조회 체계에서 EFS 이름이 해석되는지 확인한다.
# hosts 데이터베이스 조회이며 이 명령이 아무 출력도 내지 않았다는 대화가 있었다.

nslookup fs-08c05eacc10723470.efs.ap-northeast-2.amazonaws.com
# 목적: DNS에 EFS 이름을 질의한다. 실제 결과는 10.126.0.110이었다.
# 이름을 IP로 바꾸는 데 성공해도 TCP 2049 연결 성공은 별도로 확인해야 한다.
```

`nslookup`이 없을 때만 사용하는 보조 명령:

```bash
sudo dnf install -y bind-utils
# 목적: DNS 진단 도구를 설치한다. -y는 설치 확인 자동 동의다.
# 대화에서 제안된 보조 절차이며 설치 실행 결과는 별도로 확인되지 않았다.
```

### TLS 마운트

```bash
sudo mkdir -p /mnt
# 목적: 로컬 마운트 지점을 준비한다.
# -p는 필요한 상위 경로를 만들고 이미 디렉터리가 있어도 오류를 내지 않는다.

sudo mount -t efs -o tls fs-08c05eacc10723470:/ /mnt
# 목적: EFS 루트를 로컬 /mnt에 연결한다.
# -t efs는 EFS helper, -o tls는 전송 암호화, ID 뒤 :/는 원격 파일시스템 루트다.
# /mnt는 이 EC2에서 파일시스템이 보일 위치다. 콘솔 예시의 상대경로 efs와 구분한다.

df -hT | grep /mnt
# 목적: 실제 마운트된 파일시스템의 타입과 위치를 확인한다.
# -h는 읽기 쉬운 용량 단위, -T는 파일시스템 타입, grep은 /mnt가 있는 줄을 선택한다.
```

실제 성공 출력:

```text
127.0.0.1:/      nfs4      8.0E     0  8.0E   0% /mnt
```

TLS 마운트의 로컬 프록시 때문에 `127.0.0.1:/`가 표시될 수 있다. 로컬 디스크를 마운트했다는 뜻이 아니다. `8.0E`는 EFS/NFS가 보고하는 큰 논리 용량 표현이며 그만큼 저장하거나 비용을 지불했다는 의미가 아니다. 이 출력에서는 `grep efs`가 행을 놓칠 수 있으므로 마운트 경로나 타입을 확인한다.

### 공유 파일 작성

다음은 **마운트 성공을 확인한 뒤** 실행한다. 실패한 채 파일을 만들면 EFS 대신 EC2 로컬 디스크에 기록될 수 있다.

```bash
sudo mkdir -p /mnt/hello-seongmin
# 목적: EFS 내부에 개인 실습 디렉터리를 만든다. -p는 기존 디렉터리를 허용한다.

echo "Hello from Seongmin" | sudo tee /mnt/hello-seongmin/hello.txt
# 목적: 일반 ec2-user 쉘에서도 관리자 권한으로 파일을 작성한다.
# echo는 문자열 출력, |는 전달, sudo tee는 표준 입력을 지정한 파일에 쓴다.
# -a 없이 사용하므로 기존 내용은 덮어쓴다. 대화의 root 쉘 리다이렉션과 같은 결과다.

ls -l /mnt/hello-seongmin
# 목적: 파일 존재·권한·소유자·크기를 확인한다. -l은 자세한 목록 출력이다.

cat /mnt/hello-seongmin/hello.txt
# 목적: 저장된 문자열을 읽어 파일 내용을 검증한다.
```

당시에는 root 쉘에서 다음처럼 작성했다.

```bash
echo "Hello from Seongmin" > /mnt/hello-seongmin/hello.txt
# 목적: 문자열과 줄바꿈을 파일에 저장한다. >는 새로 만들기 또는 덮어쓰기다.
# 리다이렉션은 현재 쉘 권한으로 처리하므로 당시처럼 root이거나 쓰기 권한이 필요하다.
```

실제 결과는 `-rw-r--r--. 1 root root 20 ... hello.txt`, 내용은 `Hello from Seongmin`이었다. 최종 `hello-seongmin`은 **디렉터리**이고 `hello.txt`가 파일이다. 초기에 제안된 `touch hello-seongmin` 방식과 구분한다.

## 10. 짝꿍과 EFS 공유

### 같은 파일시스템을 함께 보기

```text
내 EC2 10.126.1.154 ──local─────┐
                               ├─ 내 EFS → /hello-seongmin/hello.txt
짝꿍 EC2 10.125.1.186 ─Peering─┘
```

내 EFS Mount Target SG에 `NFS / TCP 2049 / 10.125.1.186/32`를 추가하도록 안내받았다. `/32`는 한 IP만 의미하며 상대 VPC 전체 허용보다 좁다. 정확한 최종 규칙 저장 결과와 짝꿍 읽기 결과는 대화에 없다.

**중요한 보완:** EC2 간 ping이 성공했어도 EFS까지의 경로는 따로 점검해야 한다. 내 Private EC2는 `10.126.1.154`지만 EFS는 **`10.126.0.110`**에 있다.

| 위치 | EFS 공유에 필요한 경로 예시 |
|---|---|
| 짝꿍 EC2 서브넷 RT | `10.126.0.110/32` 또는 이를 포함하는 허용 범위 → 짝꿍 Peering |
| 내 EFS Mount Target 서브넷 RT (`example-pub-RT`) | `10.125.1.186/32` 또는 이를 포함하는 확인된 상대 CIDR → 짝꿍 Peering |

짝꿍 RT에 `10.126.1.0/24`만 있다면 내 EFS 주소를 포함하지 않는다. 내 **Private RT**에만 짝꿍 경로가 있어도 Public Subnet에 있는 Mount Target의 응답 경로를 대신하지 못한다. 전체 VPC CIDR을 허용할지 좁은 목적지만 허용할지는 실습 범위에 맞춰 결정한다.

### 짝꿍이 내 EFS를 마운트하는 안내 명령

다음은 전달용 재구성 예시이며 상대 실행 완료 기록이 아니다. 해당 경로가 다른 파일시스템에 이미 사용 중인지 먼저 확인한다.

```bash
sudo mkdir -p /mnt
# 목적: 짝꿍 EC2의 로컬 마운트 지점을 준비한다. -p는 경로가 이미 있어도 허용한다.

sudo mount -t nfs4 -o nfsvers=4.1 10.126.0.110:/ /mnt
# 목적: 내 EFS Mount Target 사설 IP를 이용해 EFS 루트를 마운트한다.
# -t nfs4는 NFSv4, -o nfsvers=4.1은 버전 지정, :/는 원격 루트다.
# 일반 NFS 예시에는 TLS 옵션이 없다. 앞의 EFS helper TLS 마운트와 구분한다.

df -hT | grep /mnt
# 목적: 마운트 성공을 확인한다. -h는 용량 단위, -T는 타입을 표시한다.

cat /mnt/hello-seongmin/hello.txt
# 목적: 같은 EFS의 파일을 읽는다. 기대 내용은 Hello from Seongmin이다.
```

EFS 루트를 `/mnt/hello-seongmin`에 마운트한다면 내부 `hello-seongmin` 디렉터리가 한 번 더 붙어 파일은 `/mnt/hello-seongmin/hello-seongmin/hello.txt`로 보인다. 혼동을 피하려고 문서에서는 양쪽 모두 `/mnt`를 기준으로 통일했다.

다른 VPC에서 파일시스템 DNS 이름을 그대로 사용하는 것은 추가 DNS·조회 설정이 필요할 수 있다. 대화에서는 Mount Target IP 방식을 안내했다. 운영 시 EFS helper의 교차 VPC 접근 및 TLS 설정은 별도로 검토한다. [다른 VPC에서 EFS 마운트](https://docs.aws.amazon.com/efs/latest/ug/mount-fs-different-vpc.html)

### 내 EC2에서 짝꿍 EFS 보기

짝꿍에게 **EFS Mount Target IP와 EFS 내부 디렉터리명**을 받아야 한다. `10.125.1.186`은 확인된 EC2 IP이지 EFS IP가 아니다. 대화에 등장한 `10.125.0.100`은 가정 예시였으므로 실제 값으로 사용하지 않는다.

```bash
PARTNER_EFS_IP='<짝꿍에게 확인한 Mount Target IP>'
# 목적: 확인한 EFS 서버 주소를 변수에 넣는다. 꺾쇠 자리표시자를 실제 값으로 치환한다.

sudo mkdir -p /mnt/partner
# 목적: 내 EFS /mnt와 구분되는 짝꿍 파일시스템 마운트 지점을 만든다.
# 이미 내 EFS가 /mnt에 마운트되어 있다면 이 디렉터리는 내 EFS 안에 만들어진다.

sudo mount -t nfs4 -o nfsvers=4.1 "${PARTNER_EFS_IP}:/" /mnt/partner
# 목적: 짝꿍 EFS 루트를 /mnt/partner에 연결한다.
# NFSv4.1 사용; 변수 주소와 :/를 조합한다. 왕복 RT와 상대 EFS SG가 먼저 준비되어야 한다.

ls -l /mnt/partner
# 목적: 짝꿍 EFS 최상위 목록을 확인한다. -l은 자세한 목록이다.
```

상대 EFS SG에는 내 실제 출발지 `10.126.1.154/32`의 TCP 2049 허용이 필요하다. 내 RT는 상대 **Mount Target의 서브넷**까지, 상대 Mount Target RT는 내 EC2까지의 반환 경로가 필요하다. 역방향 공유는 설명 단계이며 완료했다고 기록하지 않는다.

## 11. 트러블슈팅

### 11.1 EFS를 잘못된 VPC에 생성

- **증상:** `Failed to resolve ... ensure that the VPC has an EFS mount target`.
- **확인:** EC2는 `10.126.1.154`, 기존 EFS Mount Target은 다른 서울 VPC의 `172.31.x.x`.
- **원인:** 같은 VPC에서 사용하는 의도와 달리 네트워크 배치가 달랐고, 필요한 교차 VPC 접근 구성도 없었다.
- **해결:** `example-vpc`를 명시해 EFS를 재생성하고 새 ID `fs-08c05eacc10723470` 사용.
- **검증:** DNS에서 `10.126.0.110` 반환, 이후 마운트 성공.
- **기억:** EFS 자체와 VPC 내 Mount Target을 구분한다. 다른 VPC라는 사실만으로 EFS 사용이 불가능한 것은 아니지만 네트워크·DNS 구성이 추가로 필요하다.

### 11.2 새 EFS도 DNS 해석 실패·botocore 오류

- **증상:** 새 ID에서도 `Failed to resolve`, 이어서 `Failed to import necessary dependency botocore`.
- **해석:** 첫 번째는 DNS 실패이고 두 번째는 helper가 대체 IP 조회를 시도하다 발생한 추가 오류다.
- **점검 순서:** EFS ID·리전 → Mount Target VPC·AZ·Available 상태 → VPC DNS 설정 → EC2 resolver → 이름 조회.
- **결과:** `/etc/resolv.conf`의 `10.126.0.2`, `nslookup`의 `10.126.0.110` 확인.
- **한계:** 이 사이 정확히 어떤 DNS 설정 변경 또는 준비 시간이 해석 성공을 만들었는지는 대화만으로 확정할 수 없다. botocore 설치로 해결했다고 쓰지 않는다.

### 11.3 DNS 정상인데 mount timeout

실제 오류:

```text
Mount attempt 1/3 failed due to timeout after 15 sec
Mount attempt 2/3 failed due to timeout after 15 sec
```

- **분리:** 이름은 IP로 바뀌었지만 NFS 서비스에 도달하지 못하는 단계였다.
- **확인:** EFS 네트워크 탭에서 실제 Mount Target SG가 `sg-015e66f7e626959ea (default)`임을 확인.
- **해결:** 그 SG의 인바운드에 TCP 2049, 소스 `10.126.0.0/16` 허용 후 재마운트.
- **검증:** `df`에 `/mnt`, 타입 `nfs4` 표시 및 파일 작성 성공.
- **기억:** EC2 SG만 바꿔서는 EFS 수신 규칙이 바뀌지 않는다. 같은 이름의 SG가 많으면 ID와 연결 대상부터 확인한다. 일반적인 timeout은 RT·NACL·방화벽도 원인일 수 있지만 이번에는 SG 수정 후 성공했다.

### 11.4 Peering Active인데 ping 실패: 양방향 RT·소스 Subnet

- **증상:** 서울 Bastion에서 오리건 사설 IP ping 손실 100%.
- **원인 후보:** 출발지는 `10.126.0.174`인데 수정한 RT는 Private RT였고, 오리건 반환 목적지는 `10.126.1.0/24`였다.
- **해결 방향:** 강의 목표대로 Private EC2 `10.126.1.154`로 이동해서 테스트. Bastion을 테스트하려면 Public RT와 Public 출발지에 대한 반환 경로도 맞춰야 한다.
- **기억:** 반환 경로도 실제 source IP를 포함해야 한다. `/16`으로 넓히면 무조건 정답이라는 뜻은 아니다.
- **EFS 확장:** Private EC2 ping 성공으로 Public Subnet의 EFS Mount Target 경로까지 검증했다고 판단하지 않는다.

### 11.5 Bastion IP와 Private EC2 IP 혼동

잘못된 `/etc/hosts` 매핑은 `10.126.0.174 example-pri-vm pri-vm`이었다. 이 때문에 자기 자신에게 ping·SSH를 시도했다. 실제 Private IP `10.126.1.154`로 수정하고 `getent hosts pri-vm` 결과를 확인했다.

`10.126.1.0/24`는 네트워크 범위이고 `10.126.1.0`은 그 네트워크 주소다. EC2의 `10.126.0.174`를 `10.126.1.0`으로 바꾸는 문제가 아니다.

### 11.6 PEM 파일명·경로·로그인 사용자 오류

- `ktloud-vm.pem`은 `ktcloud-vm.pem`의 오타였다.
- root 홈에서 상대경로로 찾으면 `/home/ec2-user`의 키를 찾지 못했다.
- root에서 원격 사용자명을 생략해 `root@pri-vm`으로 시도한 것도 문제였다.

```bash
find /home/ec2-user -name 'ktcloud-vm.pem' 2>/dev/null
# 목적: 개인키 내용은 읽지 않고 파일 위치만 찾는다.
# -name은 파일명 검색, 2>/dev/null은 오류 출력만 버린다. 검색 범위를 사용자 홈으로 좁혔다.

ssh -i /home/ec2-user/ktcloud-vm.pem ec2-user@pri-vm
# 목적: 확인된 절대경로 키와 올바른 원격 사용자로 재접속한다.
# -i는 개인키 파일 지정이며 서버 IP 매핑도 앞서 수정되어 있어야 한다.
```

### 11.7 known_hosts의 호스트 키 불일치

`pri-vm`을 Bastion 주소로 사용한 기록이 있는데 실제 Private EC2로 매핑을 바꾸면서 다음 경고가 발생했다.

```text
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
Offending ED25519 key in /root/.ssh/known_hosts:1
Host key verification failed.
```

이번에는 이름이 가리키는 서버를 의도적으로 수정한 사실을 확인했다. 새 대상의 신원을 신뢰할 수 있는 방법으로 확인한 뒤 **해당 항목만** 정리한다. 이유를 모르는 경고를 무조건 삭제하거나 StrictHostKeyChecking을 끄지 않는다.

```bash
ssh-keygen -R pri-vm
# 목적: 현재 사용자의 known_hosts에서 이 이름에 해당하는 기존 호스트 키를 제거한다.
# -R은 지정 호스트 기록 제거다. 당시 root에서 실행해 /root/.ssh/known_hosts가 갱신됐다.

ssh-keygen -R 10.126.1.154
# 목적: IP로 저장된 별도 기록도 있는지 확인하여 제거한다.
# 당시 결과는 Host ... not found였다. 별칭 기록과 IP 기록은 다를 수 있다.

ssh -i /home/ec2-user/ktcloud-vm.pem ec2-user@pri-vm
# 목적: 올바른 대상에 다시 접속한다. 새 호스트 키를 확인하고 신뢰할 때만 승인한다.
```

이후 Amazon Linux 로그인 성공 출력이 확인되었다. Windows와 Bastion, root와 ec2-user는 각각 다른 `known_hosts` 파일을 사용할 수 있다. 최초 접속의 `authenticity ... can't be established` 안내와 기존 키 변경 경고도 구분한다.

### 11.8 config.txt로 저장되어 별칭 해석 실패

**증상:** `ssh: Could not resolve hostname ktcloud`.

설정 파일을 읽지 못해 `ktcloud`를 실제 DNS 이름으로 찾으려 한 상황이었다. 다른 사용자 `hhs`의 예시 경로와 본인 `user` 경로도 혼재했다.

```powershell
Get-ChildItem "$HOME\.ssh" -Force
# 목적: 실제 사용자 홈에서 파일 이름·확장자를 확인한다. -Force는 숨김 항목도 표시한다.

Rename-Item -LiteralPath "$HOME\.ssh\config.txt" -NewName 'config'
# 목적: 확인된 config.txt를 확장자 없는 config로 바꾼다.
# -LiteralPath는 경로를 문자 그대로 처리한다. 기존 config가 있다면 내용을 비교한 뒤 정리한다.

ssh -G ktcloud | Select-String 'hostname'
# 목적: 별칭 적용 확인. -G는 접속 없이 최종 설정 출력, 필터 결과는 hostname 10.126.1.154여야 한다.
```

### 11.9 config에 PowerShell 프롬프트가 들어감

**증상:** `Bad configuration option: ps`, `terminating, 1 bad configuration options`.

파일 첫 줄에 `PS C:\Users\hhs\.ssh> notepad config`가 저장되어 OpenSSH가 `PS`를 설정 옵션으로 해석했다. 그 줄을 지우고 Host 설정만 남긴 뒤 다시 읽어서 확인했다. **터미널에서 실행할 명령과 파일에 저장할 내용을 구분**해야 한다.

### 11.10 /mnt 앞 슬래시 누락·hello-seongmin 띄어쓰기

| 잘못 입력한 부분 | 실제 해석 | 해결 |
|---|---|---|
| `mnt/hello-seongmin/hello.txt` | 현재 작업 디렉터리 아래의 상대경로 | `/mnt/hello-seongmin/hello.txt` |
| `/mnt/hello seongmin` | `/mnt/hello`와 `seongmin` 두 인자 | `/mnt/hello-seongmin` |

실제 오류는 `No such file or directory`였다. 디렉터리 목록이 `total 0`으로 보인 것은 폴더는 있지만 앞선 파일 쓰기가 실패했기 때문이다. 올바른 절대경로로 작성 후 20바이트 파일과 내용이 확인되었다.

### 11.11 Public IP 없음·SG 중복·중지와 종료

Public Subnet에 배치해도 EC2에 공인 IP가 자동 보장되지 않는다. 당시 EC2는 자동 할당을 켜서 재생성했다. 기존 인스턴스 유지가 필요하다면 EIP 연결 등 대안을 검토할 수 있다.

EC2 `Name` 태그의 중복과 같은 VPC의 SG 이름 중복은 다르다. EC2 종료 뒤에도 `example-sg`가 남아 새로 만들 때 충돌했으므로 기존 SG를 선택했다. **Stop은 재시작 가능, Terminate는 해당 인스턴스를 다시 시작할 수 없음**을 구분했다.

### 11.12 PowerShell 시작 위치와 프로필 오류

홈 폴더로 자동 이동하려고 만든 프로필 `.ps1`이 실행 정책에 차단되었다. 이후 사용자는 매번 홈으로 이동하는 방식을 선택했고, 대화에서는 이번에 만든 프로필 제거가 안내되었다. 실제 삭제 완료 출력은 남아 있지 않다. 기존 사용자 설정이 있을 수 있어 일반 복습에서 프로필 전체 삭제를 기본 절차로 삼지 않는다.

```powershell
Set-Location $HOME
# 목적: PowerShell 시작 위치가 system32여도 현재 사용자 홈으로 이동한다.
# 매 세션에서 직접 실행하면 시작 프로필 변경 없이 작업할 수 있다.
```

## 12. SG·NACL 실습과 수업 코멘트

### Stateful / Stateless

| 구분 | Security Group | Network ACL |
|---|---|---|
| 적용 | ENI/리소스 수준 | 서브넷 경계 |
| 연결 상태 | Stateful | Stateless |
| 규칙 | 허용 규칙 | 허용·거부 규칙 |
| 응답 | 허용된 연결의 반환 트래픽 자동 허용 | 반환 방향도 독립 평가 |
| 평가 | 적용 가능한 허용 규칙의 합 | 낮은 규칙 번호부터 첫 일치 |

EC2 콘솔과 VPC 콘솔의 보안 그룹은 별개 종류가 아니다. 같은 ID라면 같은 SG를 다른 메뉴에서 보고 있는 것이다. SG의 stateful은 “인바운드·아웃바운드 중 하나만 사용한다”는 뜻이 아니라 **새 연결은 해당 방향 규칙으로, 기존 반환 트래픽은 연결 상태로 판단한다**는 뜻이다.

NACL 화면에서는 규칙 99 HTTP 80, 규칙 100 모든 트래픽, 마지막 `*` 거부 규칙을 비교했다. 99가 Allow면 HTTP가 허용되고, 99를 Deny로 두면 뒤의 100 Allow와 관계없이 HTTP는 거부된다. 대화의 설명에는 차단 실습 언급이 있지만 사용자 측 HTTP 요청 결과 로그는 없다.

TCP 요청 `클라이언트:임시포트 → 서버:80`의 응답은 `서버:80 → 클라이언트:임시포트`다. Stateless 정책에서는 응답 목적지 포트도 고려한다. SG가 허용해도 NACL이 거부하면 통신은 실패할 수 있다.

### 오늘 함께 복습한 개념 — 신규 구축 완료와 구분

- **IAM·Role·STS:** Role에 장기 키를 저장하는 것이 아니라 STS 기반 임시 자격증명을 사용한다. Trust Policy는 누가 Role을 맡는지, Permission Policy는 무엇을 할 수 있는지를 정한다. SSH 키 페어와 AWS API 자격증명은 별개다.
- **EC2:** AMI는 운영체제 이미지, 인스턴스 타입은 CPU·메모리 등의 사양, ENI는 네트워크 인터페이스, SG는 통신 허용, 키 페어는 SSH 인증 역할이다.
- **EBS 복습:** 이전 실습의 Root EBS 8→10GB 확대, 파티션·파일시스템 확장, 추가 1GB 디스크의 XFS 생성·마운트를 다시 설명했다. 9/28 신규 디스크 작업으로 기록하지 않는다. EBS 용량 변경과 OS 파일시스템 확장은 별도 단계다.
- **S3·DynamoDB:** EC2처럼 사용자 서브넷에 배치하는 리소스가 아니다. 접근에 IGW가 반드시 필요한 것은 아니며 Gateway VPC Endpoint라는 선택지가 있다. 오늘 Endpoint를 새로 구성했다고 기록하지 않는다.
- **IGW의 IPv4 변환:** 공인 IPv4가 연결된 EC2의 사설 IPv4와 공인 IPv4 사이 매핑을 제공한다. Private EC2의 인터넷 출구로 사용한 Public NAT Gateway와 구분한다.
- **NAT Instance:** EC2로 NAT를 직접 만들면 IP forwarding·주소 변환 규칙·RT·SG와 Source/Destination Check 비활성화가 필요하다. 설명만 다뤘으며 오늘 만든 것은 관리형 NAT Gateway다. 비용뿐 아니라 패치·장애·처리량 책임도 비교한다.
- **Routing / Forwarding:** 라우팅은 경로를 정하고 포워딩은 그 경로로 패킷을 전달하는 동작이다.
- **Multi-AZ:** VPC는 여러 AZ를 활용할 수 있지만 서브넷 하나는 한 AZ에 속한다. AZ별 분산은 자동 파일 백업과 같은 의미가 아니다. 오늘 명시적으로 구성한 두 서브넷은 같은 2a였다.
- **Peering 비전이성:** A↔B, B↔C가 있어도 A↔C가 자동 연결되지 않는다. 모든 쌍 연결은 `n(n-1)/2`개로 늘어난다. TGW의 중앙 연결 구조도 개념으로 비교했지만 구축하지 않았다.
- **Site-to-Site VPN / Direct Connect:** 온프레미스와 AWS를 잇는 IPsec 터널과 전용 연결 개념을 비교했으며 신규 연결을 구축하지 않았다.

<a id="13"></a>
## 13. 실습 종료와 비용 메모

대화 마지막에 EC2·EFS·NAT·EIP 삭제 안내를 받은 뒤 사용자가 “그건 다 삭제했어”라고 보고했다. 이는 **사용자 보고에 따른 정리 기록**이며 현재 AWS 계정의 무과금 상태를 조회해 확인한 결과는 아니다. Peering은 두 종류를 구분해 정리하도록 안내했다.

| 항목 | 비용·정리 관점 |
|---|---|
| EC2 | 실행 중 컴퓨팅 비용. 실습 종료 시 Stop과 Terminate를 구분 |
| EBS·Snapshot | EC2 중지·종료 후에도 남아 있으면 저장 비용이 발생할 수 있음 |
| NAT Gateway | 사용 가능한 동안 시간 비용과 처리량 비용. EC2만 꺼도 별개로 남음 |
| Public IPv4·EIP | 미사용 EIP만의 문제가 아님. 사용 중 공인 IPv4도 요금 대상이므로 불필요한 할당 해제 |
| EFS | 저장량·선택한 처리량 방식 등에 따른 비용. 마운트 해제만으로 파일시스템 삭제가 되지 않음 |
| VPC·Subnet·RT·SG·IGW | 기본 리소스 자체의 보유만으로 별도 시간 사용료가 붙는 항목은 아님. 연결 서비스·전송 비용은 별개 |
| VPC Peering | 연결 생성 자체보다 실제 전송의 리전·AZ 조건에 따른 비용을 구분 |

정확한 단가는 리전·사용 방식·계정 혜택에 따라 달라 이 문서에는 고정 금액을 넣지 않았다. NAT 및 공인 IPv4, Peering 비용 구조는 [AWS VPC 요금](https://aws.amazon.com/vpc/pricing/)을 확인한다. 청구 화면은 반영에 시간이 걸릴 수 있으며 이미 발생한 사용료가 리소스 삭제로 취소되지는 않는다.

### 정리 순서와 범위

필요한 파일 백업 → 클라이언트 사용 종료·마운트 해제 → 본인 EC2 종료 및 EFS/Mount Target 정리 → Peering과 관련 경로 제거 → NAT 삭제 완료 확인 → EIP 릴리스 → 남은 네트워크 의존성 정리 순으로 점검한다. EFS를 사용 중인 짝꿍과도 종료 시점을 맞춘다.

마운트 해제 복습 명령:

```bash
cd ~
# 목적: 마운트 경로 밖으로 이동해 현재 쉘이 해제를 방해하지 않도록 한다.

sudo umount /mnt/partner
# 목적: 역방향 공유를 실제 마운트했다면 하위 마운트부터 해제한다.
# 실행 전 실제 마운트 여부를 확인한다. 이 문서에서는 역방향 실행 완료가 확인되지 않았다.

sudo umount /mnt
# 목적: 내 EFS 마운트를 해제한다. 파일시스템 자체를 삭제하는 명령은 아니다.
# busy라면 사용 중인 프로세스·작업 디렉터리·하위 마운트를 먼저 확인한다.
```

NAT 삭제 뒤 EIP는 별도로 릴리스한다. Peering 삭제 뒤에는 이를 참조하는 `blackhole` 경로도 정리한다. VPC 삭제 화면에서 함께 삭제할 종속 리소스를 검토하고, 남은 ENI·SG 참조 때문에 막히면 소유 리소스부터 정리한다. `lsm-*`나 짝꿍 리소스를 이름이 비슷하다는 이유로 삭제하지 않는다.

Windows의 SSH 설정 파일은 AWS 과금과 관계없다. EC2를 삭제하면 별칭의 주소는 낡은 값이 된다. PEM은 아직 같은 키를 사용하는 서버가 있는지 확인한 뒤 보관·폐기하며 Git에 추가하지 않는다.

## 14. 핵심 개념 정리

1. **Public/Private Subnet:** 이름이 아니라 연결된 라우팅이 중요하다. Public EC2의 IPv4 인터넷 직접 통신에는 공인 IP와 보안 허용도 필요하다.
2. **Local / IGW / NAT / Peering:** 같은 VPC는 local, Public 인터넷은 IGW, Private 인터넷 출구는 이번 구성의 Public NAT, 다른 VPC 사설망은 Peering으로 구분한다.
3. **CIDR과 IP:** `10.126.0.0/16`은 VPC 범위, `10.126.1.0/24`는 서브넷 범위, `10.126.1.154`는 호스트 주소다.
4. **Longest Prefix Match:** `/16`·`/24`·`/32` 등 더 구체적으로 일치하는 경로가 기본 `/0`보다 우선한다.
5. **왕복 통신:** 요청 출발 서브넷 RT와 반환 목적지 CIDR을 함께 확인한다. Peering Active만으로 통신이 완성되지 않는다.
6. **SSH:** SG는 네트워크 허용, PEM은 사용자 인증, known_hosts는 서버 신원, config는 접속 옵션이다.
7. **EFS:** Mount Target은 접근 지점, SG TCP 2049는 NFS 허용, mount는 원격 파일시스템을 로컬 경로에 붙이는 작업이다.
8. **진단 계층:** DNS 성공 → TCP 접근 → 마운트 → 파일 읽기·쓰기 순서로 확인한다. ping 성공은 모든 포트의 성공이 아니다.
9. **공유:** 두 EC2가 같은 EFS를 보면 같은 파일을 읽는다. 로컬 마운트 경로가 달라도 EFS 내부 경로는 동일하다.
10. **삭제:** EC2와 네트워크·스토리지는 별도 수명주기를 가진다. 서버 종료만으로 모든 비용이 끝나지는 않는다.

<a id="15"></a>
## 15. 실무에서 기억할 점

- 작업 시작 전 **계정·리전·VPC ID·서브넷·현재 EC2 IP**를 확인한다. 특히 같은 `default`, `example-*` 이름만 믿지 않는다.
- 네트워크 문제는 출발 IP → 실제 연결 RT → 목적지 범위 → 반환 RT → SG/NACL → 서비스 순서로 좁힌다.
- Private 서버의 키를 Bastion에 복사하기보다 이번 최종 ProxyCommand처럼 로컬에서 인증하는 구성을 활용한다.
- 호스트 키 경고는 이유와 신원을 확인하고 해당 항목만 수정한다. 신원 검증을 꺼서 오류를 숨기지 않는다.
- EFS 마운트 성공을 확인한 후 데이터를 쓴다. `/mnt` 폴더가 있다는 사실은 EFS 마운트 증거가 아니다.
- 네트워크가 허용되어도 POSIX 소유권·권한 또는 별도 EFS 정책 때문에 쓰기가 거부될 수 있다. 실습의 root 소유 파일을 모든 사용자가 수정할 수 있다고 가정하지 않는다.
- `/mnt/partner`처럼 중첩 마운트한 경우 하위 마운트부터 해제한다. 공유 호스트들의 로컬 경로와 원격 경로를 문서에 함께 적는다.
- `fstab`을 통한 부팅 시 자동 마운트는 이번에 수행하지 않았다. 재부팅 후에도 자동으로 붙는다고 가정하지 않는다.
- 성공 로그와 제안 명령을 구별한다. 특히 오리건 사설 ping, 상대 EFS 읽기, 개별 삭제 상태의 미확인을 성공으로 바꾸지 않는다.
- Git에는 이 노트처럼 필요한 구성 정보만 넣는다. PEM·AWS credentials·세션 토큰·서명 URL·원본 터미널 전체 덤프는 포함하지 않는다.

## 16. 리소스 삭제 체크리스트

**체크 상태는 재점검용이다.** 사용자 보고상 EC2/EFS/NAT/EIP는 정리했지만 현재 콘솔을 조회하지 않았으므로 자동으로 완료 체크하지 않았다.

- [ ] 필요한 EFS 파일을 보관하고 짝꿍의 공유 사용 종료를 확인했다.
- [ ] 본인 서울 `example-bastion`, `example-pri-vm`이 Terminated인지 확인했다.
- [ ] 본인 오리건 `peer-pub-vm`도 종료했다. 짝꿍 EC2는 정리 대상에서 제외했다.
- [ ] 종료 후 남은 EBS 볼륨과 불필요한 Snapshot을 확인했다.
- [ ] 최종 EFS `fs-08c05eacc10723470`과 Mount Target을 삭제했다.
- [ ] 잘못 만들었던 EFS `fs-008116ed56f3920fe`도 남아 있지 않은지 확인했다.
- [ ] 오리건↔서울 Peering `pcx-029b23ef955056191`을 삭제했다.
- [ ] 짝꿍 Peering `pcx-0ae4436b018543733`은 사용 종료 확인 후 삭제했다.
- [ ] 양쪽에서 삭제된 Peering을 가리키는 경로를 정리했다.
- [ ] `example-nat`, `nat-0693640cc240ffe3d` 삭제 완료를 확인했다.
- [ ] NAT 삭제 후 불필요한 EIP `3.35.28.218`을 릴리스했다.
- [ ] 서울·오리건의 다른 미사용 공인 IPv4/EIP도 확인했다.
- [ ] 완전 초기화가 목적이라면 오늘 VPC 소속 SG·RT·Subnet·IGW 의존성을 확인하고 VPC를 정리했다.
- [ ] 다른 실습의 `lsm-*`, Default VPC, 상대 계정 리소스를 무작정 삭제하지 않았다.
- [ ] Bills/Cost Explorer에서 리전별 남은 비용을 확인하고, 반영 지연과 이미 발생한 사용료를 구분했다.
- [ ] Windows SSH config의 오래된 주소와 개인키 보관 필요성을 점검했다.
- [ ] Git에 추가할 파일에 개인키 본문·인증키·토큰이 없는지 확인했다.
