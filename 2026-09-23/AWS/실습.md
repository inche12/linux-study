## 1. 실습 범위와 확인된 내용

이번 실습은 파일을 S3에 저장하는 데서 시작해, 웹페이지를 공개하고 그 페이지가 백엔드 API를 호출하는 구조를 이해한 뒤, 백엔드 인프라를 위한 VPC를 구성하는 흐름이었다.

|---|---|

| 공개 웹페이지 | 대화에서 정책 적용 후 `Hello World` 표시를 확인한 것으로 기록 |
| 강사 HTML 다운로드 | 처음 403 발생 후, 같은 객체 다운로드 성공 로그 확인 |

## 2. S3 객체 공개 접근: ACL과 버킷 정책

### 목적과 개념

S3의 파일은 **객체(Object)**이고, 객체를 담는 공간은 **버킷(Bucket)**이다. 업로드 성공은 내 자격증명으로 저장할 권한이 있었다는 뜻이다. 익명 방문자가 읽을 권한까지 생긴 것은 아니다.

| 구분 | ACL | 버킷 정책 |
|---|---|---|
| 방식 | 버킷 또는 객체에 정해진 권한을 부여하는 기존 방식 | 버킷에 JSON 리소스 기반 정책 연결 |
| 표현 | 제한된 대상·권한 조합 | Principal, Action, Resource, Condition 등 |
| 실습에서의 의미 | 개별 객체 공개 접근을 이해 | 웹사이트 객체들의 읽기 권한을 일괄 설정 |
| 현재 기본 동작 | 새 버킷의 기본 Object Ownership인 `Bucket owner enforced`에서는 ACL 비활성화 | ACL을 켜지 않고도 권한 제어 가능 |

**버킷 ACL의 READ를 주는 것과 모든 객체의 GetObject를 허용하는 것은 다르다.** 버킷 수준 권한과 객체 수준 권한을 구분해야 한다. 이번 정적 웹사이트는 ACL을 다시 활성화할 필요 없이 버킷 정책으로 구성한다.

공개 접근은 다음 조건을 함께 만족해야 한다.

1. 실제 객체가 정확한 키로 존재한다.
2. 정책이 익명 사용자의 객체 읽기를 허용한다.
3. 계정·버킷 등에 적용된 Block Public Access가 그 공개 접근을 막지 않는다.
4. 다른 정책의 명시적 Deny 등 추가 제한에 걸리지 않는다.

### 확인 명령

```powershell
aws s3api get-bucket-ownership-controls --bucket web-lsm123
aws s3api get-public-access-block --bucket web-lsm123
aws s3api get-bucket-policy --bucket web-lsm123 --query Policy --output text
```

조회 자체에도 권한이 필요하다. 버킷 조회만으로 계정·조직의 공개 접근 제한까지 모두 확인한 것은 아니다.

> 코멘트: 공개 차단을 해제하는 것은 접근을 허용하는 정책을 만드는 작업과 다르다. 웹사이트 전용 버킷의 필요한 설정만 조정하고, 개인 파일·백업 버킷은 비공개로 유지한다.

참고: [S3 접근 제어](https://docs.aws.amazon.com/AmazonS3/latest/user-guide/access-control-overview.html), [Block Public Access](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html)

## 3. 일반 Object URL과 Presigned URL

### 목적과 차이

파일 주소를 안다는 사실과 그 파일을 읽을 권한이 있다는 사실은 별개다.

| 항목 | 일반 Object URL | Presigned URL |
|---|---|---|
| 형태 | 객체를 가리키는 일반 주소 | 서명·만료 정보가 포함된 임시 주소 |
| 접근 | 주소 자체가 권한을 부여하지 않음 | 서명한 주체의 권한 범위에서 정해진 작업 허용 |
| 비공개 객체 | 익명 브라우저 요청은 보통 거부 | 유효한 서명과 권한이 있으면 임시 접근 가능 |
| 활용 | 공개 이미지·정적 파일 | 비공개 파일의 한시적 공유 |
| 공유 주의 | 공개 범위를 검토 | 주소를 가진 사람이 사용할 수 있으므로 비밀처럼 취급 |

일반 객체 주소 예시:

```text
https://web-lsm123.s3.ap-northeast-2.amazonaws.com/index.html
```

### 재현 명령과 확인

비공개 백업 버킷에서 공유할 객체를 지정한다. `<...>`는 자신의 값으로 치환하며 실제 서명 URL은 GitHub에 붙이지 않는다.

```powershell
$BackupBucket = '<본인의-비공개-백업-버킷명>'
aws s3 presign "s3://$BackupBucket/bk/sample.txt" --expires-in 300 --region ap-northeast-2
```

반환된 URL로 5분 이내 다운로드를 시험한다. 임시 자격증명이 더 빨리 만료되거나 권한이 철회되면 요청한 시간보다 먼저 사용할 수 없게 될 수 있다. 원래 공개된 객체는 서명 URL이 만료되어도 일반 URL로 접근할 수 있으므로 만료 실험은 비공개 객체로 한다.

> 코멘트: 콘솔의 ‘열기’ 기능 등으로 얻은 서명 URL이 잘 열린다고 일반 Object URL도 공개된 것은 아니다.

참고: [Presigned URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

## 4. AWS CLI 설치 및 서울 리전 설정

### 목적

AWS CLI는 터미널에서 AWS API를 호출하는 도구다. 웹 콘솔 로그인과 CLI 자격증명 설정은 별개이므로, 콘솔이 열려 있어도 CLI에는 별도 인증이 필요하다.

### 설치 및 실행

1. [AWS CLI v2 Windows 설치 파일](https://awscli.amazonaws.com/AWSCLIV2.msi)을 받아 설치한다.
2. 설치 후 PowerShell을 새로 연다.
3. 다음으로 설치 여부를 확인한다.

```powershell
aws --version
```

`aws-cli/2...`가 출력되면 설치 확인이 된다. 명령을 찾지 못하면 터미널 재실행 및 PATH를 점검한다.

### configure

```powershell
aws configure
```

| 입력 항목 | 실습 설정 |
|---|---|
| AWS Access Key ID | 본인의 인증 정보 입력, 기록·공유 금지 |
| AWS Secret Access Key | 본인의 인증 정보 입력, 기록·공유 금지 |
| Default region name | `ap-northeast-2` |
| Default output format | `json` |

```powershell
aws configure set region ap-northeast-2
aws configure get region
aws sts get-caller-identity
```

리전 출력이 `ap-northeast-2`인지 확인한다. `get-caller-identity`는 현재 인증 주체를 확인하는 명령이며, 출력에 포함된 계정 번호·ARN은 공개 노트에 불필요하게 첨부하지 않는다. 명령의 `--region`이나 환경 변수·프로파일 설정에 따라 적용 값이 달라질 수 있다.

### 주의사항과 트러블슈팅

- `Unable to locate credentials`: CLI에 사용할 인증 정보가 설정되어 있는지 확인한다.
- `ExpiredToken`: 임시 자격증명이 만료되었는지 확인하고 교육 환경의 절차에 따라 갱신한다.
- `AccessDenied`: 인증은 되었더라도 해당 작업을 할 권한이 없을 수 있다.
- Windows의 `%USERPROFILE%\.aws\credentials`에는 민감한 인증 정보가 저장될 수 있다. 저장소로 복사하지 않는다.
- 기본 `aws configure`의 네 가지 질문에는 세션 토큰 입력이 없다. 임시 자격증명은 토큰까지 포함한 올바른 프로파일 구성이 필요하다.
- 루트 사용자의 액세스 키를 만들지 않는다. 교육용 IAM 권한이나 조직이 제공한 역할·SSO를 사용한다.

참고: [CLI 설치](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html), [CLI 설정](https://docs.aws.amazon.com/cli/latest/userguide/cli-chap-configure.html)

## 5. S3 명령과 버킷·객체 수준의 차이

### 명령별 목적

| 명령 | 목적 | 확인 및 주의 |
|---|---|---|
| `aws s3 ls` | 계정 버킷 목록 조회 | 객체 목록 조회와 필요한 권한이 다름 |
| `aws s3 ls s3://버킷/` | 버킷의 객체·prefix 조회 | 보통 `s3:ListBucket` 필요 |
| `aws s3 cp` | 지정 파일·객체 복사 | 업로드·다운로드·S3 간 복사 가능 |
| `aws s3 sync` | 출발지와 목적지를 비교해 필요한 항목 전송 | 한 방향 동기화, 기본은 삭제하지 않음 |
| `aws s3 mb` | 버킷 생성 | 이름 중복, 리전, 생성 권한 확인 |
| `aws s3 rb` | 버킷 삭제 | 기본적으로 빈 버킷이어야 함 |

### 재현 명령

```powershell
aws s3 ls
aws s3 ls s3://web-lsm123/
aws s3 cp .\index.html s3://web-lsm123/index.html
aws s3 cp s3://web-lsm123/index.html .\downloaded-index.html
```

실습에서 확인한 업로드 결과:

```text
upload: .\index.html to s3://web-lsm123/index.html
```

`cp`는 단일 파일에 유용하지만 `--recursive`로 여러 파일도 복사할 수 있다. `sync`는 파일 크기·수정 시각 등 명령의 비교 기준에 따라 전송 여부를 결정하므로 항상 모든 파일을 다시 올리는 것은 아니다.

다음은 **별도 빈 연습용 버킷**의 생성·삭제 예시다. 웹사이트 버킷에 삭제 명령을 적용하지 않는다.

```powershell
$PracticeBucket = '<새로운-고유-연습용-버킷명>'
aws s3 mb "s3://$PracticeBucket" --region ap-northeast-2
aws s3 ls "s3://$PracticeBucket/"
# 삭제해도 되는 빈 연습용 버킷에만 실행
aws s3 rb "s3://$PracticeBucket"
```

버킷 이름은 일반적인 S3 네임스페이스에서 AWS 파티션 내 고유해야 한다. 이미 소유한 버킷에는 `mb`를 다시 실행할 필요가 없다. `rb --force`는 객체를 삭제하므로 복습 중 무심코 사용하지 않는다. 버전 관리 버킷은 과거 버전·삭제 마커가 남아 추가 정리가 필요할 수 있다.

### 버킷 ARN과 객체 ARN

```text
arn:aws:s3:::web-lsm123       → 버킷 자체
arn:aws:s3:::web-lsm123/*     → 이 버킷 안의 모든 객체
arn:aws:s3:::web-lsm123/bk/*  → bk/로 시작하는 객체
```

| 작업 | 권한 예시 | 리소스 범위 |
|---|---|---|
| 객체 목록 | `s3:ListBucket` | 버킷 ARN |
| 객체 읽기 | `s3:GetObject` | 객체 ARN |
| 객체 쓰기 | `s3:PutObject` | 객체 ARN |

> 코멘트: ‘버킷 정책을 설정했다’와 ‘버킷 수준 작업을 허용했다’는 같은 말이 아니다. 버킷에 붙인 정책으로 객체 수준 작업을 허용할 수 있다. 공개 GetObject만 허용하면 파일은 열리면서 `aws s3 ls`는 거부될 수 있다.

참고: [S3 고수준 명령](https://docs.aws.amazon.com/en_en/cli/latest/userguide/cli-services-s3-commands.html), [sync 명령](https://docs.aws.amazon.com/cli/latest/reference/s3/sync.html)

## 6. 로컬 bk 디렉터리를 S3에 백업

### 목적과 경로 해석

`aws-files` 아래 `bk` 폴더의 **내용**을 비공개 S3 버킷의 `bk/` prefix에 동기화한다. S3의 prefix는 실제 파일시스템 디렉터리가 아니라 객체 키의 공통 앞부분이다.

```text
로컬 aws-files/                 S3 비공개 백업 버킷
└─ bk/                          └─ bk/        ← prefix
   ├─ sample.txt                   ├─ sample.txt
   └─ data/                        └─ data/
      └─ memo.txt                     └─ memo.txt
```

### 실행 및 확인

`$BackupBucket`에는 실습에 사용한 본인 비공개 버킷명을 입력한다. 기존 이름에 계정 번호가 포함되어 있어 공개 노트에서는 일반화했다.

```powershell
Set-Location "$env:USERPROFILE\Downloads\aws-files"
$BackupBucket = '<본인의-비공개-백업-버킷명>'
Get-ChildItem .\bk\ -Recurse

# 먼저 어떤 파일이 전송될지 확인
aws s3 sync .\bk\ "s3://$BackupBucket/bk/" --dryrun

# 확인 후 실제 동기화
aws s3 sync .\bk\ "s3://$BackupBucket/bk/"
aws s3 ls "s3://$BackupBucket/bk/" --recursive

# 재실행 시 변경 사항이 없으면 보통 전송 출력도 없음
aws s3 sync .\bk\ "s3://$BackupBucket/bk/" --dryrun
```

### 주의사항과 코멘트

- `.\bk\`는 현재 위치 기준이다. ‘경로가 없다’면 `Get-Location`과 폴더 이름을 확인한다.
- 목적지에 `bk/`를 지정했기 때문에 객체가 그 prefix 아래에 저장된다. 출발지 폴더명이 자동으로 한 번 더 붙는 것이 아니다.
- 같은 키는 갱신될 수 있으므로 기본 sync만으로 과거 백업 이력이 보장되지 않는다. 이력이 필요하면 버전 관리·날짜별 prefix를 검토한다.
- 기본 sync는 로컬에서 없어진 파일을 S3에서 삭제하지 않는다. `--delete`를 추가하면 목적지의 불필요한 항목을 삭제할 수 있어 별도 검토가 필요하다.
- `sync .\cloudfront\ ...`에서 `cloudfront`는 로컬 폴더 이름일 뿐이다. 해당 명령이 CloudFront 배포를 생성하는 것은 아니다.
- 공개 정책이 `web-lsm123/*` 전체에 적용되므로 이 웹사이트 버킷에는 개인 백업을 넣지 않는다.

<a id="07"></a>
## 7. web-lsm123 정적 웹사이트 배포

### 목적과 개념

S3에서 HTML·CSS·JavaScript를 제공한다. S3가 Node.js나 데이터베이스를 실행하는 것은 아니며, JavaScript는 방문자의 브라우저에서 실행된다.

### 1단계: index.html 준비·업로드

최초 페이지를 재현할 때 사용할 최소 HTML 예시다. 기존 프론트엔드 파일이 있다면 덮어쓰지 말고 별도로 보관한다.

```html
<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8">
  <title>S3 Website Lab</title>
</head>
<body>
  <h1>Hello World</h1>
</body>
</html>
```

```powershell
Get-Content .\index.html
aws s3 cp .\index.html s3://web-lsm123/index.html --content-type "text/html; charset=utf-8"
aws s3 ls s3://web-lsm123/index.html
```

### 2단계: 정적 웹사이트 호스팅 활성화

콘솔에서 **S3 → web-lsm123 → 속성 → 정적 웹 사이트 호스팅 → 편집**으로 이동한다.

1. 정적 웹사이트 호스팅을 활성화한다.
2. 인덱스 문서를 `index.html`로 지정한다.
3. 오류 문서는 준비한 경우에만 지정한다.
4. 저장 후 표시되는 웹사이트 엔드포인트를 복사한다.

동일 설정의 복습용 CLI 명령:

```powershell
aws s3 website s3://web-lsm123/ --index-document index.html
aws s3api get-bucket-website --bucket web-lsm123
```

### 3단계: 공개 읽기 버킷 정책 설정

권한 탭에서 계정·버킷의 공개 접근 차단을 확인한다. 이 실습은 공개 웹사이트이므로 공개 버킷 정책을 막는 설정을 조정해야 한다. ACL을 사용하지 않으므로 ACL 관련 차단까지 일괄 해제할 필요는 없다. 조직이 강제한 제한은 개인이 우회하지 않는다.

버킷 정책 편집기에 다음을 적용한다. 기존 정책이 있다면 다른 항목을 지우지 않도록 검토한다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadGetObject",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::web-lsm123/*"
    }
  ]
}
```

| 필드 | 의미 |
|---|---|
| `Sid` | 문장을 식별하기 위한 이름, 권한을 결정하는 예약 명령이 아님 |
| `Effect: Allow` | 해당 작업 허용 |
| `Principal: *` | 익명 방문자를 포함한 누구나 |
| `Action: s3:GetObject` | 객체 내용 읽기 |
| `Resource: ...web-lsm123/*` | `web-lsm123` 안의 모든 객체 |

**모든 버킷을 공개하는 정책이 아니다.** 해당 버킷 안의 객체 읽기만 허용하며, 익명 업로드·삭제·객체 목록 조회는 이 정책으로 허용하지 않는다.

### 4단계: 결과 확인

```text
http://web-lsm123.s3-website.ap-northeast-2.amazonaws.com/
```

실제 주소는 콘솔의 엔드포인트와 비교한다. 브라우저에서 `Hello World`가 표시되는지, 로그인 세션이 없는 창에서도 열리는지 확인한다. 대화에서는 정책 적용 후 페이지 표시 성공이 기록되었다.

S3 웹사이트 엔드포인트는 HTTP를 사용하며 일반 REST Object URL과 기능이 다르다. 운영 환경에서 HTTPS와 비공개 S3 원본을 함께 사용하려면 CloudFront와 S3 REST 원본·OAC 구성을 검토한다. 웹사이트 엔드포인트를 OAC로 보호하는 구성과 혼동하지 않는다.

참고: [웹사이트 공개 권한 설정](https://docs.aws.amazon.com/AmazonS3/latest/userguide/WebsiteAccessPermissionsReqd.html), [웹사이트 엔드포인트](https://docs.aws.amazon.com/AmazonS3/latest/userguide/WebsiteEndpoints.html)

<a id="08"></a>
## 8. 403 AccessDenied 진단

### 실습에서 발생한 문제

웹사이트 호스팅을 켜도 공개 읽기 권한이 없으면 방문자는 콘텐츠를 읽을 수 없다. 또한 강사 버킷에서 `index.html`을 다운로드할 때 `HeadObject` 단계에서 403이 발생했다가 나중에 다운로드가 성공한 기록이 있다.

**403만 보고 원인을 하나로 확정하면 안 된다.** 다음 순서로 요청 대상과 권한을 나누어 확인한다.

| 확인 항목 | 점검 내용 | 대응 |
|---|---|---|
| 버킷·객체 키 | 버킷명, `index.html` 대소문자, 중복 `/` | 실제 키와 정확히 일치시키기 |
| 공개 읽기 | 익명 `s3:GetObject` 허용 여부 | 웹사이트 전용 정책 검토 |
| 공개 차단 | 버킷·계정·조직 설정 | 적용된 차단 범위 확인 |
| ARN | 객체 작업인데 버킷 ARN만 지정했는지 | `web-lsm123/*` 확인 |
| CLI 주체 | 예상한 사용자·역할인지 | `get-caller-identity` 확인 |
| 명시적 Deny | 버킷·IAM·조직 정책 등 | 관리자와 제한 사유 확인 |
| 객체 암호화 | SSE-KMS 등 추가 권한이 필요한지 | 익명 웹사이트 제공 방식과 호환성 검토 |

```powershell
aws s3 ls s3://web-lsm123/ --recursive
aws s3api head-object --bucket web-lsm123 --key index.html
aws s3api get-bucket-policy --bucket web-lsm123 --query Policy --output text
```

이 명령은 CLI 자격증명으로 수행되므로 성공해도 익명 공개 접근 성공을 보장하지 않는다. 브라우저의 비로그인 요청도 별도로 확인한다.

### 경로 오류도 놓치지 않기

```text
s3://web-hhs123/index.html    → 객체 키: index.html
s3://web-hhs123//index.html   → 의도와 다른 /index.html 키를 가리킬 수 있음
```

S3 키의 슬래시를 일반 파일시스템처럼 자동 정규화한다고 가정하지 않는다. 존재하지 않는 객체를 REST API로 요청해도 요청자에게 `ListBucket` 권한이 없으면 404 대신 403을 받을 수 있다.

> 코멘트: ‘처음 실패, 나중 성공’은 정책 변경 가능성을 보여주지만 확정 증거는 아니다. 정확한 키, 사용 프로파일, 요청 시점의 권한을 함께 비교해야 한다.

## 9. 강사 프론트엔드 배포 및 fetch 오류

### 목적과 실행 흐름

강사 `web-hhs123/index.html`을 로컬로 받은 뒤 내 `web-lsm123/index.html`로 업로드한다. 같은 이름으로 다운로드하면 기존 로컬 파일이 덮어써지므로 먼저 보관한다.

```powershell
Set-Location "$env:USERPROFILE\Downloads\aws-files"

# 기존 파일이 있으면 최초 1회 별도 보관
if (Test-Path .\index.html) {
    Copy-Item .\index.html .\index-before-frontend.html -ErrorAction Stop
}

aws s3 cp s3://web-hhs123/index.html .\index.html
Get-Content .\index.html
Select-String -Path .\index.html -Pattern 'fetch|http://http://'

# URL을 수정하고 저장한 다음 배포
aws s3 cp .\index.html s3://web-lsm123/index.html --content-type "text/html; charset=utf-8"
```

실습 대화의 다운로드 성공 결과:

```text
download: s3://web-hhs123/index.html to .\index.html
```

파일을 받았다는 것과 내 버킷에 최신 파일을 배포했다는 것은 별도 단계다. 다운로드 후 내용 확인 → 수정 → 업로드 → 브라우저 새로고침 순서로 진행한다.

### http://http:// 중복 오류

```javascript
// 잘못된 예: 프로토콜 중복
fetch('http://http://YOUR-ELB-DNS/api');

// 형식 수정 예: 실제 본인 ELB DNS로 치환
fetch('http://YOUR-ELB-DNS/api');
```

`http://`는 한 번만 넣는다. `[주소](주소)` 같은 Markdown 링크 문법을 JavaScript 문자열에 넣지 않는다. HTML 태그 앞의 불필요한 역슬래시도 실제 파일에 남기지 않는다.

강사 파일 안의 ELB는 **강사 백엔드**를 가리킨다. S3 업로드 대상만 내 버킷으로 바꿔도 API 대상은 그대로다. 향후 본인 ELB를 생성하면 DNS 이름과 `/api` 경로를 본인 환경으로 교체한다. HTTP/HTTPS는 실제 리스너·인증서 구성에 맞춰 사용한다.

### 버튼 동작 예시

다음은 응답 실패도 확인하도록 보강한 예시이며 강사 원본 코드의 완전한 복사본은 아니다.

```html
<h1>Hello from the frontend!</h1>
<button id="fetchDataButton">Fetch Data from Backend</button>
<pre id="backendData"></pre>
<script>
  const apiUrl = 'http://YOUR-ELB-DNS/api'; // 본인 환경으로 교체
  document.getElementById('fetchDataButton').addEventListener('click', async () => {
    const output = document.getElementById('backendData');
    output.textContent = 'Loading...';
    try {
      const response = await fetch(apiUrl);
      if (!response.ok) throw new Error(`HTTP ${response.status}`);
      const data = await response.json();
      output.textContent = JSON.stringify(data, null, 2);
    } catch (error) {
      output.textContent = `API 요청 실패: ${error.message}`;
      console.error(error);
    }
  });
</script>
```

### 전체 구조와 확인 방법

```text
브라우저 ── HTML 요청 ──▶ S3 정적 웹사이트
브라우저 ◀─ index.html ── S3
    │
    └─ 버튼 클릭 / fetch ──▶ ELB ──▶ Backend ──▶ DB
              ◀────────────── JSON 응답 ─────────┘
```

S3 서버가 ELB를 호출하는 것이 아니라 **브라우저가 JavaScript를 실행해 ELB로 직접 요청**한다. S3는 Nginx의 `/api` 리버스 프록시 역할을 자동으로 제공하지 않는다.

| 증상 | 확인·해결 방향 |
|---|---|
| 이전 Hello World가 보임 | 업로드한 버킷·키 확인, 강력 새로고침, 캐시 확인 |
| 제목·버튼만 표시 | HTML 제공 성공과 API 연결 성공을 구분 |
| 잘못된 호스트·요청 URL | 개발자 도구 Network에서 중복 프로토콜·실제 ELB DNS 확인 |
| CORS 오류 | API 응답에서 프론트엔드 Origin 허용, 필요 시 OPTIONS 처리 |
| Mixed Content | HTTPS 페이지에서 HTTP API 호출 여부 확인, API도 HTTPS 구성 |
| 502·503·타임아웃 | ELB 리스너, 대상 그룹 상태, 서버 포트·보안 그룹·경로 확인 |
| JSON 변환 오류 | API가 JSON 대신 HTML 오류 페이지 등을 반환하는지 확인 |

API의 CORS 문제는 보통 S3 CORS를 바꿔 해결하지 않는다. 브라우저가 호출하는 **백엔드 응답**을 확인한다. `mode: 'no-cors'`는 읽을 수 없는 응답을 만들 수 있어 JSON 표시 해결책이 아니다.

> 코멘트: 실습 기록에서 URL 중복은 확인되었지만, 본인 ELB와 DB까지 연결한 성공 결과는 확인되지 않았다. 후속 실습에서 버튼 클릭 후 HTTP 성공 응답과 실제 JSON 표시까지 검증한다.

## 10. VPC 네트워크 핵심 개념

### 목적

서버가 사용할 IP 범위를 정하고, 외부에 공개할 계층과 내부 계층을 분리하며, 통신 경로와 허용 규칙을 설계한다.

| 개념 | 역할 | 혼동하기 쉬운 점 |
|---|---|---|
| VPC | 리전 안의 논리적으로 분리된 가상 네트워크 | 하나의 AZ에만 묶이지 않음 |
| Subnet | VPC 주소 공간을 나눈 네트워크 | 하나의 서브넷은 하나의 AZ에 속함 |
| CIDR | IP 주소 범위와 네트워크 비트 길이 | 숫자가 클수록 같은 주소 계열에서 범위가 작음 |
| Public Subnet | IGW로 향하는 직접 경로가 있는 서브넷 | 이름을 Public으로 붙인 것만으로 공개되지 않음 |
| Private Subnet | IGW로 직접 나가는 경로가 없는 서브넷 | NAT가 없어도 Private Subnet은 만들 수 있음 |
| Route Table | 목적지별 다음 경로 결정 | 패킷 허용 규칙 자체와는 다름 |
| IGW | VPC와 인터넷 사이 통신 경로 제공 | 연결만으로 모든 EC2가 인터넷에 노출되지는 않음 |
| NAT Gateway | 사설 주소의 외부 연결에 주소 변환 제공 | 인터넷에서 임의의 신규 연결을 받는 용도가 아님 |
| Security Group | ENI·인스턴스 등의 stateful 허용 규칙 | 서브넷 라우팅을 대신하지 않음 |
| VPC Peering | 두 VPC 간 사설 IP 통신 연결 | 경로·보안 설정 필요, 전이적 라우팅 불가 |

이 문서의 NAT 경로 예시는 Public Subnet에 배치하는 **퍼블릭 NAT Gateway**를 기준으로 한다. 퍼블릭 NAT에는 EIP와 IGW 경로가 필요하다.

### Public과 Private의 IPv4 경로

```text
Public Route Table
10.26.0.0/16 → local
0.0.0.0/0   → Internet Gateway

Private Route Table — NAT를 구성한 경우
10.26.0.0/16 → local
0.0.0.0/0   → NAT Gateway
```

Public Subnet의 EC2가 직접 인터넷 IPv4 통신을 하려면 공인 IPv4/EIP, 경로, Security Group 및 Network ACL 등이 맞아야 한다. Private EC2가 업데이트를 받는 흐름은 다음과 같다.

```text
Private EC2 → Private Route Table → Public NAT Gateway → IGW → Internet
```

Security Group은 허용한 연결의 응답 트래픽을 추적한다. SSH는 자신의 IP 범위 등 필요한 출발지로 제한하고, DB 포트는 백엔드 보안 그룹 등 필요한 대상에만 허용한다.

VPC Peering은 겹치지 않는 CIDR을 계획하고 연결 수락·양쪽 라우팅·보안 규칙을 구성해야 한다. A–B와 B–C를 연결해도 A–C가 자동 연결되지 않으며, 상대 VPC의 NAT/IGW를 인터넷 출구처럼 공유할 수 있는 것은 아니다.

> 코멘트: 일반 S3 버킷은 EC2처럼 내 서브넷 안에 배치하지 않는다. VPC에서 S3로 사설 경로를 사용하려면 S3 Gateway Endpoint 등을 별도로 검토한다.

참고: [Public·Private·NAT 구성 예시](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-example-private-subnets-nat.html)

## 11. 서울 VPC 생성 실습

### 실습 설계

| 항목 | 설정 |
|---|---|
| 리전 | 서울 `ap-northeast-2` |
| 생성 모드 | VPC 등(VPC and more) |
| VPC CIDR | `10.26.0.0/16` |
| AZ | `ap-northeast-2a`, `ap-northeast-2c` |
| Public Subnet | 2개 |
| Private Subnet | 2개 |
| 각 Subnet CIDR | `/24` |
| NAT Gateway | 실제 선택·생성 여부 별도 확인 필요 |

```text
Seoul Region / ap-northeast-2
└─ VPC 10.26.0.0/16
   ├─ ap-northeast-2a
   │  ├─ Public  10.26.0.0/24
   │  └─ Private 10.26.128.0/24
   └─ ap-northeast-2c
      ├─ Public  10.26.16.0/24
      └─ Private 10.26.144.0/24
```

`/16`은 전체 65,536개 주소 범위이고 `/24`는 256개 주소 범위다. 일반 IPv4 서브넷에서는 AWS가 5개 주소를 예약하므로 `/24`에서 리소스에 할당 가능한 주소는 251개다. **VPC를 /24로 바꾼 것이 아니라 서브넷 각각을 /24로 설정했다.**

### 콘솔 실행 순서

1. 서울 리전에서 VPC → VPC 생성으로 이동한다.
2. **VPC 등**을 선택한다.
3. VPC IPv4 CIDR을 `10.26.0.0/16`으로 지정한다.
4. AZ를 2개로 하고 사용자 지정에서 2a·2c를 선택한다.
5. Public 2개, Private 2개를 선택한다.
6. 서브넷 CIDR 사용자 지정에서 위 네 대역을 입력한다.
7. NAT Gateway·VPC Endpoint 등 선택 옵션과 비용을 검토한다.
8. 미리 보기에서 서브넷·라우팅 테이블·게이트웨이 연결을 확인하고 생성한다.

`VPC 등`은 선택한 옵션에 따라 서브넷, 라우팅 테이블, IGW, NAT Gateway 등을 함께 구성한다. EC2·ELB·DB 애플리케이션 전체를 자동 배포한다는 뜻은 아니다. NAT를 선택하지 않았다면 NAT 경로도 있다고 가정하지 않는다.

### 결과 확인용 명령

먼저 CIDR로 후보를 조회한 뒤, 콘솔 이름·태그와 비교하여 정확한 VPC ID를 선택한다. 아래 명령은 생성 명령이 아니라 읽기 전용 확인 명령이다.

```powershell
aws ec2 describe-vpcs --region ap-northeast-2 --filters "Name=cidr-block,Values=10.26.0.0/16" --query "Vpcs[].{ID:VpcId,CIDR:CidrBlock,State:State}" --output table

$VpcId = '<조회한-실습-VPC-ID>'
aws ec2 describe-subnets --region ap-northeast-2 --filters "Name=vpc-id,Values=$VpcId" --query "Subnets[].{AZ:AvailabilityZone,CIDR:CidrBlock,ID:SubnetId}" --output table
aws ec2 describe-route-tables --region ap-northeast-2 --filters "Name=vpc-id,Values=$VpcId"
aws ec2 describe-internet-gateways --region ap-northeast-2 --filters "Name=attachment.vpc-id,Values=$VpcId"
aws ec2 describe-nat-gateways --region ap-northeast-2 --filter "Name=vpc-id,Values=$VpcId" --query "NatGateways[].{ID:NatGatewayId,State:State,Subnet:SubnetId}" --output table
```

콘솔의 리소스 맵에서 네 서브넷의 AZ·CIDR을 대조하고, 각각 **어떤 라우팅 테이블에 연결되었는지** 확인한다. `MapPublicIpOnLaunch` 설정만으로 Public/Private을 판정하지 않는다.

### 주의사항과 트러블슈팅

- CIDR 충돌: 네 서브넷이 VPC 범위 안에 있으며 서로 겹치지 않는지 확인한다.
- 인터넷 통신 불가: 서브넷 연결 테이블, 기본 경로, IGW 연결, IP, 보안 규칙 순으로 점검한다.
- Private에서 외부 연결 불가: NAT를 실제로 생성했는지, 상태와 경로가 정상인지 확인한다.
- 2a·2c 사용은 이번 교육 구성이다. ‘서울 2b는 사용하면 안 된다’는 일반적인 AWS 규칙으로 이해하지 않는다.
- 나중에 Peering·VPN을 연결할 네트워크와도 CIDR이 겹치지 않도록 계획한다.

참고: [VPC 생성](https://docs.aws.amazon.com/vpc/latest/userguide/create-vpc.html)

<a id="12"></a>
## 12. 비용 확인과 실습 종료 점검

### 목적

‘VPC 생성’과 ‘그 안에 만든 유료 리소스’의 비용을 구분하고, 실습이 끝난 뒤 사용하지 않는 리소스가 남아 있는지 확인한다.

| 리소스 | 비용 확인 포인트 |
|---|---|
| VPC·Subnet·Route Table·Security Group | 기본 구성 자체에 별도 사용료 없음 |
| IGW | 생성·연결 자체 요금과 데이터 전송 요금을 구분 |
| NAT Gateway | 시간 및 데이터 처리 기준 비용, 트래픽이 없어도 시간 비용 가능 |
| EC2 | 실행 중 컴퓨팅 비용, 약정 등 별도 결제 조건은 따로 확인 |
| EBS | EC2를 중지해도 볼륨 저장 비용 지속 |
| Snapshot | 저장된 스냅샷 비용 확인 |
| Public IPv4·EIP | 보유·사용 상태 및 적용 요금 확인 |
| ELB | 생성 후 시간·처리량 등에 따른 비용 확인 |
| S3 | 저장량·요청·데이터 전송 등 확인 |

요금 숫자는 리전·상품·시점에 따라 달라지므로 고정 금액을 기록하지 않는다. 크레딧이 있더라도 유료 리소스 사용량은 누적될 수 있고 적용 가능 범위·만료 조건을 확인해야 한다.

### 실습 종료 순서

1. VPC 콘솔 왼쪽 **NAT 게이트웨이**에서 생성 여부를 확인한다.
2. EC2 콘솔에서 사용하지 않는 인스턴스를 확인하고, 다시 사용할 목적이면 중지한다.
3. 중지 완료 상태까지 확인하고 EBS·EIP·ELB가 남아 있는지 점검한다.
4. NAT가 불필요하면 의존 경로를 검토한 후 삭제한다. NAT Gateway에는 EC2처럼 중지하는 방식이 없다.
5. NAT 삭제 후 남은 EIP의 필요 여부도 확인한다.
6. Billing and Cost Management에서 비용·크레딧·예산을 확인한다. 비용 표시는 즉시 반영되지 않을 수 있다.

기존 대화에서 `lsm-vm1`, `ktcloud-vm`이 실행 중으로 언급되었으나, 최종 중지 완료 여부는 확인되지 않았다. NAT 목록이 비어 있더라도 **조회한 리전 외의 리소스**까지 없다는 뜻은 아니다.

> 코멘트: 중지는 종료(삭제)와 다르다. 종료는 데이터·볼륨 보존 설정을 확인한 뒤 수행한다. EC2를 중지하는 것만으로 계정의 모든 비용이 0이 되지는 않는다.

참고: [Amazon VPC 요금](https://aws.amazon.com/vpc/pricing/)

## 13. 보안 및 GitHub 업로드 점검

이 문서에는 실제 Access Key·Secret Key·세션 토큰 및 서명 URL을 포함하지 않는다. 인증 정보는 HTML·JavaScript에 넣어서도 안 된다. 브라우저에 전달된 소스는 사용자가 읽을 수 있다.

- [ ] 액세스 키·비밀 키·세션 토큰이 파일·스크린샷·터미널 로그에 없는가?
- [ ] `.aws/credentials`, `.env`, 개인 키, DB 비밀번호 파일을 제외했는가?
- [ ] Presigned URL의 서명 쿼리 문자열을 제거했는가?
- [ ] 공개 웹사이트 버킷에 백업·개인정보 파일이 없는가?
- [ ] 계정 번호·개인 이메일 등 불필요한 식별 정보를 제외했는가?
- [ ] 실제 성공 결과와 예상 결과·추가 과제를 구분했는가?

저장소의 `.gitignore` 예시:

```gitignore
.aws/
.env
.env.*
!.env.example
*.pem
*.key
credentials
```

`.gitignore`는 이미 추적하거나 커밋한 파일을 제거하지 않는다. 키가 노출되었다면 파일 삭제만으로 끝내지 말고 해당 키를 즉시 폐기·교체하고 Git 이력 노출도 처리한다.

AWS 루트 사용자, IAM 사용자, Linux `root`는 서로 다른 개념이다. 일반 실습에는 필요한 IAM 권한을 사용하고, 루트 로그인은 계정 이메일·MFA 등 별도의 절차로 관리한다.

## 14. 복습 포인트와 참고 자료

1. **업로드 성공과 공개 읽기는 별개다.** 웹 호스팅 활성화도 공개 권한을 대신하지 않는다.
2. **버킷 정책의 부착 위치와 권한 대상은 구분한다.** `GetObject`는 객체 ARN에 적용한다.
3. **sync는 한 방향 비교·전송이다.** 기본 삭제나 과거 버전 보존을 가정하지 않는다.
4. **HTML 표시와 API 성공은 별개다.** 브라우저의 실제 요청 주소·응답·CORS를 확인한다.
5. **Public/Private은 경로로 판단한다.** 서브넷 이름이나 공인 IP 설정만 보지 않는다.
6. **VPC 등은 선택한 네트워크 리소스를 함께 만든다.** NAT 등 유료 옵션은 별도 점검한다.
7. **EC2 중지 후에도 남는 비용이 있다.** EBS·NAT·EIP·ELB·S3 등을 함께 확인한다.

추가 확인에 유용한 공식 문서:

- [S3 HeadObject API와 403/404 응답](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html)
- [서브넷 CIDR과 예약 주소](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-sizing.html)
- [VPC Peering 제한 사항](https://docs.aws.amazon.com/vpc/latest/peering/invalid-peering-configurations.html)
- [Security Group 기본 동작](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-security-groups.html)

**후속 실습:** 본인 ELB/API 구축 → HTML의 API 주소 교체 → 응답·CORS 검증 → 필요 시 HTTPS 구성 → 네트워크 연결과 비용 정리 상태 확인.
